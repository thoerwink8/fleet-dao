# `discuss`：讨论

规矩本身在 `docs/design.md` 第五节「讨论」，这里只写怎么做。和审查是两回事：审查看代码，讨论定方案。

## 何时用

- 要请人拍改规矩、改架构、改阶段划分、改验收标准这类决定之前。
- 用户说「出设计题」「先出盲设计题」「让别家看看」。

小选择题（已经收敛成 A 还是 B）不用。

## 做法：一问一答，不起完整会话

每轮都是一问一答：不读仓、不跑命令、限 400 字、中等思考强度，十几秒一轮。

1. **第 0 轮，各自独立答**：只写题面（背景、诉求、要回答的），**不带自己的方案**，并行发两家。题面一字不提示期望的方案形态。
2. **第 1 轮，挑错**：自己的方案 + 第 0 轮的答案一起发一家，要它说框架对不对、漏了什么、选项怎么改。
3. 有新分歧再来一轮，最多两三轮。

材料里附上相关规则原文、数据和出处（对方看不到仓，漏写的事实它就不知道）。

## 交给人

只写三样：各家一致的、还剩的分歧、推荐哪个。对方的每条意见写明收没收、为什么。讨论是 AI 之间的事，人只拍板。

## 本机工具（引擎接活之前）

`node ~/.local/share/second-opinion/second-opinion.mjs --text 材料.md --name 短名 --effort medium [--blind] [--agent code|kimi]`

- `--blind` 是第 0 轮的题面模式；不带是第 1 轮的挑错模式。
- `--agent code` 是 GPT（luna）；`--agent kimi` 走 pi，吃 Mirasim 服务端默认模型（2026-09-25 是 DeepSeek Flash），实际模型看结论文件头。
- 结论落在那个脚本旁边的 runs 目录（本机，不进仓）。

## 判例

- 2026-08-14 第一次三臂盲设计：两个守住盲的臂独立得出同一个答案，证明「各自独立答」能给出收敛信号。当时每臂起完整会话、读仓外中性目录，一轮要几十分钟。
- 2026-09-25：创始人把总指挥的分析手贴给网页 GPT，20 秒拿回把框架推进一步的反驳（bootstrap 与生产运营混了）。挑错要的是对方看到具体方案，快比完整重要；于是改成一问一答。同日实测 medium、限 400 字：12–20 秒一轮；第 0 轮两家独立答 + 第 1 轮挑错，全程约一分钟（#69 的讨论稿就是这样出的）。
