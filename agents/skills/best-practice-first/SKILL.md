# best-practice-first：提方案之前先查业界怎么做

## 什么时候读

**任一「提方案」的时刻**，用户提的或我自己提的：

- 用户说「我想做一个 X」「加个机制」「多个 skills」这类方案、设计类输入；
- 我自己准备**改协作方式、加规则、造长驻机制**；
- **从 `chain-first` 转过来**：查断链查到最后，修法是新造或换掉一个机制。现状已经在那边查清了，本页从第 1 步接着走，不重查。

**不归本页管**：现状不对、还没搞清断在哪——先去 `chain-first`。本页只管「要提一个方案了」之后。

**一句话**：**设计问题不许凭记忆答。** 记忆里的「业界做法」可能已经过时；用户也不该每次打字提醒「你去查查最佳实践」。

## 怎么做（五步，顺序不可换）

1. **先查**（怎么查见 `docs-lookup`）：搜索、库和框架文档、GitHub 上的实现与讨论。**至少两条独立来源**，记下**链接和日期**。
2. **摆对照**：一张表，「业界怎么做」对「我们的约束」（写清约束：本仓的规矩、机器形态、成本）。**业界做法和我们的约束冲突的地方，正是要拍板的地方。**
3. **给从零方案**：剥掉现状重推一遍（和 `grill-ai` 同一个精神），**必须摆出「删掉整层」的选项**。
4. **摆代价表**：从零方案 / 现状方案 / 业界更重的方案，各写代价和风险，交用户拍板：用当前环境的提问工具出选择题，没有就列编号选项。**禁止替用户默认取舍，也禁止「两个都做」。**
   唯一的例外：**从 `chain-first` 转来、修法不碰人闸（对外发布、花钱、删数据）、不改规矩、也不是重大设计岔路**——代价表照摆，写进 PR 正文，自己拍、接着干，不停下来问。用户要的是「问题和机制同一轮修掉」，不是每个小机制都等他。拿不准算不算重大，就按重大处理（问）。
5. **落库**：结论 + 依据（链接）+ 拍板结果，写进对应的 issue、PR 或需求文档。**只写指针和结论，不抄大段文档。**

## 硬规矩

- **没有查证的设计回答，视为未完成。** 可以答，但要标「未查证」并说明为什么这次不查（例如纯本仓内部的事实）。
- **引用必须点得开**：给 URL 或 `文件:行`；不许写「业界普遍认为」这种没出处的句子。
- **不许拿记忆当来源**：本 skill 的起因就是这条——AI 凭印象答设计题，用户每次要自己补一句「去查最佳实践」。

## 和相关 skill 的分工

| skill | 管什么 |
| --- | --- |
| `docs-lookup` | **怎么查**：搜索、库文档、GitHub、已知网页各走哪条路 |
| **best-practice-first（本页）** | **什么时候必须查**，查完**怎么摆给用户拍** |
| `chain-first` | **现状不对时**先查断在哪（谁写、谁读、谁报警）；查到要新造或换机制，才转到本页 |
| `design-exam` | 重大岔路时**盲平行设计**：几家模型各自独立出方案，再比对 |
| `grill-ai` | 自查**我自己**的路是不是从一开始就走歪了（补丁链） |
| `grill-me` | 拷问**用户**的想法：该不该做、长什么样 |
| `judge-or-code` | 某一处机械判断该写代码、交给判断题小模型，还是这次不固化 |
