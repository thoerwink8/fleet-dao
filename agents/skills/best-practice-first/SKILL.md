# `best-practice-first`：从业务推，拿业界比

## 什么时候读

**任一「要设计一样东西」的时刻**，用户提的或我自己提的：

- 新做或重做**任何一层**：页面、接口、数据结构、流程、模块拆法、命令行、配置格式、协作机制、规矩；
- 用户嫌界面难看、布局不对、「从上往下堆」「宽屏空着」：这是版面、视觉两层没设计过，回第 3 步分层找对照；
- 用户说「我想做一个 X」「加个机制」「推倒重来」「从零做」「一切围绕业务」「你没站在用户角度」「去查查最佳实践」；
- **自查**：我正在说「在现有基础上调整」「保留原结构再优化」「把这几块挪一挪」——出现即读；
- **从 `chain-first` 转过来**：查断链查到最后，修法是新造或换掉一个机制。现状已经在那边查清了，本页从第 1 步接着走，不重查。

**不归本页管**：现状不对、还没搞清断在哪——先去 `chain-first`。本页只管「要设计了」之后。

**三句话**：
- **现有实现是需求的证据，不是设计的起点。** 读它，是为了挖出它在守什么业务规矩；怎么做，从业务重新推。前端后端都一样：界面、接口、表结构都为业务服务，不是业务本身。
- **设计问题不许凭记忆答。** 记忆里的「业界做法」可能已经过时；用户也不该每次打字提醒「你去查查最佳实践」。
- **用户在哪一层、什么精度上评判，就在那一层、那个精度上设计、拍板和验收。** 界面用户是看着真屏幕评判的：只在文字草图上拍过分块，不等于拍过版面；只核对过「画没画对」，不等于验过「屏幕用得好不好」。

## 怎么做（六步，顺序不可换）

### 1. 挖业务：写一份业务说明

只取两样：

1. **这件事替谁、干成什么**：每个页面、接口、流程、机制各一句，写全四样——谁、在什么场合、要干成什么、干成的标志是什么。
2. **业务规则**：不变量、判定口径、约束和红线、写操作的前置条件、出错时该怎么说。每条标出处：需求文档、决定记录、用户原话，或现有代码里的哪一处。

现有代码要读透，但只从里面**抽规则**（它在判什么、拦什么、保证什么），不抄它的组织方式。改动大的（重做一整页、一整个模块、一套机制），这份说明先给用户过目再往下走。

### 2. 隔离现有实现

把现有实现里「怎么做」的部分逐样点名，写明**不作为设计起点**：分块和布局、步骤划分、接口切法、表结构、模块边界、叫法和文案、自造的公共设施。

它们在后面可以被重新选中，但必须是从业务推出来又恰好一样，不许是「原来就这样」。

### 3. 查业界、找对照

怎么查见 `docs-lookup`：搜索、库和框架文档、GitHub 上的实现与讨论。**至少两条独立来源**，记下**链接和日期**。

- **找用户用过的同类产品**，看同一步它们怎么做（例：目标平台自己是扫码登录，工具就该把二维码搬到自己页面上，而不是让人按 F12 复制 Cookie）。比对照差的地方，要么做到，要么写明为什么不做。
- **分层找对照，一层都不许空着**。设计有几层就分几层找，每层至少一个同类产品的真实样子（链接或截图）：
  - 界面三层：**信息架构**（分几块、每块管什么）→ **版面**（目标屏幕上各块放哪、宽屏怎么用满、细节放在哪一栏）→ **视觉**（字号层级、颜色、密度）；
  - 接口：调用方的真实调用顺序、同类服务的接口形状；流程和机制：同类团队真跑起来的样子。
  - 只对照了「这一步怎么做」、没对照「这一屏长什么样」，等于版面没对照——第 4 步给不出版面，只能照草图硬排。
- **技术细节用所选框架的标准机制**（组件库的主题 token、框架自带的调度、数据库自带的约束），不另造一套平行的。
- 摆一张表：「业界怎么做」对「我们的约束」（本仓的规矩、机器形态、成本）。**冲突的地方，正是要拍板的地方。**

### 4. 从业务重推，给从零方案

1. **写操作剧本**：真实的人（或调用方）从起念到干成的每一步：在哪台机器、屏幕多大、手里还有什么、要等什么。数三样代价：**动手次数、搬运次数**（复制粘贴、手抄、在两个工具间来回）、**离开次数**（要切到别的系统或看说明书）。
2. **定目标**：搬运和离开都是 0；一个画面只有一个最显眼的「下一步」；同一个业务对象只在一处出现，一眼看出它走到了哪。
3. **再定各层**：先定业务对象和它的状态怎么流转，再由它推出接口（按业务动作切，不按旧页面切）、数据（按业务对象建）、界面（按操作剧本排）。
4. **必须摆出「删掉整层」的选项**（和 `grill-ai` 同一个精神）。
5. **对账**：旧实现守着的每条业务规则，在新设计里都要有落点、有测试钉住；旧实现里**找不到业务出处**的东西单独列出来，问用户删掉还是补成规则，不许默默留着，也不许默默删掉。
6. **先给草图或草案再写代码，草图的精度要够拍它要拍的那一层**：
   - 分块、流程、接口形状：文字草图、草案就够；
   - **版面、视觉：必须是目标尺寸下的真实画面**（真组件、像样的数据，每个目标屏幕尺寸各一张，比如 1920×1080 和 1366×768），和第 3 步的对照画面并排交给用户拍；
   - 用户在文字草图上点头，点的是分块，不是版面。拍了哪一层，就只算那一层拍过；没拍过的层照样要出画面再拍。用户交代了不用等（比如让你无人值守推进），就照对照自己定，画面和对照截图照出、照存，留给用户回来看。

### 5. 摆代价表，交用户拍

从零方案 / 现状方案 / 业界更重的方案，各写代价和风险，交用户拍板：用当前环境的提问工具出选择题，没有就列编号选项。**禁止替用户默认取舍，也禁止「两个都做」。**

唯一的例外：**从 `chain-first` 转来、修法不碰人闸（对外发布、花钱、删数据、改标准）、不改规矩、也不是重大设计岔路**——代价表照摆，写进 PR 正文，自己拍、接着干，不停下来问。用户要的是「问题和机制同一轮修掉」，不是每个小机制都等他。拿不准算不算重大，就按重大处理（问）。

### 6. 落库，按剧本验收

- 结论 + 依据（链接）+ 拍板结果，写进对应的 issue、PR 或需求文档。**只写指针和结论，不抄大段文档。**
- 做完照第 4 步的操作剧本真人走一遍，报改前改后的三样代价。检查、测试全绿只是前提，不算验收。
- **界面另验版面**：每个目标屏幕尺寸各截一张，和第 3 步的对照画面并排，逐条写下答案（写不出、答案是否，都不算验收）：
  1. 屏幕用满了没有：工作区里空着的那一块多大、是不是刻意留的；
  2. 要紧的细节是不是一眼可见：藏在抽屉、悬停、折叠、「详情」按钮后面的，逐个说为什么非藏不可；
  3. 这一屏最显眼的是不是下一步。
- 能写成检查的写成检查，挂在每次改动都要过的那一步（例：页面骨架铺满视口的测试；页面只许用统一页面框架的 lint 规则），并配一条故意造出失败的用例。

## 硬规矩

- **没有业务说明就动手设计，视为未完成。**
- **没有查证的设计回答，视为未完成。** 可以答，但要标「未查证」并说明为什么这次不查（例如纯本仓内部的事实）。
- **引用必须点得开**：给 URL 或 `文件:行`；不许写「业界普遍认为」这种没出处的句子。不许拿记忆当来源。
- 设计理由里出现「原来就是这样」「沿用现有」「兼容旧结构」，要换成业务上的理由；换不出来，回第 2 步重推。
- 业务规则只增不丢：新设计漏了旧实现守着的一条规矩，比界面难看严重得多。
- 重做范围由用户定：用户说「全部推倒」就全部，别自己缩成「先改一页」；分期可以，但每期都按本页走。
- **关卡看不见的错，关卡不算过。** 每道关（草图、预览、测试、截图、清单、用户的点头）用之前先问：要是那个错就在这儿，这份证据会显出来吗？不会，就换一份会显出来的证据再过关。tsc 看不见画错，文字草图看不见宽屏空着，没有对照的截图看不见难看。

## 判例

每条规矩是哪次出事加上的（凭记忆答设计题、照旧实现改版、文字草图冒充版面），见同目录 `references/判例.md`；改规矩时回来看。

## 和相关 skill 的分工

| skill | 管什么 |
| --- | --- |
| `docs-lookup` | **怎么查**：搜索、库文档、GitHub、已知网页各走哪条路 |
| **`best-practice-first`（本页）** | **要设计时**：从业务推、拿业界比，摆给用户拍 |
| `chain-first` | **现状不对时**先查断在哪（谁写、谁读、谁报警）；查到要新造或换机制，才转到本页 |
| `discuss` | 要人拍板的方案先让几家模型**快速讨论**：各自独立答，再挑错 |
| `grill-ai` | 自查**我自己**的路是不是从一开始就走歪了（补丁链） |
| `grill-me` | 拷问**用户**的想法：该不该做、长什么样 |
| `judge-or-code` | 某一处机械判断该写代码、交给判断题小模型，还是这次不固化 |
