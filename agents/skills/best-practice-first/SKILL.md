# 设计先查业界，现状不对先查断链

## 设计
- 现有实现只是需求的证据，不是起点：从它抽出守着的业务规则（替谁、干成什么、判什么、拦什么），怎么做从业务重新推。大改动先把这份业务说明给用户过目。
- 设计问题不凭记忆答，去查业界：至少两条独立来源，记链接；找用户用过的同类产品，分层对照（界面：信息架构、版面、视觉；接口：真实调用顺序；流程：同类团队的真做法）。技术细节用所选框架的标准机制。
- 按操作剧本数代价（动手、搬运、离开的次数）；摆出「删掉整层」的选项和代价表，给一个推荐。只有要掏新钱、要删找不回又没备份的、和已拍的规矩冲突、要删整层才停下问。
- 草图精度要够拍它要拍的那一层：分块、流程用文字草图；版面、视觉必须是目标尺寸的真画面，和对照并排。
- 旧实现守着的业务规则只增不丢；找不到出处的旧东西单独列出来问删还是补，不默默留也不默默删。
- 结论和依据（链接）写进对应的单、PR 或需求文档，不抄大段原文。做完照剧本真走一遍；界面按目标尺寸截图，和对照并排看。
- 每道关用之前先问：要是错就在这儿，这份证据会显出来吗？显不出来就换一份。

## 现状不对
- 症状是链上某一环断了的结果：画出「谁写、存哪、谁读、坏了谁报警」，去机器上读（修改时间、进程在不在、数据时间），不凭记忆；再问「为什么这么久没人知道」。
- 修法优先：删层、读时现算、读方查新旧、最后才加报警。问题和机制同一轮一起修；同一处要打第二层补丁就停手，回到这里重推。
- 读不到先追数据源，不放宽读方判据凑绿；「没查成」和「查了没事」必须分得开。
