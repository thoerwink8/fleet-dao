## 一、三套工作流并存（这正是 #250 说的「两套工作流并存」）

| 工作流 | 是什么 | 现状 |
|---|---|---|
| **Fusion**（`workflows/fusion.ts`，#214） | 一张单一个主导模型（Lead）会话领着走 0–7 步，派一个副手（Sidekick）干界定清楚的活；引擎推分支、开 PR、合并、关单，不往主线直接写。**后端拉起一张单起的是它**（`requirement-start.test.ts`） | 默认；断点多 |
| **需求工作流**（`requirement.ts`）+ **子任务工作流**（`subtask.ts`） | 旧流程：分诊 → 需求文档 → 方案拆子任务 → 按依赖起子任务 → 结果文档 → 关单 | 切换之前起的旧任务照旧跑完（`requirement-start.test.ts`）；#250 说 Fusion 跑通后删掉旧的（连同直写主线的 `writeSpecDoc`） |
| **合并队列**（`merge-queue.ts`）、**开 PR 前验证**（`verify.ts` 只是给 Fusion 调的一块，自己不是工作流）、**并主线**（`sync-mainline.ts`） | 共用零件 | 见下 |

## 二、业务规则（每条标出处）

**A. Fusion 0–7 步（`fusion.ts`，`fusion.test.ts` 55 条）**

1. 步骤：**1 收单**（引擎，不用模型：看流程配置副本，读不到、认不出就停派报红；认单子正文里指的需求文档目录；建工作树）→ **2 规划**（Lead 读需求文档和代码，把方案写进 `specs/<号>-<短名>/方案.md` 提交，交方案摘要和任务简报，先推上去）→ **3 方案评审**（小单跳过；不算小单的引擎还没接评审 #249，照跳过、PR 里写明）→ **4 执行**（副手照简报在同一棵树上干，按流程配置派别家的便宜路由，派不出、没额度就 Lead 自己干；Lead 验收，打回最多 2 次或自己接手）→ **5 开 PR 前别家验证** → **6 开 PR、过 CI、Lead 最终审查** → **7 合并、写结果、关单**。——`fusion.ts` 头注释；0003 第 5 条。
2. 没指需求文档的单：停下等人、不建工作树；正文补上后点「继续」，按库里最新的正文认。**引擎自己开的单（对账后续单、巡检单）正文写全了需求、没有需求文档的照收**：目录按标题取短名，Lead 把照正文写的需求文档和方案一起提交，开 PR 前验证照正文逐条核，「对应计划」照单子挂的版本写（#295）；Lead 只提交了方案没提交需求文档：方案不收、退回，几次都不交就停下等人、不推；开 PR 前单子正文里的「怎么算做完」被删了：不验、也不当成验过，停下等人补。——`fusion.test.ts`「正文写全了需求」。
3. 流程配置读不到、认不出：这张单停派报红、一个会话都不起，修好点「继续」接着走；停派时叫停：库里的任务记成叫停（不留在排队）；全组织默认读不到判停派、不拿空配置顶。——`fusion.test.ts`；`decisions.test.ts`。
4. 副手打回两次还没做好 → 第三次 Lead 接手自己写，后面照常验证、开 PR；全组织默认的配置在 PR 里写明（#246）；副手碰了简报外的文件、Lead 看过收下 → 直接收下推上去，不返工，状态、PR 正文、关单评论记下来；**验证照推上去的头相对主线的净改动判，不按界面派**（副手并过主线、主线上别人改了页面代码的场景，#293）。——`fusion.test.ts`。
5. 验证挡两轮（Lead 没驳回）：回去改一轮还没过就停下等人、不开 PR；CI 红三轮都没修好：Lead 每轮写修复简报、副手改，第四次还红就停下等人；没有别家可验（写过这张单的两族之外没有能派的路由）：停下等人、不拿同族顶、不开 PR。——同上。
6. **先审后合（#253）**：碰安全的 PR 请第二意见 → 必须改 → 修一轮 → 再审通过 → 照常合并；不碰高风险路径一次都不请；连着两轮必须改停下等人；`merge-gate` 单独报红不当 CI 没过；**合并闸连着 3 次只报自己红、没有别的失败检查：停下等人时带出合并闸自己的说明，不猜「多半是别的原因」**（#444），没读到说明就照实说没读到；高风险清单读不到：停下等人；贴第二意见状态没权限：停下等人；**写这张单的是 Grok、review 排法第一个也是 grok：整族避开，不许挑到自己审自己**；**请第二意见前不信开工时的快照，现读流程配置副本**（#199 教训：项目开工后才声明清单，读不到就当没碰到，白白红了 3 次），读不到明确失败。——`fusion.test.ts`「#253 先审后合」。
7. 合并那一步头变了（合并队列把主线并进来）：合并闸只缺 `second-opinion` 不当「测试没过」退回（不进 `mergeReturns`、不派 Lead 改代码）；新头相对主线的 patch-id 和上一轮通过时一样就沿用、不再拉一次审查会话；patch-id 算不出来不许当成一样、照常请一轮真的第二意见；合并前重跑真的红了算一次返工；等 CI 查到 PR 已在外面合并了（GitHub 自动合并先合了）当合并成功走收尾；PR 被关但没合并：连着 3 次没查成停下等人。——同上。
8. CI 报和主线冲突：**自动并主线**并上了接着在新头上查 CI（不算「没查成」的次数）；遇到真冲突派会话照冲突文件解开，改完推上去；一直冲突自动并主线连试满上限就停下等人；**PR 的头被改写了（新头不含老头）立刻停下等人**，不当成没查成、不试着并主线；任务边界并主线：没有会话在跑时点一次、在派新会话之前，遇到冲突最佳努力不挡这一步，读不到 GitHub（活动一直失败）挂起报警、不静默卡住。——同上。
9. **问创始人不挡路**（#259）：Lead 写方案时 `fleet blocked --needs human`：不停下等，退回让它带推荐用 `fleet ask` 问、续同一个会话；退回到数还说要人但带着推荐：按会话自己的话接着做，PR 正文「按推荐先做了」记一条，照常发卡片；退回到数还说要人却一个字的推荐或假设都拿不出：说不清，走失败梯子、不当按推荐放行；要的是只有他本人才有的东西（`--needs access`）不退回、照旧停下；他晚到改选了别的（还没开 PR）：存档点交给 Lead，本来的活收下后回第 4 步照改，改完推上去记「照改了」，再验证、开 PR；他在 Lead 写方案时就改选了：不跳过这之间的步骤（方案评审照走）；PR 已经开了：算开了 PR 之后修一轮；超出这张单范围的：这张单绕开它做到合并、PR 正文写明另开单等他拍；**这张单问过创始人的读不到（库没查成）不当成一条都没问过往下走，挂起报警**。——同上。
10. 单模型模式：Lead 自己写、不派副手、不高风险就不验证，照样最终审查写结果；高风险的单（要验）Lead 自己写那一步带上「给验证留一家」；副手派不出、Lead 是 Grok：Lead 自己写、PR 正文写「Lead 单干」，不说成 Claude 单干；方案里写了人闸：合并前发卡等人批，批了才进合并队列。——同上；0003 第 7 条。

**B. 开 PR 前别家验证（`workflows/verify.ts`，`verify-round.test.ts` 12 条；#213）**

11. 一轮 ＝ 读默认分支上需求文档的「怎么算做完」→ 查写这张单的会话用过哪几族 → **只派别家**起验证会话（检出送检的头、只读；整份提示词先过卫生检查）→ 经 `decide` 判结论（`core` 的 `decideVerdict`）→ 记进库；Lead 拿证据驳回再判一次、改写同一行；几轮、挡了回哪一步照 `core` 的 `nextFlow` 走（默认 1 轮、最多 2 轮）。——`verify.ts` 头注释。
12. 每条失败路径都挂起等人、不当成验过了：Lead 的驳回没带证据不算数（这一轮照样挡着）；结论文件解析不出作废并挂起；**没写结论（会话结束了、没交结论文件）退回重写、换别家模型，还不交就挂起，一行「过了」都不记**；审的不是送检的头作废挂起（写明送的和审的各是哪个）；选路出错派成了同一族作废挂起；没有别家可验挂起、不拿同族顶、不起会话；发给别家的材料没过卫生检查不发、挂起；需求文档读不到不验、挂起；查不到写这张单的是哪一族不验、挂起（不当成谁都能验）。——`verify-round.test.ts`。

**C. 子任务工作流（`subtask.ts`，`subtask.test.ts` 49 条）**

13. 建树 → 执行（AI 会话，只在本地提交）→ 引擎推分支、开 PR → 验证（同步主线 + 等 CI ∥ 全新会话第二意见；意见回主会话）→ 人闸（带人闸标记的等人批准）→ 进合并队列 → 收树。编号是 `subtaskWorkflowId(subtasks.id)`，驾驶舱后端可以直接给它发信号；需求工作流以子工作流起它，也能单独起。——`subtask.ts` 头注释。
14. 起会话：每次一个新的 `runId`；worker 现签只对这次会话有效的通行证、把 `fleet` 命令放进 `PATH`、给停滞超时；起会话还没返回时叫停：收尾按 `runId` 停掉它、后来才做完的起会话不再起进程（不白烧额度）；起会话做完了、回话丢了：重试拿同一个 `runId` 拿回已经起的那个、不起第二个；会话结局记进库：花费是会话累计值和上一轮的差（续会话时不重复算）。——`subtask.test.ts`。
15. 人发的命令：**暂停**（会话停在干净的点，继续后续上同一个会话；暂停 5 小时再继续：等人的时间不算进墙钟预算）、**继续**（不在暂停也不在挂起时收到，回执里写明忽略）、**叫停**（停会话、收树先存档、以 `stopped` 结束、不进合并队列）、换路由、回答、批准、加人闸；**不认识的命令不静默丢、回执里写明忽略**。——同上。
16. 交付对账：改的文件和方案点名的地方一个都对不上，不推不验、回主会话重做；推之前的卫生检查拦下：退回会话（带着拦在哪）、会话拿掉再交就推上去；同一处连续被拦两次不再退回、挂起报警；名单没读到、没扫成：配置问题挂起报警、不退回会话；第一次推就报 `BEHIND_MAINLINE`：原地再推一次；推之前并主线有冲突（MC1）退回会话解冲突；推的端口说没交付（有没提交的改动，DL1）退回会话；开 PR 被卫生检查拦（会话总结里有）退回会话只改总结。——同上。
17. 判断出错不判死：本地活动 `decide` 自己的重试用完，按兜底梯退避后再判；判断一直出错挂起报警、修好后人发「继续」；活动失败先按活动自己的重试来；会话失败按兜底梯走（路由繁忙换路由、认不出的错重试、都不停下等人）；封号整池避开；等额度清零的长觉：人中途换了路由就醒；额度用满（Claude 订阅池，#59）不睡到清零、马上回去选路续同一个会话；非 Claude 订阅池挂起到清零续同一条路由、等的时间不算墙钟预算；设备被撤销挂起报警。——同上；见 `engine-1` 的失败分流。
18. 工作流事件数到了报警线报一次警（一条执行一张卡）、照样走完；工人丢了：长活动靠心跳超时秒级发现并重试接上；换了工人：停在暂停里的在途任务照样能查状态、收信号、走完。——同上；`worker.test.ts`。
19. 第二意见打回：意见回主会话（续上同一个会话）再审通过；连续两轮提同一条必须改：不开第三轮、挂起交人；合并队列在最新主线上测红：退回主会话修、修完重新排队；合并队列并好主线推上去之后测红退回：回会话之前照原来的头同步一次、带着树，会话起在并好的头上（不然再推就分叉）。——同上。

**D. 需求工作流（旧流程，`requirement.ts`，16 条）**

20. 分诊 → 需求文档 → 方案 → 子任务 → 结果文档 → 关单；需求文档、方案、子任务标题写进主线或 issue 进度段前被卫生检查拦下：退回对应会话（续同一个）拿掉再交，名单没读到挂起报警；看不懂的带选项和推荐问创始人、不停下等、按推荐先做，后面的会话带着这个假设（#259）；子任务按依赖先后跑，会改同一块的不同时跑、互不相干的并行；叫停：在跑的子任务停会话、收树，需求以 `stopped` 结束、不关单；依赖的子任务被叫停：后面的起不来、需求以没做完结束并报警、不关单；`fleet` 叫醒直接发给会话所属的子任务工作流、需求不转。——`requirement.test.ts`。

**E. 合并队列（`merge-queue.ts`，14 条）**

21. 每个仓一条、一次只合一个（同步主线 → 重跑测试 → 合并整段不交叠、先来先合）；红了退回子任务；由子任务的 `enqueueMerge` 活动 `signalWithStart` 拉起；空闲一阵就收工，攒够一批换一次历史（continue-as-new）；撤出（暂停、等人批、叫停）一定回话：还没开始合的当场回 `withdrawn`，正在合的等那一步做完；回过的话记在 `recent`（撤回也记）：撤出比排队先到，排队信号会被挡回去；同一个条目排两次只合一次；项目没声明先审后合清单时合并前重跑测试不带清单文件。——`merge-queue.test.ts`。

**F. 重放安全（贯穿）**

22. 工作流文件的规矩写成检查（`structure.test.ts` 11 条）：判断只经本地活动 `decide`（工作流文件对 `decisions` 只许 `import type`）；工作流里不碰活动、worker、客户端、假实现、真端口、`@fleet-dao/db`、`@fleet-dao/shared` 运行时、Node 自带模块；不生成编号（`uuid4`、`Math.random`）；`decide` 只在 `kit.ts` 里直接调，别处一律经 `judge` / `judgeRetrying`（判断出错按兜底梯走、不判死）。**改调度顺序（多调、少调、换顺序调活动或 `decide`）要用 `patched()`**，`replay.test.ts` 拿录好的历史（做完、暂停、挂起、等回答、在合并队列里、需求在调度……）对现在的代码重放，「不许重录夹具让它变绿」。——`kit.ts`、`merge-queue.ts` 头注释。

## 六、怎么算做完（重做之后）

1. 三段一条龙（指挥官定需求 → 工人干到开 PR、CI 绿 → Review 审一次就合）替掉 Fusion 与两套旧工作流：**一张单交接不超过 2 次**（需求文档交给工人、PR 交给 Review），不在中间来回对话。
2. 保留的规矩：不直写主线；人闸只在四类上停；问创始人不挡路；先审后合的第二意见；卫生检查拦下退回、名单没读到挂起；重放安全（`decide`/`patched()`）。
3. 上线的同一个 PR 删掉 Fusion 的代码、测试、库表、驾驶舱入口、design/ops/AGENTS 里的说法；在巡检仓跑一张完整的单确认没把能用的删坏。
