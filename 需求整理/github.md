# github：引擎和 GitHub 之间的一切（业务说明）

> 一句话：引擎替创始人对 GitHub 做的所有动作都在这一个包里——用两个机器人账号（App）拿令牌、把会话写好的提交推成分支、开 PR、等 CI、合并、改 issue 进度段和关单、认「自己写的回声」、每小时对账补漏事件；每个写动作都带幂等键防重复，每条读都「读不到就报没查成、绝不当成没有」。
> 出处：`packages/github/package.json` 说明；`src/` 各文件头注释；`test/`（23 个文件、约 480 条用例）；`docs/reference/github.md`（从旧系统移植的坑，用例里写成 A1、B1、C6、C13 这类编号）；`docs/design.md` 第十四节「主线只有引擎能动」。

## 一、干什么、不干什么

- **干**（30 个源文件）：
  1. **身份**：`app-auth.ts`、`credentials.ts`、`client.ts`、`errors.ts`——两个 App（「干活的」「引擎」）的 JWT、安装令牌、HTTP 客户端、限流退避；
  2. **推分支**：`push.ts`、`bundle.ts`、`sync.ts`、`git.ts`——会话打成 git 包交出来，引擎在自己的裸仓（镜像）里导入、推上去、并主线；
  3. **PR**：`pulls.ts`（开、等 CI、合并）、`checks.ts`（CI 结论）、`text.ts`（PR 正文模板、关单词中和）；
  4. **issue**：`issues.ts`（进度段、关单、开单、评论）、`progress.ts`、`groom.ts`、`issue-plan.ts`、`close-facts.ts`；
  5. **需求文档直写主线**：`contents.ts`；
  6. **防重复与镜像**：`idempotency.ts`、`ledger.ts`、`echo.ts`；
  7. **事件和对账**：`events.ts`、`reconcile.ts`、`repos.ts`、`interaction.ts`、`commit-relation.ts`、`claims.ts`；
  8. **公开仓卫生**：`publish-check.ts`。
- **不干**：决定「该不该合、该不该开」——那是引擎的工作流和 `@fleet-dao/conventions` 的事；也不解读事件里的文字（事件只当「叫醒」）。
- **硬约束**：不经 `gh` 命令行（源码里不许起 `gh` 子进程，`static.test.ts` 盯着）；源码里不许出现字面量 `master`（分支一律读仓库的 `default_branch`，G1）。

## 二、业务规则（每条标出处）

**A. 身份、凭据、请求**

1. 两个机器人分工固定：「**干活的**」开 PR、推分支；「**引擎**」合并、改 issue 进度段、关单、读、贴提交状态、撤自动合并。合并闸只认「引擎」那条状态。——`claims.ts`、`pulls.ts` 头注释；`client.test.ts`。
2. 令牌：JWT 用 RS256，`iat` 往前拨 60 秒抗时钟漂移、9 分钟过期；安装令牌 1 小时过期、剩不到 10 分钟就重换（长任务跑到一半 401 就是这么来的）；一枚令牌只对一个仓；令牌只在内存里，**不落盘、不进日志、不进命令行参数**；GitHub 把令牌或 JWT 回显在报错里，`message` 和 `details` 逐层打码。——`app-auth.ts`、`errors.ts`；`client.test.ts`。
3. 凭据文件三种坏法分开处置：缺文件＝这台机器没装（`NOT_INSTALLED`）、读不了＝运行用户不对（`CREDENTIALS_UNREADABLE`）、缺字段/私钥坏＝配置错了（`BAD_CONFIG`）；报错只写路径和缺哪个字段，不带文件内容。——`credentials.ts`。
4. 直接走 HTTP：写请求全局串行且间隔 ≥1 秒；次级限流（403/429 + `retry-after`）后所有请求先停；没给头至少等 60 秒、再撞翻倍；主配额用完等到 reset；要等太久不干等，抛可重试的 `RATE_LIMITED` 带上要等几秒。——`client.ts`；`client.test.ts`（F1）。
5. 失败分三类：能重试、不能重试、**可能已经写成**。POST 断在回执上（网络错、5xx）不自动重试，抛 `AMBIGUOUS_WRITE`，交幂等层先回查；404 不一定是「不存在」（App 没装到这个仓也回 404，报错两种都写）；一直 401 报 `AUTH_FAILED`；翻页翻到上限没翻完报「没查成」，不悄悄截断；超过 JS 安全整数的数字（19 位投递编号）按原文留成字符串。——`client.ts`；`client.test.ts`。
6. 仓的事实一律从 GitHub 读、短时缓存：默认分支（旧代码到处写死 master，G1）、主线必过检查（从规则集读——手打常量早晚被凭印象填错）。——`repos.ts`。

**B. 防重复写（每个写动作都过这一层）**

7. 每个写操作带幂等键，账记在 Postgres 的 `idempotency_keys`（不放本机文件：换机器、多个工人、从备份恢复后重放都认得出，旧网关的账是每台机器一份本地文件）。流程：占键 → **先回查远端**有没有（按正文里的隐藏标记、按分支）→ 没有才写 → 记回执。占到键就一路续占用；写之前再确认占用还在自己手里；写到一半断了下次先回查，找到就补账，找不到且占用过期才重写；确定没写成（GitHub 明确拒了、回查就失败了）放键，只放自己那一份；键由内容推出（动作 + 目标 + 内容摘要），给 issue 和给 PR 的同一组改动是两个键（B4）。——`idempotency.ts`；`ledger.test.ts`（24 条）。
8. 跨工人的锁：同键串行；两个工人抢同一个键一个放了另一个才进；持锁时锁不占着数据库连接（只有一条连接的库也不会自己等自己）；持锁的工人死了（2 分钟没续）等它过期再接、不提前闯进去；锁那一行被记成「已完成」（账写错了）报出来、不干等。——`ledger.test.ts`。
9. PR 镜像（`pull_requests`）：写入按 GitHub 的 `updated_at` 防倒退；换了头 CI 汇总重置为 pending；CI 汇总只写到 head 还是那个 sha 的行上；「这次没读到」（审计补合并那一路没带正文）不拿空顶、旧的链接留着，带了空正文才清；合并提交号必须是 40 位十六进制（库的约束拒半截）。驾驶舱和 `fleet done` 都只读镜像、不直接查 GitHub，所以镜像写错了人看到的就是错的。——`ledger.ts`；`ledger.test.ts`。
10. 认回声：自家机器人写了 issue/PR（改进度段、关单、开 PR、合并），GitHub 上它的 `updated_at` 就等于写入回执里的值；轮询补收时看不出是谁改的，就按这个值认，对上了当成自家回声、不叫醒工作流（自己不叫醒自己）。记在幂等账里，跨工人跨重启都认得。——`echo.ts`；`events.test.ts`。

**C. 会话外推分支（`push.ts`、`git.ts`、`bundle.ts`、`sync.ts`）**

11. AI 会话只在本地提交；提交由**会话用户**打成 git 包（bundle）交出来，引擎只把包导入自己的裸仓（镜像），在镜像里用「干活的」机器人推。**带令牌的 git 绝不在 AI 会话的工作树里跑**（工作树的 `.git/config`、钩子会话写得到，一条 `core.hooksPath` 或 `insteadOf` 就能把令牌带走）；凭据只走环境变量里的一次性配置，不进命令行参数（`ps` 看得见）、不写进 remote、不落盘；子进程环境里不留 `GH_TOKEN`，也不让它弹窗要密码。——`git.ts` 头注释；design 第十四节；`push.test.ts`。
12. 推之前核五件事：不是主线（拒绝推默认分支）；包含此刻最新的主线（否则先同步）；相对主线真有内容（**不推空交付**，C7）；还没推上去的提交逐个过卫生检查（先加后删、写进提交说明的也扫）、分支名也按名单比（推送带 `--no-verify`，git 钩子不跑，只能在这儿拦）；远端分支要么没有、要么是我们的祖先（别人在上面推进过就报出新头，分叉就停，**绝不强推**，C6）。同一个头再推一次什么都不做；被 workflows 权限拒一次判「要人」、不当可重试（C3）。——`push.ts`；`push.test.ts`（23 条）。
13. 包的校验：不是包、截断、改坏一个字节 `BUNDLE_INVALID`，缺对象 `BUNDLE_INCOMPLETE`，超大 `BUNDLE_TOO_LARGE`，提交不在包里 `HEAD_NOT_FOUND`，都不可重试；以 `-` 开头的 tip/exclude 一律拒收（防参数注入）；分支名不合规不发一个请求就拒；抓取失败（网络类）报可重试的 `GIT_FAILED`，不当成「分支不在」。——`bundle.ts`；`bundle.test.ts`。
14. 并主线（合并队列和子任务返工用）：在镜像里把最新主线并进 PR 分支推上去；冲突回冲突文件清单、远端分支不动；远端头被人推过报出新头什么都不做；重试时远端头正是自己上次推的并主线提交，认出来当成功；非快进被拒报可重试的 `PUSH_RACE`；git 太旧报 `GIT_TOO_OLD`。并主线、推分支同一个仓用同一把镜像锁，否则两边同时 fetch/push 会互相踩对象库。——`sync.ts`；`sync.test.ts`。

**D. PR：开、等 CI、合并（`pulls.ts` 41KB，55 条测试）**

15. 开 PR：「干活的」机器人；**按分支幂等**（同一个分支只有一张开着的 PR，回执丢了回查分支，绝不开第二张，B1）；编号读返回体的 `number`、不从链接里抠（B5）；标题正文里的关单词改成「关联」（C13）；正文超 65536 字发出前就拒并报实际字数；新开的 PR 回读作者不是「干活的」判失败；分支上已有一张目标不对的 PR 拒绝、不另开；照抄需求 issue 的类别标签和里程碑（issue 同时贴了两个类别报 `ISSUE_CATEGORY_CONFLICT`，等人改）。——`pulls.test.ts`。
16. PR 正文模板：栏目和 `.github/pull_request_template.md` 一样、顺序也一样（引擎开的 PR 和人开的长一个样）；16 行以内，多了从最长的一栏砍、写「另有 N 条」；「这个 PR 做完就关单」一律写「否」（引擎的单第 7 步自己关；写「是」GitHub 替引擎关了单，接活当成叫停）；「按推荐先做了」（#259）一条一行；没写的写「（没写）」让合并闸照样提醒，不冒充填了。——`text.ts`；`text.test.ts`（18 条）。
17. 往公开仓写东西之前先过一遍卫生检查（推前扫描和 git 钩子拦不到这几条路：需求文档直写、开 PR 的标题正文、issue 进度段）：内容被拦 `HYGIENE_BLOCKED`（不可重试，退回会话改）、名字被拦 `HYGIENE_NAME_BLOCKED`（文档路径、分支名是引擎按 issue 标题定的、会话改不了，挂起等人）、名单没读到 `HYGIENE_LIST_MISSING`、扫不成（带 NUL）`HYGIENE_UNSCANNED`——**都不写**；报错只带位置（文件、行、规则名），不带值。——`publish-check.ts`；各测试文件的「卫生检查」节。
18. 等 CI：按**必过检查的名字**等（从主线规则集读）；**零条检查不算绿**；同名只认最新一条（rerun、双触发，C9）；冲突态 PR GitHub 不起 CI，单独认出来交回同步主线（C1）；「CI 根本没跑」和「跑了没跑完」分开报；读不到算「没查成」不当零条（C16）；超时、取消、要人操作都算红；头变了（C8）：新头不含老头就不再等、报 `head_moved`，新头含着老头（人或引擎并了主线）认新头接着等；刚推完读回更早的头，隔一会儿再读；读到红隔一会儿在同一个头上再确认（C17），确认过还是红才报红；PR 已关：合并关的（GitHub 自动合并先合了）`merged=true` 带合并提交，人关的 `merged=false`；心跳带着计时，工人重启后接着算。——`pulls.ts`、`checks.ts`；`pulls.test.ts`、`text.test.ts`「CI 结论」。
19. 合并：「引擎」机器人 squash；合并前再核一遍——头没变（C8）、基于最新主线（落后就先同步）、CI 在这个头上是绿的、能合（`mergeable` 还没算出来就重读，C10）；squash 带 sha 头约束、显式提交标题与**非空**正文（空串 GitHub 会换成默认正文，把分支提交里的 `Fixes #N` 带进主线，C13）；失败不看文案，重读 `mergeable` 再分类（C11）；合并记进幂等账（对账拿它核「是合并队列合的」，C21），合完回执丢了补记、不再合；合并人不是「引擎」要标出来（C22）；草稿先转正式；同一个仓的两张 PR 从核对主线到发合并请求按仓串行；合并后分支上又有新提交不删。——`pulls.ts`；`pulls.test.ts`。

**E. issue：进度段、关单、开单、评论（`issues.ts`、`progress.ts`）**

20. 进度段：只替换 `<!-- fleet:progress:start as-of=<时刻> -->` 到 `<!-- fleet:progress:end -->` 之间，**人写的部分一字不动**（含 CRLF）；同一张单的写入加锁串行；慢到的旧快照不盖新快照（as-of）；内容没变就不写（省 GitHub 内容创建配额）；GitHub 的写没有「版本不对就拒」，所以写完用编辑历史核对——读和写之间插进人手编辑被盖掉了，把人写的那一版找回来放回进度段并报警；编辑历史读不到，写是写成了但标明「没核对成」；正文超上限发出前就拒；拿 PR 号来更新进度段拒绝。——`issues.test.ts`；`progress.ts`。
21. 关单：先发一条写明去向的评论（带标记，幂等），再关（带 `state_reason`），**回读** `state` 与 `state_reason` 才算成（A8）；回执丢了重试不再发第二条评论；评论过百也翻得到自己那条；接口回成功、回读却没关上报错。——`issues.test.ts`「关单」。
22. 开单：正文末尾带标记 + 幂等键；账丢了按标记翻页回查（最近 3 页、300 张，找不到就当没开过）；来自 AI 的正文（提问、回答）写之前先中和 `@` 提醒和能伪造/截断标记的 `<!-- -->`，再过卫生检查；标题空或超 256 字 `INVALID_INPUT`；里程碑为 null 时请求里不带。——`issues.test.ts`「开单」。
23. 评论（#259：引擎对账时给提问另开单、把回答写到另开的单上）：同一个 key 只发一条；账上记着发过了就一个请求都不发（对账每轮拿同一个 key 来认，不能每轮读一次单子）；对 PR 号报 `NOT_AN_ISSUE`。——`issues.test.ts`。
24. 一张 issue 此刻挂在哪个版本、开没开着、是不是母单或子单（`readIssuePlan`）：一次 GraphQL 查全（REST 的父单接口没父单时回 404，和「没装到这个仓」分不开）；读不到、形状认不出、没翻完（标签超过 100 个）一律抛错，**不拿「没挂里程碑」「不是子单」「开着」顶**。后端接活判「挂在当前版本、不是母单子单」和 `fleet-api handover` 判「开着没有、重开过没有」都用它。——`issue-plan.ts`；`issue-plan.test.ts`；0003 第 2、8 条。
25. 单子进门自动打标（#448）要读写的现状：开着的单（标题、正文、作者、标签、里程碑、创建/更新时刻）、全部里程碑（含关了的：挂在已关里程碑上还开着的单正是版本交接要处理的断链）、一张单的标签时间线、补类别标签、挂里程碑；PR 混在 issues 列表里的过滤掉；机器人开的 `authorIsBot`，作者账号删了（user 为 null）不算机器人；读不到、形状认不出抛错。——`groom.ts`；`groom.test.ts`（23 条）。

**F. 事件之后的处理与对账补漏（`events.ts`、`reconcile.ts`）**

26. 事件只当「叫醒」：里面的文字不当指令；CI 结论回 GitHub 重读、不信事件里带的（事件会乱序、晚到、被补收重放）；PR 事件写镜像并叫醒对应工作流；合并的 PR 记成 merged，晚到的旧事件不把它改回 open；事件里没带正文（只有号和头）不把镜像里的链接清空；issue、评论事件按 issue 号叫醒，PR 上的评论按 PR 号；**叫醒失败就抛**——后端把这条投递记成出错、原文留着，对账时按原文重放，所以每一步都要能重放。——`events.ts`；`events.test.ts`（27 条）。
27. 重投：GitHub 不自动重投失败的投递，用 App 身份拉投递日志，同一次投递（guid）一次都没成功、后端库里也没有原文的才重投（后来成功过的不动；库里有原文的交后端按原文重放，不叫 GitHub 送第二遍）；名额不够时老的优先（不然新失败的把老的挤出去，等 `since` 窗口一过就永久补不回来）；19 位编号按原文拼路径（法国实测 …928 被改成 …000，重投全 404）；投递编号认不出、投递日志读不到 → 「没查成」、一个都不重投。——`reconcile.ts`；`events.test.ts`「对账与补漏」。
28. 轮询：按 `updated_at` 拉 issue、评论、PR，整条原样送进后端**同一道门**（白名单、去重）；同一版本只收一次；认得出自家回声不叫醒，人改的照样叫醒。——同上。
29. 核对：白名单作者开的开放 issue 都有工作流（没有就重新送进引擎，陌生人的不算问题）；合并的 PR 都记在镜像里；**我们两个机器人开的** PR 还要是「引擎」合的、账上有合并队列的合并记录（C21/C22），人开的不查这两项。每一项都分清「查了、0 个问题」和「这次没查成」：读不到报 `unscanned`、做了一半报 `partial`、全没做成报 `failed`，**绝不报 ok**。自检：两个机器人的权限够不够（「引擎」缺 `statuses:write` 要报出来，贴不了「认领对得上」），读不到权限表算没查成、不写「缺这缺那」。——`reconcile.ts`；`events.test.ts`、`unreadable.test.ts`。
30. 互动限制「只限协作者」自动续期（公开仓，每次最长 6 个月）：剩余不足 30 天才续，显式 `six_months`（不写默认只续一天）；回读到期时间确实往后推了才算（A8）；读不成、写不成、账户级限制挡着（409）都报出来：没续成 ≠ 不用续。——`interaction.ts`；`issues.test.ts`。

**G. 需求文档、流程配置文件、认领、关单对账（这几块在删除范围）**

31. 需求文档直写主线（`contents.ts`）：以「引擎」身份用 Contents API 写 `specs/` 下（路径必须在 `specs/` 下、相对、不含 `..`、反斜杠、控制字符）；sha 过期（409）重读再写一次；403 明确报错；409/422 不是 sha 过期报 `SPEC_DOC_REJECTED`；内容和远端一样不写；同样先过卫生检查。头注释自己写明：**这是「临时定法」**（design 没写清谁写、写到哪个分支）。读：`readSpecDoc`（文件不在回 null、读不了报错）、`readRepoFile`（读仓的 `.fleet/flow.json`，先读默认分支头再按这个提交读，文件不在 `missing`）。——`contents.ts`；`contents.test.ts`（29 条）；#250。
32. 认领对得上（`claims.ts`，#348）：以「引擎」贴提交状态（要 `statuses` 写权限，没有或权限表读不到都明确报错、不当成贴上了）、读头上某 context 最新一条、撤自动合并、关 PR（分支不动）、PR 上留言。——`claims.test.ts`。
33. 关单对账要读的仓现状（`close-facts.ts`，#241、#460）：主线上 `specs/` 下的文件、开着的单连子单、最近关掉的单、开着的 PR、最近合并的 PR（按 `updatedAt` 翻到早于 `since` 就停）；读不到、翻不完抛错；仓里没有 `specs/` 是 `null`，和没读到分开。——`close-facts.test.ts`。
34. 判两个提交谁含谁（`commit-relation.ts`）：流程配置对账用它判「读到的新字段，是不是还没发布的引擎版本才认得」；比不出（404）回 null、不当成「不含」，接口真出错照抛。——`commit-relation.test.ts`。

**H. 总则**

35. **「读不到」一律报明确的失败**（通用规矩「底线」）：每条读 GitHub 的路径各造一次读不到或形状认不出，结果必须是「没查成」或抛错——不许变成空列表、0、ok，更不许据此去**写**（没找到旧 PR 就再开一张＝重复写）。——`unreadable.test.ts`（12 条）。
36. 录好的真返回回放：`test/fixtures/github` 里是真机验收时 `--record` 录的（已脱敏、占位账号），把真返回跑一遍同一段代码，证明解析与判断对得上真世界；夹具自己过脱敏检查，故意放的违规样本拦得住。——`fixtures.test.ts`。
37. 真机验收：在巡检仓上走一遍「开 issue → 开分支 → 推一个提交 → 开 PR → 等 CI → 合并 → 更新进度段 → 关单」，每步核对回读（作者、头、合并人、正文、`state_reason`）。——`test/e2e/github-e2e.ts`。
