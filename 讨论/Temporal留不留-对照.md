# Temporal 留不留：业务、对照、推荐（2026-09-30 凌晨，已过别家模型一轮挑错；对应 `docs/goals.md` §七第 3 条）

## 一句话

**推荐：新引擎先按「库里一张任务表 + 一个监督进程」做原型（方案 C），过了 6 条验收标准才正式采用；任何一条过不了，就退到 DBOS（B）或留 Temporal（A）。** 现在要你拍的不是「永远不用 Temporal」，只是「同意按这个办法做 D0 原型」。理由：新流程只剩四件事，每一件的真相都能从外面直接读到（GitHub 上的 PR 和 CI、会话进程在不在、库里的额度），用不着再存一份「工作流历史」去跟外面对；今天所有「每断一次就加一个对账任务去兜」都出在这份历史和外面对不上。别家模型（GPT）挑了 4 条，核心是「动作做了一半崩了谁来恢复」，我都收进验收标准了。

## 1. 业务：新引擎到底要干什么

三段一条龙（指挥官 → 工人 → Review）+ 副手，引擎只负责工人和 Review 这两段的「跑」：
1. **放单**：有空位（同时最多约 10 个会话、每个账号池的额度够）就把一张「准备好」的单交给一个工人。
2. **盯死活**：会话还在不在、有没有动静；停滞、被杀、额度用尽要发现。
3. **失败换模型重试**：按失败原因分流（我们自己的、账号的、上游的、没给原因），换一条路由再来，有上限。
4. **接力**：工人交出提交 → 推分支、开 PR → 等 CI（几分钟到几十分钟）→ 绿了起 Review 会话 → 通过就合，不通过带意见回工人（最多 2 轮）→ 关单。碰四类人闸的只在那一步停下等人。

三个必须「读得出来」的事实：一张单现在到了哪一步（驾驶舱要显示）、谁在干什么（会话名和进程）、下一步在等什么（CI、Review、人）。

## 2. 现有实现当证据（不当起点）

- Temporal 相关代码不多：`packages/engine/src/workflows/` 14 个文件共 235 KB、`decisions/` 48 KB，占引擎源码 1355 KB 的约 21%；相关测试 219 KB。其余（选路、失败分流、会话驱动、GitHub 写入、额度读取）都是不依赖 Temporal 的纯函数和端口。这 285 KB 里最大的一块（Fusion 92 KB、kit 57 KB）本来就要随三段一条龙一起删。
- 代价证据（都在仓里）：①工作流要写成**重放安全**的确定性代码，靠 `decide` / `newIds` / `patched()` 这一整层，另有 `replay`、`evolution` 测试守着老历史能重放；②工作流编号的拼法「进了在途任务的历史」，改格式要在引擎里用 `patched()` 同时改后端（`packages/engine/src/contract.ts`）；③Fusion 与旧工作流「两套并存」的教训（#250）；④驾驶舱平时读 Postgres 不读 Temporal（「查询要重放历史，结束太久的执行可能查不了」，同一份 `contract.ts`）；⑤每小时对账、看门狗、开着的单都有工作流、合了的 PR 都记了账……一批为了「让 Temporal 里的历史和 GitHub 上的事实对上」而加的兜底（`docs/goals.md` §六把它们列进了删除计划）。
- 运维证据：Temporal 服务端 1.32.0 是装机脚本自己装的，另有两个库（`temporal`、`temporal_visibility`）要备份和恢复演练、一条防火墙规则（Temporal 没开认证，只靠只许 root 和引擎用户连）、`fleet-temporal` 命令行、「你好」验收脚本、健康页里 Temporal 和引擎工人两项。

## 3. 业界怎么做（引用；厂商自述的标出来）

- **Temporal 自己的生产清单**：自托管要自己建基础设施（Kubernetes 或等价物、数据库）；服务端「最快每两周发一版」，要求「按小版本顺序升级、不跳版」；自托管版**没有 RBAC 和审计日志**。<https://docs.temporal.io/self-hosted-guide/production-checklist>
- **DBOS**（开源，Postgres 里的库）：官方写明「什么时候用 Temporal：不想给技术栈加 Postgres，或者需要 DBOS 还不支持的语言」——我们已经有 Postgres、写 TypeScript。带队列（并发上限、限速）、定时、信号（`recv`）。生产上「建议」接他们自家的控制面 Conductor（是否收费没查；单进程重启恢复用不着它）。<https://github.com/dbos-inc/dbos-transact-ts>、<https://docs.dbos.dev/architecture>、<https://docs.dbos.dev/typescript/tutorials/queue-tutorial>
- **Restate**（单个二进制的持久执行引擎）：厂商页写「Replit 把 Replit Agent 从 Temporal 迁到了 Restate」（厂商自述）；第三方对比文章的总拥有成本排序是「已有 Postgres 的团队 DBOS 最低，要自托管又想少运维选 Restate，Temporal 最高但托管服务最成熟」。<https://restate.dev/vs/temporal>、<https://kanopylabs.com/blog/restate-vs-temporal-vs-dbos-durable-execution>
- **Anthropic 自己怎么跑长时间、并行的编码会话**：用 git 和进度文件当状态，每个新会话开头读 git 日志、进度文件、功能清单来「找回自己在哪」，不靠一个协调者记着（《Effective harnesses for long-running agents》，2025-11）；多个 Claude（第三方摘要写 16 个）并行写一个 C 编译器，**不用协调代理**，靠往 `current_tasks/` 写文本文件「抢任务」、git 的同步机制保证不重复，外面一个死循环不断起新会话（《Building a C compiler with a team of parallel Claudes》）。<https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents>、<https://www.anthropic.com/engineering/building-c-compiler>
- **控制循环（调节器）模式**：Kubernetes 的控制器就是「一个不停止的循环，看当前状态、把它推向期望状态」，每一轮都重新观察，所以重启、丢事件都无所谓。<https://kubernetes.io/docs/concepts/architecture/controller/>

## 4. 三个方案的代价表

| | A 留 Temporal，工作流压成三段线性 | B DBOS（Postgres 里的库） | C 任务表 + 监督进程（推荐做原型） |
|---|---|---|---|
| 要运维的东西 | Temporal 服务端 + 2 个库 + 每两周一版的升级 + 防火墙规则 + 备份演练 | 无新服务（用现有 Postgres）；控制面 Conductor 可不接 | 无新服务；少两个库、少一个服务、少一条防火墙规则 |
| 重放安全（确定性代码约束） | 有（线性流程下轻，但 `patched()` 这层还在） | 有（库替你管） | **没有**：状态是读出来的，不是重放出来的 |
| 迁移工作量 | 中：工作流重写，基础设施不动 | 中高：新依赖 + 重写（迁移本身要单独估） | 高：调度器自己写，但代码量小（估约 1–2 千行 + 测试） |
| 成熟度 | 最高 | 中（较新；厂商自述） | 自己负责 |
| 代码可读性 | 高（线性 `await`） | 高 | 中（状态机风格；`下一步 = f(单, 观察)` 是纯函数，好测） |
| 「历史和外面对不上」这一类断点 | 还在 | 还在 | **结构上没有**（每一轮都重新观察外面） |
| 「动作做了一半崩了」谁负责恢复 | 引擎（重放 + 活动重试，要求活动幂等） | 库（检查点 + 步骤重试，要求步骤幂等） | 我们自己：靠**外部动作可去重**（见第 6 节） |
| 和「要删的都要删」的一致度 | 中 | 中高 | **最高**：Temporal 整个撤，删除计划再多删一层 |

## 5. 推荐和理由

推荐 **C，但有条件**：先做原型、过 6 条验收标准（第 7 节）才采用。三条理由：①新流程只剩四件事，每一件的真相都在外面（PR、CI、进程、额度），「不存就不会过期」（`chain-first` 第 4 步）；②我们最大的痛就是「历史和外面对不上 → 加对账 → 对账又出新断点」，C 是从结构上去掉它，A、B 只是换了个更好用的历史；③一个人用、一台机器、约 10 个并发，Temporal 的强项（大规模、多语言、多集群）用不上，它的成本（自托管升级、重放约束、两个库）全在。

B 是好备选：要是原型过不了某条、或状态机写着写着变复杂，换成 DBOS 的线性代码，因为 C 把「下一步」写成纯函数、把外部动作放在端口后面，换调度层只动一小块（DBOS 的迁移也要单独估，不是白送）。A 只在「不想动基础设施」时才选。

## 6. 外部动作清单：每一个怎么去重、怎么确认（C 的核心前提，逐项过）

| 动作 | 去重办法（天然唯一性） | 崩了以后怎么确认结果 | 不确定时（超时、限流） |
|---|---|---|---|
| 起会话 | 会话单元名 = 单号 + 第几次，同名起不来 | 看这个单元在不在 | 当「不知道」，下一轮再看，不重复起 |
| 停会话 | 停一个已经没了的单元是空操作 | 看单元在不在 | 同上 |
| 推分支 | 固定分支名，同样的提交推第二次没有副作用 | 读远端分支的提交号 | 同上 |
| 开 PR | GitHub 一个 head 分支只能有一个开着的 PR，第二次会被拒 | 按分支名查 PR 列表 | 查不到（限流、500）不等于「没有」：先退避重查，**不直接开** |
| 起 Review 会话 | 同「起会话」，第几次写进名字 | 同上 | 同上 |
| 合并 | 已合的 PR 再合会被拒，是稳定的结果 | 读 PR 是否已合 | 同上 |
| 进度和评论 | 评论里放隐藏标记、原地更新（现有的「进度段」做法） | 按标记找评论 | 同上 |
| 关单 | 关一张已关的单没有副作用 | 读单状态 | 同上 |
| 问副手 | 只读，可以重复问 | — | 重问 |

**观察结果在类型上分三态**：「有」「没有」「没查成」——只有「没查成」时不许当成「没有」去动手（限流、超时、500、认不出，一律「没查成」，退避重查）。这条延续仓里「没查成 ≠ 没有」的底线，每条路径配一条故意造出失败的用例。

## 7. 6 条验收标准（原型全过才采用 C）

1. **动作清单**（第 6 节）每一行都有对应用例：故意让动作「做了但状态没写上」，重启后不重复、不丢。
2. **「没查成」不等于「没有」**：GitHub 限流、超时、500 时不重复起会话、不重复开 PR、不误判 PR 不存在。
3. **混沌**：在每个阶段的边界各 `kill -9` 一次监督进程——起会话后、推分支后、开 PR 后、CI 中、Review 中、合并前——并在「动作做了、状态没写」的缝里注入崩溃；断言重启后接着往下走。
4. **数据库恢复**：任务表里哪些是可以从外面重建的（PR、CI、进程），哪些**必须持久保留**（重试次数、路由决策、人工闸门、审计记录——都放库里，追加式的事件表，进现有的每晚备份）；从备份恢复任务表后监督进程能继续。
5. **发布交替**：先停旧、再起新，不允许新旧两个版本同时写同一批单；租约用库的时钟，不用各进程自己的；长时间 GitHub 故障之后积压能恢复，不一拥而上。
6. **压测**：10 张单 × 3 个仓同时跑，会话、CI、Review 全程不重复、不卡死。
过不了任何一条 → 不采用 C，回到 B（先做同样三段小样比较行数和可读性）或 A，并写明为什么。

## 8. 别家模型（GPT）一轮挑错和我的处理

结论「有异议 4 条」。①「真相来自外面，不代表历史没价值；该比的是谁负责恢复『动作做了一半』的状态」→ 收：第 4 节加一行、第 6 节整张清单；②「外面观察不总能判定结果，限流、超时会把『没查到』当『没发生』」→ 收：观察三态 + 验收 2；③「先写打算再做再写结果仍有崩溃窗口，动作不支持幂等就不成立」→ 收：验收 1、3，第 6 节逐项证明；④「数据库故障、备份恢复、任务表损坏；发布交替、租约和时钟、GitHub 长时间故障后的积压」→ 收：验收 4、5、6。它的建议「暂不拍『永久不用 Temporal』，先把 C 的前提列成验收标准，全过再选 C」我全采纳，所以第 1 节一句话改成了现在这样。

## 【推演】（从创始人的角度，把一张单的一生走一遍，边界和最坏情况）

**平时**：他在驾驶舱看到一张单从「准备好」到「工人在干（第 N 分钟）」到「等 CI」到「Review」到「合了」，每一步的状态就是任务表里的那一行，加上现读的 GitHub 和会话状态；他不用管调度器。
**中途重启**（发布新版本）：监督进程停 10 分钟内让在跑的会话干完手上的、不起新的（现有的「排空」），重启后每张单重新观察一遍：会话还活着就接着盯，已经结束就收结果，PR 已经开了就别再开。
**最坏情况**：①监督进程在「开 PR」那一步崩了 → 重启后先按分支名查 PR，有就接着走，没有才开；②GitHub 限流或断了 → 这一轮「没查成」，不当成「没有」，下一轮再看，超过时限报警；③会话被杀（内存上限）→ 观察到进程没了，按失败原因换路由重试，有上限；④两个监督进程同时起来（手滑）→ 行级租约让后到的拿不到单，只报一条日志。
**边界**：只管工人和 Review 这两段；指挥官段（和他对话）不归引擎；四类人闸在「合并」或「对外发布」那一步停下，行里记「等人」，人回了就往下走。
**对照**：Kubernetes 控制器（重新观察、期望状态驱动）；Anthropic 的长时间编码会话（git 和进度文件当状态、每个会话先找回自己在哪）；工作流引擎（Temporal、DBOS、Restate）——要历史重放，换来「等待很长也不占资源」，我们的等待最长是 CI 的几十分钟，轮询一下就行。
