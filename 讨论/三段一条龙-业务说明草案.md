# 三段一条龙：业务说明草案（D0③，2026-09-30 凌晨；草案，不改代码）

对应：`docs/goals.md` §四 A、§七第 1、2 条；母单 #509「先做的分析」第 3 条。写法照 `best-practice-first`：先说业务，再隔离现有实现，再对照业界，再从零推方案，最后摆代价表。**「定」= 创始人拍过的；「提议」= 我的判断，数字要用演练台的实测校准；「待拍」= 要你选。**

## 一句话

一张单从需求到合并只走三段：**指挥官**把需求写清（一份需求文档，含「怎么算做完」）→ **工人**一个会话干到开出 PR 且 CI 绿 → **Review**（GPT，全新会话）审一次，过了就合；三段之外有一个**副手**（每张单一份档案，谁问它，就把档案连同问题交给 GPT 一问一答）。引擎只管四件事：有空位就放单、盯死活、失败换模型重试、把每段的产物交给下一段。**任何时刻的「这张单走到哪了」都从 GitHub 和会话进程现读，不再存一份「流程状态」去跟外面对**（今天的断点都出在那份副本和外面对不上，见 `Temporal留不留-对照.md`）。

## 一、每个角色：谁、什么场合、干成什么、干成的标志

| 角色 | 谁 | 什么场合 | 干成什么 | 干成的标志 |
|---|---|---|---|---|
| 创始人 | 一个人 | 电脑前对话定需求；手机上扫一眼；远程约十天无人值守 | 只在「要我拍的」出手 | 首页「要我拍的」空着，就可以放心走开 |
| 指挥官 | 创始人正在对话的那个 AI 会话（技能 `commander`）（定） | 创始人提需求、讨论、改主意 | 一份工人拿到就能干、Review 拿到就能验的**需求文档** | 「怎么算做完」每一条都能用命令、测试或一个看得见的现象验证；工人开工后指挥官不用再插话 |
| 工人 | 引擎起的一个 AI 会话，路由从几家订阅里选（Claude、Cursor、Grok、Mirasim），跑在隔离用户里、没有 GitHub 凭据（定） | 有一张「准备好」的单、还有空位 | 在自己的工作树里做成一组本地提交、跑改动影响到的测试，用 `fleet done` 交出；PR 开出后 CI 红了它接着修 | PR 开出、CI 全绿；「做了什么 / 怎么验证的 / 还欠什么」写清 |
| Review | GPT 的一个**全新**会话，只读；改到界面代码的换非 GPT 的模型（定） | PR 头上 CI 全绿 | 对着「怎么算做完」逐条判：做到 / 没做到 / 看不出，**每一条都要有证据**；三种结论：**通过**、**打回给工人**（没做到验收条、有证据弄坏原有功能、安全或丢数据，或某条验收「看不出」——先要工人补证据）、**退回指挥官**（需求有歧义、或验收标准本身是错的：暂停这张单，不让工人猜）。其余问题只写进 PR 当建议（旧规矩，留；**「看不出」不再放行**，见规则 18） | 在**被审的那个提交**上写一个 `second-opinion` 状态：通过 / 打回；打回带着「照着能改」的意见 |
| 副手 | 没有常驻进程；每次被问才起一次 GPT 调用（走 Cursor 命令行，Mirasim 云端作后备）（提议） | 指挥官、工人、Review 有疑问：「这个决定为什么这么定」「现在做到哪了」「别处有没有做过」 | 答得出，并且能指出依据在档案的哪一条 | 两次提问之间不占服务器进程；档案在机器没了也在 |
| 引擎 | 法国上一个常驻服务（不是角色，是跑腿的） | 一直在 | 放单、盯死活、失败换模型重试、接力（推分支开 PR、等 CI、起 Review、挂自动合并、关单） | 任何时刻重启都能接着走：下一步只由「这张单 + 现在观察到的事实」决定 |

## 二、一张单的一生

```
准备好 ─放单→ 干活中 ─交活→ 等 CI ─全绿→ Review ─通过→ 合并 → 完成
  ▲            │ 会话死了/停滞/额度用尽    │ 红        │ 打回（最多 2 轮）
  └─换路由重试──┘                     回工人修 ◀───────┘
任何一步碰到：人闸四类 / 问了创始人还没答且不能先按推荐走 / 重试用完 → 「等人」（驾驶舱「要我拍的」）
```

| 状态 | 谁在做 | 事实从哪读（不存副本） | 往下走的条件 | 出岔子怎么办 |
|---|---|---|---|---|
| 准备好 | 指挥官已写好 | GitHub 单 + 里程碑 + 标签 + 仓里的需求文档 | 接活开关开着、挂当前版本、不是母单、没有「本机做」、需求文档有「怎么算做完」、有空位且路由额度够 | 需求文档缺「怎么算做完」：明确报错、不放单（旧规矩） |
| 干活中 | 工人 | 会话进程在不在、`fleet plan/say` 的汇报、库里这一轮的运行记录 | 工人 `fleet done` | 会话死了、被杀、停滞、额度用尽：按失败原因分流（旧规则表，留），先撤回得了的梯子（重试→换路由→换模型），用完挂起 |
| 等 CI | 引擎（推分支、开**草稿** PR）；会话已结束，空位放回去 | GitHub 上的 PR 和检查 | 必过检查全绿 | 红：续同一个会话（续不了就带档案起新会话）修，最多 N 轮；「没查成」≠「红」：读不到就退避重查，不当成没红也不当成红 |
| Review | GPT 全新会话，只读 | PR 头上的提交号（审的必须是这个头） | 通过（状态写在被审的那个提交上） | 打回给工人：意见回去，最多 2 轮；连续两轮提同一条必须改：不开第三轮、挂起交人（旧规矩，留）。**退回指挥官：** 需求有歧义或验收标准自己错了 → 这张单进「待澄清」，进「要我拍的」（带推荐的澄清写法），别的单照常走 |
| 合并 | 引擎：先核「PR 头 = 被审的提交」，再把草稿转成就绪、挂自动合并（带 `--match-head-commit <被审的提交>`）；GitHub 合 | PR 是否已合 | 已合 | **头在审完之后变了（含并主线）：通过状态自动失效**，重审；只有「并进主线后相对主线的 patch-id 和上一轮通过时一样」才沿用（旧规矩，留），算不出来不许当成一样。和主线冲突：自动并主线；真冲突派工人解；PR 的头被别人改写：立刻停下等人（旧规矩，留） |
| 待澄清 / 等人 | 创始人（或指挥官） | 驾驶舱「要我拍的」 | 他回了 | 见第六节第 6 点 |
| 完成 / 挂起 | — | PR 已合、单已关 / 重试用完 | — | 挂起报警，进「要我拍的」 |

**为什么用草稿 PR：** 合并闸本来就把草稿判成「不能合」（`docs/design.md` 第五节「合并闸」），所以「Review 通过之前不合」用现成的机制就有了，不用新造一道关；Review 通过后引擎把草稿转成就绪并挂 `gh pr merge --auto --squash`。**已核（读代码，2026-09-30）：** `.github/workflows/ci.yml` 对 PR 的 `opened/synchronize/reopened/edited` 都跑、没有草稿条件，所以草稿 PR 上 CI 照跑；`merge-gate.yml` 在 `ready_for_review` 和 `converted_to_draft` 事件上重算，草稿一转就绪合并闸立刻更新。

**旧实现里找不到业务出处的东西（单独列出，不默默留、不默默删）：**
- 「存档点、换 Lead、Lead 验收副手打回满 2 次自己接手」：出处是 Fusion 的分工（Lead 写方案、副手写码）；三段一条龙没有 Lead 和副手写码这一层 → 随 Fusion 删。
- 「多套流程配置 + 全组织默认 + 各仓 `.fleet/flow.json` + 库里 45 分钟新鲜度的副本」：业务理由是「各仓测试命令不同、禁令项目改不掉」（0003 第 9 条）。新设计里测试命令写进**需求文档**，禁令写进仓里的规矩；**「一份配置」要不要还留，待你定**（第七节问题 8，我的提议：不留）。
- 「单模型模式」：Fusion 的降级形态 → 随 Fusion 删。
- 「每个仓一次合一个的合并队列」：出处是防止并行 PR 合起来把主线弄红（`engine-2` 规则 21），**业务理由成立**，实现形态待定（第七节问题 6）。

## 四、隔离：现有实现里「怎么做」的部分，不作为起点

Fusion 0–7 步的划分；「Lead / 副手」这套叫法和分工；存档点；`verify_rounds`（验证轮）；流程配置副本和它的新鲜度判断；帅位座位、认领和「待起认领」握手；母单工作流（`requirement.ts`）与子任务工作流（`subtask.ts`）的形态；工作流重放安全的代码写法；合并队列做成一个工作流；`fleet done` 要求「会话里真跑了交代的那条测试」；进度栏。它们后面能被重新选中，但只有一个理由：从业务推出来恰好一样。

## 五、业界对照（都点得开；「取」= 我这次读原文的日期，2026-09-30）

| 层 | 同类做法 | 我们的约束 | 结论 / 冲突 |
|---|---|---|---|
| **整体形状**：委派 → 独立环境干活 → PR → 人审 | GitHub Copilot cloud agent：「研究仓库、做实现计划、在分支上改；你审 diff、迭代，准备好再开 PR」，跑在 GitHub Actions 的临时环境里，每一步落在提交和日志里，取自 <https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent>（取 2026-09-30）；OpenAI Codex Cloud：每个任务自己的工作区、电脑睡着也能继续，「检查改动和结果、要求跟进修改、准备好再提交或开 PR」，<https://learn.chatgpt.com/docs/cloud>（取 2026-09-30）；Anthropic：智能体能仅凭 PR 描述解决 SWE-bench Verified 里的真实 GitHub 单，但「人审对确保方案符合整体系统要求仍然关键」，<https://www.anthropic.com/engineering/building-effective-agents>（2024-12-19；取 2026-09-30） | 一个人、约十天不在、几家订阅混用、跑在自己的机器上 | 形状一致（单 → 独立工作区 → PR）。**冲突：它们最后一步都是「人点合并」。** 我们的方案用「CI 全绿 + GPT Review + 四类人闸」代替「人点合并」，风险靠 Review、CI、先审后合路径、审计记录、「出问题回退不用再问」兜 |
| **权限边界** | Copilot：代理只能做「简单推送」、**不能自己 `git push` 等 Git 命令**；草稿 PR 必须由人审、由人合，它不能标「可以审」、不能批准或合并；默认 Actions 不跑，要有写权限的人点「批准并运行」；提交署名 Copilot、带会话日志链接，取自 <https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations>（取 2026-09-30）；Codex Cloud 的环境把「密钥、对外身份、网络」显式配置（同上 Codex 页） | 会话里没有 GitHub 凭据，提交打成包由引擎在会话外推（定，design 第十四节） | 一致。工人不碰凭据、不自己推，业界主流做法就是这样；**我们比 Copilot 多做的：** 提交署名和「引擎开的 PR」的审计（工人机器人和运行记录对上） |
| **单代理还是拆给多个** | Cognition「Don't Build Multi-Agents」（2025-06-12；取 2026-09-30）：子代理各自误解、各做各的决定，「动作带着隐含的决定，冲突的决定带来坏结果」，原则是共享完整上下文，<https://cognition.com/blog/dont-build-multi-agents>；Anthropic 多代理研究系统（2025-06；取 2026-09-30）：多代理约耗 15 倍 token，「多数编码任务能真正并行的部分比研究少」，<https://www.anthropic.com/engineering/multi-agent-research-system>；另一面：同一家的《Building effective agents》说 orchestrator-workers 适合「子任务没法预先定」的多文件编码改动；Anthropic 的 C 编译器实验（2026-02-05；取 2026-09-30）：多个并行代理**没有协调代理**，用 `current_tasks/` 里的锁文件抢任务、靠 git 同步，「合并冲突常有，但 Claude 能自己解」，<https://www.anthropic.com/engineering/building-c-compiler> | 每张单一个工人；单与单之间并行 | **拆分只发生在「单与单之间」，一张单内部不拆**——这样单内没有「互相不知道对方决定」的问题；单与单的冲突靠合并时并主线解。这对应 §七第 1 条，我的提议：工人自己定方案接着干 |
| **交接物**：需求怎么交给会话 | Anthropic《长时间运行的智能体》（2025-11-26；取 2026-09-30）：两种典型失败——一口气做太多、太早宣布做完；对策是特性清单 + 进度文件 + 每个会话结束留下「能合并的干净状态」，<https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents>；Claude Code 官方最佳实践：「给它一个能自己跑的检查：没有检查，『看起来完成了』就是唯一信号」，<https://code.claude.com/docs/en/best-practices>（取 2026-09-30） | 会话里不跑全量检查（省内存），全量交给 CI | 需求文档里的「怎么算做完」= 特性清单；`fleet plan/say` = 进度文件。**冲突：**「给它能跑的检查」 vs「会话不跑重检查」→ 折中：会话跑**改动影响到的测试 + 类型检查**（约 3.5G 峰值、最多同时 2–3 个），全量归 CI；这个折中要在演练台量 |
| **Review** | Claude Code 官方：「全新的上下文让审查更好，因为它不会偏袒自己刚写的代码」，Writer / Reviewer 两个会话（同上最佳实践页）；NeurIPS 2024《LLM Evaluators Recognize and Favor Their Own Generations》：评审模型能认出自己的输出并偏爱它，<https://proceedings.neurips.cc/paper_files/paper/2024/hash/7f1f0218e45f5414c79c0679633e47bc-Abstract-Conference.html>（取 2026-09-30）；Cursor Bugbot：审查结果就是 PR 上的检查状态，未解决的问题让检查失败，<https://cursor.com/docs/bugbot>（取 2026-09-30）；它的 autofix 模式「可以往被审的分支推修复提交」这一条取自第三方文章 <https://www.augmentcode.com/guides/cursor-bugbot-code-review-capabilities-limits>（2026-09-16，未在 Cursor 文档里核到原句） | Review 用 GPT，写码常是 Claude/Grok/Cursor（跨家族）；结果写 `second-opinion` 提交状态，合并闸已经认它（定） | 跨家族 + 全新会话 + 状态检查，三条业界都印证。**不学 Bugbot 的 autofix：** 审的直接改，等于审的替写的背书；我们让审的只读，打回给工人（审改分离） |
| **副手 / 追问** | GitHub Copilot：从 Chat 起的会话带着聊天上下文，可继续追问进度（同上 about 页）；Anthropic《有效的上下文工程》（2025-09-29；取 2026-09-30）：结构化笔记（NOTES.md）是「几乎不占开销的持久记忆」，<https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents>；C 编译器实验里代理卡住时自己维护「失败做法和剩余任务」文档 | 两次提问之间不占服务器进程；机器没了档案也在 | 档案 = 库里的完整记录 + 单子上的摘要（摘要沿用现有的「进度段」：`packages/github/src/progress.ts`，写在单子**正文**里两个标记之间原地更新，带 `as-of` 保护、旧快照盖不掉新的）；一问一答。**冲突：** GitHub 正文 / 评论上限 65,536 字符（社区讨论 <https://github.com/orgs/community/discussions/27190>，2020-12）→ 单子上只放摘要、库存全文 |
| **失败换模型** | LiteLLM 路由器：冷却、回退、超时、重试（固定 + 指数退避），<https://docs.litellm.ai/docs/routing>（取 2026-09-30）；OpenRouter：`order` 顺序和 `allow_fallbacks`，<https://openrouter.ai/docs/features/provider-routing>（取 2026-09-30） | 我们已有按失败原因分流的规则表、熔断、停滞判断、选路（旧，留） | 业界的是「按顺序回退」，我们的更细；**不重做，留** |
| **合并串行** | GitHub 合并队列：只在**组织**名下的公开仓、或企业云私有仓可用，<https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue>（取 2026-09-30）；本仓的规则集 `strict_required_status_checks_policy` 是 `false`（不要求「和主线最新」才能合，取 `gh api repos/<账号>/fleet-dao/rulesets/23955578`，2026-09-30） | 本仓是个人账号名下，用不了 GitHub 的合并队列；并行 10 个会话，语义冲突会把主线弄红 | 只能自己做「一个仓一次合一个」；做法是待拍问题 6 |

## 六、从零方案

### 1. 操作剧本（真实的人，从起念到干成）

**场景 A：创始人在电脑前，提一个新需求。**
1. 他对指挥官说要什么（对话，不算搬运）；指挥官问清、写下「要什么、怎么算做完」，用 `pnpm issue:new` 开单（要跨会话才开单；一个 PR 当轮做完的直接干，通用段）。**动手：对话 1 次；搬运 0；离开 0。**
2. 单挂上当前版本、需求文档进仓 → 引擎自动放单。**动手 0。**
3. 之后他只在两种情况下出手：驾驶舱「要我拍的」里有卡（人闸、问题），或最后看到「合并了」的通知。**动手：0–2 次点选；搬运 0；离开 0。**

**场景 B：创始人外出十天。** 每天早上打开驾驶舱首页：一屏三块，「要我拍的」（编号、带推荐）、「在跑的」（每张单到了哪一段、谁在做）、「做完的」（带 PR 号）。语音回「按推荐」就够。**在这个场景里，「不用他」是常态，人闸和问题才是例外。**

**场景 C：夜里无人。** 工人失败按梯子往下走；走到头的挂起，早上进「要我拍的」，卡里写「试过什么、卡在哪、我推荐什么」。**不会因为一张单卡住而停掉别的单。**

目标（提议，用演练台校准）：搬运 = 0、离开 = 0；一张单**交接不超过 2 次**（需求文档交给工人；PR 交给 Review）；做完的单平均会话数从 7.7 降到 ≤ 3（数据来自 `docs/goals.md` §四 A）；近 7 天写码会话成功率从约一半提到 ≥ 80%。

### 2. 三段各自的输入、输出、超时、失败

- **指挥官 → 需求文档。** 输入：创始人的话、仓里现有代码和规矩。输出：`specs/<号>-<短名>/需求.md`，必含：目标、不做什么、约束（要守哪些规矩）、**怎么算做完（逐条可验证）**、怎么验证（命令）、会不会碰人闸（碰安全 / 迁移里有删改 / 改标准）。缺「怎么算做完」明确报错（规则 10）。这份文档是**唯一**的交接物。
- **工人 → 本地提交。** 输入：需求文档 + 仓 + 档案（若是续跑）。输出：本地提交 + `fleet done`（总结、跑过的测试）。会话内可用：`fleet plan`（勾选框进度，整张替换）、`fleet say`（一句话，≤500 字）、`fleet ask`（带选项和推荐，不等回答）、`fleet blocked --needs`、`fleet history`。**没有 GitHub 凭据，不推分支、不开 PR。** 超时：沿用现有停滞判断。
- **引擎 → 草稿 PR。** 收到 `fleet done`：交付对账（改的文件和需求对得上）→ 卫生扫描 → 推分支 → 开**草稿** PR，正文按模板写；空位放回。
- **CI。** 必过检查全绿才往下；红了把失败原文交给工人**续跑**（同一会话，续不了带档案起新会话），最多 N 轮（提议 N = 2，和 Review 打回同一个上限）。
- **Review → `second-opinion` 状态。** 输入：需求文档 + PR 的头和 diff + CI 结果（**默认不给工人的思路**，免得偏袒；要问，走副手）。输出：逐条「做到 / 没做到 / 看不出」+ 证据。三种结论：通过 / 打回给工人（三类硬伤，或某条「看不出」→ 补证据）/ 退回指挥官（需求有歧义、验收标准自己错）。打回最多 2 轮。状态写在被审的那个提交上。
- **合并。** 通过 → 引擎先核「PR 头 = 被审的提交」，再把草稿转就绪、挂自动合并（带 `--match-head-commit`）；GitHub 合。审完头变了：通过状态自动失效、重审（规则 17）。合并后不再补审（0002 第 4 条）。

### 3. 副手（提议，等你定 §七第 2 条）

- **档案 = 一份追加式记录，每张单一份**，内容：指挥官的想法（需求文档 + 讨论里没写进文档的「为什么、别做什么」，由指挥官交单时写一段「交代」）、工人的思路（`fleet plan / say / ask` 自动追加）、每一次问答、每一次 Review 意见。
- **存在哪：** 完整记录在库里（引擎写、追加式、进每晚备份）；给人看的摘要放在**单子上**（沿用现有的「进度段」：写在单子正文里两个标记之间、原地更新；也可以另用一条带隐藏标记的评论，二选一，我倾向沿用现成的进度段）——手机上看得见、机器没了还在；**不放分支里的文件**（会进 PR、进主线，污染）。
- **怎么问：** `fleet ask-buddy <问题>`（新子命令）→ 引擎把档案 + 问题交给 GPT（Cursor 命令行 12–20 秒一轮；Mirasim 云端作后备；**不接按量计费的直连接口**，#118 那算花钱）→ 答案回给提问的人，同时追加进档案。
- **两次提问之间：** 没有进程。

### 4. 状态放哪

| 东西 | 放哪 | 为什么 |
|---|---|---|
| 单、PR、检查、合并、评论、标签、里程碑 | GitHub（现读） | 真相在那，不存副本 |
| 会话活着没有、跑到哪 | 会话进程（现读）+ `fleet` 汇报 | 同上 |
| 这一轮的运行记录：用的哪条路由、试了几次、花了多少、出了什么错 | 库（追加式） | 外面读不到，且要备份 |
| 人闸批准、人发的命令、审计 | 库（追加式，进每晚备份） | 同上，且是「谁在什么时候批了什么」的凭据 |
| 档案 | 库全文 + 单子评论摘要 | 见上 |
| 「工作流历史」 | **不作为真相来源**（留不留 Temporal 见 `Temporal留不留-对照.md`） | 今天的断点都出在它和外面对不上 |

### 5. 失败怎么办（沿用现有失败规则表，梯子不变）

| 失败 | 先做什么 | 用完了 |
|---|---|---|
| 会话死了 / 被杀 / 起不来 | 同一路由重试 1 次 | 换路由 → 换模型 → 挂起报警 |
| 停滞（很久没动静） | 叫停、按「没动静」记原因，换路由 | 同上 |
| 额度用尽 | 换有额度的路由，不算重试 | 全都没额度：挂起，写明「等额度」 |
| CI 红 | 续跑修，最多 N 轮 | 挂起报警，卡里附失败原文 |
| Review 打回 | 意见回工人，最多 2 轮 | 连续两轮同一条必须改：挂起交人 |
| 读不到 GitHub | 退避重查，不动手 | 超时限：报警（不静默卡住） |
| 推分支被卫生扫描拦 | 退回会话、带着拦在哪 | 同一处连续两次：挂起交人 |

### 6. 四类人闸落在哪一步

| 人闸 | 谁触发、怎么发现 | 落在哪一步 | 前面的步骤 |
|---|---|---|---|
| 对外发布 | 上线是按版本由创始人确认的动作，**不在这条流程里**；引擎永远不发布 | 不适用 | — |
| 花钱 | 工人 / Review 要用按量计费的东西、买东西 | 工人 `fleet blocked --needs human` 或 Review 判「安全或花钱」 | 已付套餐以内的订阅额度不算花钱，照常干 |
| 删数据 | PR 改到 `packages/db/migrations/` 且有删改语句（先审后合） | 挡在「合并」：Review 通过后进「等人」 | 前面照常干 |
| 改标准 | PR 改到 `standard-paths.json` 列的路径 | 同上，等驾驶舱写在 PR 头上的「创始人已同意」状态 | 同上 |

### 7. 「删掉整层」的选项（必须摆出来）

| 删掉哪一层 | 得到什么 | 失去什么 | 我的看法 |
|---|---|---|---|
| 删 Review（CI 绿就合） | 每张单少一个会话，更快 | AI 写的 PR 无人审；你 09-29 明确要 GPT 审 | **不删**；但 Review 的范围可缩（问题 3） |
| 删副手 | 少一个机制 | 工人换会话时丢上下文；Review 不能追问；卡住时没人答 | **不删**：业界的 NOTES.md / 进度文件就是它 |
| 删指挥官和工人的分离（一个会话包办） | 没有交接 | 无法并行、创始人得一直在场 | 这就是今天的本机模式，**不符合「十天不在」** |
| 删自研引擎，直接用 Copilot cloud agent / Codex Cloud | 不用自己养调度、隔离、回收 | 要买 Copilot 付费计划或 ChatGPT 计划（**花钱**）；不能几家订阅自由组合、GPT 只能审不能写；不能控制会话在哪跑、用哪台机器；四类人闸和「引擎不直写主线」只能靠它们自己的开关 | **不删**，但要**借它们的做法**：环境显式配置密钥/网络、审计署名、Actions 需批准 |
| 删 Temporal | 见 `Temporal留不留-对照.md` | 同上 | 待验收标准过了再定 |

## 七、代价表、推荐、要你拍的

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A（推荐）三段一条龙** | 工人自己定方案；Review 每个引擎 PR 一次；副手 = 档案 + GPT 一问一答；引擎四件事 | 重写引擎流程层（删 Fusion 51 个整文件，约 750 KB，见 `01-文件级删除清单.md`）；新做档案和 `ask-buddy` | 新流程没有线上数据，靠演练台校准阈值 |
| B 现状精简 | 保留 Lead / 副手分工，只砍认领、座位这些 | 改动小 | 仍是 0–7 步，每张单平均 7.7 个会话的根子没动 |
| C 业界更重 | 指挥官写详细方案，多个工人拆块并行 | 要设计块之间的接口、合并顺序 | Cognition 讲的「互相不知道对方决定」；多代理 15 倍 token；正是 Fusion 今天的问题 |
| D 不造引擎 | 用现成云代理 | 花钱；失去自由组合 | 见上表 |

**要你拍的（每条推荐的放前面）：**

1. **§七第 1 条：工人自己定方案接着干**（推荐），还是指挥官先写详细方案再由工人照做。理由：单内不拆，就没有「互相不知道对方决定」；Cognition（2025-06-12）、Anthropic（2025-06）都指向这一点；要并行，并在「单与单之间」。
2. **§七第 2 条：副手怎么做。** 推荐：档案完整放库、摘要放单子上（沿用现有的正文进度段）；GPT 走 Cursor 命令行，Mirasim 云端后备，**不接按量计费的直连接口**。
3. **Review 范围和标准：** 推荐每个**引擎开的** PR 都过一次 Review（你 09-29 的原话）；创始人自己本机开的 PR 照旧「CI 绿就合，先审后合两种才审」。另一个选项：Review 只审先审后合和改标准的 PR（省一个会话，但等于没有 Review）。**标准也定一下（GPT 反方提的，和你的底线「没验证过不说完成」一致）：** 推荐「看不出」不放行——每条验收都要有证据，缺证据先打回工人补一次，补不出退回指挥官改成能验证的、或明说豁免；旧规矩只有三种能挡（没做到、弄坏原有功能、安全或丢数据）、「看不出」只当建议。代价：偶尔多一轮；好处：没有「验收项没验证就进了主线」。
3b. **Review 的第三种结论：退回指挥官**（需求有歧义、验收标准自己错）：推荐加。这张单进「待澄清」、别的单照常走；你不在时，卡里带推荐的澄清写法，你回「按推荐」就往下。
4. **子单怎么并行：** 推荐默认并行、指挥官只在「会撞同一批文件」时声明先后；冲突靠合并时并主线，真冲突派工人解（Anthropic C 编译器实验同款）。另一个选项：一个母单下的子单一律串行（更稳、更慢）。
5. **CI 红了谁修：** 推荐续同一个会话（续不了带档案起新会话）；最多 2 轮。另一个选项：一律起新会话（简单，但每次要重新读代码）。
6. **合并串行：** GitHub 的合并队列本仓用不了（个人账号）。推荐：先不做队列，演练台观察「语义冲突把主线弄红」的实际频率再定；要做就做成引擎每一轮的一个小步骤（并主线 → 等 CI → 合），不做成单独的工作流。另一个选项：照旧保留现在的合并队列。
7. **「超出范围另开一张未排期单等他拍」这条业务规则还留不留**（现在由每小时扫描的 `ask-issues.ts` 实现，随提醒派单删）：推荐留，实现搬进 `fleet ask` 的后端（工人问「超范围」时当场开，不再靠扫描）。
8. **「一份简单流程配置」还要不要：** 推荐不要——测试命令写进需求文档，禁令写进仓里的规矩。
9. **「本机做」标签保留：** 推荐保留，它是「不给引擎」的开关（引擎自己的认领记录没了以后，它是唯一的分流）。

## 八、怎么算做完（提议）

1. 一张单从开单到合并，**交接不超过 2 次**；演练台跑通一张完整的单（#452）；巡检单全绿。
2. 做完的单平均会话数 ≤ 3；写码会话成功率 ≥ 80%（阈值来自 `docs/goals.md` §四 A 现状的对照，数字要用演练台校准）。
3. 10 张单 × 3 个仓并行：内存、CPU 不越线；会话、CI、Review 全程不重复、不卡死。
4. 第三节的规则 1–19 每条有落点、有用例；每个「读不到、认不出」的路径有一条故意造出失败的用例。
5. 每一条外部动作可去重、可确认（`Temporal留不留-对照.md` 第 6 节）。

## 九、【推演】和请你挑的地方

**推演一张单：** 创始人在对话里说「给登录页加个记住我」。指挥官问了两句，写好需求文档（目标、不做什么、怎么算做完：勾上「记住我」后 30 天内不用重新登录，测试命令 `pnpm exec vitest run packages/web/`，不碰人闸），开单挂当前版本。引擎见到「准备好」，选路选出一条有额度的 Claude 路由，起工人：会话里读代码、自己定方案、改文件、跑改动影响到的测试，`fleet plan` 报进度，`fleet done`。引擎对账交付、卫生扫描、推分支、开草稿 PR，会话结束；CI 红了一项（类型检查）：引擎把失败原文交给同一个会话续跑，修好再推，全绿。引擎起 GPT 全新会话审：对着三条验收逐条判，第三条「看不出」（没有测试覆盖过期）→ 打回给工人补证据（第 1 轮）；工人补了一条过期用例，引擎推上去、CI 全绿，Review 在新头上再审：三条都有证据，`second-opinion` 状态写在这个新头上：通过。引擎核头没变，把草稿转就绪、挂自动合并（`--match-head-commit`），GitHub 合并，引擎关单。创始人看到一条「合并了」。**最坏情况：** 工人第一轮被 OOM 杀了 → 观察到进程没了、原因「内存」→ 换路由再来；两轮都失败 → 挂起，卡里写「试了 Claude 和 Grok 两条路由，都是内存不够，建议把这张单拆小或等新机器」，进「要我拍的」。

**请你挑（别家模型）：**
1. 「拆分只发生在单与单之间、单内不拆」这条，有没有漏掉需要单内并行的真实场景？业界证据（Cognition、Anthropic）够不够？

## 十、别家模型（GPT）反方第 1 轮：意见和处理（2026-09-30）

结论「有异议 3 条」，都收了：

| 意见 | 处理 |
|---|---|
| 框架：把「PR 头上第二意见通过」当成可合并的充分条件，没说状态怎么绑定具体提交、合并前内容变了怎么办 | 新增规则 17：状态写在被审的提交上、合并闸读当前头、头变了自动失效、挂自动合并前先核头没变并带 `--match-head-commit`（本机 `gh` 帮助里有这个选项；是否传给自动合并的 `expectedHeadOid`，演练台实测）；并主线后只有 patch-id 一样才沿用（旧规矩） |

GPT 认为下面三项**属于演练台验证项，暂不据此改选项**：各家「续跑」支持不一致时怎么办（Claude / Cursor / Grok / Mirasim）、单内并行的证据够不够、合并串行的语义冲突实际频率。我把它们记进「演练台要量的东西」：①四家的续跑是否都支持、不支持的降级成「带档案起新会话」的额外成本；②语义冲突把主线弄红的实际次数；③一张单需要的会话数（对照 7.7）。
