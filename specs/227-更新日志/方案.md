## 这一版做什么

仓库根 `CHANGELOG.md` 是唯一来源（Keep a Changelog 1.1.0）。发版时 `deploy/release.sh` 多走一步「记一版」：

1. 从 `## [Unreleased]` 抽出这一版干了什么；
2. 打 git tag（`v<N>`）并推到 GitHub；
3. 建 GitHub 发布记录（正文照抄那一段）；
4. 关掉对应 GitHub 里程碑；
5. 飞书群推一条「vN 上线了」（消息正文也照抄那一段）。

幂等：同一个提交再跑一遍什么都不改——tag 已存在就当打过、发布记录已建、里程碑已关、飞书已发，都不重复。

驾驶舱留入口：`/changelog` 路由 + 导航，点开是骨架页「更新日志还没做好」，不存数据，等单独做它自己的那一份。

CI 加一道检查：改到 `deploy/` 或 `CHANGELOG.md` 的 PR，`CHANGELOG.md` 里 `## [Unreleased]` 下面必须有内容（不为空、不能只写「还没有」），不然不让合——Persistence 测的就是它：**改发版脚本忘改 Unreleased 会被发现**。

## 没做的（留给下一个 PR）

- 起草自动化（AI 起草那一份，人改）：需求.md 第 1 条；这一步走完前 Unreleased 靠人手改。
- 驾驶舱「更新日志」页真正的数据面（按项目、按版本倒序，需求.md 第 4 条）。
- 「发布」/「部署」文案分清（需求.md 第 5 条）已在 release.sh 注释里。
- 状态在驾驶舱看得见（「待发布、已打标记、发布记录已建、里程碑已关、已通知」），这个发布跟框架联动的部分（需求.md 第 3 条后半的「每步可重试、重跑不重复做；状态看得见」）这次只把「可重试、幂等」做完，状态那一列留给驾驶舱「展示」页顺带的去自己背。

## 接口契约

- `deploy/release.sh` 在切到目标版本、健康检查全过后调一次：`deploy/bin/finalize-release.sh <full sha>`；脚本返回 0 = 记一版走成，非 0 = 记一版没走成（健康检查之外的那一步出错）；发起人（release.sh）照原样继续余下发布流程，不因为记一版失败就把已经切过去的版本退回来。
- root 那一侧状态：`/srv/fleet-dao-releases/.finalize/<提交号>.json`，字段单调走 `pending → tagging → tagged → release-created → milestone-closed → notified`；哪一步断了，下次同一个提交再进，从断点继续走，已经做过的跳过。
- `packages/conventions/src/bin/changelog-release.ts` 是业务那一侧：读 CHANGELOG、按 Unreleased 拼一次正文、逐个调 GitHub/飞书。它由 root 一侧的 shell 拉起，跟日常 CI 不同的只在工作目录是按预先检出的那一版；它不写 RELEASES 目录。

## 拍板过不能动的

- `CHANGELOG.md` 格式不松：Unreleased 标题必须恰恰是 `## [Unreleased]`（不是 `## Unreleased`），版本标题是 `## [v<N>] - YYYY-MM-DD`；识别不到模样的行一律算错（Persistence 测的）。
- 同一提交幂等：在用的 tag/release/milestone/飞书哪一样已经做完，再进一次就跳过；重跑不重复发通知。
- tag 名只能 `v<N>`（一位或多位数字，不带 + 建造号）；里程碑名、GitHub Release 名、飞书消息头都照它来。
- 三回头的来源：GitHub Release 是只读的「存档本」，飞书消息提示不实际服务驾驶舱页；展示的来源一律回归到仓根 `CHANGELOG.md`。
