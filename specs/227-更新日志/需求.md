# 更新日志：仓里 CHANGELOG.md 为唯一来源，发布时自动打标记、建发布记录、关里程碑、推飞书，驾驶舱加更新日志页（#227）

对应计划：v1 Fusion 接活
设计依据：0003 第 2 条（版本收尾：发布说明、创始人拍发布、关里程碑）、第 18 条（发布按版本确认，合并≠上线）；`docs/design.md` 第五节「人闸第四类：改标准」（同意状态同一套）、15.3「要人拍」
原话：「我记得成熟的产品都有更新日志；我们能不能也有更新日志页+代码存更新日志+联动机制（我没想好是联动github?)，你帮我补齐思路」（创始人 2026-09-27 早）。帅位补齐思路、GPT 挑过一轮后，创始人选 1：仓里 CHANGELOG.md 为唯一来源，其余自动生成。
AI 理解：每个项目都有一份写给人看的更新日志，按版本记做了什么。它和代码一起存在仓里，GitHub 上的发布记录、驾驶舱页面、飞书消息都从它自动生成。版本收尾时自动起草，创始人点「发布」就全部联动好，不用人手抄。

## 创始人拍板（2026-09-27 早）

- 选 1：每个项目仓根的 `CHANGELOG.md` 是唯一来源；GitHub 发布记录（Release）、驾驶舱「更新日志」页、飞书消息都从它自动生成，不另存一份。

## 要什么

1. **起草**：版本收尾时（0003 第 2 条），脚本从 GitHub 拉这个里程碑里已合并的 PR（关掉没合的、挪到别的版本的不算），按类别标签分组（需求→新增，缺陷→修复，杂项→其他），用 PR「做了什么」栏的白话起草。AI 改成人话摘要，写明做了、没做、挪去哪，写进 `CHANGELOG.md`（照 Keep a Changelog 的分段，改成白话小标题），开「发布 vN」PR。
2. **确认**：「发布 vN」PR 属人闸「对外发布」。它进驾驶舱「要人拍」，创始人看这段、点「发布」就是合这个 PR；合并闸认驾驶舱写的同意状态，和 #133 改标准同一套。
3. **联动**：合并后按固定顺序做：打版本标记（tag）→ 建 GitHub 发布记录（正文照抄那一段）→ 关里程碑 → 飞书推一条。
   - 每步可重试、重跑不重复做；状态看得见（待发布、已打标记、发布记录已建、里程碑已关、已通知）。
   - 做到一半就显示「发布处理中」并报警；发布记录读回核对过，才关里程碑、发通知。
   - 发布记录只许机器人写；对账发现和 `CHANGELOG.md` 不一致就改回来，并记一笔。
4. **页面**：驾驶舱「更新日志」页，按项目、按版本倒序，分新增、修复、其他，每条链到单和 PR。
   - 顶部「即将发布」一栏读的时候现算：当前版本里已合并的，不存。
   - 有新版本时导航上亮一个小点，记每个人上次看过的版本。
   - 读不到 `CHANGELOG.md` 或 GitHub 时写「没读到」和原因，不显示成空。
5. **分清发布和部署**：界面和文案里写清「发布」是版本收尾、对外说明，「部署」是装到机器上。fleet-dao 自己的法国引擎跟主线自动部署；给用户用的产品，发布就是上线（0003 第 18 条）。

## 依据

- 调研（2026-09 现查）：Keep a Changelog（https://keepachangelog.com/ ，2.0.0 @ 2026-06-07）；GitHub 按标签自动生成发布说明（https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes ，文本是 PR 标题堆砌，只拿来当草稿）。release-please 按提交信息算语义化版本号，和「版本＝里程碑名」对不上；changesets 要每个 PR 多写一段，和「流程只为快」冲突；semantic-release 没有人工确认发布；git-cliff 只渲染文本。「一份来源、两个展示面」见 https://releaseglow.com/blog/github-releases-vs-public-changelog （2026-04-27）。页面参照 Linear、Vercel、GitHub Changelog。
- GPT 挑错（1 轮，2026-09-27）：同意 CHANGELOG.md 做唯一来源（能审、能回滚、随提交走；发布记录能被手改、删掉，不能当来源）。补上的几条：只收已合并的 PR；发布流程可重试、幂等、有状态；先堵「打了标记、没建成发布记录」的半截状态——里程碑不关，自动补并报警；发布和部署分开写。
