# 问创始人不挡路：方案（#259）

对应需求：`specs/259-问创始人不挡路/需求.md`；设计：design 第五节「讨论」的「状态」「没人拍板」，0003 第 5 条第 2 步。

一句话：单子里问创始人一律带选项和推荐，`fleet ask` 当场返回、不等回答；按问题落在哪分三种——这张单范围内的按推荐先走，超出范围的另开单、这张单绕开接着做，碰人闸四类的也先按推荐做、只挡合并那一步。他晚到的回答按「单子走到哪」生效。判法全在 core 的 `packages/core/src/ask.ts`，后端、引擎、卡片、驾驶舱都照它。

## 三种提问

| 范围 | 会话里怎么问 | 后端当场回 | 库里（`asks` 表） | 卡片（飞书一张、驾驶舱这张单上一条） |
|---|---|---|---|---|
| 这张单范围内（默认） | `fleet ask "<问题>" -o 甲 -o 乙 -r 甲` | `assumed`，答案就是推荐的；会话照推荐接着干，交活总结里写上 | `scope = task`、`recommended`，推荐的排在选项第一个 | 第一行「已按推荐先做：甲。改选别的，下个存档点交给 AI 改。」，推荐的是第一个（主）按钮 |
| 超出这张单范围 | 加 `--outside` | `outside`；会话绕开那一块接着做 | `scope = outside` | 「超出这张单的范围：这张单绕开它接着做，另开一张单等你拍（#N）。」 |
| 碰人闸四类 | 加 `--hold release\|spend\|delete\|standard` | `held`，答案是推荐的；同时给这张单的工作流加人闸（和驾驶舱加人闸同一个 `requireApproval` 信号），合并前等他批 | `scope = hold`、`hold` | 「碰了人闸（花钱）：先按推荐做（甲），合并前等你批。」 |

- **不合格的退回**：没带选项、不到 2 个或超过 4 个、没带推荐、推荐不在选项里、人闸认不出、`--outside` 和 `--hold` 一起给：后端回 400 `ask_incomplete`，写清怎么补（`fleet` 退出码 4），一条都不记。命令行本地先挡一遍（超过 4 个选项、老的 `--no-wait`）。
- **只有他本人才有的东西**（账号、权限、登录）不是提问：`fleet blocked "<缺什么>" --needs access`，这一块等他。
- **库里的约束**兜底：带了范围的一定有推荐、推荐一定在选项里；`scope = hold` 和 `hold` 同有同无、`hold` 只认四类；`applied_at` 只在回答了之后有；`follow_up_issue` 是正数。迁移只加列、加约束（`0014_ask_not_blocking.sql`），老的提问这几列都是空，照老样子算。

## 他晚到的回答（core 的 `lateAnswer`）

| 他选的 | 单子走到哪 | 算什么 | 卡片原地改成 |
|---|---|---|---|
| 就是推荐的 | 任何时候 | `confirmed`，只记一笔 | 你选了：甲（就是推荐的），已生效 |
| 别的 | 还在做、PR 没合 | `change`：下一个存档点交给 Lead 改；改完记 `applied_at` → `applied` | 你选了：乙，下个存档点生效 → 已生效 |
| 别的 | 已经合进去（`done`） | `follow-up`：开一张后续单，挂同一个版本、链接原单，单号记 `follow_up_issue` | 你选了：乙；这张单已经合进去了，会另开后续单 / 另开了后续单 #N |
| 别的 | 叫停、失败 | `recorded`：只记下，重开时照他选的做 | 你选了：乙；这张单没做成就停了，只记下 |

飞书里回复卡片、驾驶舱里点选项都走同一条回答的路（`answer-ask.ts`）；回复卡片时回的那句话照上表说清会怎样。按推荐先做了的、另开单的提问在单子合进去以后照样能答（卡片不收、驾驶舱的「回答」照样能点），叫停、失败的收起。

## 顺带改的几处（不改就和「不挡路」对不上）

1. **停滞判断**：会话里还没答的提问原来一律算「会话在等人」，真停滞会被当成等人放过；现在只有老式的（没带范围、会话真停着等的）才算（`runProgressFacts`）。
2. **飞书盘面「等你们」**：只算老式的提问；带了范围的不挡路，碰人闸的到合并那一步另有要人拍。
3. **GitHub 评论当回答**：带了范围的提问整张单做完前一直开着，随手一句评论（问进度、帅位用创始人账号写的「在做」）会被当成改选；现在带了范围的只有和某个选项一字不差的评论才算回答它，老式的照旧任何一句都算。
4. **后端不再长轮询等回答**：去掉 `AskWaiters`、`FLEET_ASK_WAIT_SECONDS`、命令行的长超时；`fleet ask` 和别的命令一样几秒内回。
5. **提示词**：规矩段写明怎么问（带选项和推荐、按推荐接着干、`--outside`、`--hold`、`--needs access`），写码段写明「要他挑的不算卡住」。

## 分两个 PR

1. **第 1 个（#274，已合）**：core 的判法和记数（`checkAsk`、`lateAnswer`、`tallyAsks`）、库的列和约束、`fleet ask` 不等回答、后端当场回并给碰人闸的加人闸、卡片和驾驶舱的说法、上面「顺带改的几处」、提示词、design 第五节和 0003 第 5 条的说法。合进去以后会话问了就接着干、碰人闸的合并前一定挡住；晚到的回答先只记下、卡片写明「下个存档点生效」。
2. **第 2 个（引擎，已做，怎么做的见下面「第 2 个 PR 定下的」）**：存档点（Fusion 每一步交界；旧的需求工作流在 #250 删掉之前不接，没来得及照改的由合并后开后续单兜住、不丢）读这张单「选了别的、还没照改」的回答交给 Lead（该改的回到执行、已经在 PR 上的算一轮修），改完记 `applied_at`；对账每轮给「合并后才改的」开后续单、给超出范围的开单（GitHub 开 issue 的端口、挂版本、链接原单、单号回写 `follow_up_issue`）；会话 `fleet blocked --needs human|info` 退回让它带推荐重问（有上限，到数再等人），`access` 和别的照旧等；PR 正文加「按推荐先做了」一栏，关单评论写按推荐先做几条、事后被改几条（`tallyAsks`）；引擎自己问的（分诊说不清）也带推荐。需求里「怎么算做完」的四条故意造出的失败，没带推荐被退回、碰人闸的挡住合并那一步在本 PR；合并后才到的回答开出后续单、超出范围的开了单原单接着做在第 2 个。
3. **法国演练**：第 2 个合进去、自动发布发到法国以后，跑一张会提问的单，创始人不回答：单子不停、按推荐做到 PR，卡片写「已按推荐先做」；之后点另一个选项，看下个存档点生效，或合并后开出后续单。

## 定下的（帅位派的活里我自己定的，理由附后）

1. **后端当场回，不等**：「不许卡住活」最直接的做法是命令本身不阻塞；原来的长轮询（最长 4 分钟）占着会话、也占着后端一个连接，他多半不在，等满了照样是按会话自己的判断走，不如一开始就按推荐走、写明假设。
2. **不合格的当场 400 退回，不收下再让引擎退**：会话就在命令行上，退回的原因（缺什么、怎么补）当场看得到、马上重问；收下再由引擎在下一步退，会话已经按没推荐的问题走了一段。
3. **人闸由后端当场加，不等第 2 个 PR**：碰人闸的回「合并前等批」就必须真挡得住；加人闸复用驾驶舱已有的 `requireApproval` 信号（旧的需求工作流和 Fusion 都认），引擎连不上就回 503、问题留着，`fleet` 重试时去重、再加一次，不回「已挡住」装作拦下了。
4. **选项 2–4 个、推荐的排第一**：飞书卡片一排放得下 4 个按钮，第一个是主按钮；推荐的排第一，他一眼看到 AI 按哪个做了。
5. **合进去以后卡片不收**：需求说合并后才到的回答要开后续单，卡片收了就没处点；叫停、失败的单没有东西可改，收起。
6. **旧的需求工作流也受益**：不挡路是在后端和命令行做的，不依赖 Fusion；旧工作流里会话的提问同样当场回、碰人闸的同样加人闸。存档点交给 Lead 只接 Fusion：旧的等 Fusion 在法国跑通就删（#250），期间没来得及照改的由合并后开后续单兜住。

## 第 2 个 PR 定下的（帅位派的活里我自己定的，理由附后）

1. **存档点在规划之后的每一步交界读**（方案评审、执行、验证、开 PR、最终审查、合并之前；`fusion.ts` 的 `checkpoint`）：读这张单的提问，经 core 的 `lateChanges` 挑出「选了别的、还没照改、还没交过」的。还没开 PR 的回第 4 步（core `nextFlow` 的 `changed` 事件）：正派着的活先收下，再由 Lead 写修改简报、副手照改（单模型模式 Lead 自己改）；PR 已经开了的算开 PR 之后的一轮修，和 CI 红了的修同一套、占那 3 轮。改完推上去才记 `applied_at`，卡片这时才变「已生效」。理由：打断正在跑的会话会丢活；照改和别的改动走同一条验证、CI 的路，不另开口子。交过还没记上的按提问编号记着，不会交两遍。读不到提问（库没查成）挂起报警，不当成一条都没问过。
2. **对账开单放在 GitHub 对账里，不放在工作流里**（`jobs/ask-issues.ts`，每 15 分钟一轮）：合并后工作流已经结束，只能由定时任务兜；超出范围的也在这里开，会话、工作流都不用等 GitHub。按提问编号幂等（开单键 `ask:<提问编号>`，账本加正文里的隐藏标记），开不出两张。
3. **后续单放哪**：类别照抄原单（只认一个类别标签，认不出按「需求」），「母单」不抄；挂原单此刻挂的版本（「引擎」机器人现读），那个版本关了先放未排期、正文写明。超出范围的一律未排期：等他拍，引擎不碰未排期（0003 第 2 条）。后续单是独立单，不挂成子单：挂在当前版本上的由接活照常自动派（#287）。
4. **开单没成照实记**：GitHub 报错、卫生检查拦下、单开了库里却记着别的单号，都不回写单号；这一轮对账记没查全（`partial`），`why` 写明哪一条，报提醒 `ask-issue:<提问编号>`，下一轮再开，好了自动撤。卫生检查拦下的只写规则和位置，不写值。
5. **超出范围的回答写到另开的单上**：他在卡片上回答了，对账把回答写成那张单的一条评论（键 `ask-answer:<提问编号>`），写上了记 `applied_at`（对超出范围的提问表示「已转交」），之后不再进对账的候选。理由：那张单等他拍，拍了什么得在单上看得见。
6. **退回重问**（`kit.ts` 的 `stageLoop`，Fusion 和旧工作流共用）：会话 `fleet blocked --needs human|info` 退回同一个会话，带上「用 `fleet ask` 带选项和推荐问、按推荐接着干」；同一步最多退回 `reaskRounds`（默认 2）次，到数照旧停下等人；`access`、`other` 照旧等。
7. **PR 正文「按推荐先做了」**：模板、引擎的 `renderPrBody`、CI 的栏目清单一起加；写的是开 PR 那一刻的提问（core 的 `assumedLines`），之后才问、才答的算进关单评论的记数（`askTallyLine`）。
8. **分诊说不清也带推荐**（旧需求工作流的分诊）：分诊交选项和推荐，合格的问他（发卡、记进库，算这张单范围内的）、不等，按推荐先做；没带或带得不对退回分诊补，退回够了按写明的假设继续。
9. **老历史照老样子重放**：Fusion 新加的读提问、PR 正文、关单记数包在 `patched('ask-not-blocking')` 里，退回重问包在 `patched('blocked-reask')` 里；分诊的新结论经 decide 进历史，重放照记下的走。
10. **还欠的**：引擎开的单没有需求文档（引擎不往主线直接写），自动派下去会停在收单等人补，另开 #295；法国演练由帅位安排。
