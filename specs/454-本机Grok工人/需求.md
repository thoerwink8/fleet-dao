# 本机环境里的 Grok 普通模式工人：起停、并发上限、额度保护、只限本仓的推送令牌（#454）

对应计划：v1 Fusion 接活
设计依据：specs/169-Fusion形态/需求.md 09-28 凌晨「普通模式对照」第 4 条（起停、上限、额度保护照那里的做法）

原话（创始人 2026-09-28 下午）：「仓库要存放一个代码库，不管是通过docker还是什么方式，保证本地环境和vps相同，然后本地全流程走通，该做的事情全做完，再正式上线到vps；之前做法存在很大问题」「本机其实帥位可以当前会话修断链，其他场景可以放到这个wsl上，用grok模型去干活，批量快速干完，走普通模式」；帅位出方案、GPT 挑错后他选「1」＝照方案做。决定记在 specs/169-Fusion形态/需求.md「删减清单全按帅位的做；本机建一个和法国一样的环境」。

AI 理解：本机环境里起一组 Grok 普通模式工人（不经引擎，一个会话一张单、各自克隆），批量做帅位派的单：推分支、开草稿 PR，帅位验收后合。Grok 订阅和法国引擎共用一份额度，要设上限、报限额就全停、法国优先。推送用一个只限 fleet-dao 这一个仓（内容、PR 读写）的细粒度令牌，放在本机环境里，不用创始人的 gh 登录；令牌由创始人在 GitHub 网页上建（只有他能建）。

## 要什么
- 起停脚本：给一串单号，一张单起一个 Grok 会话（Grok 4.7），工作目录各自克隆；起步 3 个，看内存和负载加到 6 个；可用内存不够或负载过高就不加。
- 额度保护：Grok 报限额，本机工人全停、写明原因；不抢法国引擎。
- 每个会话照 AGENTS.md 干活：开草稿 PR、正文照格式；卫生检查照跑（推前钩子装好）。
- 令牌只放本机环境里、权限只到这一个仓；日志、PR、提交里不出现令牌的值。
- 帅位能一眼看到每个工人在做哪张单、做到哪（进度页或命令）。

## 怎么算做完
- 一次派 3 张小单，3 个 Grok 工人各开出草稿 PR，帅位验收过了合进去。
- 故意造出的失败，每条一个测试：令牌没配 → 起不来、报清楚；Grok 报限额 → 全停；内存不够 → 不再加。
