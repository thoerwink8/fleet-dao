## 起因

#58（飞书后端 9 条接口）在 api 包的 draft-opening.ts 里留了窄接口（#58 合进来之前主线上还没有这个文件） `DraftOpener`（方法 `open`、`check`），`main.ts` 装的是空实现 `notWiredDraftOpener()`：飞书里确认过的草稿停在「待开单」，接上后后台每分钟自动补开。#58 的工人提出 `main.ts` 里两处「等 #43 接」的注释要有单号挂着，不能只写在注释里。#43 本体（issue 进来 → 建任务 → 拉起需求工作流）另行在做，这张单只管「飞书草稿 → 开 issue」这一段。

## 要做什么

- 在 `packages/api/src/main.ts` 把 `notWiredDraftOpener()` 换成真实现，接口和要求见 #58 合进来后 `packages/api/src/ports.ts` 的 `DraftOpener` 和 #58 带进来的 #44 方案里讲谁来接的那段：
  - `open` 按草稿编号幂等，幂等记在重启后还查得到的地方（不靠进程内存：库里先占住、开出来马上记 issue 号，或 issue 正文带草稿编号能查回来）；issue 开出来、还没交回结果时进程没了，再来也认出那张 issue，不开第二张。
  - 开 issue（机器人写，贴类别标签和里程碑）、走 #43 的接活入口建或复用「仓 + issue 号」的任务行、拉起需求工作流；没接上或暂时不通抛 `DraftOpenerUnavailableError`；signal 中止后尽快放手。
  - 开不了（GitHub 读写失败、库读写失败、仓不在受管名单）：明确报错，不当成「待开单」照常返回；每条配一条故意造出失败的测试。
  - `check` 给健康检查用：开不了单就抛。
- 接上那一刻积压的待开单会一口气全开：接上前先给创始人过目，或给待开单设过期（#58 正文「还欠什么」里记过）。
- `main.ts` 和 `draft-opening.ts` 里「等 #43 接」的注释删掉，改指本单或直接去掉。
