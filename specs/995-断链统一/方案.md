# 断链统一：里程碑、重复、需求的参考（2026-10-05）

对应创始人 2026-10-05 约 08:30：「流程里的断链也要修复，比如 v3 里程碑，为什么没有及时同步对里面的 issue 做反应；然后我们做的事情是否有重复性；做需求的时候是否有参考内容？……不管是本机无人值守还是 vps 引擎流程需要修复断链，达到逻辑上统一；方法我没思路，你思考下给我拍板」。

**实锤（就在写这一页的过程中发生）**：v3 发布（PR #991，tag `v3`，2026-10-05 00:57）时，`release.yml` 把里程碑 #10 关了，**里面 17 张开的单跟着一起被关在关掉的里程碑里**——没有任何东西拦一下、也没有东西把它们搬走。这已经不是「可能会断」，是当场断了。已开 v4（milestone #11）把 17 张搬过去。

## 一、断在哪（三处，一条根）

### 1. 没有人负责「确认一张单的活做完了、把它关掉」
- 关单只有两条路：PR 正文写 `Closes #N`（合并时 GitHub 自己关）、`pnpm issue:close`（要证据）。**两条都得有人主动去做**。
- 每日 `github-audit`（`.github/workflows/github-audit.yml` 01:41，`packages/conventions/src/github-audit.ts:101-120`）只查四类：开着的单没类别标签、**母单子单全关却没关**、子单挂在已关母单下、`fleet:order` 和实际对不上。**它不查「有合并的 PR 提到它、却还开着」**。
- 引擎侧 `github-reconcile`（每 15 分，含每小时 `issue-groom`）、`hourly-reconcile`（每时 41 分）都不碰单的开关状态；`issue-groom.ts:251-254` 唯一会自动关的是**未排期**单闲置超期。
- 结果：#593（PR #726/#839 都提到它）、#76（#837）、#323（#747/#840）**没有一张 PR 写 `Closes`**，于是从没被关；#902 是我这次手工关的。

### 2. 版本里程碑关的时候不看里面还剩什么
`release.yml` 的七步是「tag → release → 关 milestone → 飞书」，`release-finalize.ts` 里顺序写死、测试钉着，但**没有一步是「里面有开着的单就先别关 / 先搬到下一个版本」**。所以 v3 是带着 17 张开的单关的。

### 3. 没有「新单先查旧单」这一步
- 动手会话拿到的上下文：单子正文（场景/原话/已知的模块/怎么算做完）+ 仓里的 `AGENTS.md`；`specs/<号>/需求.md` 只有老单有。
- **不塞**：设计文档、同类/同模块的旧单、旧 PR、`specs/` 里的旧方案。
- 对题（`pnpm issue:new`）只保证四节写全，**没有一步是「这张单和已有单是不是同一件事」**。
- 结果：同一个根被反复开单——「偶发超时」开成 #353 #706 #718 #264 #307 #88 一族；「起子代理前取远端/走代理」#888 #909 #912 #932 四张围绕 #786 一个根；「残留清理」散在 hourly-reconcile / canary / orphan-reap 三处各一遍（#247 #336 #987 就是这么来的）。

## 二、本机 vs 法国：现在的分工（查实了，不是猜）

- **八个 Temporal 定时活是一份代码**（`packages/engine/src/jobs/schedules.ts`），法国和本机跑同一个 worker，只差 `FLEET_CANARY_REPO`（法国 `fleet-dao-canary-fr`、本机 `fleet-dao-canary`，`#777` 钉着不许相同）和代理/并发登记。
- **本机现在根本没起引擎**（`deploy/local/install.sh` 只装 WSL loopback 两个单元），所以本机侧那些定时活一个没在跑。
- **只有法国有的**：`github-audit`/`branch-hygiene`（在 GitHub Actions，不在引擎）、`auto-release`、`backup`、`demo-scopes`。
- 「断链怎么被发现」两边是**同一份**（`docs/design.md` 第六节五层 + 外部看门狗 #292）——没有各做一套。**真正的重复在别处**：同一件事被「引擎定时活」和「GitHub Actions 定时」各查一半（引擎管 PR/额度/提醒，Actions 管单/母子/先后/分支），两边都不知道对方查了什么，新加一种断法时不知道该往哪边加。

**所以「本机无人值守」和「VPS 引擎」不是两套流程要合并的问题**——它们本来就用一份代码。要统一的是**断链检查的清单**：一份可枚举的检查表，谁跑（引擎 / Actions）只标一次。

## 三、要创始人拍的（3 条，各有选项）

### 拍 1：关单这件事，谁来收口
- **选项 A（推荐）**：合并那一步自动收口——PR 合并时，它 `Refs` 的单若已无在跑工作流、无开着子单，自动 `issue:close`（改的是动作必经的那一步，不是文档）。代价：中（碰合并流程，要走第二意见）。风险：误关「有意留着的单」，用两个条件收紧。
- **选项 B**：只加每日检查——`github-audit` 加一条「有合并 PR 提到、却还开着」的规则，列成 finding + 留言，人再关。代价：小。风险：还是靠人，但至少**会被发现**。
- **选项 C**：先只做「发版前拦一下」——`release.yml` 关里程碑前，若里面有开着的单，报错停下、等人搬走。代价：小。风险：只治了里程碑这一处。

我的推荐：**A + C**（A 治单、C 治版本）。B 可以作为 C 的兜底一起加。

### 拍 2：版本里程碑关的时候，里面的单怎么办
- **选项 A（推荐）**：关之前**自动搬到下一个版本**（没下一个就搬「未排期」）并留言说明；关的时候里程碑里不该有开着的单。
- **选项 B**：不自动搬，只报错停下、等人手工搬。
- **选项 C**：维持现状（带着开的单一起关）。

推荐 A。这次 17 张已经手工搬进 v4（milestone #11）。

### 拍 3：新单要不要先查旧单、要参考什么
- **选项 A（推荐）**：开单那一步（`pnpm issue:new`）**先按关键词/模块查一遍同仓开着的单和最近合并的 PR**，把「可能重复的」列出来给建单的人看（不自动拦，只提示）；同时动手会话的提示词里加一句「同模块的历史单和它的 PR 在 `specs/` 与该单 `Refs` 里，先读」。
- **选项 B**：只做提示（不动会话提示词）。
- **选项 C**：不做，靠人记得。

推荐 A。这是「重复开单」和「需求没有参考」两件的同一个修法。

## 四、CI：现在多久、上限在哪（另一路调查的结论）

**真数字**（最近 60 轮）：

| PR 类型 | 排队 | 墙钟 | 最慢的一台 |
|---|---|---|---|
| 小代码 PR | 2–3 秒 | 中位 **55 秒** | 测试台 30–35 秒 |
| 全量 PR、不带 e2e | ~3 秒 | 中位 **~90 秒** | `test (5/8 · temporal)` 75 秒 |
| 全量 PR、带 e2e | ~3 秒 | **370–390 秒** | **`e2e` 364 秒** |
| 主线推送、命中同树复用 | ~2 秒 | 中位 **48–61 秒** | lint 37 秒 |

**一句话**：**e2e 一台 364 秒，是全仓最大的那一块钱**；带 e2e 的 PR 从 90 秒被拉到 380 秒。不带 e2e 的两条线（小 PR ~50 秒、全量 ~90 秒）已经贴着地板，再压都在噪声里。

**能省的**：
1. **e2e 那 318 秒**（10 个用例 × 2 个视口**串行**跑，`workers: 1`）：拆成两台并行 → 364 秒降到约 180–200 秒。多占 1 个并发槽。**最值。**
2. **e2e 触发面收窄**：现在碰 `db/shared/lockfile` 就开 e2e。要先量「只改 db/shared 的 PR，e2e 抓到过单测漏掉的错没有」，抓到就不动。
3. **不值得做**：加测试台（和并发槽打架）、拆 lint、tsc 缓存、压固定开销——三轮都量过，收益在噪声里。

**花钱的选项（要创始人拍）**：免费档并发 20 是硬的、按账号算（Free 20 / Pro 40 / Team 60 / Enterprise 500，官方限额页查过）。多个会话同时开 PR 时排队中位 53 秒、最长 131 秒。升套餐能治排队，但**价钱读不到**（pricing 页是 JS 渲染），要创始人自己看 github.com/pricing。公开仓用标准 runner 本来就免费，花钱只花在并发槽或更大的机器上。
