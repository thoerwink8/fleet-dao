# 方案：会话内存上限按实测定、测试按内存限进程数；交活核对只认改动影响到的测试（#164）

需求见同目录 `需求.md`。接着 2026-09-26 停在本机的 WIP（分支 `fix/session-tests-memory`，提交 e1d3ae6）做完；和原先定的做法不一样的两处写在「和原定做法不一样的」。

## 做法

1. **测试开几个进程按内存上限算**（`packages/conventions/src/test-run.ts`，仓根 `vitest.config.ts` 接上）：读本进程所在 cgroup 从自己那层到根的 `memory.high`、`memory.max`，取最小的；放得下几个 =（上限 − 1300）÷ 900，至少 1 个、不超过 vitest 默认的「核数 − 1」，比默认少时打一句说明。没有上限（本机、CI、不是 Linux）照 vitest 默认。读不到、认不出（没有 `/proc/self/cgroup`、不是 cgroup v2、文件内容认不出、读文件报别的错）直接报错，要硬跑给 `VITEST_MAX_WORKERS`（这个变量也先校验，vitest 自己读会把 `abc` 悄悄当成默认）。
2. **会话内存上限按法国实测容量重算**（`packages/engine/src/limits.ts`）：硬上限 =（能分给会话的 11G − 平台常驻约 0.6G）÷ 同时跑测试的 3 个会话 = 3554 MiB；软上限只低 256（3298）：超了软上限又没 swap，内核压着回收、会话半死不活（#160 就卡在软 1.5G、硬 2G 之间），夹缝留窄，真超了撞硬上限被明确杀掉。3298 放得下 2 个测试进程。只改默认值，在途任务照旧用开工时那一套（上限在工作流开头解析一次、进历史）。
3. **`pnpm test:changed`**（入口 `packages/conventions/src/bin/test-changed.ts`，判法 `packages/conventions/src/test-changed.ts`）：改动 = 和 `origin/main` 分叉以来提交的 + 暂存的 + 没暂存的 + 没跟踪的；跑哪些测试用 CI 按改动跑同一套判法（`ci-plan.ts` 的 `planCi`：改到的包和依赖它们的包、测试读的包外文件；根配置、锁文件、shared、夹具、`deploy/` 改到就全跑），再加上 CI 每个 PR 都跑的文档检查两份。`origin/main` 读不到、和它没有共同祖先、git 哪步没成都退出 2，写明原因；不收参数（加过滤会把「影响到的」跑漏）。
4. **引擎给会话的树钉好 `origin/<主线>`**（`packages/engine/src/real/user-git.ts` 的 `pinMainline`）：会话的树是从 bundle 建的、没有远端。建写码树时钉到起点（第一轮就是建树时记下的主线头）；分诊、文档、方案的检出副本钉到检出的主线头；审查另取主线进树再钉（提示词里的 `git diff origin/main...HEAD` 也就能用了）；推分支前把最新主线取进树后、并主线后快进时都重钉。三个点的比法只看分叉点，钉旧了只会多算并进来的主线改动，不会少算。
5. **交活核对只认仓的测试命令**：
   - 插头认「跑了测试」改成测试命令要在某一段命令的开头（按 `&&`、`;`、`|` 拆开，引号里的先抹掉，段首的环境变量、`cd … &&`、`timeout` 不算数）。原来是「命令里含测试命令」：`grep -n "pnpm test:changed" AGENTS.md` 会被记成跑了测试、而且通过。
   - 结果认不出的那一次（接了管道、放了后台）不再丢掉：列出来、`passed` 为空，交活以最后一次为准，它前面一次「通过」顶不上；退回时写明原因和「原样跑」。
   - 没跑过就退回，写明要原样跑哪一条（会话的仓的 `test_command`）。
   - 测试命令的出处：`repos.test_command` 只在 ops 第九节那条 insert 里手写，发布、目录装载都不碰它（查过 `deploy/`、`packages/db/src/bin/`），不会被写回 `pnpm check`。法国那一行要改一次（ops 第九节写了 update 和读回）。等 #191 定下每个仓一份的流程配置 JSON（#169 定稿第 1 条），测试命令、会话内存搬进那里，库里的变副本。
   - （合并后查断链补的，#229）上面那条手写的 update 没人跑，法国一直是 `pnpm check`。读配置这条链已接好，测试命令先走它：出处改成仓里的 `.fleet/flow.json`（fleet-dao 的写 `pnpm test:changed`），引擎每轮对账读默认分支头上的这份、写进库里的副本（`repos` 的 `flow_*` 列），手写的 update 作废；起写码会话时拿副本里的命令、记进 `session_runs.test_command`，交活核对只认它；项目没写、副本认不出或超过 45 分钟没同步成都明确停下（`packages/core/src/replica.ts`）。#214 在这条链上接整份配置。
6. **文档**：ops 第五节（上限和进程数怎么来的）、第九节（测试命令放什么、法国怎么改），design 第四节（实测数），AGENTS 本仓段和 README（本机也用 `pnpm test:changed`，它要全跑时本机改单跑包），`fleet done` 的帮助、写码和审查会话的提示词，目录配置样例里「每个会话按 1.2–1.6G 算」的旧说法。

## 和原定做法不一样的

需求里定的是「`vitest run --changed origin/main --passWithNoTests`，vitest 顺着 import 找不到的依赖放进 `forceRerunTriggers`、改到就全跑」。实现时发现两个洞：

- **基准分支读不到时 vitest 不报错**：它调 git 用的 tinyexec 不抛非零退出码，`git diff origin/main...HEAD` 失败就当「没提交过改动」，只测没提交的，照样退出 0。本机实测：给一个不存在的分支名，它只跑了没提交的那一个测试文件。引擎的树没有 `origin/main` 时，会话交的就是一次什么都没测的「通过」。
- **只顺着 import 找，看不到的依赖不止文档和迁移**：引擎的工作流测试跑的是 Temporal 打包器按路径打的包（没有一个测试 import `src/workflows/`），好几个命令行测试另起进程跑 `src/bin/`，结构测试按目录读源码。改了引擎的工作流代码，`--changed` 一个工作流测试都不跑；要靠 `forceRerunTriggers` 补，就得把引擎大半个 `src/` 列成「改到就全跑」，比按包还粗。

所以改成按包选（CI 那套判法，`ci-plan.test.ts` 扫所有测试源码兜着「测试读包外文件」的清单，漏记一条就红），代价是比按文件多跑一些；再在前面严格核对 `origin/main`。命令名 `pnpm test:changed`、「只认改动影响到的测试」、「只改文档不算失败」都照原样。

## 依据（实测）

同一组测试（`packages/api`、`packages/db`、`packages/engine/test/real`，57 个文件）：

| 开几个进程 | 法国 09-26，临时 scope，含页缓存的峰值 | 用时 | 本机 Windows 09-27，整棵进程树的工作集峰值 | 用时 |
|---|---|---|---|---|
| 1 | 1613 MiB（另一次读到回收不掉的至少 1697） | 279 秒 | 1510 MiB | 217 秒 |
| 2 | 2493 MiB | 151 秒 | 2344 MiB | 120 秒 |
| 3 | 3164 MiB | 99 秒 | 2971 MiB | 90 秒 |

- 每多一个进程多 880、671（法国）/ 834、627（本机）：按 900 算。开 1 个时的峰值按 1700 算，减一个 900，加会话里的 Claude Code（#160 那次约 270，按 300）、外面那层 pnpm（约 60）、余量约 140：给主进程和 Claude Code 留 1300。
- 本机的主进程峰值工作集约 260 MiB、私有提交约 650 MiB；单个测试进程工作集最高约 1.3–1.4G（一个进程在内存里建一份 PGlite）。
- 平台常驻四个服务合计约 0.6G（`docs/decisions/0002-fusion.md`「容量」）。
- 本机量法：跑 vitest，每 0.5 秒读一次整棵进程树的工作集和私有提交，取峰值（Windows 没有 cgroup，量的是进程自己的，不含页缓存）。

在法国复测（上线后照这个核对一遍，数字对不上就改 `test-run.ts` 的两个常数和 `limits.ts` 的算法，改了写进上表）：以会话用户在一棵装好依赖的 fleet-dao 工作树里，开一个和会话一样上限的临时 scope 跑同一组测试，最后读这个 scope 的 `memory.peak`（内核 5.19 起有；没有就每 0.5 秒读一次 `memory.current`、`memory.stat` 的 anon 取最大）：

```
sudo -n /usr/local/sbin/fleet-agent-scope run measure-164 --user fleet-agent-carpool \
  --memory-high 3298M --memory-max 3554M --memory-swap-max 0 --cwd <工作树> -- /bin/bash -c \
  'VITEST_MAX_WORKERS=2 pnpm exec vitest run packages/api packages/db packages/engine/test/real; cat "/sys/fs/cgroup$(cut -d: -f3 /proc/self/cgroup)/memory.peak"'
```

这条命令没在法国跑过（这次不部署到法国），第一次跑时核对 scope 名、PATH 里有没有 pnpm。

## 还没做的（都挂在 #164 下，#164 不关）

- **法国真机**（#164「怎么算做完」第二条）：合进主线后发布到法国；手动跑一轮对账，读回库里的副本：fleet-dao 的 `flow_source` 是 project、`flow_config` 里的测试命令是 `pnpm test:changed`（不再手改 `test_command`，ops 第九节）；照上面复测一遍内存；重开 #160（或同样的需求），引擎全程无人插手做完：写码会话跑测试不再被内存卡住、交活核对通过。算做完：那张单合并、关单，中间没人插手。
- **测试共用一个真 Postgres**（需求「追加」，design 第三节第 39 条）：没配测试库时（本机、CI）照旧用 PGlite；配了时每个测试进程从模板库克隆自己的测试库，测试库和正式库分开装、会话碰不到正式库。牵涉在法国另装一套 Postgres、会话用户的连接权限（碰登录鉴权，先审后合），这次没做。算做完：法国配好测试库后，同一组测试每个进程的峰值实测降到约 0.3G 上下，`test-run.ts` 的常数、`limits.ts` 的同时跑测试数跟着按实测改。
- **同时跑测试的不超过 3 个**：现在没有东西拦（账号池并发加起来比 3 大，design 第四节「放行看三样」的内存准入也还没做）。真撞上了，每个会话照样被自己的硬上限封住，整机可能不够。可以先给 `fleet-agents.slice` 加一个总的上限兜住平台的四个服务（`deploy/france.sh` 现在读回核的是「池子不设上限」，要一起改）。算做完：四个会话同时跑全量测试时，引擎、后端、Temporal、库都不被内核杀掉、健康页不红。
