# 结果（#44）

## 做了什么

- 后端按 `FeishuRoutes` 实现了网关要的九条接口，数据都落 Postgres（新表四张，迁移 `0004_feishu`）；做法见同目录 `方案.md`。
- 网关通行证只放行约定里那几条：九条飞书接口按各自的 acting 放行，驾驶舱接口只放查任务、叫停、回答追问三条，别的一律 403。原来通行证能调驾驶舱全部接口，这次一并收紧；实时推送（`/api/events`）的测试原来断言「网关能连」，改成断言 403（网关的推送走长轮询待推送，不用它）。
- 确认后开 issue、拉起工作流那一步定成窄接口 `TaskIntake`，生产上先接「没接上」：确认照样记下、进「待开单」，后端每分钟补开，接上后自动开出来。
- 网关那边改了一处卡片：确认了、issue 还没开出来的草稿卡写明「正在开成任务」，不再退回成带确认按钮的样子。

## 怎么验证的

- `pnpm check` 全绿（格式、类型、全部测试、卫生检查、文档指针）。
- 验收（`packages/api/test/feishu-gateway-e2e.test.ts`）：网关的真客户端 `createBackend`（香港跑的同一份代码）对着后端、库是 PGlite 上的真迁移，跑通 记一句 → 回复确认卡改一句 → 卡上改一下 → 确认（旧版本 409、新版本开成任务、另一位再点不开第二个）→ 查任务 → 看详情 → 关注 → 盘面（含登记后找回置顶卡）→ 会话里 AI 追问一句 → 待推送出卡 → 回执「发了」后不再给 → 卡上回答 → 下一版「已回答」带上次送到的卡 → 回执「改了」后不再给 → 后端拒收时网关拿到带 code 的错误。另一条：开单没接上时确认进「待开单」，接上后补开，任务查得到。
- 每条接口的「参数认不出、库读不到、状态冲突」都有故意造出的用例（`feishu-routes.test.ts`，库读不到用打桩让 Store 抛错，断言 500 而不是空列表 / ok / 全是 0 的盘面）；门按路由表逐条核对（每条都挂上、acting=none 不认代表人、required 不带就 403、不带通行证 401）。
- 新的 Store 方法内存版、Postgres 版过同一套契约（`store-contract-feishu.ts`，21 条，各跑一遍）；四张表的库级约束另有用例（`feishu-constraints.test.ts`）。
