# 方案（#44）

## 怎么做

- **数据**：四张新表（`packages/db/src/schema/feishu.ts`，迁移见「各改哪里」）：草稿、关注、推送的送达状态、卡片登记。收到的话（按飞书消息编号）和卡上「改一下」（按请求编号）的幂等记录放现有的 `idempotency_keys`，和草稿同一事务写；记录认不出、键被别的命令占着都明确报错（500），不当成「没处理过」再处理一遍。
- **门**：九条接口在 `packages/api/src/feishu-routes.ts` 按 `FeishuRoutes` 逐条挂，方法、路径、acting 都取自表；只认网关通行证，acting=required 的认出是哪位创始人（操作记录 via=feishu），none 的只验通行证。驾驶舱那道门（`session.ts`）对网关通行证只放行 `FEISHU_GATEWAY_WEB_ROUTES` 三条，表里没有的 403——约定本来就这么写，原来的实现漏了（通行证能调驾驶舱全部接口）；三条里的 taskAction 只放「叫停」（网关也只发叫停），暂停、继续、换路由 403。
- **进来的话先规范化**：孤立的半个 emoji（被截成两半的代理对）在入口换成 �、记日志。不换的话，写进 text 列时驱动会悄悄换掉、和幂等摘要对不上，写进 jsonb（操作记录）时整条被库拒收。网关截断时也不再切在 emoji 中间（`packages/feishu/src/words.ts`）。
- **一句话**：还没接模型理解，按原话记草稿、标拿不准；只有一个仓、或原话里恰好提到一个仓名，就放那个仓。回复某张卡按卡片登记分流：草稿卡 = 改理解；AI 追问卡 = 回答（和驾驶舱回答同一条路，抽成 `answer-ask.ts`：写库、叫醒等着的 `fleet ask`、发信号）；要人拍的卡只算追问；别的卡如实说「还答不了」，不编。卡片登记记着的草稿、追问在库里读不到时如实说「这句没记下 / 没记成回答」，不另起一张草稿、不把回答吞掉。
- **改一下**：补充整句接在原话（`raw_text`，没有长度上限）后面，开单时整段交出去，一个字不丢；「我理解为」（最多 1000 字）也整句接上，放不下时截旧的、不截新补的。所以新补的一句有上限，约定里一个数（`FEISHU_NOTE_MAX`，`packages/shared/src/feishu-api.ts`）：卡上的输入框、改一下这条接口都按它卡住，回复确认卡补的超过它，后端回一句说明、草稿不动；网关万一收到更长的也照实说最长多少字，不发给后端。
- **确认 →「待开单」**：记下确认人和仓，当场开一次单（`DraftOpener`：开 issue、建任务行、拉起需求工作流），最多等 8 秒（网关等确认 15 秒），开成就把任务号带回卡上；没等到、没成都回「已确认、待开单」，原因记在草稿上，后端每分钟补开一轮（按次数退避，最多隔 30 分钟；进程刚起来全试一遍）。
  - 时限后端自己掐（`draft-opening.ts`），不指望实现理会 signal：一次开单到 30 秒没回就记「开单超时」、算一次没成；那次调用留着直到真的结束——期间这张草稿不开第二次、确认也不干等；后来开成了照样记上任务。开之前重读一次草稿（手上的可能是一分钟前列出来的）。
  - 一直开不成要有人知道：健康检查加两项，`draft_opener`（开单那一步接没接上）和 `draft_backlog`（最早一张待开单等了 15 分钟以上）。补开一轮没跑完时下一轮跳过、记一笔。`draft_backlog` 会随时间自己变红、和换没换版无关：发版脚本（`deploy/release.sh`）对它只标待处理，不当成这一版的错去退回。
  - 「正在开」只记在后端进程里：发版重启后一起来就不管退避把待开单全开一遍，上一次调出去还没回的也会再调。所以开单的实现必须按草稿编号幂等、记在库里（见「谁来接」）。
  - 为什么不在确认时就建 `tasks` 行：`tasks.issue_number` 必填，约定里草稿的 `task` 也要 issue 号；issue 没开出来就没有号。所以「待开单」记在草稿上（确认了、还没 `task_id`），任务行由开单那一步建——它和接活入口（#43）按「仓 + issue 号」共用一行，不会建两行。
- **待推送不另存一份队列**：推什么从源头现算——没答的和最近答过的追问（`ask:<编号>`）、没处理的和最近处理过的通知（`notification:<编号>`，要人拍 / 卡住 / 日报）。`feishu_outbox` 只记「第几版、这版内容的指纹、回执到哪一版、上次送到哪张卡」；内容一变指纹就变、版本加 1，网关按版本原地改卡。这样引擎照常写 `asks`、`notifications` 就会推到飞书，不用另调接口，也不会有「写了库、忘了进队列」。
  - 待推送 = 当前这一版没收到「发了 / 改了 / 不发了」，也不在推迟、没发成的等待期内（到点再多等 2 秒，防两台机器的钟差一点）；已经了结、又从没发过卡的不给。
  - 回执按条处理：认不出的跳过并记日志，不让整批 4xx；旧版本的「发了 / 改了」只记下送到的卡；回执没记上时按卡片登记里的 `ref.outboxId` 补「上次送到的卡」；同一条回执重复到达（记下来什么都不变）不再记一次。通知类的「发了 / 改了 / 没发成」同时写进通知的送达记录（驾驶舱「通知」页），推迟和「不发了」不算送达尝试、原因记在推送本身。库写不进就 500，网关留着下次再送。
  - 长轮询：追问、通知、需求有变化就醒，另每 3 秒回库看一眼（别的进程写的不一定叫得醒）。免打扰时段读驾驶舱设置，设过却读不懂就 500，不当成「不设」。
- **盘面**：从库里算——在干（没结束、没卡住的需求，带「此刻在干什么」）、卡住（需求或子任务卡住，最久的在前，写明卡在哪）、等你们（没答的追问 + 没处理的要人拍）、今天合并（北京时间今天进入「已合并」的子任务）、快清零还剩不少或快用完的额度（读数太旧的不上）、最新登记的盘面卡。
- **关注**：只存谁关注了哪个需求（取消只改标记，不删行）。
- **网关顺手改两处**：确认了、issue 还没开出来的草稿卡，原来会退回成带「确认」按钮的样子，改成「已确认，待开单」并写明会自动补开（和点确认那几秒的「正在开成任务…」分得开）；改一下时草稿已确认（409），照后端说的写明在哪一步（待开单 / 已开成 #n），不再自己说「已经开成任务了」。

## 谁来接

- **开单的真实现**：接口 `DraftOpener`（`packages/api/src/ports.ts`），由 #43 接，在 `packages/api/src/main.ts` 把 `notWiredDraftOpener()` 换掉。要求：`open` 按草稿编号幂等——确认、补开、超时之后都可能再来，发版重启后后端一起来就会马上再调；幂等要记在重启后还查得到的地方，不能靠进程内存（比如开 issue 之前先在库里按草稿编号占住、开出来马上记下 issue 号，或者 issue 正文带上草稿编号、再来时能查回来）；issue 已经开出来、还没交回结果时进程没了，再来也得认出那张 issue、交回它，不开第二张。开 issue（机器人写，贴类别标签和里程碑）、建或复用「仓 + issue 号」的任务行、拉起需求工作流；交回任务编号和 issue 号；没接上或暂时不通抛 `DraftOpenerUnavailableError`；signal 中止后尽快放手。`check` 给健康检查用：开不了单就抛。接上之前确认的草稿都在「待开单」里，接上后自动补开。测试里的假实现（`packages/api/test/feishu-gateway-e2e.test.ts` 的 `fakeOpener`）就是按库幂等的写法。
- **关注的推送**：到关键节点（方案好了、PR 开了、合并了、卡住了）私聊推给关注的人，要引擎报出关键节点；推送条目按 `follow:<需求>:<open_id>` 加进待推送的源头即可（`composeOutbox`）。
- **要人拍的卡上的按钮**：网关按追问回答（`askId` + 选项）；引擎那边的人闸批准记在 `approvals`（#28），不是追问，所以现在这类卡只有「打开驾驶舱」。两边对齐后在 `composeOutbox` 里给要人拍的条目带上回答的去处。
