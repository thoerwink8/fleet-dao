# 路由探针：定时给每条开着的路由发最小请求、写在线与否，引擎才派得出活（routes.alive 现在没人写）（#129）

对应计划：plan.md P1「核心闭环」的验收（巡检仓一张 issue 由引擎从收单做到合并、关单：派活要有在线的路由）
设计依据：design 第九节（选路：在线、额度够、有空位、不犯禁令）、第十节（额度与探活「不刷」）。

原话：路由探针用 pnpm issue:new 开单：kind 选需求，里程碑挂 P1，写清怎么算做完——引擎能把一张单派到一条探过、在线的路由。（总指挥 2026-09-26，起因是法国驾驶舱逐页排查）
AI 理解：库里 `routes.alive` 只由探针和熔断写（`packages/db/src/schema/catalog.ts`），这两样都还没做，所以法国上每条路由都停在默认的「不在线」；引擎选路第一步就把不在线的挡掉（`packages/db/src/queries/candidates.ts` 的 `offline`），一张单都派不出去，挡着 P1「机器接管」验收。要做一个探针：定时给每条开着的路由发一次最小的真请求，按结果写 `alive`。

## 起因

2026-09-26 法国驾驶舱上线后逐页排查：调度台每条路由都显示「离线」。查下去是 `routes.alive` 从来没人写过——目录装载器不写它（「只由探针和熔断写，新路由没探过，默认不在线」），探针和熔断都还没做。P1 验收（巡检仓一张 issue 由引擎从收单做到合并、关单）因此走不通。驾驶舱在探针做好之前先显示「还没探过」，不说成「离线」（另一个 PR 当场改）。

## 要做什么

- 引擎里加一个定时任务（Temporal 定时，和对账补漏同一种登记法，结局记进 `schedule_runs`）：逐条探开着的路由——按路由的插头（Claude Code 经 reclaude 以会话用户起、cursor-agent、Grok 命令行、Mirasim、接口外壳）发一次最小请求，成功写 `alive = true`，失败写 `false` 并记原因。插头还没接的路由记「这种插头还没接」，不写成探过、不在线。
- 探一次花的额度要小（一问一答、最短输出），频率按 design 第十节「不刷」的规矩定（起步 15 分钟一轮，和额度读取错开）。
- 驾驶舱调度台和渠道页：探过的显示在线 / 离线和上次探的时刻、失败原因；探针接上后去掉「还没探过」那一档里「探针还没接」的说法。
- 熔断（连续失败判不在线）不在这张单里，归 P5。
- 每条读不到、跑不成的路径（插头起不来、超时、输出认不出、写库失败）明确报错，各配一条故意造出失败的测试。

## 怎么算做完

- 法国上 Claude 订阅那条路由（`claude-carpool:opus-5.5:claude-code`）被探针探过、`alive = true`，驾驶舱调度台上它显示「在线」和上次探的时刻。
- 引擎能把一张单派到一条探过、在线的路由：巡检仓开一张测试单、交给 fleet，分诊阶段选中这条路由、真起了会话（`session_runs` 有一行，路由是它）。
- 把会话用户的 reclaude 临时弄成登录失效，下一轮探针把这条路由写成离线、写明原因，驾驶舱看得到；恢复后下一轮转回在线。
- 定时任务页有「路由探针」这一行，上次跑成的时刻、扫了几条、几条不在线都对得上。
