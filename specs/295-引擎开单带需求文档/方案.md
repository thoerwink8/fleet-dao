# 引擎开的单没有需求文档也能接着做：方案（#295）

对应需求：`specs/295-引擎开单带需求文档/需求.md`；设计：design 第五节「第 5 步开 PR 前验证怎么做」、第七节「分工」，0003 第 5 条第 1 步。

一句话：收单时认单子正文里写全了的需求。没有「文档：」那一行、正文里有写了字的「## 怎么算做完」的单照收，引擎照正文写好需求文档交给 Lead，Lead 在第 2 步原样和方案一起提交，随这张单的 PR 进主线。开 PR 前验证照单子正文核，「对应计划」照单子挂的版本写。

## 比了两个方向

| | 方向 1：引擎开单时先把需求文档写进分支、开 PR 合进主线，再让接活派 | 方向 2（选这个）：收单时认正文里写全了的需求，文档随这张单的 PR 进主线 |
|---|---|---|
| 要加的东西 | 对账里多一串跨轮的步骤：开单（先不挂版本，免得被接活抢先派走）→ 推一个只带需求文档的分支 → 开 PR、等 CI、合进去 → 回头给单子补「文档：」那一行、挂版本 | Fusion 收单、规划、验证、开 PR 四处各加一个分支（只在这种单上走），core 加两个判法 |
| 多久能开工 | 至少多等一轮 CI 和一两轮对账（15 分钟一轮） | 开单的下一轮对账就派，和别的单一样 |
| 新的出错点 | 文档 PR 红了、冲突了、合不进去，单子卡在半路；这几步都要能重来、要报提醒 | 正文没写全照旧停在收单；验证时正文里的「怎么算做完」被删了停下等人 |
| 验收条会不会被改 | 不会：读主线上的文档 | 不会：读库里这张单此刻的正文，会话改不了（改正文要白名单里的人在 GitHub 上改，接活跟着改库） |
| 别的仓、巡检单能不能用 | 每个开单的地方都要接这一串 | 能：只要正文写全了需求，哪个仓、谁开的都照收 |
| 和已拍的规矩 | 合「issue 不抄文档内容」 | 合 0003 第 13 条「需求、方案、结果随 PR 进仓」；「issue 不抄文档内容」对引擎开的单开个例外（design 第七节「分工」写明） |

选方向 2：一样不直写主线、验收条一样改不了，要加的少得多，也不多一道等 CI 的路。巡检（#223）在巡检仓开的单照这个写就能接。

## 做法

1. **core**（`criteria.ts`）：`specOf` 判需求文档从哪来。正文里有「文档：」那一行的照它（写错了、指的是别的单照样报错，不改用正文）；没有那一行、正文有写了字的「## 怎么算做完」的，目录是 `specs/<号>-<短名>`，短名按标题取（只留字母、数字、汉字，最多 20 个字，同一个标题总是同一个短名），需求文档是「# 标题（#号）」加正文（去掉 HTML 注释：引擎开单留的标记、模板里的提示）；两样都没有报错，停在收单等人补。`bodyCriteria` 照正文读「怎么算做完」逐条。
2. **收单**：判出来带着需求文档的，记下这份（进历史）。
3. **规划**：交给 Lead 的交代里带上这份全文，写明原样写进需求文档路径、和方案一起提交（要补充的写进方案）；`checkLeadPlan` 这种单要需求文档也在提交里，没交就退回，几次都不交停下等人。
4. **验证**：这种单主线上还没有需求文档，「怎么算做完」读库里这张单此刻的正文；读不到、没有、空了都停下等人补，不验、也不当成验过了。
5. **开 PR**：`planFromIssue`，「对应计划」照单子此刻挂的版本写，没挂写「未排期」（和 `pnpm issue:new` 写进需求文档的那一行同一个写法）；读不到单子明确报错，不当成未排期。
6. **对账开的单**（`ask.ts` 的 `askIssueText`）：正文写全需求，那句「引擎接手时照正文写需求文档」放在「怎么算做完」前面，不然会被当成一条验收条。
7. **欠账定时任务**：开着的单正文写全了需求的，不算欠需求文档。

## 老历史

收单的判法经 decide 进历史：已经过了收单的单照记下的走，这几处新分支只在判出「照正文写」的单上走，不用 `patched()`。停在收单等人的老单，点「继续」以后照新判法再判，正文写全了的就照收。

## 巡检单（#223）照这个写

正文要有写了字的「## 怎么算做完」（一条一个列表项，写成能检查的样子），不用写「文档：」那一行，也不用在巡检仓里先建需求文档；前面写起因和怎么理解。「怎么算做完」下面别放说明的话，放了会被当成一条验收条。
