### 第 2 题：一张单分几步、每步谁做（创始人 2026-09-26 拍：「你现在说的我挺赞同的」，即选 1）

Fusion 模式七步；每步结束主导模型存一个存档点：

| 步 | 做什么 | 谁做 |
|---|---|---|
| 1 收单 | GitHub 上的单进来，建任务、排队 | 引擎，不用模型 |
| 2 规划 | 读单和相关代码，判大小；写方案：范围、做法、改哪些文件、怎么算做完，拆成几份任务简报；说不清就问创始人 | 主导模型（查代码可以派副手） |
| 3 方案评审 | 方案发给 1–2 家别的模型挑错，1 分钟内；主导模型逐条写明收还是驳、为什么 | 别家模型；小单跳过 |
| 4 执行 | 按简报派活，副手交回改动和测试结果，主导模型验收：收下、打回（最多 2 次）或自己接手 | 副手干，主导模型验收 |
| 5 验证 | 对照「怎么算做完」和方案核整个改动 | 验证模型（别家的） |
| 6 开 PR、过 CI | 引擎推分支、开 PR（正文写做了什么、怎么验证、评审和验证的结论）；CI 没过交回主导模型派副手改，最多 3 轮 | 引擎 + 主导、副手 |
| 7 合并、关单 | CI 全过自动合；碰人闸四类的等创始人拍；关单留一条结果：改了什么、用时、各模型花的额度 | 引擎 |

- **多个副手同时干**（创始人提、同意）：拆得开才同时派，由主导模型判断；先定接口和「谁改哪些文件」，每个副手只改分给自己的文件、在自己的工作副本里干，要动别人的文件就回报主导模型改派；主导模型逐个合进来、每合一个跑一遍测试；副手定时交进度，主导模型可叫停、改派、补一句指示再续上（没法在它干到一半时插话）；一张单最多 3 个副手同时干；小单或拆不开的照旧一个副手。几个副手可以各用不同的订阅。
- **验证五条**（防止重现「合并后补审一条接一条」）：①在合并前、同一张单里改完，不开新 PR、不补审；②只对照清单核：「怎么算做完」和方案逐条答做到 / 没做到 / 看不出，带证据；③只有三种能挡：没做到验收条、有证据弄坏了原有功能、安全或丢数据，其余只作建议写进 PR；④默认 1 轮、最多 2 轮，主导模型可以拿证据驳回并记下；⑤统计挑出的真问题占几成，误报多就调问法或对低风险的单关掉。
- **单模型模式**：第 2、4 步同一个模型做完；第 3 步默认关；第 5 步只对高风险的开。
- 「创单时就讨论」（创始人同轮提出）在第 4 题一并定。

### 第 4 题前半：创单时就讨论（创始人 2026-09-26 提出，同意）

- 流程最前面加一步「0 创单并讨论」：不管人开还是 AI 开的单，开单时就让几家模型讨论一轮；讨论记录写进单的评论（GitHub 为准，驾驶舱展示；09-26 晚提议改成以法国库为准、公开仓只放链接，见「第 4 题后半、第 5 题」），主导模型规划前先读它。第 2 题的「方案评审」成了它的后半段：主导模型的方案和讨论结论一致就不再评。
- 讨论的配置在驾驶舱调：哪几家、几轮、每家多少字、想多深、超时、同时几家；项目有默认，单条可临时改（design 第九节「讨论」阶段的配置）。按大小分档：小单 1 家 1 轮或跳过，大单 2–3 家先各自独立答、再互相挑错；开单的人可以手动指定。
- 每次讨论最后一行写「结论 + 谁拍的」，没结论的挂「待拍板」。驾驶舱显示每次讨论花了多少额度。
- 发给别家模型的内容要过敏感信息检查；私有项目按项目设「哪些渠道能看代码」。
- 「流程中途随时拉别家讨论」留在第 4 题后半，和第 5 题一起定。

### 第 6、7 题（合并）：骨架能力——驾驶舱之外也有同样的规矩和能力（创始人 2026-09-26 拍：选 1）

- 规矩和能力（开单、讨论、评审、验证、交给 fleet、查状态、问模型、记决定）只写一份，在仓里；四个入口用同一份代码、读同一份配置：驾驶舱（网页）；`fleet` 命令（像 gh 一样单独装，本机任何仓都能用，不用 fleet-dao 仓常驻）；各家 AI 的技能和工具（同步脚本装到每台机器）；引擎收单时补齐（GitHub 网页上直接开的单，收单时发现缺讨论、缺标签就自动补）。
- 本机 `fleet` 命令调法国的接口：讨论和记录在法国完成，驾驶舱马上看得到，钥匙只放法国一处；法国连不上才用本机渠道兜底，标「待补齐」，联网后由引擎补上，不许假装讨论过。命令每次对一下版本，旧了提示更新（和 #132 标准体检同一件事）。
- **适用于驾驶舱管的所有项目，不只 fleet-dao**（创始人原话：「不然人会遗忘，代码也会有遗忘，AI 也会遗忘」）：规矩长在每个项目都必经的那一步上，不靠谁记得。落实：①所有项目的单和 PR 的事件都经 GitHub App 到法国后端，后端收到就按「对账表」查这一个对象：该有的讨论、标签、里程碑、检查在不在，能自动补的当场补（结构化的用代码判，要读文字的用 Jev），补不了的挂出来等人；②标签的含义写成标准里的数据，标签一出现、一变（或该有却没有）就触发对应做法（比如「要人拍」停派活；「界面」「本机」同日晚改掉，见下面「插题」）；③事件触发为主，定时全量扫只兜底漏掉的事件，不当主力；④每条规矩配一个自动检查和一条故意造出失败的测试；⑤各项目、各机器对标准的版本，落后了报出来、开补齐 PR（改标准仍走人闸第四类）。和 design 15.7「项目与标准」、对账表是同一套，实施时并进来。

### 第 3 题：换模型接手（创始人 2026-09-26 拍：同意在存档点换，中途也允许换、自担后果；新模型自己读上一个会话）

- **在存档点换**：主导模型每走完一步存一个存档点，存档点连着一个 git 提交和一段写明白的进度（做到哪、定了什么、为什么、试过什么、卡在哪）。像游戏读档：可以换模型从当前存档点接着做，也可以读回更早的存档点重来（在新分支上读回，原来的记录保留）。
- **中途也能换，自担后果**：一步做到一半要换时，引擎先把工作副本里没提交的改动提交成一个临时提交，再从这个会话的记录自动写一个存档点，然后换；记录里标「中途切换」。
- **新模型自己读上一个会话**（创始人提，同意；比只读任务简报好）：引擎把每个会话的完整记录（说的话、调了什么工具、工具回了什么）按统一格式存下来，Claude Code 的会话记录和其他命令行工具的输出都收进来。新会话先读存档点入门，再按需翻上一个会话的完整记录和改动，自己分析，不一次全塞进上下文（太长太贵）。
- **「思考」要写出来**：模型内部的思考过程多半没存下、也带不到别家模型，所以规定每个模型把关键的想法（为什么这么做、试过什么、卡在哪）写进会话里或存档点，下一个模型才读得到。
- **谁来换**：引擎自动换（额度不够、连着失败两次、渠道下线），创始人在驾驶舱手动换，主导模型给每份任务简报挑副手模型；主导模型换同一家的模型时接着原会话做，换别家时从存档点重开。每次换都记一笔，驾驶舱看得到。

### 插题：版本、统领单、流程配置（创始人 2026-09-26 晚提方向；AI 整合方案待拍）

原话：「根本不需要"页面"这个标签。其实只需要在 Fusion 的派单页面流程中，去选择每个流程推荐的模型顺序……并且可以支持多套配置。……需要有一个类似于 JSON 的方式，可以自由地编辑和改造这个文件，然后在服务器端和代码端都能拿到这个文件」「大单确实是需要的，关键是要有里程碑的概念。每一个版本应该只做一些事情，一些问题要攒在大单里面一起修复」「问题可以去开 Issue，开完的 Issue 要放在大单里面。大单其实就是……"统领单"的概念」「一个好的机制应该是：……问题还少的时候，就不去做这个」

创始人定的方向：

- 不要「界面」标签。每一步用哪些模型、按什么顺序，在派单页上选，存成一份能自由改的 JSON 配置，可以有多套；法国和代码两边读同一份。
- 要统领单（借自旧仓 windsurf-dao：同一起因只一张统领单，新单先查起因再挂上去）：小单挂进统领单，攒着一起修；做成机制、不靠手工，单少时不整理。
- 里程碑＝版本：每个版本只做几件事。

AI 整合方案（待拍）——三层，各管一件事：

1. **计划层（做什么、先后）**：版本（里程碑）→ 统领单（GitHub 母单）→ 小单（子单）。
   - 第 0 步讨论时按起因把新单自动挂到已有统领单下；挂不上的进收件箱（没有母单的单）。
   - （第二轮撤回：收件箱攒够几张归成统领单，会把不相干的硬凑在一起，见「插题（续）」）
   - 派活的单位是统领单：一个主导模型会话领一整张，拆成几个 PR；小单随修它的 PR 合并自动关；子单全关后，验证模型核统领单自己的「怎么算做完」再关；版本里的统领单全关 → 发布（人闸）→ 里程碑关。这些由引擎按事件做，不指望 GitHub 自己关。
   - 统领单有上限（Shape Up 的熔断）：超了先合做完的，剩下的连同统领单挪出这个版本，等下次排。
   - 不等版本、立刻做的：坏了的（主线红、生产坏、数据、泄露、安全）、挡住当前版本的、正在做的统领单范围内的、创始人说「现在修」的。
   - plan.md「现在的目标」＝当前版本的统领单和先后。现有 P0–P6 里程碑改成版本；旧单挂到约 5 张统领单下（各自的「怎么算做完」保留），Fusion 后用不上的关单写去向。
2. **配置层（用谁、怎么跑）**：每个项目仓里一份流程配置 JSON。
   - 写几套配置（如「默认」「省额度」），每套写每一步的模型顺序（前一个没额度、连不上自动换下一个）、讨论和评审找几家几轮、验证几轮；再写测试命令、会话内存、高风险路径、哪些路径是页面代码、各类别默认用哪套。
   - fleet-dao 放一份全组织默认，项目只写和默认不同的（Renovate 的 extends）；禁令（GPT 不做界面、不用 Fable）写在全组织默认里，项目改不掉（Claude Code 组织管的设置同理）；改全组织默认＝改标准（人闸第四类）。
   - 引擎每次派活（副手、评审、验证）按要改的和改了的文件过滤：碰到页面代码就不给 GPT。不靠人挑对配置，所以「界面」标签不要了。
   - 驾驶舱派单页是它的编辑器：改了开 PR 自动合，仓里的文件是唯一的那份。单张单临时换配置、换本机或法国，在派单页或 `fleet` 命令改，记在这张单上，不改文件；所以「本机」标签也去掉（待拍）。标签只剩类别（人可改）和机器贴的状态（人闸、等你拍、卡住了、有冲突，只显示）。
   - 没有这份文件＝用全组织默认（驾驶舱标出来）；格式错＝编辑器、驾驶舱、CI 都拦；法国读不到或认不出＝这个项目停派、报红，不拿默认顶。每条配一条故意造出失败的测试。
3. **执行层**：Fusion 七步不变，领的单位从小单变成统领单。

和已拍规矩的冲突（定稿时照改标准走人闸第四类）：通用段「发现问题谁发现谁当场修、不开单」，本仓先后顺序第③条「创始人发现的问题能当场修完的当场修」、「发现问题当场修」（09-26 替掉「合并后的问题开单攒着」）、「只有两种事开单」。建议改成：上面「立刻做」那几种照旧当场修，其余开小单进统领单、按版本修。

依据：Shape Up 第 7 章 Bets, Not Backlogs（不攒大清单，每轮只挑几件）https://basecamp.com/shapeup/2.1-chapter-07 、第 8 章 The circuit breaker（做不完默认不延期）https://basecamp.com/shapeup/2.2-chapter-08 ；Linear Triage（新单先进收件箱再归入）https://linear.app/docs/triage ；GitHub 子单（每张母单最多 100 张、8 层，母单上看进度）https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues ；Renovate 共享配置 extends https://docs.renovatebot.com/config-presets/ ；Claude Code 设置分层（组织管的设置优先，组织定的可用模型表项目加不进）https://code.claude.com/docs/en/settings 。

### 插题（续）：创始人 09-26 晚第二轮——按 k8s 的思路再想

原话：「如果你真的要做收件箱，一定要做得特别好……如果它们南辕北辙，真的也要派成一个统领单吗？……小单未必不能做，也未必非要把小单整合在统领单里」「让统领单去派比较好……让 LEAD 高阶模型去分析指导、去拆解、去整合，顺便再去更新统领单的内容。这样能让低级模型首先看到他要负责哪一部分内容，又能看到整个全局的项目」「只要涉及到驾驶舱里面需要操作读取的东西，其实都是一些配置。这些配置就是要存在仓库里，随时变更的……还要能随时在页面上刷新读取」「多想想比如k8s的设计理念和设计思路，和其他产品的思路；再多思考一下对我们整体流程考虑」

创始人定的：

- 按统领单派活：主导模型分析、拆解、整合，并随时更新统领单正文；副手先看到自己负责哪块，也看得到全局。
- 小单可以单独做，不必都并进统领单；上一版「收件箱攒够几张归成统领单」撤回。
- 配置存在仓里、随时能改，页面上能刷新读取（形态待定）。

AI 第二版（按 k8s 的思路，待拍）：

- **框架**：所有东西都是对象，每个对象分「想要的」（人和主导模型写）和「实际的」（系统写）；一组对账程序各管一类对象，不停把实际的拉向想要的——事件来了马上对一次，漏了的定时补上，不靠抓全每个事件（k8s 设计原则的 level-based）。所有读写只走法国一个接口（第 6、7 题已定的四个入口）；规矩只放两个必经口：写进接口时的准入检查、派活时的调度。标签不驱动流程，只用来分类和显示。
- **小单**：收单时只做两件事——同一件事就并进已有的单；明显属于某张已开的统领单就挂上（第三轮改：只挂还没开工的，见「插题（再续）」）。其余单独派。主导模型规划统领单时，可以把同一块里没开工、没挂靠的小单收进来（k8s 的 ReplicaSet 收养没有主人、又匹配自己的 Pod）。没有收件箱，不凑数。
- **统领单**：GitHub 母单。正文上半是「想要的」（目标、怎么算做完、上限、全局图和接口、分工），只由主导模型写；下半是「实际的」（各块进度、花费、存档点），由系统写。子单是别人开的具体问题；主导模型拆出的块不开成单，免得单子爆炸。副手拿到自己那块、全局图、接口和只许改的文件（Cognition 的 Flappy Bird 反例：副手各做一半、各自猜，拼不起来）。统领单必须一个版本内做得完——「驾驶舱」「渠道」这类做不完的是领域，不是统领单；两张统领单要改同一批文件时不同时跑；创始人改了正文，主导模型收到后重排。
- **调度**：模型渠道像 k8s 的节点，额度像资源，禁令像污点（GPT 带「不碰页面」的污点，页面活派不到它那里），配置里的模型顺序是偏好，坏了的优先级最高、可以挤掉在跑的。
- **驾驶舱里的东西分四类**：规则（以后都这么跑：模型顺序、几套配置、禁令、测试命令、哪些路径算页面）放仓里 JSON，页面上改了开 PR 自动合，法国收到推送后重读、校验、存副本、推给页面，库里那份只是副本、谁都不直接改；指令（现在这么做：开关 AI、暂停、这张单换模型或换本机、先后）存法国库、马上生效；计划（版本、统领单、小单）在 GitHub；状态（谁在跑、进度、花费、出错）系统写，人只看。每次执行记下用的是哪一版配置。
- 依据：Kubernetes 设计原则（level-based、只有接口碰存储、声明式）https://github.com/kubernetes/design-proposals-archive/blob/main/architecture/principles.md ；API 约定的 spec 与 status https://github.com/kubernetes/community/blob/master/contributors/devel/sig-architecture/api-conventions.md ；污点与容忍 https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/ ；ReplicaSet 收养 https://kubernetes.io/docs/concepts/workloads/controllers/replicaset/ ；Argo CD 以 git 为准 https://argo-cd.readthedocs.io/en/stable/ ；Cognition「Don't Build Multi-Agents」https://cognition.com/blog/dont-build-multi-agents 。

### 插题（再续）：母单会不会永远关不掉——边界推演（创始人 09-26 晚第三轮）

原话：「母单里面不断塞子单，怎么处理呢？……假设最坏情况下，这个母单不就永远结束不了了？……你能不能把这些边界情况都帮我想清楚，自己把边界情况全都分析完毕之后，再给我结论呢？」「你好像把思考也当成做事情了……没有想着去验证一下这个思路」

创始人定的：母单和它的子单在一个里程碑（版本）里做完；k8s 的思路对。

AI 第三版（推演过边界、对照过案例、GPT 挑过一轮；待拍）。上一版「收单时明显属于某张已开的统领单就挂上」正是母单被无限塞子单的入口，改掉。三个保证：一定会停、没做完的有人管、等人等外部不卡死。

1. **按目标关**：开工时定好「怎么算做完」，别家模型验证达成就关，不要求子单全关。
2. **开工后范围冻结**：开工前新单可以自动挂上；规划时只收这一轮做得完的子单，其余当场摘下来单独放、标「相关：#母单」（进度条只反映这一轮）；开工后一律不自动挂，新的相关单只通知主导模型——只有「不修它，『怎么算做完』里某一条就过不了」的才换进来，写明理由、吃上限，验证模型会看。
3. **上限和熔断**：上限按额度和干活时长，先到先停，按大小给默认（实测后定）；到了就熔断：已合的保留（每个 PR 合进去都得让主线能用，半截功能先藏起来），没做完的挪走写去向，母单关成「部分完成」写清差什么。默认不延期；剩下的全是必须做、又没有未知时才延一次。同一目标熔断两次，不再自动排，交创始人定（换做法、缩目标或不做）。
4. **结束写去向**：每张开着的子单写去向（下个版本 / 单独排 / 不做了和理由）；AI 不重开关了的母单，同一起因再来就开新的、链接旧的；创始人手动重开算新一轮，重新规划、重算上限。
5. **改目标**：小改（说清楚点）主导模型直接吸收；大改（目标变了）当前这轮按熔断收尾，按新目标重新规划、重算上限，页面告诉创始人会推迟多久。
6. **等待不卡死**：等创始人拍、等额度恢复这类，只停那一块，写明等什么、谁在等、下次什么时候看；等待不耗上限，超过一天报创始人；版本里其余都结束、只剩等的，等的那块挪到下个版本，版本照样收尾。
7. **版本同理**：开始后范围冻结（AI 不往进行中的版本加非紧急的；创始人随时能加、能插队，见第四轮）；都结束 → 发布说明（做了、没做、挪去哪）→ 创始人拍发布 → 里程碑关，没做完的挪下个版本。创始人一直没拍发布：下个版本照常开工，每天提醒一次；下个版本发布时一起带上、两个里程碑一起关。坏了的（主线红、生产坏、数据、泄露、安全）走快修道，不进版本，发布照样要拍。
8. **不会忘**：每张开着的单都要答得出「谁在管、下一步是什么、什么时候再看」；未排期的统一由版本规划管。对账程序按状态查，答不上就报；开着的单挂在已关的母单下、留在已关的里程碑里 → 挪走并报。
9. **未排期不自动关**：每次版本规划全过一遍，每张写决定（排进 / 继续等和理由 / 不做了和理由）；等了 3 个版本还没排上的，在规划说明里单列给创始人。
10. **并行和依赖**：两张母单要改同一批文件不同时跑；母单之间有先后写明、按先后跑；前面那张熔断了，后面那张的主导模型重新判断能不能绕开。「驾驶舱」「渠道」这种做不完的是领域，只当分组看。

GPT 挑错（gpt-6-luna，有异议 5 条，全收）：等待外部没定义 → 第 6 条；「挡住目标」没判据 → 第 2 条的判据；创始人不拍发布版本会悬空 → 第 7 条；连续 3 个版本没排上就自动关会误杀 → 第 9 条改成单列给创始人；对账要看得出有没有人管 → 第 8 条。

依据：Shape Up 第 14 章 Decide When to Stop（范围会自然长；比基线不比理想；延期两条件）https://basecamp.com/shapeup/3.5-chapter-14 、第 8 章熔断 https://basecamp.com/shapeup/2.2-chapter-08 ；Scrum Guide（冲刺目标不变，范围可重新谈）https://scrumguides.org/scrum-guide.html ；Jira 发布版本时把没解决的挪到别的版本 https://confluence.atlassian.com/adminjiraserver/managing-versions-938847201.html ；Linear 没做完的自动滚到下个周期 https://linear.app/docs/use-cycles ；僵尸 Epic（不断加故事、截止日一直往后推；close the old, open the new）https://katanu.com/zombie-epics/ ；k8s Job 到 activeDeadlineSeconds 就终止、判失败 https://kubernetes.io/docs/concepts/workloads/controllers/job/ 。

### 插题（第四轮）：插队、母单谁开、盘面同步、帅位、流程核心进代码（创始人 09-26 晚）

原话：「应该是随时能加的，我也可以额外去强制塞入……有的东西确实比较急，如果排期的话，不知道排到什么时候了」「母单由谁去创建呢？盘面上的信息怎么才能实时同步给各个机器和各个仓库？本身正在进行的帅位的对话呢？」「核心的流程引擎……在我们的代码层面是不是也要有地方体现呢？……这些核心部件也要存在代码里呢？」（「帅位」按上下文理解成总指挥，即和创始人讨论的这个会话。）

创始人定的：进行中的版本随时能加东西，还能强制插队。

AI 第四版（推演过、对照过案例、GPT 挑错 5 条全收；待拍）：

1. **插队**：四档先后——急修（主线红、生产坏、数据、泄露、安全，只认看得见的证据，AI 不能凭感觉标急修）> 插队（只有创始人能点，AI 只能建议）> 本版（按拖动）> 未排期。有空位直接跑；满了就让最不急的那张在下一个存档点让位（最多等 10 分钟，超了按中途切换就地存档），让位的不耗上限、有空位自动续上；同一张活最多被让位 2 次，之后不再被挤；插队的和某张正在做的母单是同一块，交给那张的主导模型当最急的一块，上限自动加上这块的量；页面告诉创始人插这一张会让谁等多久。
2. **母单谁开**：创始人（直接开，或开的单本身就大）、开单第 0 步（生下来就大）、版本规划时 AI 把未排期里的单归成母单写进提案（创始人可改）、主导模型（小单做大了升成母单；熔断后把剩下的开成后续母单）；副手不开单。归成一张的条件是「能一起验收」，不是「起因一样」；主导模型规划时发现验收不同就拆。写进接口时检查：没有目标、怎么算做完、起因、大小的不收；能一起验收的只许一张开着（先查重复和相关，像 Linear Triage Intelligence）。
3. **盘面同步**：法国一处为准，各处按需取、订阅变化；断线回来比最后的同步号，补漏或整份重取（k8s list+watch、410 重列；Linear 同步引擎比 lastSyncId）。驾驶舱推送；法国上的会话开工时拿自己那一片，中途的变化在回合之间送进去；本机会话靠 Claude Code 钩子：开场注入「等你拍的、当前版本、最近的决定」，每一轮注入「和你有关的变化」（限 10 行），标准落后开场自动同步。仓库只收慢变化的：标准、配置、每个版本开始和结束各一份计划快照，不写实时状态。法国连不上：照最后快照干、标过期；攒下的写入回来后先对照最新状态重算，冲突的交人，不直接覆盖；快照过期的会话不许推 PR；钩子取不到要明说没取到。计划在 GitHub、规则在 git、库有备份，法国挂了只是降级。
4. **帅位（总指挥）**：只一个座位，用租约占，会话心跳续约，过期了别的会话才能接（k8s 控制面用 Lease 选主）；每次写入带租约代号，旧代号写不进（防两个都以为自己是总指挥）；第二个会话只能当工人：能开单，不能定规矩、排版本。它不写代码，只把对话变成盘面上的东西（母单、决定、版本提案）、处理等你拍、盯盘面。存档点是盘面不是聊天记录：崩了、上下文满了，新会话开场由钩子注入「等你拍的、在做的、刚定的」。等你拍是盘面上的一条，驾驶舱和飞书卡片能直接点选项，不会被别的消息刷掉；会话里的心跳定时任务挪到法国。
5. **流程核心进代码**：新建核心包（暂名 core）：对象和格式定义（驾驶舱编辑器、fleet 命令、CI、法国用同一份）、状态机（母单、版本、执行）、写入检查、派活（先过滤：禁令、额度、文件冲突；再打分：配置顺序、战绩——k8s 调度框架的 Filter / Score）、对账决策、规矩（禁令、人闸、上限），全是纯判断、不碰网络和库；引擎、后端、网页、fleet 命令、钩子都是外壳，调它判、自己去做。讨论出的每张边界表变成 core 的测试，一行一条，含故意造出失败的。规则搬进 core 的同一个 PR 里删掉外壳那份；design 里每条规则写编号，CI 查两边编号对得上。这是第 6、7 题「规矩和能力只写一份、四个入口用同一份代码」落到代码上的样子；engine/decisions、conventions 里的判断逐步搬进来。

GPT 挑错（有异议 5 条，全收）：抢占要防饿死 → 同一张最多让位 2 次、急修只认证据；租约防不了假活的会话 → 写入带租约代号；离线写入回来可能盖掉新决定 → 先重算、冲突交人、过期会话不许推 PR；起因一样不等于能一起交付 → 归并条件改成能一起验收；搬迁期外壳和 core 各写一份会漂 → 同一个 PR 搬一条删一条、规则编号两边对账。另提「法国是单点」：计划在 GitHub、规则在 git、库有备份，法国挂了只降级。

依据：k8s 优先级与抢占 https://kubernetes.io/docs/concepts/scheduling-eviction/pod-priority-preemption/ ；Lease 选主 https://kubernetes.io/docs/concepts/architecture/leases/ ；API 的 list+watch 与 410 重列 https://kubernetes.io/docs/reference/using-api/api-concepts/ ；调度框架 Filter / Score https://kubernetes.io/docs/concepts/scheduling-eviction/scheduling-framework/ ；Linear 同步引擎（逆向分析）https://github.com/wzhudev/reverse-linear-sync-engine ；Linear Triage Intelligence https://linear.app/docs/triage-intelligence ；Claude Code 钩子 https://code.claude.com/docs/en/hooks 。

### 第 4 题后半、第 5 题：讨论记录与分层看板（创始人 09-26 晚答了三问并补充）

原话：「大多情况下，我只会看并确认按计划走……如果我要插话，最大的场景其实是在我当前的"帅位会话"里面，而在驾驶舱，我一般只是看比较多」「电脑 > 手机 > 飞书。飞书主要用于跟团队伙伴讨论的场景，这样可以把讨论的内容记载下来……讨论其实也是一个流程，这个流程需要记载内容，需要有简报和全文帮助梳理和查看……每一个单子都要有这样一个记录，这样才能很清爽地看到整体的脉络走向」「仓库下面的层级是"里程碑"；"里程碑"下面才是母单或子单；母单下面还有"子单"的层级……母单和子单之间还要有一个关联关系进行展示」

创始人定的：驾驶舱以看为主（电脑 > 手机 > 飞书）；插话主要在帅位会话里；飞书用来和团队伙伴讨论、要记下来；每张单都要有讨论记录（简报 + 全文）；看板分层：项目 → 版本（里程碑）→ 母单或单独的小单 → 子单，要显示母单和子单的关系。

AI 方案（推演过、GPT 挑错 4 条全收；待拍）：

1. **每张单一份记录：简报 + 全文**。来源：帅位和创始人的对话、飞书群里和队友的讨论、模型之间的讨论（开单讨论、方案评审、验证）、引擎的事件。全文按时间存原话、可搜，编辑和撤回都留版本和时间，分清「更正」和「撤回」，不抹掉当时的依据。简报由便宜模型在有新内容时增量更新，限一屏，固定几栏：一句话现状、方向、已定、待定（等谁）、分歧、下一步；每条链回原文；逐层往上汇总（子单 → 母单 → 版本 → 项目，像 Linear 的项目更新和 Pulse）。一段对话涉及几张单就分段挂几张；归不了单的由帅位当天收尾时归，实在不属于任何单的进「帅位日志」。
2. **「已定」只认拍板记录**：简报里的「已定」只能来自一条拍板记录（谁拍的、有没有这个权、何时、原文链接），模型只能写成「讨论倾向」；人改过的行模型不覆盖，但来源变了会提示复核。拍了但单子正文（目标、怎么算做完）没跟上，对账就报。
3. **隐私**：全文和简报以法国库为准；公开仓的单上只放链接，私有仓可以把简报同步到单上；往外写都过卫生检查，查访问权限和内容范围；飞书群要告知在记录，只收挂了单的讨论群和机器人被 @ 的消息，无关闲聊不收。第 4 题前半定的「讨论记录写进单的评论、GitHub 为准」要改成这样（公开仓的单谁都看得到）。
4. **分层看板**：总览（只显示有事的项目：在跑、卡住、等你拍）→ 项目 → 版本（当前版本默认展开；未排期、历史版本折叠只显示个数；「急修道」单列在项目顶上；插队的在当前版本最上面）→ 母单 / 单独的小单 → 子单为主、块为辅（块是主导模型拆的活，母单在做时显示，做完收进历史）→ PR 和执行步骤在详情里。每个节点一行：白话状态、进度、正在干活的模型；点开右侧详情，最上面是简报。关系：包含用树，「相关」用虚线，「等它先做」用箭头，熔断后的后续母单链回原母单。子单的版本和母单不一致、GitHub 上嵌套超过两层、有人手动改了母单关系，对账都会改正或报。跨项目的子单两边都显示并标项目。手机上不用画布，用列表树加面包屑（项目 › v0.3 › 母单 #12 › 子单 #15）。先做当前项目和等你拍的视图，用顺了再加多层关系。
5. **插话（第 4 题后半）**：主要走帅位对话。帅位把创始人的拍板写成拍板记录（留痕），再经接口给主导模型发信号、或在单上发起讨论；页面显示信号「已送达 / 已生效」，主导模型在跑长任务、帅位离线或送达失败都标出来，驾驶舱留少量按钮兜底（停、换模型、发起讨论）。主导模型没底时也能在上限内自己拉别家讨论，讨论都挂在单上、进全文。

GPT 挑错（有异议 4 条，全收）：撤回、编辑会抹掉当时依据 → 留版本、分清更正和撤回；「已定」可能是模型误写 → 只认拍板记录、人改的行来源变了提示复核；全文可能泄露队友隐私 → 只收挂单的讨论群和 @ 机器人的消息、往外写查权限和范围；信号可能没送达或没生效 → 显示送达和生效状态、驾驶舱按钮兜底。

### 第六轮：看板定调、记录补全、插话找主导模型、讨论能接着聊（创始人 09-26 晚）

原话：「没错，我理解的就是这个。这个东西关联度很高，要以这一套为方式去设计我们整体驾驶舱的每一个模块」「简报和全文在刚开始时，很有可能某一块会有缺失。所以需要有方式让 AI 去补全……这些简报和全文其实是存在 GitHub Issues 里面的……要补齐这些信息，能随时去预览，并且能很快在页面上通过数据库去查看」「用户随时插话是和主脑 LEAD 去对话」「对于不确定的地方，你可以找其他模型去互相讨论，直到讨论出结果，而不是说问完一轮讨论就弃掉了。我觉得会话可以随时拉起来继续聊、继续改」

创始人定的：

- 驾驶舱首页那张画布按「项目 → 版本 → 母单或单独的小单 → 子单」分层，驾驶舱其余模块都以这套层级为骨架来设计。
- 简报、全文缺了，AI 有按钮补，先预览再存；页面从库里快速看。简报和全文放 GitHub Issues（AI 提的两处限制待拍：公开仓的单谁都看得到；单条正文和评论最多 65536 字）。
- 用户随时能插话，插话的对象是这张单的主导模型。
- 讨论改成能随时接着聊的会话：不确定的地方和别家模型来回讨论，直到有结果，不是问一轮就放下。
- UI 大改（设计 token、每页加载、空、出错重试、刷新）排期靠后，单是 #182。

AI 补充（待拍，细节随「整条流程串起来」的结果一起给）：全文只能从已有的材料里收（单子正文、评论、PR、需求文档、会话记录），收不到的标「缺」，不许编；简报可以生成草稿，标「AI 补的、待确认」。插话：单内的事找这张单的主导模型（副手从不直接收人的话），跨单的事（先后、版本、规矩）找帅位；主导模型是长开的会话，插的话排队、在两步之间处理，「停」可以立刻打断（Claude Agent SDK 的 streaming input）。讨论会话：codex 能 `exec resume`、cursor-agent 能 `--resume`，同一场讨论的参与方保留各自的会话，随时接着聊；停在「收敛」或「分歧定型、写清各方理由和推荐、交给该拍的人」，另设轮数和额度上限。

### 整条流程串起来的检查（09-26 晚，子代理和 GPT 两条线各讨论 5 轮）

收敛的要点：
- **帅位合一**：design 第十二节和代码里的「AI 帅位」（法国定时值班会话）和本机总指挥是同一个座位、两种占座者；版本规划由引擎触发、谁在座谁做，本机关机法国接座。写入带围栏号和幂等键，续租由处理消息的长轮询自己做（假活续不上）；帅位空闲时靠后台长轮询「有消息就退出」唤醒。
- **版本**：有预算（并发槽位 × 主导模型额度预测，留两成给急修和插队），超了告诉创始人会推迟多久，到上限做完的发布、剩下的滚到下个版本；未发布的版本积压到 2 个就不开新版本。

- **半截功能**：先「最后才接入口」（Fowler 的 KeystoneInterface），做不到才用配置里的开关；开关登记属于哪张母单，打开给用户用的开关算发布。
- **执行**：座位长开、会话在存档点按上下文用量滚动换新；母单按块循环（副手干、主导验收、这块验证、PR、CI 最多 3 轮），所有块完成后做一次母单级验证；只有存档点由主导模型写，简报和母单正文下半从它生成。
- **防机器给自己派活**：只有带证据的急修能自动开单；验证的建议每张母单最多并成 1 张后续单。空位时只做本版能并行的块、下个版本候选母单的只读准备、第二意见和考新模型，不碰未排期。

- **讨论停止条件**：收敛；分歧定型（主张没变、证据没新增、小模型也判没有新论据）；到上限。拉起要写明能改变结论的新证据。
- **往外写**：AI 往外写的（母单正文、简报、发给别家模型的题面、本机 AI 用 gh）都调法国同一个检查；人手写的只能事后扫到、折叠并提醒。流程配置带格式版本号，引擎认当前和上一版。里程碑可空，空就是未排期。
