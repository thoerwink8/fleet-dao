### 第 2 题：一张单分几步、每步谁做（创始人 2026-09-26 拍：「你现在说的我挺赞同的」，即选 1）

Fusion 模式七步；每步结束主导模型存一个存档点：

| 步 | 做什么 | 谁做 |
|---|---|---|
| 1 收单 | GitHub 上的单进来，建任务、排队 | 引擎，不用模型 |
| 2 规划 | 读单和相关代码，判大小；写方案：范围、做法、改哪些文件、怎么算做完，拆成几份任务简报；说不清就问创始人 | 主导模型（查代码可以派副手） |
| 3 方案评审 | 方案发给 1–2 家别的模型挑错，1 分钟内；主导模型逐条写明收还是驳、为什么 | 别家模型；小单跳过 |
| 4 执行 | 按简报派活，副手交回改动和测试结果，主导模型验收：收下、打回（最多 2 次）或自己接手 | 副手干，主导模型验收 |
| 5 验证 | 对照「怎么算做完」和方案核整个改动 | 验证模型（别家的） |
| 6 开 PR、过 CI | 引擎推分支、开 PR（正文写做了什么、怎么验证、评审和验证的结论）；CI 没过交回主导模型派副手改，最多 3 轮 | 引擎 + 主导、副手 |
| 7 合并、关单 | CI 全过自动合；碰人闸四类的等创始人拍；关单留一条结果：改了什么、用时、各模型花的额度 | 引擎 |

- **多个副手同时干**（创始人提、同意）：拆得开才同时派，由主导模型判断；先定接口和「谁改哪些文件」，每个副手只改分给自己的文件、在自己的工作副本里干，要动别人的文件就回报主导模型改派；主导模型逐个合进来、每合一个跑一遍测试；副手定时交进度，主导模型可叫停、改派、补一句指示再续上（没法在它干到一半时插话）；一张单最多 3 个副手同时干；小单或拆不开的照旧一个副手。几个副手可以各用不同的订阅。
- **验证五条**（防止重现「合并后补审一条接一条」）：①在合并前、同一张单里改完，不开新 PR、不补审；②只对照清单核：「怎么算做完」和方案逐条答做到 / 没做到 / 看不出，带证据；③只有三种能挡：没做到验收条、有证据弄坏了原有功能、安全或丢数据，其余只作建议写进 PR；④默认 1 轮、最多 2 轮，主导模型可以拿证据驳回并记下；⑤统计挑出的真问题占几成，误报多就调问法或对低风险的单关掉。
- **单模型模式**：第 2、4 步同一个模型做完；第 3 步默认关；第 5 步只对高风险的开。
- 「创单时就讨论」（创始人同轮提出）在第 4 题一并定。

### 第 4 题前半：创单时就讨论（创始人 2026-09-26 提出，同意）

- 流程最前面加一步「0 创单并讨论」：不管人开还是 AI 开的单，开单时就让几家模型讨论一轮；讨论记录写进单的评论（GitHub 为准，驾驶舱展示），主导模型规划前先读它。第 2 题的「方案评审」成了它的后半段：主导模型的方案和讨论结论一致就不再评。
- 讨论的配置在驾驶舱调：哪几家、几轮、每家多少字、想多深、超时、同时几家；项目有默认，单条可临时改（design 第九节「讨论」阶段的配置）。按大小分档：小单 1 家 1 轮或跳过，大单 2–3 家先各自独立答、再互相挑错；开单的人可以手动指定。
- 每次讨论最后一行写「结论 + 谁拍的」，没结论的挂「待拍板」。驾驶舱显示每次讨论花了多少额度。
- 发给别家模型的内容要过敏感信息检查；私有项目按项目设「哪些渠道能看代码」。
- 「流程中途随时拉别家讨论」留在第 4 题后半，和第 5 题一起定。

### 第 6、7 题（合并）：骨架能力——驾驶舱之外也有同样的规矩和能力（创始人 2026-09-26 拍：选 1）

- 规矩和能力（开单、讨论、评审、验证、交给 fleet、查状态、问模型、记决定）只写一份，在仓里；四个入口用同一份代码、读同一份配置：驾驶舱（网页）；`fleet` 命令（像 gh 一样单独装，本机任何仓都能用，不用 fleet-dao 仓常驻）；各家 AI 的技能和工具（同步脚本装到每台机器）；引擎收单时补齐（GitHub 网页上直接开的单，收单时发现缺讨论、缺标签就自动补）。
- 本机 `fleet` 命令调法国的接口：讨论和记录在法国完成，驾驶舱马上看得到，钥匙只放法国一处；法国连不上才用本机渠道兜底，标「待补齐」，联网后由引擎补上，不许假装讨论过。命令每次对一下版本，旧了提示更新（和 #132 标准体检同一件事）。
- **适用于驾驶舱管的所有项目，不只 fleet-dao**（创始人原话：「不然人会遗忘，代码也会有遗忘，AI 也会遗忘」）：规矩长在每个项目都必经的那一步上，不靠谁记得。落实：①所有项目的单和 PR 的事件都经 GitHub App 到法国后端，后端收到就按「对账表」查这一个对象：该有的讨论、标签、里程碑、检查在不在，能自动补的当场补（结构化的用代码判，要读文字的用 Jev），补不了的挂出来等人；②标签的含义写成标准里的数据，标签一出现、一变（或该有却没有）就触发对应做法（比如「要人拍」停派活；「界面」「本机」同日晚改掉，见下面「插题」）；③事件触发为主，定时全量扫只兜底漏掉的事件，不当主力；④每条规矩配一个自动检查和一条故意造出失败的测试；⑤各项目、各机器对标准的版本，落后了报出来、开补齐 PR（改标准仍走人闸第四类）。和 design 15.7「项目与标准」、对账表是同一套，实施时并进来。

### 第 3 题：换模型接手（创始人 2026-09-26 拍：同意在存档点换，中途也允许换、自担后果；新模型自己读上一个会话）

- **在存档点换**：主导模型每走完一步存一个存档点，存档点连着一个 git 提交和一段写明白的进度（做到哪、定了什么、为什么、试过什么、卡在哪）。像游戏读档：可以换模型从当前存档点接着做，也可以读回更早的存档点重来（在新分支上读回，原来的记录保留）。
- **中途也能换，自担后果**：一步做到一半要换时，引擎先把工作副本里没提交的改动提交成一个临时提交，再从这个会话的记录自动写一个存档点，然后换；记录里标「中途切换」。
- **新模型自己读上一个会话**（创始人提，同意；比只读任务简报好）：引擎把每个会话的完整记录（说的话、调了什么工具、工具回了什么）按统一格式存下来，Claude Code 的会话记录和其他命令行工具的输出都收进来。新会话先读存档点入门，再按需翻上一个会话的完整记录和改动，自己分析，不一次全塞进上下文（太长太贵）。
- **「思考」要写出来**：模型内部的思考过程多半没存下、也带不到别家模型，所以规定每个模型把关键的想法（为什么这么做、试过什么、卡在哪）写进会话里或存档点，下一个模型才读得到。
- **谁来换**：引擎自动换（额度不够、连着失败两次、渠道下线），创始人在驾驶舱手动换，主导模型给每份任务简报挑副手模型；主导模型换同一家的模型时接着原会话做，换别家时从存档点重开。每次换都记一笔，驾驶舱看得到。

### 标签更正（创始人 2026-09-26）

> 同日晚创始人改方向：「界面」标签不要了；「本机」建议也改成派单时的选项（待拍）。见下面「插题」。

- 「本机」不是「只能本机做」：本机和法国随时能切。在 GitHub 上改标签或在驾驶舱里改，就切到本机做、切到法国做、或者先不做；两边改的是同一份数据。
- 「界面」的意思：这张单是改页面长什么样的活。按全局规矩「GPT 系不做界面类的活（包括审界面）」，带「界面」的单派副手、挑错、验证都不用 GPT。

### 插题：版本、统领单、流程配置（创始人 2026-09-26 晚提方向；AI 整合方案待拍）

原话：「根本不需要"页面"这个标签。其实只需要在 Fusion 的派单页面流程中，去选择每个流程推荐的模型顺序……并且可以支持多套配置。……需要有一个类似于 JSON 的方式，可以自由地编辑和改造这个文件，然后在服务器端和代码端都能拿到这个文件」「大单确实是需要的，关键是要有里程碑的概念。每一个版本应该只做一些事情，一些问题要攒在大单里面一起修复」「问题可以去开 Issue，开完的 Issue 要放在大单里面。大单其实就是……"统领单"的概念」「一个好的机制应该是：……问题还少的时候，就不去做这个」

创始人定的方向：

- 不要「界面」标签。每一步用哪些模型、按什么顺序，在派单页上选，存成一份能自由改的 JSON 配置，可以有多套；法国和代码两边读同一份。
- 要统领单（借自旧仓 windsurf-dao：同一起因只一张统领单，新单先查起因再挂上去）：小单挂进统领单，攒着一起修；做成机制、不靠手工，单少时不整理。
- 里程碑＝版本：每个版本只做几件事。

AI 整合方案（待拍）——三层，各管一件事：

1. **计划层（做什么、先后）**：版本（里程碑）→ 统领单（GitHub 母单）→ 小单（子单）。
   - 第 0 步讨论时按起因把新单自动挂到已有统领单下；挂不上的进收件箱（没有母单的单）。
   - 收件箱攒到 5 张、或一个版本做完时，AI 才把收件箱归成统领单、定下个版本做哪几张（照现有先后规则定、告诉创始人，驾驶舱可拖动改）；单少就什么都不做，不另起定时任务。
   - 派活的单位是统领单：一个主导模型会话领一整张，拆成几个 PR；小单随修它的 PR 合并自动关；子单全关后，验证模型核统领单自己的「怎么算做完」再关；版本里的统领单全关 → 发布（人闸）→ 里程碑关。这些由引擎按事件做，不指望 GitHub 自己关。
   - 统领单有上限（Shape Up 的熔断）：超了先合做完的，剩下的连同统领单挪出这个版本，等下次排。
   - 不等版本、立刻做的：坏了的（主线红、生产坏、数据、泄露、安全）、挡住当前版本的、正在做的统领单范围内的、创始人说「现在修」的。
   - plan.md「现在的目标」＝当前版本的统领单和先后。现有 P0–P6 里程碑改成版本；旧单挂到约 5 张统领单下（各自的「怎么算做完」保留），Fusion 后用不上的关单写去向。
2. **配置层（用谁、怎么跑）**：每个项目仓里一份流程配置 JSON。
   - 写几套配置（如「默认」「省额度」），每套写每一步的模型顺序（前一个没额度、连不上自动换下一个）、讨论和评审找几家几轮、验证几轮；再写测试命令、会话内存、高风险路径、哪些路径是页面代码、各类别默认用哪套。
   - fleet-dao 放一份全组织默认，项目只写和默认不同的（Renovate 的 extends）；禁令（GPT 不做界面、不用 Fable）写在全组织默认里，项目改不掉（Claude Code 组织管的设置同理）；改全组织默认＝改标准（人闸第四类）。
   - 引擎每次派活（副手、评审、验证）按要改的和改了的文件过滤：碰到页面代码就不给 GPT。不靠人挑对配置，所以「界面」标签不要了。
   - 驾驶舱派单页是它的编辑器：改了开 PR 自动合，仓里的文件是唯一的那份。单张单临时换配置、换本机或法国，在派单页或 `fleet` 命令改，记在这张单上，不改文件；所以「本机」标签也去掉（待拍）。标签只剩类别（人可改）和机器贴的状态（人闸、等你拍、卡住了、有冲突，只显示）。
   - 没有这份文件＝用全组织默认（驾驶舱标出来）；格式错＝编辑器、驾驶舱、CI 都拦；法国读不到或认不出＝这个项目停派、报红，不拿默认顶。每条配一条故意造出失败的测试。
3. **执行层**：Fusion 七步不变，领的单位从小单变成统领单。

和已拍规矩的冲突（定稿时照改标准走人闸第四类）：通用段「发现问题谁发现谁当场修、不开单」，本仓先后顺序第③条「创始人发现的问题能当场修完的当场修」、「发现问题当场修」（09-26 替掉「合并后的问题开单攒着」）、「只有两种事开单」。建议改成：上面「立刻做」那几种照旧当场修，其余开小单进统领单、按版本修。

依据：Shape Up 第 7 章 Bets, Not Backlogs（不攒大清单，每轮只挑几件）https://basecamp.com/shapeup/2.1-chapter-07 、第 8 章 The circuit breaker（做不完默认不延期）https://basecamp.com/shapeup/2.2-chapter-08 ；Linear Triage（新单先进收件箱再归入）https://linear.app/docs/triage ；GitHub 子单（每张母单最多 100 张、8 层，母单上看进度）https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues ；Renovate 共享配置 extends https://docs.renovatebot.com/config-presets/ ；Claude Code 设置分层（组织管的设置优先，组织定的可用模型表项目加不进）https://code.claude.com/docs/en/settings 。
