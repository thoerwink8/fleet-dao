# 结果（#88）

## 原因

不是 CI 机器慢，是用例的剧本和子任务的先后在赛跑。

- 用例要挂住 form 的第一个写码会话，条件写的是 `input.subtaskKey === 'form' && n === 1`；假世界（`packages/engine/src/fakes.ts`）给剧本的 n 是「这个阶段第几次起会话」，所有子任务一起数。
- form 和 readme 互不相干、同时开工，谁的写码会话先起不一定。平常 form 先起、拿到 1；readme 先起时 1 被它拿走，form 那次是 2，没挂住，整条需求照常跑完，用例却一直在等「form 的写码会话挂着」，20 秒到点报错。
- CI 上翻到 5 次，都是这一句：运行 36187873146 第 1 次尝试、36194311338 第 1 和第 2 次尝试（#85）、36199735435 第 1 次尝试、36203357350（主线推送）。用时都是 20.4–20.6 秒（等满上限）。机器那会儿并不慢：以 36194311338 第 1 次尝试为例，同一个文件里其余 13 条用例都是 0.7–1.9 秒；这条过的时候也只要 2.1–2.4 秒，20 秒的上限留了近十倍的余量。
- 本机钉住 readme 先起，原来的条件每次都报 CI 上那一句。

## 改了什么

- 假世界给会话剧本多给一个 own：这个子任务自己这个阶段第几次起会话。n 的说明写明所有子任务一起数、要挑某个子任务的第几次看 own。用例改看 own。
- 用例拆成两条：form 先起、readme 先起，各自钉死先后（后起的那个起会话的活动，等先起的那个记下了再起；readme 的会话等 form 的起了才往下走，最后比时间段靠这个）。readme 先起那条就是这次的失败；以后谁再按 n 挑会话，它当场红。
- 不靠真实等待：假世界加 `until`，每有一次端口调用开始或结束、会话开始看守、放行，就当场重查条件，不按 50 毫秒轮询；到点等不到报错、写明在等什么。这条用例里等 form 挂着、等 readme 合并（看写进库的状态）、钉先后都换成它。
- 假世界自己的测试 `packages/engine/test/fakes.test.ts`：n 和 own 各怎么数；钟停着（假计时器）`until` 照样等得到，换成轮询的写法这条就红；等不到到点报错；条件抛错（包括抛空值）原样报出，不当成等到了。

## 怎么验证的

- 把用例的条件换回 `n === 1`：form 先起那条过，readme 先起那条每次报「等了 20000 毫秒还没等到：form 的写码会话挂着」。换回 own，两条都过。
- 本机：两条各连跑 20 遍（`vitest --repeats 19`），跑了 5 轮，其中 3 轮同时起，共各 100 遍全过；engine 包全部测试跑一遍，全过。
- CI：本 PR（#202）草稿时加过一个临时提交让两条各连跑 20 遍（合并前撤掉），运行 36268766150 的 test (engine) 里两条都是 20 遍全过，和 engine 其余测试同时跑。
