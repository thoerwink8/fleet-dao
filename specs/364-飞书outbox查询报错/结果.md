# 结果：飞书 outbox 联查反复报错回 500（#364）

## 真正的根因

不是仓名字段大小写（`repos.owner`/`repos.name` 进库都是 `text`，join 走 `repos.id = tasks.repo_id` 都是 `uuid`，schema 一致），也不是发布重启那几秒。

抓 #391/#361/#415 这条链时发现：09-27 晚那次「`Failed query: select ... inner join "repos" on ...`反复 4 小时」是**发布迁移自己等不到锁、被 systemd 的 `TimeoutSec` 就地杀掉**。迁移会话本人没设锁超时（`packages/db/src/bin/migrate.ts` 连的是主库，不像应用走的 `withStatementTimeout` 那条），`ALTER TABLE` 撞上了 fleet-api 里一条还在跑的长事务（飞书 outbox 长轮询本身），等 4 个钟头；systemd 杀它的时候 postgres.js 抛 `X PostgreSQL-backend-error: session terminated`（不带 SQLSTATE），之前日志只看到「Failed query」壳子，看不出是这个。

证据链：
- 09-27 15:27 UTC 前后法国跑了 8 次发布（977 个迁移之后是 #320 的 0017，同一分钟 2 分钟前还跑了 b34bcb）；
- 19:28–23:24 连续报错 4 小时，task id 列表从 3 个涨到 6 个不退；
- `feishu-routes.ts` 那时还只把 `57014`/`55P03` 当锁错，`session terminated` 一路冒到全局 `errorHandler` 回 500；
- 第二天起这类错不再出现（迁移会话被杀之后锁自然放开），直到后面再有别的人为改动。

## 修法

联表逻辑本身没错——sanity 测试（Owner/Name 大写）钉住 200，防止「修锁」过程把它打松。

把「等锁」的三种样子统一成 `TableLockedError`（pg-store.ts 的 `isLockWaitError`）：
1. Postgres 自己的两种锁超时（`57014` 语句超时、`55P03` 等锁超时）：原来就认；
2. 迁移被发布超时就地杀掉时的 `session terminated` / `connection terminated`（postgres.js 的致命错，`X PostgreSQL-backend-error` 前缀）：这次加上。

`feishu-routes.ts` 的 `outbox` 长轮询看到这三种都是「再等一下」，重试到 deadline 才回 503 `outbox_locked`，不再是冒到全局错误处理回 500。

测试：
- `health.test.ts`「等锁的三种样子都认得出来」：钉住 `isLockWaitError` 不误判（syntax error、duplicate key、普通 Error、null），认得出三种等锁（带 SQLSTATE 的两种、postgres.js 致命错的两种措辞）。
- `feishu-routes.test.ts`「联查的仓带大写的 owner、name…」：健康数据走通联表、回 200 不是 500——挡住「修分类时把真 join 弄断」这一类意外。

## 还欠什么

- 真根上那条「迁移会话不设锁超时、等 4 小时」是**发布侧**的事：#372 的「自动发布不用人跑 france.sh」里要改的是迁移也要带锁超时、或发布期把 outbox 长轮询的等待压短（等锁的两种形态统一认出来之后，这台出锁错的现象从「反复 500」变成「重试到 503」，不再无声）。这单只把 API 这边的认错修好。
- #364 原本只防 SQLSTATE 那两种；session terminated 这种（09-27 晚真正的形态）当时就已经走不到 `TableLockedError`，只是之前没人往日志里看到底。如果之后再撞上 systemd 杀迁移的错，现在会走到 503 + 日志里带原因，而不是 500。

## 出 200 的接口

`GET /api/feishu/outbox`：owner/name 带大写时联表走通、返回 200（之前那次事故并没有复现成 SQL 层错，现象这层清掉）。
