# 飞书 outbox 轮询：task/repos 联表查询反复报错，回 500（不影响 GitHub 事件）（#364）

对应计划：未排期
设计依据：docs/design.md 第 15.4 节「飞书」——outbox 轮询是这一节里飞书消息外发的既有机制，这单只是它反复报错，不改设计。

查 #293（GitHub 对账补漏一直 partial）时，在法国 fleet-api 的 journalctl 里顺带看到一个不相关但确实在反复出错的另一条链：`GET /api/feishu/outbox` 这个接口，`taskInfos`（`packages/api/src/pg-store.ts`）联查 `tasks` 和 `repos` 的那条 SQL 反复抛错，被 Hono 的全局 `errorHandler` 接住、回 500（"未处理的错误"），不影响 GitHub 事件、不会让进程崩，但飞书那几条待发的提问/通知看起来一直发不出去。

## 查到这里、没往下查的部分
- 只在法国日志里看到这条反复出现，没登录库看这 6 个 task id 对应的 `asks`/`notifications`/`tasks`/`repos` 行长什么样，没确认是不是同一个原因。
- `taskInfos` 是 inner join，正常情况下某个 task 被删或 repo 没了只会让那一行在结果里消失，不会让整条查询抛错——所以「引用了已删的 task」这个最直觉的猜测大概率不对，得有人实际连库看这几个 id 才知道是什么错（约束、类型、连接问题都有可能，我没验证）。
- 没确认是每次轮询都失败（100%）还是偶尔失败：只搜了 error 级别日志，没有对照成功的请求量。
- 不影响本次 #293 的修复范围（GitHub 事件对账），只是顺手记一笔，没有当场修。

## 09-27 后续排查（fleet-api 平滑重启这张单顺带接手，没有法国库的直连权限，没能查到根因）

**两个「重启造成」的猜测都不成立**：上面的现象是 19:28 到 23:24 连续报了快 4 个小时（task id 列表单调变长，3→4→5→6，从没缩回去过）。发布重启的空档、迁移跑 DDL 锁表，都是几秒到几十秒量级的事，撑不出 4 小时连续报错——如果真是这两种，报错应该是一阵一阵的（发布那一下报几次就停了），不会连续 4 小时不断。id 列表只涨不消也说明：一旦这条链开始报错，当时在等待区间里的 ask/notification 就再也没被成功送出过（`syncOutbox`/送达确认都要先过 `pendingBatch()` 这一步），所以每一轮新出现的待发项都会叠加进 `IN (...)` 列表——这更像「查询从某一刻起持续失败，直到我们观察窗口结束」，不像间歇性的锁等待。

**顺带找到一个让这单一直查不出来的真原因**：`http.ts` 的全局错误处理把「未处理的错误」记日志时写的是 `String(err.stack ?? err)`；drizzle 把驱动的错包成「Failed query: …」，真正的 SQLSTATE、驱动原话都挂在 `err.cause` 上（`pg-store.ts` 的 `sqlState()` 就是这么读的），但 `Error.prototype.stack` **不会**自动带上 `cause` 链（只有 `console.error`/`util.inspect` 才认，`String(err.stack)` 不认——已经用 `node -e` 验证过）。上面贴的那段 journalctl 原文正是如此：只有外层「Failed query: select …」和四行调用栈，没有一个字提到底层驱动错误是什么、SQLSTATE 是几——不是 Postgres 没报，是日志这行代码把它吞了。这个 PR 把 `errorHandler` 改成打完整 cause 链（`http.ts` 新增 `fullStack()`），下次再报这条错，journalctl 里就能看到真正的驱动错误和 SQLSTATE 了。

**这个 PR 顺带修的、但不确定是不是本单根因的部分**：
- `pg-store.ts` 的 `listOutboxSources` 把 57014（语句超时）、55P03（等锁超时）分类成 `TableLockedError`，`feishu-routes.ts` 的 outbox 长轮询遇到它当「再等一下」重试，重试到 deadline 还没成功才回 503（不再是无分类的 500）。如果本单的根因真是某种锁等待（哪怕不是发布重启触发的，比如别的长事务、卡住的迁移进程），这个改动会让现象从「反复 500、日志看不出原因」变成「503 outbox_locked、日志里有 sqlstate」，但**不会让锁本身消失**——如果生产上现在还有东西一直占着 `tasks`/`repos` 的锁，这仍然是个需要有人连库查 `pg_locks`/`pg_stat_activity` 的活性问题。
- main.ts 收到 SIGTERM 时先通知这条长轮询别再查库（`deps.shutdownSignal`）：修的是「重启那几秒」这个确实存在但持续时间短得多的问题，跟上面 4 小时那次大概率不是同一次事故。

## 怎么算做完
- 连库看这几个 task id（或复现时新出现的 id）在 `tasks`/`repos`/`asks`/`notifications` 里的实际状态，或者等下一次复现、就着新日志（这个 PR 合并后日志会带 cause 链和 sqlstate）直接定位，找到 `taskInfos` 这条 join 真正持续报错快 4 小时的原因（不是靠猜）——顺手看一眼法国这台机器现在的 `pg_locks`/`pg_stat_activity` 里有没有长时间占着 `tasks`/`repos` 锁或者卡住的迁移/事务，如果有，这是要立刻处理的活性问题，不只是等下次复现。
- 按查到的原因修：如果是数据问题（脏数据、约束冲突）就修数据来源或加防御性处理；如果是查询本身的 bug 就改查询；如果是某个长事务/卡住的迁移占着锁不放，修那个事务/迁移本身。
- 配一条复现这个失败场景的测试。
- `specs/<本单号>-飞书outbox查询报错/结果.md` 写清楚原因和修法。

## 现状

部分排查：「重启/迁移瞬时锁表」两个猜测已经用 09-27 的时间线证据排除；顺带发现并修了挡住诊断的日志 bug（cause 链被吞）、把这条链的失败模式从无分类 500 改成了分类清楚的重试/503。真正让查询报错快 4 小时的根因还没查到——需要连法国库看当时的具体数据/连接状态，这个环境里查不了，留给能连库的人接着查。
