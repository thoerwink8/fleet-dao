# 方案：飞书 outbox 联查报错——不改 SQL，把写过头的根因改回来，非锁错误的正文带上 sqlstate（#364）

需求见同目录 `需求.md`。#407 已经做完的不动：`http.ts` 的 `fullStack`（日志打出 cause 链）、57014/55P03 收成 `TableLockedError`、outbox 长轮询遇锁就重试、到点回 503、停机信号来了不再查库。

## 查到的

链是这样：引擎写 `asks` / `notifications`（带 `task_id`）→ 飞书网关 `GET /api/feishu/outbox` → `pendingBatch` → `listOutboxSources` → `taskInfos` 一条 `tasks inner join repos`。网关把 5xx 当成这一轮没走通，退避重试；连续 5 分钟没走通会自己往团队群报警（`packages/feishu/src/watch.ts`），报警正文来自接口返回的那句话，不是法国 journal 里的栈。

09-27 日志里的 `Failed query:` 是 drizzle 的 `DrizzleQueryError`：只包「驱动执行这条 SQL」抛出来的错，`cause` 上才有 SQLSTATE。行映射在这层外面，映射失败不会长这样。`task` 被删、join 少一行，也不会长这样——少一行之后代码另抛「追问 … 的需求 … 读不到」，那是另一句。

本机用 PostgreSQL 16.15 + postgres.js 3.4.9（和仓里锁的驱动同一版）跑了日志里那条 SQL：6 个合法 uuid、inner join，6 行都回来了；删掉其中一个 task，变成 5 行，不抛错。所以不是「这条 SQL 在干净库上必失败」，也不是「引用了已删的 task 整句就炸」。法国库和 journal 这个环境读不到，那 4 小时的 SQLSTATE 仍然没有。不编一个。

另外两处不能当成已经坐实的根因：

- 发布重启、迁移锁表是秒级的。#407 把这两种收成「再等一下」是对的，但注释里写「4 小时那次的根因就是它」超出了证据。
- `OUTBOX_LOOKBACK_MS` 是 15 天。答过的追问、处理过的通知在这 15 天里仍会进 `IN (...)`。4 小时里 id 从 3 个涨到 6 个，只说明窗口里多了几条，不能证明中间一次都没查成。需求里写的「只搜了 error、没对成功量」仍然成立。

## 不这么做

- 不改 `taskInfos` 的 SQL，不改成按 id 拆开、失败的跳过。没看到是哪一种 SQLSTATE 之前，跳过会把「没查成」变成「这几条不用发」。锁、缺列、断连拆开也是全失败，还会把一次超时乘成好几次。
- 不改 `asks` 的对账查询（`packages/db/src/queries/asks.ts` 的 `askIssueCandidates`，同一组列）。日志里没看到它失败；SQL 形状在干净库上能跑。它不在这张单里动。
- 不改 `http.ts`。cause 链 #407 已经在打。
- 不连法国库、不写生产 task id、不在仓里写地址或连接串。

## 改哪些文件

1. `packages/api/src/pg-store.ts`

   把 `listOutboxSources` 里那段「认 57014 / 55P03」提成纯函数 `classifyOutboxQueryError(err)`，`listOutboxSources` 的 catch 只调用它再抛出。判法和现在一样，多一种出口：

   - 已经是 `TableLockedError`：原样返回。
   - `sqlState` 是 `57014` 或 `55P03`：仍是 `TableLockedError`，正文里带 sqlstate（现有那句可以留）。
   - 有别的 sqlstate：`new Error('outbox 联查 tasks/repos 失败（sqlstate <码>）', { cause: err })`。码写在第一句，原错误留在 `cause`，`fullStack` 和 `sqlState` 都还读得到。不要改成 `TableLockedError`，也不要吞掉。
   - 没有 sqlstate（包括「追问的需求读不到」）：原样返回。

   函数上面用两三句写明：锁超时只说明「这几秒表锁着」，不是 09-27 那 4 小时已经对上的原因；非锁错误把 sqlstate 放到第一句，是因为网关报警和 `String(err)` 看不到 `cause`。

2. 注释改口，行为不变（锁了照样重试，到点照样 503，停机照样不再查库）：

   - `packages/api/src/feishu-routes.ts`：outbox 处理函数里那两段（停机、表锁）。停机查到正在关的库、以及 57014/55P03，都是要单独处理的短失败。不要写「#364 反复 500 的根因就是这个」。
   - `packages/api/src/ports.ts`：`listOutboxSources` 和 `TableLockedError` 的注释。锁超时是这类错的含义，不是那 4 小时的结论。
   - `packages/api/src/pg-store.ts`：`listOutboxSources` 上面现有那句「发布跑迁移时表被锁住」同样改口。
   - `packages/api/test/feishu-routes.test.ts`：1710 行附近「另一半根因就是迁移锁」改成「锁超时走重试 / 503」，不要写成那 4 小时的结论。测试断言不用改。

## 测试

新文件 `packages/api/test/outbox-query-error.test.ts`。两条都要有，不许只用 mock 代替真查询。

1. 纯函数，不连库。造 `cause.code`：
   - `57014` 和 `55P03` → `TableLockedError`。
   - `42703` → 不是 `TableLockedError`，`message` 含 `42703`，`cause` 仍是原来的错，`sqlState` 仍读得到 `42703`。
   - 没有 code 的 `Error('追问 x 的需求 y 读不到')` → 同一个对象原样返回。
2. 故意造出失败，走真的 `taskInfos`。自己 `createTestDb()`，种一条未答追问（没有追问的话 `taskInfos` 直接返回，SQL 不会跑）。然后 `ALTER TABLE tasks DROP COLUMN title`，再 `listOutboxSources`。必须抛错：不是 `TableLockedError`，正文里有 `42703`，不能变成空的成功结果。用单独的一份库，测完 `close`。不要改 `store.pg.test.ts` 那份共用库的表——`resetTestDb` 只清空数据，不把列加回来。

`42703` 不是生产上那次的结论，只是「这条 join 真失败时不许被收成锁、也不许被收成没有待发」。生产 SQLSTATE 没读到，测试里不要写成「就是缺列」。

## 结果.md

同目录 `结果.md` 写这几样，短：

- 链和断点：上面那条。断在 `taskInfos` 的驱动执行，不在「行没了」。

- 这次排除了什么：干净的 PG 16 + postgres.js 上那条 SQL 能跑；缺 task 不抛 SQL。
- 没查到什么：法国上的 SQLSTATE，以及现在有没有长时间锁着 `tasks` / `repos` 的事务。没有就写没有，不要补一个原因。
- 改了什么：分类函数、注释、测试。查询没改。
