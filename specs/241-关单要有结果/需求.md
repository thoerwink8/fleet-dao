# 做完的单要关、关单要有结果：pnpm issue:close、合并时自动关、每天对账补漏（#241）

对应计划：v1 Fusion 接活（版本里的先后第 8 位）
设计依据：`docs/design.md` 第七节「标签与里程碑」（关单与需求文档）、第五节「发现问题当场修」第 5 条（合并闸只看哪几样）

原话：无。帅位 2026-09-27 查断链时发现：#211 关单时没写 结果.md，后来靠人补上（PR #224）。同日创始人：「issues能不能尽快处理，这种不应该本机去快速处理吗？」——开着 79 张，不少是做完了没关的。

AI 理解：
- 引擎做的单合并后第 7 步自己关（#214），关之前第 6 步要 结果.md 在 PR 里（core 的 `checkLeadReview`）。
- 本机工人合完 PR 就交回，帅位也没关，仓里又没有关单工具；`gh issue close` 关单没有任何一步拦「没写结果」。做完的单就一直开着，母单要等子单都关才能关，连带关不掉。
- 缺了 结果.md，以后回看「这张单做成什么样、怎么验的、还欠什么」就只能翻对话。

## 怎么算做完

- `pnpm issue:close <号>`：主线上有 `specs/<号>-<短名>/结果.md` 才关（关成「完成」），评论里贴结果文档的链接；没有就拒关、写清缺什么；下面还有开着的子单也拒关、列出是哪几张；读不到 GitHub、读不到主线都明确报错、不关；关完回读是「关了、完成」才算关上。
- 「这张单有没有结果」只判一份：`packages/conventions/src/issue-close.ts` 的 `resultDocOf`，pnpm issue:close、每天对账都调它。放 conventions 不放 core：合并闸不装依赖跑、只引 conventions 自己的文件，core 只许依赖 shared 和 zod；引擎第 6 步收 结果.md 用的 core 的 `specDocs`，engine 包里一条测试钉住两边对得上。
- 合并时自动关：
  - PR 模板在「需求」栏后面加一栏「这个 PR 做完就关单」：是 / 否（缺了、写的认不出只提醒）。填「是」的要在正文写 `Closes #<号>`，由 GitHub 合并时关，这个 PR 要自己带那份 结果.md。
  - 合并闸挡住没带结果的这种 PR：撞上创始人 2026-09-27 晚拍的规矩（#299：合并闸只看草稿、冲突、各项检查的结果和「认领对得上」，往里加要先改 design 第五节「发现问题当场修」第 5 条），这张单里不做，另开 #325 等创始人拍。拍之前，Closes 合并时关掉却没带结果的，由下面的每天对账兜住。
  - 引擎开的 PR 这一栏一律写「否」，正文里的关单词照旧改成「关联」：GitHub 替它关了单，接活会当成叫停，第 7 步的关单评论和记账就做不完。
- 每天对账补漏：放进引擎的 GitHub 对账补漏里，每天北京时间 9 点那一小时跑（看单子开关这类外部状态，只留言、进驾驶舱提醒，不挡 PR）：
  - 开着的单：主线上有它的 结果.md、没有开着的 PR 引用它（「需求」栏、标题里的 (#号)、关单词）、下面也没有子单 → 单上留言一次、驾驶舱提醒「该关了」；
  - 开着的母单：子单都关了 → 单上留言一次、驾驶舱提醒照母单的目标看能不能关；
  - 最近 30 天关成「完成」、主线上却没有 结果.md 的（直接 `gh issue close` 关的、Closes 合并时关的都兜得住；关成「不做了」「重复」的不算）→ 单上留言一次、驾驶舱提醒补结果；
  - 条件没了（关了、补上了）驾驶舱的提醒自动撤；读不到 GitHub、列不出主线上的 specs 算没查成（这一轮记没查全），不当成齐了，也不撤提醒。
- 规矩：AGENTS.md 本仓段、design 第七节讲关单的地方改成——做完一张单，收尾用 `pnpm issue:close` 关，或者最后一个 PR 写 `Closes #号`；「做完」＝合进去了、单也关了。
- 故意造出失败的测试，每条一个，拿改动前的代码跑都红：没结果文档拒关；读不到 GitHub、读不到主线就报错不关；对账读不到记没查成；子单全关提醒母单。合并闸挡住缺结果的「Closes」PR 那一条归 #325。
