# 版本交接时自动派不断档：当前版本的里程碑关了，下个版本里早就排着的单自动再判一次；做完没发布的版本还算不算当前版本请创始人拍（#284）

对应计划：未排期
设计依据：design 第九节「在哪能做与接活开关」（只派当前版本）；0003 第 2 条（版本收尾、下个版本照常开工）、第 8 条（不碰未排期）。

原话：帅位派工（2026-09-27，#283）「自动派只派当前版本的单……当前版本 = 还开着的 `v<N> …` 里程碑里 N 最小的那个」；0003 第 2 条「收尾：发布说明 → 创始人拍发布 → 里程碑关；没拍发布，下个版本照常开工」。
AI 理解：#283 之后，接活只在收到这张 issue 的事件（开单、改、贴标签、挪里程碑、对账补收）时判一次版本。有两处在版本交接时会卡住：① 当前版本的里程碑一关，下一个版本变成当前版本，可它里面早就开着、排队的单（当时判成 `not_current_version`）不会再收到事件——关里程碑不动这些单的 `updated_at`，webhook 和对账轮询都不会再送它们——一直排着，要人 `fleet-api handover` 一张张交，或者随手改一下单子；② 0003 第 2 条说做完没拍发布的版本，下个版本照常开工，可做完没发布的版本里程碑还开着，按「开着的 N 最小」它还是当前版本，下个版本的单不会自动派。第 ② 条是规矩怎么认的问题，要创始人拍。

## 要什么

- 当前版本变了（引擎对账每轮读一次仓里还开着的里程碑，和上一轮比），把「开关打开以后开的、还在排队、现在挂在当前版本上」的单再送进接活判一次，照常拉起；开关打开以前开的照旧不自动派。读不到里程碑照实记没查成，不当成版本没变。
- 「做完没发布」的版本怎么认、下个版本什么时候算当前版本：先请创始人拍（选项：做完的版本在里程碑说明里打个标记就跳过它；或发布前先关里程碑；或维持现状、交接时人手交），拍完照拍的改 `packages/core/src/dispatch.ts` 的 `currentVersion`。

## 怎么算做完

- 测试（故意造出的失败）：v1 开着时 v2 里排队的单不派；关掉 v1 之后下一轮对账，v2 里开关打开以后开的排队单拉起，开关打开以前开的不拉起；读不到里程碑这一轮记没查成、不拉起。
- 第 ② 条有创始人拍板记录，`currentVersion` 和它的边界表照拍的改。
- 法国读回：造一个测试仓的版本交接，下一轮对账后排队的单起了 Fusion。
