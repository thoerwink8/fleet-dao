## 五、要拍板的

### 总设计
- **存量不删、不迁**：删了找不回，GitHub 也不该删。日常只看开着的（66 条），历史靠搜索和按版本的里程碑。
- **从源头砍记录类 PR**：引导、测试耗时表不再每条开 PR。
- **「开单 → 马上做完」照旧**：一张单一个 PR，这是每次改动的验收记录，不砍。
- **自动观测和 AI 读取**：已在 #3741（只进账本、读账本）和 #3757 里做，不重复。
- **额度**：查清 10-30 谁用光了核心额度，再定（第七节）。

### 要拍的几条

1. **存量怎么收**
   - 推荐：不动存量；在 GitHub 上建两个保存的筛选（开着的单、开着的 PR）当默认入口，驾驶舱只列开着的。
   - 备选：新开一个仓，老仓归档只读。编号从 1 重来，但单子、PR 的链接和引用全断，引擎、规矩里写死的单号都要改，不推荐。
2. **创始人引导记在哪**
   - 推荐：不再一条一个 PR，记进驾驶舱库（全局说明本来就要求原话只进私有处），仓里只留按周汇总的意思。
   - 备选：照旧进仓，但攒一天一个 PR。少了，但原话仍进公开仓。
3. **测试耗时表**
   - 推荐：改成每周一次 PR（耗时变化慢，每天刷新没必要）。
   - 备选：放进 CI 缓存或法国库，不进仓。分台要读它，改读法国就多一个依赖，不推荐。

## 六、顺序、验收和风险

| 批 | 内容 | 怎么算做完 |
|---|---|---|
| 1 | 测试耗时表改每周一次 | 定时工作流改成每周；一周内 `ci-timings/` 分支的 PR 不超过 1 个 |
| 2 | 引导改记驾驶舱库（随拍板第 2 条） | `pnpm progress directive` 不再开 PR，有单测断言；一周内 `directive/` 分支的 PR 为 0 |
| 3 | 查清额度用光的来源，按结果再定 | 第七节那条有结论（哪个令牌、哪类请求、每小时多少） |

改前改后要比的：每周新开单数、PR 数、不挂单的 PR 数、开了就关的比例、核心额度每小时峰值。目标：不挂单的 PR 每周 ≤ 2 个；额度一周内不再用光。

## 七、没核实的

- **10-30 核心额度谁用光的**：合并闸报的是一个 5000/小时的令牌（不是工作流自带的 GITHUB_TOKEN），是创始人的个人令牌还是某个 App 的安装令牌、哪类请求最多，没查。
- **AI 每个会话读 GitHub 多少**：没统计会话里 `gh` 调用的次数和读入大小。
- **回放**：没把过去一个月的单按新规则逐张重放；本稿的砍法只动两类不挂单的 PR，按分支名就能数出来（引导 60、耗时表 18），没有误拦真单子的风险。
- 拍板前还没让别家挑错（`discuss`）。
