# 路由两层 DB：routing_catalog 表 + routing.default.json 配置骨架（#574）

对应计划：v3 三段一条龙
设计依据：`specs/509-需求梳理/流程重做方案.md`（讲路由配置改成两层的那一段）

创始人 2026-10-02 讨论方案时说：「opus 5.5 有很多个供货渠道，是不是在这个模型里面还要选供货渠道的优先级。」

AI 理解：现在 `stage_policies` / `stage_policy_routes` 是每个阶段直接挂一串 `routeId` 的平铺结构，加一个能跑 Opus 的新渠道要在每个阶段里各插一行。改成**两层**：用途 → 模型顺序，模型 → 渠道顺序；加一个渠道只动它所属模型那一行。同时把「接得上、额度够、没被禁令挡」的存法在表里写清楚，读法留给后续切片。

## 要干成什么：把路由配置从「每个阶段一串平铺路由」改成「用途 → 模型 → 渠道」两层，存进 DB，并有一份进仓的默认配置骨架。

## 为什么现在做：创始人 2026-10-02 提出；方案里讲路由配置改成两层的那一段要求两层每层都能一眼看出「这条现在活着吗」，否则层级一深，会看着一份整齐的配置、却一条都派不出去（#293 那次断 47 分钟就是这个形状）。

## 怎么算做完：
1. 新表 `routing_catalog`（迁移带 drizzle meta）：一行一个「模型 → 渠道顺序」，另有「用途 → 模型顺序」的一层；两层都能被查询出来，且顺序有唯一约束（同一层不许两行同一个位置）。
2. `routing.default.json`（进仓）给出默认骨架：每个用途的模型顺序、每个模型的渠道顺序；读不到、格式认不出时**明确失败**，不拿空配置或旧配置冒充（通用段底线第三条），每条这样的路径配一条故意造出失败的测试。
3. 两层的每一层都有「现在活着吗」的存法：接得上、额度够、没被禁令挡各是什么字段、从哪来，在表和类型里写清楚；**读法和选路切换留给后续切片**，本单只落存的形状。
4. 旧的平铺表在本单里**不删**（删数据要创始人点头，随 #556-4 的库表清单一起走）；新旧并存期间，选路仍读旧表，不改行为。
5. 迁移里没有删改语句（有就按先审后合走）；本单测试在 PGlite 上跑真迁移，旧库升级到新表不丢数据。
