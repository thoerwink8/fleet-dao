## 真机上跑了几遍

帅位已经在真机 `fleet-local`（Ubuntu 24.04.5、systemd、15G/8 核、D 盘、代理已配好）建好、`git clone` 到 `/srv/fleet-dao`。本会话一共跑了 5 遍 `FLEET_PROFILE=local bash deploy/france.sh`（第 1、2 遍在改 `readback_config` 之前，验证装机本身；第 3 遍验证 `readback_config` 分档位比对；第 4 遍在改完 `FLEET_PUBLIC_URL`/`desiredPath` 那两处代码之后；第 5 遍和第 4 遍之间代码零改动，专门验证幂等）：

- **改动次数**：第 3→4 遍报「本次改动 1 处」（`写 /usr/local/lib/fleet-dao/auto-release/config.mjs`）——这一处改动是因为这两遍之间我自己改了 `deploy/france/auto-release/config.mjs`（`desiredPath` 那处修复），装机脚本把它同步到系统固定路径，是应该发生的改动，不是幂等性的问题；第 4→5 遍（代码零改动）报**「本次改动 0 处」**——这才是真正验证「装机跑两遍，第二遍零改动」的一对。
- **两次真实的、非脚本 bug 的网络问题**：`corepack install -g pnpm` 一次卡在下载中途（`/proc/<pid>/io` 确认连接空转超过 165 秒，单独 `curl` 同一个地址两秒内就通，判定是网络瞬断，`kill -9` 后重跑自动从断点续上）；grok 官方安装脚本（`https://x.ai/cli/install.sh`）**连续 3 遍都在这台机器上连不上**（`curl: (28) Connection timed out`，`--retry 3 --max-time 120` 用完，`ensure_grok()` 按设计把它记成非致命的红、装机继续），这是这台机器网络路径到 `x.ai` 持续性的问题，不是偶发也不是脚本的 bug——`deploy/lib/grok.sh` 该有的超时兜底（rc 124/137 不致命）确认生效，没有让整个装机停下。

## nftables 防火墙：两个 WSL2 平台限制（真实发现，不是脚本 bug；规则本身是对的）

**这台机器真实跑起来的表拦不住会话口**：`fleet-agent-carpool`（会话用户）能直接连上 `127.0.0.1:7243`（Temporal）和 `127.0.0.1:5432`（Postgres），`fleet` 也能连上会话用户开在回环上的 reclaude 代理端口——`systemctl is-active fleet-firewall.service` 显示 active，`nft list table inet fleet_dao` 里规则和法国要求的一模一样，规则**没有加载错**。用一条一次性诊断规则（`oifname "lo" tcp dport 7243 counter reject`，`type filter hook output`）确认：一次成功连接之后计数器停在 `packets 0 bytes 0`——`input` 方向同样测过，结果一样。结论：这台内核（WSL2，版本 6.6.87.2-microsoft-standard-WSL2）的 netfilter 在 `networkingMode=mirrored`（这次装机要求的设置）下，**宿主机自己的网络命名空间**里，回环接口的流量不经过标准的 `output`/`input` filter hook。

**规则本身是对的，证据是 `deploy/test/session-ports.test.sh`**（`sudo bash deploy/test/run.sh` 在真机上跑的，见下面「怎么验证的」）：这条测试拿同一份 `deploy/france/fleet-dao.nft` 模板，在 `unshare --net` **新建的**网络命名空间里（不碰宿主的表和连接，是一个全新的回环）真连一遍——挡新连接、SYN 洪水下强制 syncookie 那条规则、读回核对表内容，一共三大块、几十条断言**全部通过**：别人连不上会话口、会话用户和 root 连得上、被挡的连接一个都没到会话用户那头。这证明 hook 在**一个普通、新建的网络命名空间**里工作正常，问题精确定位在「宿主机被 `mirrored` 模式接管的那个命名空间」，不是 nftables 在 WSL2 上全面失效，也不是这份规则写错了。

**第三个、更窄的限制**：同一条测试的第 4 部分（规则加载前就已经建立的连接，要用 `ss -K` 强制断开）在这台机器上失败——`ss -K` 报「断不掉（内核要开 SOCK_DESTROY）」，即使在新建的隔离命名空间里也一样。这是这台内核缺 `SOCK_DESTROY` 支持（和上面「宿主机回环不过 hook」是两回事，这条和 `networkingMode` 无关，隔离命名空间里也一样发生），影响面很窄：只影响「防火墙规则生效那一刻，规则生效前就已经连上的旧连接要不要被强制断开」，不影响「规则生效之后」的正常拦截（那部分是通的，见上一段）。

以上都是本机（不对公网开放的开发/演练机器）上的已知内核限制，法国（bare-metal/真实内核）不受影响。没有改共用的、先审后合的 `fleet-dao.nft`，也没有改 `networkingMode`（这次任务明确要求 mirrored）。
