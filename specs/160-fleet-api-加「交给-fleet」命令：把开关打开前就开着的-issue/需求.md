# fleet-api 加「交给 fleet」命令：把开关打开前就开着的 issue 交给引擎派（#160）

对应计划：plan.md P1「验收：机器接管」
设计依据：design 第九节「在哪能做与接活开关」（开关打开那一刻已存在的 issue 不自动派，要点「交给 fleet」）；ops 第九节 `fleet-api dispatch`（运维后备命令的写法）。

原话（创始人 2026-09-26）：「事情是不是可以交给vps去做了？」「我建议你先在本机修好vps上线前的必要内容，安排工作优先级」

AI 理解：P1 验收过了，fleet-dao 打开「让 AI 接活」，之后新开的单自动派；但开关打开之前就开着的单（项目模型 #131、拼车自动切换 #157、文档整套改法 #137–#140 等）按设计不自动派，要人点「交给 fleet」。驾驶舱的按钮随 #131 才做，命令行也没入口，这些单交不出去。先做运维后备：法国上一条命令把指定的单交给引擎，和以后驾驶舱按钮写同一份数据。这张单也是 P1 验收第 2 步（吃自己的狗粮）用的真需求。

## 要什么

- `fleet-api handover <owner>/<repo> <issue号>`：root 在法国跑，和 `fleet-api dispatch` 同一个入口、同样的连库方式。交出去以后，这张单和开关打开后新开的单走同一条路（分诊、需求文档、方案、派活……）。
- 只收：仓在库里、这个仓「让 AI 接活」开着、issue 开着、任务还在排队（从没派过）。其余一律明确拒、一句话说清原因、退出码非 0、库里不改：
  - 仓不在库里；
  - 开关关着（提示先 `fleet-api dispatch <仓> on`）；
  - issue 已关；
  - 任务已经在做（不重复拉起）；
  - 任务做完了（要重做就在 GitHub 上重开）。
- 交过的要记下来（谁交的、什么时候），和以后驾驶舱按钮写同一处。派活判断（`packages/api/src/issue-intake.ts` 的 `dispatchDecision`）看到「交过」就不再判 `opened_before_switch`，之后这张单再来事件照常处理。
- 交出去要真开工：最好当场拉起需求工作流；当场拉不起，就要在下一轮对账补漏（`github-reconcile`，15 分钟一轮）里拉起。注意现有对账只往回看 2 小时，旧单不一定被扫到——「交过但没拉起」的要单独查出来补，不能靠碰巧有新动静。命令回显交成了什么、工作流已经起来了还是几点前会起。
- 每次交（包括被拒的）都写一条操作记录，和 `dispatch` 一样，驾驶舱操作记录页看得到。
- `fleet-api dispatch <仓> status` 里「这之前就开着的不自动派，要人点「交给 fleet」」这句，驾驶舱按钮做好之前改成指到这条命令。
- `docs/ops.md` 第九节加这条命令的用法和退出码（照 `dispatch` 那段的写法：0 交成了；1 没做成并说原因；2 参数不对或没带上库连接——具体以方案为准）。

## 怎么算做完

- 单元测试：开关开着、排队中的旧单交出去就拉起工作流（或记下待拉起、下一轮对账拉起），写了操作记录；交过的单再来一个 issue 事件，派活判断不再是 `opened_before_switch`。
- 被拒的五种情况各一条故意造出来的测试：仓不在库里、开关关着、issue 已关、任务在做、任务做完了——都退出码非 0、库里不变（被拒的操作记录除外）、原因写清楚。
- CI 全绿、合进主线。

## 不做

- 驾驶舱「交给 fleet」按钮（随 #131）。
- 发到法国、用它交出 #131 等单：由总指挥在合并之后做，不算在这张单里。
