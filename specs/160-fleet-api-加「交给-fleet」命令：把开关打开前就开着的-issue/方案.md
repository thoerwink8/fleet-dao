# 方案：fleet-api handover —— 把开关打开前就开着的 issue 交给引擎派（#160）

## 现状（读代码得出的）

- 派不派看 `packages/api/src/issue-intake.ts` 的 `dispatchDecision`：`created_at < repos.auto_dispatch_since` 就回 `opened_before_switch`，任务行照建（`queued`），不拉起工作流。
- 对账 `reconcileGitHub`（`packages/api/src/reconcile.ts`，引擎装配在 `packages/engine/src/real/github-reconcile.ts`，15 分钟一轮）里查开放 issue 那一步（`auditOpenIssues`）只看「有没有任务行」：旧单已经有 `queued` 的任务行，对账**不会**再碰它。所以「交过但没拉起」的必须单独一步查出来补，不能靠现有步骤。
- `fleet-api dispatch`（`packages/api/src/cli.ts`）只连库，不连 Temporal；写库和操作记录走 Store 的一个方法、同一事务，改完读回。
- 需求工作流按工作流编号去重（`requirements.start` 回 `started` / `already_running`），重复拉起是安全的。

## 做法

1. **库里记「交过」**：`tasks` 加两列 `handed_over_at timestamptz`、`handed_over_by text`（只加列，不删不改）。`Task`（shared）带上 `handedOverAt?`。
   新 Store 方法 `handOverTask({taskId, by}, audit)`：同一事务里 `update tasks set handed_over_at=now, handed_over_by=… where id=? and state='queued'`，并写操作记录；回 `'ok' | 'already' | 'not_queued' | 'not_found'`（`already` = 之前交过、还在排队：不重记，只再试拉起，当重试用）。以后驾驶舱按钮调同一个方法。
   另加 `listHandedOverQueued(limit)`：交过、还在 `queued` 的任务（带仓）。内存库、PG 库都实现，走 store 合同测试。
2. **派活判断认「交过」**：`dispatchDecision` 的 task 参数多带 `handedOverAt`；非空就跳过 `opened_before_switch`（开关关着仍是 `dispatch_off`，其余不变）。之后这张单再来事件照常走 `start` / `in_progress` / `finished`。
3. **拉起一张交过的单**：抽一个 `startHandedOver(deps, task, repo)`（新文件 `packages/api/src/handover.ts`）：用任务行里的标题、原话拼 `requirements.start` 的输入，`started` 时记 `task.start`（reason「交给 fleet」）。命令和对账共用。
4. **对账补一步 `handover`**：`reconcileGitHub` 在重放之后跑：`listHandedOverQueued` → 仓的开关还开着的逐个 `startHandedOver`；出错记进这一步的 why（`partial`），不影响别的步。`ReconcileParts` 加 `requirements`，引擎装配里把现成的 `requirements` 传进去。
5. **命令 `fleet-api handover <owner>/<仓名> <issue号>`**（cli.ts，同一入口、同一连库方式）：
   - 解析：恰好两个参数，仓照 `REPO_ARG`，号是正整数；不对退出码 2。
   - 依次查、不对就拒（退出码 1，库里只多一条 `ok:false` 的操作记录 `task.handover`，写明原因）：仓不在库里（target `repo:<owner/仓名>`）；开关关着（提示先 `fleet-api dispatch <仓> on`）；库里没这张单的任务行（没收进来：说等下一轮对账或检查仓是否受管）；任务 `stopped`（issue 已关或被叫停：在 GitHub 上重开）；任务在做（`queued` 以外、未结束：不重复拉起）；任务 `done`/`failed`（做完了：要重做在 GitHub 上重开）。issue 开没开从库里的任务状态判断（关单事件把任务记成 `stopped`），命令不连 GitHub。
   - 收下：`handOverTask` 记下（谁＝`FLEET_OPS_OPERATOR`，何时），然后**试着当场拉起**：按 `loadConfig` 的 Temporal 地址、命名空间、任务队列连 Temporal 调 `startHandedOver`。起来了回显「已交给 fleet，需求工作流已拉起（工作流编号 …）」；连不上或出错回显「已交给 fleet（操作记录 …），工作流没当场起来（原因），下一轮对账补漏会拉起，约 HH:MM 前」（现在 + 15 分钟），退出码仍是 0——交已经记下了，对账保证会起。
   - `dispatch status` 里「要人点「交给 fleet」」改成「用 `fleet-api handover <仓> <issue号>` 交」。
6. **文档**：`docs/ops.md`「让 AI 接活」那段后加 handover 的用法、拒的几种、退出码（0 交成了（含等对账拉起）；1 没交成；2 参数不对或没带上库连接）；`packages/api/bin/fleet-api` 头注释加一行用法。

## 拆分与先后

| key | 内容 | 依赖 |
|---|---|---|
| `handover-store` | 迁移 + schema + Task 字段 + `handOverTask` / `listHandedOverQueued`（内存、PG、合同测试）+ `dispatchDecision` 认交过 + `handover.ts` 的 `startHandedOver` | — |
| `handover-reconcile` | 对账加 `handover` 一步 + 引擎装配传 `requirements` + 测试 | store |
| `handover-cli` | `fleet-api handover` 命令、当场拉起、`dispatch status` 文案、ops.md、bin 注释 + 测试 | store |

后两块改的文件不重叠，可以并行。

## 测试（对着「怎么算做完」）

- store：交排队中的单 → 记下时刻和人、写操作记录；对 `stopped`/在做的单回 `not_queued`、库里不变。
- 派活判断：交过的旧单再来 issue 事件 → 不是 `opened_before_switch`；开关关着仍是 `dispatch_off`。
- 对账：交过、排队中的单被拉起并记 `task.start`；拉起出错这步记 `partial`，别的步照常。
- 命令：收下时假 Temporal 起来了 → 回显已拉起、操作记录一条；假 Temporal 连不上 → 回显几点前会起、退出码 0、库里记下了交过。拒的五种（仓不在库里、开关关着、issue 已关（`stopped`）、任务在做、任务做完了）各一条：退出码 1、库里除一条 `ok:false` 操作记录外不变、输出写清原因。

## 没做到 / 留意

- issue 在 GitHub 上关了、关单事件又丢了时，库里任务仍是 `queued`，命令会收下（没查工作流拉起后会不会自己发现已关）。这张单不补 GitHub 查询，命令里不连 GitHub；交出去的都是创始人点名的开着的单，风险小。
- 迁移只加两列可空列；按规矩这块写成 high，合并前审一轮。
