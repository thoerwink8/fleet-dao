# 方案：会话端口、路由探针按执行方式分派，接上 cursor-agent（#212）

需求见同目录 `需求.md`。和派工交代不一样的有三处：续会话多了三种接力的情形（第三节）、cursor 的探针按成本放慢（第四节）、找 cursor-agent 的办法由会话用户自己现找（第一节第 3 条）。

## 一、做了什么

1. **插头从 adapters 导出**（`packages/adapters/src/index.ts`）：cursor 的 run、args、stream 三个文件整套导出，查过和 claude-code 的导出没有重名。`runCursorAgent` 加了 `onSessionId`：init 帧报出会话号时同步调一次；续会话报回来的号对不上就当场停掉、不调；回调抛了记进报告的 hookError，不打断读流。
2. **按执行方式分派**（`packages/engine/src/real/hosts.ts`）：每种执行方式一个驱动，管三件事——拼起会话的参数、跑插头、把插头的报告整理成同一个形状 `HostReport`（判定事实交给 `judgeRun`，会话号，token，只有 Claude 有的花费、实际模型、上下文大小、清零时刻，只在 stderr 里的报错原话）。起会话、看守、结局判定、失败分流、记账（`packages/engine/src/real/sessions.ts`）和路由探针（`packages/engine/src/real/route-probe.ts`）只认这个形状。接上的是 Claude Code 和 cursor-agent；别的执行方式起会话明确报 `HOST_NOT_WIRED`（写明现在接了哪几种），选路不派，探针记 not_wired。测试按执行方式各给一个假插头。
3. **cursor-agent 怎么起**：它装在会话用户自己家里，升级会删掉旧版本目录（CU-03），引擎又进不去会话用户的家（700），所以每次起都由会话用户自己现找：`cursorLaunchCommand` 给的是 `/bin/sh -c <一行脚本> cursor-agent <版本目录> <插头的参数…>`，脚本先看 `current`，没有就按 `sort -V` 从新到旧找「数字.数字」开头的版本目录（安装时下载的临时包是 UUID 起名的，不认），里面的 cursor-agent 能跑才算，找到就 exec 成它（进程号不变）；一个都没有就退出 127、stderr 写「spawn cursor-agent ENOENT：…没装 cursor-agent」，失败分流认成执行方式配置不对（CF1）。版本目录是参数、不拼进脚本；整条命令没有换行（要经 sudo 记日志）。目录在 engine.env 的 `FLEET_CURSOR_VERSIONS_DIR`（默认 `/home/{user}/.local/share/cursor-agent/versions`，要绝对路径，写错了引擎起不来）。
4. **放开权限、钥匙**：干活的会话带 `--force`，理由和 Claude 放开权限一样（会话用户读不到引擎的配置和机器人凭据；无头会话没人批）；探针不带。登录态在会话用户家里，不往会话环境里塞 `CURSOR_API_KEY`——帮手脚本本来也只放 `FLEET_*`、语言这几样变量（`packages/adapters/src/env.ts` 和帮手脚本都没改）。
5. **会话用户**：Claude 照账号池（`pools.run_as_user`，它绑着 reclaude 组织，没定就起不了）；Cursor 的池不绑（库里约束会话用户和 reclaude 组织类型同有同无，Cursor 没有组织），用法国唯一的会话用户。会话用户不止一个时明确报缺什么，不瞎挑一个。
6. **结局判定、失败分流**：判法只有 `judgeRun` 一份，各家插头各出判定事实（`claudeRunFacts`、`cursorRunFacts`）。cursor 的认证、额度、网络报错只在 stderr（退出 1、没有 JSON），驱动把 stderr 最后几行原话接在失败信息后面（「执行体原话：…」），规则表靠它认：
   - **AU5 Cursor 登录失效**（新加，排在 AU2 前面）：认 `run 'cursor-agent login'`（命令名也可能是 `agent`）、`Authentication required to use Cursor Agent`、`Backend rejected authentication`。原文取自发行包 2026.09.23、2026.09.26 的 index.js 和 4507.index.js。整池暂停、推「要人拍」，写清去哪台机器、以哪个会话用户跑 `cursor-agent login`；不算路由的账；下一次跑通撤掉。
   - **额度用满**：插头按「usage limit」这类说法认成 quota_exhausted，走 QT1——整池等清零、不算路由的账、不要人。
   - **没装**：CF1，算路由的账。**连不上**：没有终帧（no_result），带着原话按原来的判法。
   - 整池暂停那条提醒原来不写修法（AU2 管各家的登录，没写修法），现在由驱动给：Claude 写重跑 reclaude 登录，Cursor 写 `cursor-agent login`。Claude 那条也因此写清了。
7. **记账**：cursor 终帧只报这一轮的 token（输入、输出、缓存读、缓存写），没有花费、没有实际模型（init 里的 model 是界面名，CU-08）、没有上下文大小——这几项不记，不记成 0；终帧里读不到、不是数的那几项也不记。缓存读写随会话结局交给工作流（`SessionEnd.usage`），库里还没有这两列，#216 加。
8. **测试**：拿法国真跑的过程记录（`packages/adapters/test/fixtures/cursor-agent/`）喂真的读取器：写码会话的三种交付核对（没用 fleet done、有没提交的改动、没有新提交）、只读会话的结论文件、续会话的每一种接力、登录失效、额度用满、没有 init 帧、一帧都没有、没装；探针的在线、离线、没登录、没装、额度用满、回答认不出、放慢；找版本目录的那段 sh 真跑（本机的 sh、假的 cursor-agent）。

## 二、会话号怎么定

- cursor 的会话号是它在 init 帧里自己起的，事先定不了（没有 `--session-id`）。开新会话时 `startSession` 先回一个一眼看得出不是 UUID 的临时号 `cursor-pending:<runId>`，库里这一轮先记它；init 帧一到，真号记在看守上；结束时 `SessionEnd.sessionId` 交真号，一直没报出来就交空串（工作流只在它非空时换号，保留上一个），`finishSessionRun` 把真号写进库，下次 `latestRunOfSession(真号)` 查得到这一轮。
- 没报出真号就断了（连不上、没登录、工人重启后接不上）：库里留着临时号，工作流手里的也是临时号（接不上时它拿的是开工时回的号），下次拿它续会话照样查得到上一轮，认出不是 UUID，改走接力。
- 续会话（`--resume <真号>`）报回来的号对不上：插头当场停掉，判 session_mismatch。
- 工人重启、看守接不上时，真号还只在内存里（结束才写库），这时续会话走接力、不 `--resume`。接力是对的（已提交的不重做），只多花一点上下文；工人重启本来就少见，不为它在 init 帧时多写一次库。

## 三、续会话：为什么没有 fork，什么时候接力

- cursor-agent 没有 fork，只有 `--resume <会话号>`。Claude 要 fork 是因为切号后原会话绑在旧组织上；Cursor 的池不绑组织，换池（以后有第二个 Cursor 账号时）原会话不在那个账号下，只能开新会话带接力任务书。
- 判法写成纯函数 `decideContinuation`（`sessions.ts`），先后就是判断的先后，每个分支一条测试（`packages/engine/test/real/continuation.test.ts`；起会话那一段在 `sessions.test.ts` 用真库、假插头各走一遍）：
  1. 上一轮的记录查不到 → 接力。
  2. 上一轮跑在别的（已停用的）会话用户下 → 接力。
  3. 上一轮的路由已不在 → 接力（新加：原来会往下走到 fork）。
  4. 换了执行方式 → 接力（新加：原来 Claude 会拿 cursor 的号去 fork）。
  5. 续的号不是 UUID（cursor 的临时号）→ 接力（新加）。
  6. 换了工作目录 → 接力（新加：两家的会话记录都按目录存，Claude 在 `~/.claude/projects/<目录>`，cursor 在 `~/.cursor/chats/<目录的哈希>`，换了目录续不上；现在的流程续会话都在同一个目录，这条是兜底）。
  7. 同一个池 → `--resume`。
  8. 换了池、执行方式不能 fork（cursor）→ 接力。
  9. 换了池的 Claude：上一轮上下文比上限小 → fork；不知道多大或大了 → 接力。
- 比派工交代多了 3、4、6 三条：不加的话，要么拿一家的号去另一家续（一定失败，白起一次会话），要么在找不到记录的目录里 `--resume`。

## 四、探针怎么探

- 和干活的会话同一个驱动、同一套判法：以会话用户在 `<工作树的根>/_route-probe/<会话用户>` 起一次最小的无头会话，模型照路由上写的（不限定 auto，创始人 2026-09-27 更正），问一句「只回 OK」。cursor 不带 `--force`，什么命令都跑不了；它没有不存会话记录的开关，探针的会话会留在会话用户家里的 `~/.cursor/chats` 下。
- 判法：去掉首尾空白后整句只回 OK 才算通；额度用满被拒算通（额度那一套挡）；没登录认成 AU5，同一轮不再试、离线、整池暂停，原因里写清去哪台机器、以谁跑 `cursor-agent login`，下一轮探通就撤掉；连不上、没装、认不出的隔 20 秒同一轮再探一次，还不通才离线。
- 频率按一次的成本放慢（design 第九节「路由探针」本来就写了「贵的放慢」）：本机实测一次最小会话（Auto，只回 OK）用了 13271 输入、3840 缓存读、32 输出 token，4 秒；扣的是按月的包含用量、和创始人在编辑器里用的是同一份。每 15 分钟一次，一条路由一个月约 2900 次、约 5000 万 token，太多。所以上一次探通了隔 2 小时再真探（一个月约 360 次、约 600 万）；没通的照样每轮探（没登录、连不上的报错走不到模型，不扣用量；登好了 15 分钟内转回在线）；中间那几轮结论照旧、不重写，算扫过、算在线。过期线跟着放宽成间隔加两轮（2 小时 30 分），驾驶舱「探测过期」和派工理由里的那句是同一条线（`packages/shared/src/web-api.ts` 的 `routeProbeStaleMinutes`）。间隔配在同一个文件的 `ROUTE_PROBE_HOST_EVERY_MINUTES`，以后接别的插头照这个办法定。

## 五、花费

以 Cursor 官方定价与账单文档为准（帅位 2026-09-27 查），创始人 2026-09-27 确认：

- **走订阅，没开按量计费，也没额外充钱。** 两个用量池（Grok、Composer 这类 Cursor 自家模型一个，其他高级模型一个）都在订阅里，按月重置；用完就停，请求被拒、不多扣钱。失败分流按额度用满（QT1）判，整池等清零，不当成执行体出错。
- **和创始人自己在编辑器里用的是同一份额度。** 引擎用掉多少，他编辑器里就少多少；探针按成本放慢（第四节）就是为这个。
- 官方出处：Auto 按它实际选中的模型的标价扣包含用量——「All Auto modes bill at the list price of the model each request is routed to.」（cursor.com/docs/account/pricing）；个人档按量计费默认关——「On-demand usage must be explicitly enabled in your settings」，Teams 档默认开（cursor.com/help/account-and-billing/overages）。命令行和编辑器同一套计费，官方文档没写，论坛高信任用户说一样，按一样算。
- 所以接 cursor 不会多出账单，不碰人闸「花钱」。真流量（调度台哪个阶段用 Cursor 的路由、排第几）等创始人定。
- 额度用满时的原话：正文由服务端给，发行包里只有 `PRO_USER_USAGE_LIMIT` 这类错误码；论坛有人贴过命令行的 `Error: You've hit your usage limit`（forum.cursor.com/t/cursor-agent-cli-limit-hit/128577），我们还没撞上过。插头按「usage limit」认；真撞上时说法要是不一样，会按「没有终帧」算这条路由失败（不扣钱，但不会整池等清零），真撞上一次再补样本（#230）。
