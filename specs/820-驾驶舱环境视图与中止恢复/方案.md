# #820 驾驶舱补 WSL 和法国两个环境的视图 + 全局/单任务中止与恢复：方案

- 母单 #902 下，大 L。本文只是方案，没有实施；实施由指挥官看完后另派。2026-10-05（北京时间）写，按 `best-practice-first` 六步。
- 范围：#820，并入 #856 的第 1 处（驾驶舱页面上暂停、继续、叫停点不到）。#856 的第 2 处（渠道开关没入口）不并进来，留在 #856。
- 本文引用的代码位置都是 2026-10-05 的 `origin/main`（`bd7767ba` 之后）。

## 先说结论

1. **中止和恢复永远只作用在一个环境上**，写进那个环境自己的库。法国和 WSL 是两套各自完整的栈（引擎、Temporal、Postgres、驾驶舱后端各一份），法国没有入站口，WSL 只能出站，页面同源规则也不让一个页面去写另一个后端。跨环境只做只读观察。
2. **全局中止做成一个新设置 `engine.paused`**，沿用已有的设置接口（带版本锁、操作记录）和引擎读设置的先例（`engine.soloPaused`），不新建表、不迁移。引擎有「不起新会话、选路回等一会儿」的排空机制可借，但**得先补一个缺口**：三段流程的一次性会话（动手、验收）没登记进排空的在途清单，现在的发布排空看不见它们、到点也停不到它们。
3. **单任务**：「叫停」是终局，不假装能恢复；新增「暂停」信号才是和「继续」成对的中止。叫停过的单要想再做，诚实地叫「重开新跑」，是另一件事，建议不做。
4. **环境视图**分两步：先做每个环境各自一页「本环境」（只读、不跨环境，不开口子）；跨环境并排（WSL 把快照推给法国）单列成可选的第 3 片，要创始人点头。
5. 摆出的「删」选项：只做第 1 片（只读环境页），全局暂停、单任务暂停都不做。我不推荐，理由在 §4.7。

## 1. 业务说明

### 1.1 替谁、什么场合、干成什么

| 场合 | 谁 | 要干成什么 | 干成的标志 |

## 2. 现状证据

### 2.1 驾驶舱里和环境相关的页

- 导航里没有「环境」页：`packages/web/src/components/shell/nav.ts` 四组（盘面、调度、运转、管理）。
- 主页顶部状态条有三格：额度、中转、引擎（`packages/web/src/components/home/health-strip.tsx`）。**「引擎」那一格只读 `release.env` 的开关**：`packages/api/src/views.ts:606` 的 `homeHealth` 只看 `config.engineOff`（`packages/api/src/config.ts:106` 的 `engineEnabled` 读 `FLEET_SERVICES`），不看引擎此刻在不在跑。
- 健康页是香港的静态页 `deploy/web/health`（读 `/healthz`），只连法国。`/healthz` 逐项给结论（`packages/api/src/health.ts` 的 `serviceHealthChecks`：database、realtime、temporal、engine、deploy_lag、session_org、canary、watchdog 等）。`deploy_lag` 只在 `FLEET_ENV=production` 的机器上查（`packages/api/src/main.ts:160` 的 `onFrance`）。
- 定时任务页 `/schedules`、额度页 `/quota`、通知中心都是「本后端自己的库」。
- **查了 `packages/engine/src/jobs/` 和 `packages/db/src/queries/`：没有任何表或行存「这个环境现在怎样」**。可复用的现成读法：`/healthz`、`listRuns({active:true})`（在跑的会话）、`buildPools`（池占用，`/api/pools`）、`scheduled_jobs`/`schedule_runs`（最近一轮拉单）、引擎排空提醒（键 `engine-drain`，`packages/engine/src/real/drain-alerts.ts`）、版本和落后状态（`packages/store/src/deploy-lag.ts` 的 `readDeployLagInput`）。
- **WSL 没有可开的驾驶舱**：`docs/ops.md` 第十三节写着本机档没有香港、不发前端。2026-10-05 02:5x 实测：WSL 里 `curl http://10.99.0.2:8787/healthz` 回 503（`deploy_lag` 报「版本标记读不到」、`session_org` 红，`engine`、`database`、`temporal`、`canary` 绿），在跑的是 `e0ede519`（比主线旧）；Windows 上 `127.0.0.1:8787` 被拒、`10.99.0.2:8787` 超时。就是说**WSL 的后端活着，但创始人的浏览器够不着它**。
- 环境之间的隔离：写请求核对来源只认本后端的 `FLEET_PUBLIC_URL`（`packages/api/src/session.ts:166-176`）；生产模式强制 https（`packages/api/src/config.ts:125`）；香港 nginx 只把 `/api`、`/auth`、`/github/webhook`、`/healthz` 转给法国（`deploy/hk/nginx-https.conf:135`），转之前清掉 `Authorization` 和 `X-Fleet-Acting-Feishu`（同文件 :121-122）。

### 2.2 「叫停」现在怎么走（#925 之后）

- 页面：`packages/web/src/components/task-actions.tsx` 的 `ActionButtons`、`availableActions` 没有页面调用（只剩通知中心用 `useTaskActions`），任务页 `routes/task.tsx` 没有任何操作按钮——这就是 #856 第 1 处。
- 后端：`packages/api/src/cockpit.ts:304` 的 `POST /tasks/:taskId/actions`。`resume` 发 `taskContinue`，`stop` 发 `taskAbandon`；`pause`、`reroute` 当场回 409（`cockpit.ts:84-95` 写明「任务工作流没有暂停」）；任务已进终态（`done/stopped/failed`，`packages/api/src/views.ts:80`）回 409 `task_finished`；工作流不在了回 409 `workflow_gone`。
- 引擎：任务工作流只听三个信号（`packages/engine/src/task-contract.ts:86-88`）。放弃后工作流收尾退出，工作树存档后删（`workflows/task.ts` 的 `abandoned()`），库里记 `stopped`。
- 同一张单不能再起同名工作流：`packages/engine/src/real/intake.ts:156` 用 `REJECT_DUPLICATE`。**所以被叫停的单，现有机制下没有「恢复」，只可能新开一跑**。
- 单子「停下等人」（`park`）已经有成对的「继续」：`packages/engine/src/workflows/task-runtime.ts` 的 `park()`，但它会发一条 `stuck` 级提醒（进「要你拍的」），不适合拿来做人主动暂停。

### 2.3 排空与恢复（`drain.ts`）

- 不起新会话：选路回「过一会儿再选」（`packages/engine/src/real/store-ports.ts:480` 的 `pickRoute` 开头），起会话前再拦一道（`real/session-launch.ts:148`）；在跑的最多再做 `RELEASE_GRACE_MS`（10 分钟），到点停下交回 `engine_stop`，失败分流 `KL3` 认它为「不算失败、不记账、免费重试」；被拦的交回 `engine_stopping`，`ES1` 同样免费重试。
- 叫排空的只有两处：发布脚本写的请求文件、systemd 停机信号（`drain-control.ts`）。**没有人手叫的排空，也没有 `engine_dispatch_paused` 这个开关**（全仓搜不到，只在决定 0011 和进度文件里提过）。
- 恢复 = 撤掉请求，选路下一轮就派（`drain-control.ts` 的 `lift`，只撤发布来源的）。
- `Cordon` 只有 `release | signal` 两种来源，并发合并规则是「截止只提前不推后」；`until` 必填、认不出按已到点算（`drain.ts` 的 `overdue`）。软暂停（没有截止）要改这里。
- **同根缺口（已核）**：三段流程的一次性会话登记在 `packages/engine/src/real/one-shot-sessions.ts`（按池登记，给切号用）；`drain.track/settle` 只在老的 `session-launch.ts` 里调（:155、:170），`drainStop` 只停那一路（`session-lifecycle.ts:108`）。所以**发布排空看不见动手、验收会话，到点也停不到它们**，`waitDrained` 会因「在途清单为空」立刻放行。全局暂停要的「手上还剩几个在跑」必须先把这一路登记进去。
- 一次性会话的停法只有「切号叫停」一条（`ticket.signal`）：`packages/engine/src/runner/one-shot.ts:92,234` 结局写死 `org_switch`；工作流只对 `org_switch` 带「上一次为什么停」的提示词重跑（`workflows/task-session.ts:83`）。`engine_stop` 在三段流程里**不带**这句提示词。
- 引擎读设置的先例：`engine.soloPaused`（`packages/shared/src/web-api.ts:1125`），读法 `packages/db/src/queries/session-org-state.ts:20` 的 `readSoloPaused`（没设=关、true=开、认不出按开并报错）。

### 2.4 现有实现里「怎么做」的部分，都不作为设计起点

主页状态条的三格和叫法、`/healthz` 的项目切法、`ActionButtons` 的悬停条和右键菜单形态、`Cordon` 的两种来源和必填截止、`park` 的告警套路、`oneShotSessions` 的按池登记、单一工作流编号。它们在 §4 可以被重新选中，但必须是从业务推出来恰好一样。

## 3. 业界对照（2026-10-05 取）

| 层 | 来源 | 他们怎么做 | 对我们的约束 |
|---|---|---|---|
| 机制：暂停派发 | Buildkite「Pause Queue」<https://buildkite.com/docs/pipelines/clusters/manage-queues>（2026-10-05） | 暂停后「已派发的继续跑」，新作业等恢复；暂停时可写一条说明，显示在队列详情页和受影响的构建上；有对应的「Resume Queue」 | 同我们 soft 暂停；原因要显示在每张被拦的单上 |
| 机制 | Jenkins「Prepare for Shutdown」<https://www.jenkins.io/doc/book/managing/>（2026-10-05） | 「只防止新构建启动」，不停在跑的；顶上红条带自定义说明 | 顶栏红条+说明，同一个思路 |
| 机制 | Nomad `node eligibility` / `node drain` <https://developer.hashicorp.com/nomad/tutorials/manage-clusters/node-drain>（2026-10-05） | 「不可调度」只管新的；drain 带截止（默认 1 小时），到点「剩下的全停」，`-force` 立即截止；取消 drain 默认恢复可调度 | 就是我们已有的排空（宽限+到点停）；soft/hard 对应「无截止 / 截止=现在」 |
| 机制 | Kubernetes `kubectl cordon` <https://kubernetes.io/docs/reference/kubectl/generated/kubectl_cordon/>（2026-10-05） | 「Mark node as unschedulable」，已有 pod 继续跑；与 drain 是两个动作 | 同上：拦新的与停旧的是两个显式动作 |
| 机制 | Argo Workflows suspend <https://argo-workflows.readthedocs.io/en/latest/walk-through/suspending/>（2026-10-05） | 「Once suspended, a Workflow will not schedule any new steps until it is resumed」，`argo resume` 恢复；已知问题：停下后已起的 pod 继续跑到结束 | 单任务暂停=不再起新的一步；在跑的那一步怎么处理要单独定 |
| 机制 | Temporal Activity Pause <https://docs.temporal.io/activity-operations>（2026-10-05） | 暂停「停重试，在途执行继续，除非 Activity 心跳」；Unpause「下一次执行马上开始」；Web UI 的工作流动作只有取消、信号、重置、终止，没有暂停整条工作流 | 我们的工作流是自己的状态机，暂停要自己加信号；在途会话靠心跳停得下来（`task-segment.ts` 已有心跳） |
| 信息架构+版面 | Octopus Deploy 项目看板 <https://octopus.com/docs/projects/project-dashboard>（2026-10-05） | 以「环境」为单位排：每个环境显示最近部署的版本（成功或失败）、上一个成功的、最近几个没部署的 | 每个环境一块、块里先写在用哪版和健康；法国、WSL 并排 |
| 信息架构 | Argo CD 多集群 <https://argo-cd.readthedocs.io/en/stable/operator-manual/declarative-setup/#clusters>（2026-10-05） | 一个控制面登记多个集群，应用声明自己的目标集群；集群凭据以密钥登记 | 我们不做「一个控制面管多个环境」：法国没入站、凭据不能外放 |
| 信息架构 | Temporal Web UI 命名空间切换 <https://docs.temporal.io/web-ui>（2026-10-05） | 右上角切换命名空间，每个命名空间一份自己的工作流列表；写操作在各自命名空间内 | 「切换环境」的做法需要页面能连多个后端，被同源规则挡住（§2.1） |

对照里一致的做法：**暂停 = 拦新的，在跑的怎么办是另一个显式动作；恢复是对称的一个动作；原因要写在能看见的地方；环境各管各的。** 差别（要拍板的地方）：他们的控制面能直达每个被控对象；我们的法国够不着 WSL，所以只读观察和写控制必须分开处理（要创始人定的 #1、#2）。

版面和视觉这两层，业界只找到文档没有截图的，我在第 1 片实施时按 `best-practice-first` 第 4 步第 6 条：每个目标尺寸出真实画面，和 Octopus 看板的「环境一列」并排比（见 §5 片 1 的画面要求）。本文没有出画面（只给方案，没做界面）。

## 4. 从业务重推

### 4.1 操作剧本和代价

| 剧本 | 现在 | 目标 |
|---|---|---|
| 看两台各自在干嘛 | 法国：开健康页看一串红绿，没有会话数和版本；WSL：开不了页，只能进 WSL 敲命令 | 开驾驶舱，一页看到；动手 1、搬运 0、离开 0 |
| 想停所有新活 | 没有办法：只能在机器上改 `FLEET_SERVICES` 再发布，或停服务（会白杀在跑的） | 点一个按钮、写一句原因；动手 2（点、确认）、搬运 0、离开 0 |
| 停了之后恢复 | 同上 | 点一个按钮；动手 1 |
| 停一张单 | 只有叫停（终局），页面上还点不到 | 任务页暂停、继续成对 |

### 4.2 原则

1. 每个环境自己管自己：控制状态（暂停）写进该环境的库，在该环境的库里就是权威；快照只用于展示，不拿来当停止的依据。
2. 软、硬分开：soft = 拦新的、手上的做完这一段；hard = 再把在跑的停下。默认 soft。
3. 「已停」只在拿到确认后才说：区分「本地进程已终止」和「还没确认」，没确认的数照实显示。

### 4.4 全局中止与恢复：引擎里的真实语义

引擎没有暂停。要做的是三件事：

1. **新设置 `engine.paused`**（加进 `SETTING_SCHEMAS`，值形如 `{ paused: boolean, mode: 'soft' | 'hard', reason: string }`；没设过 = 没暂停）。三态读法照 `readSoloPaused`：值认不出按「暂停」并报错，不当成没暂停。库读不到时保持上一次已知状态并记日志。
2. **引擎侧**：
   - 拉单（`jobs/intake.ts` 的 `round`）开头读它，暂停就这一轮记 `ok`、写明「引擎已暂停，没拉单」，不起新工作流；
   - `pickRoute` 开头读它（现读，不等 5 秒轮询），暂停就回「过一会儿再选」，沿用排空的 `waitFor: 'slot'` 路径；
   - 起会话前再拦一道（沿用 `engine_stopping`，失败分流 `ES1` 免费重试）；
   - `Cordon` 加第三种来源 `pause`，`until` 允许为空（soft）；hard 时截止=现在，借已有的到点停会话；发布排空撤请求时不能把暂停撤掉（来源分开存）；
   - **前置缺口**：把三段一次性会话登记进在途清单、并能被「停下」（`one-shot-sessions.ts` 加按单号或全部停；`task-segment.ts`、`task-verify.ts` 登记 `drain.track/settle`）。这一步同时修好发布排空看不见一次性会话的问题。
3. **hard 之后恢复的真实样子**：一次性会话被停下，树里可能留着没提交的改动；恢复后在原树上重跑这一段，会话上下文丢失（和切号重跑同一个处境）。要让新会话知道「上次为什么停」，`task-session.ts:83` 现在只对 `org_switch` 带 `interrupted`，要扩到「被人暂停」（用 `patched()`，Temporal 重放测试交 CI）。

**语义表**

| 动作 | 效果 | 在跑的会话 | 恢复 |
|---|---|---|---|
| 全局 soft 中止 | 不拉新单、不起新会话 | 做完当前这一段，之后在选路等待里等恢复 | 清设置；引擎下一次选路就派（拉单最长 5 分钟） |
| 全局 hard 中止 | 同上 | 立刻停下，回应写「已请求停 N、已确认 M、未确认 K」 | 同上；停下的段在原树上重跑 |
| 重复点中止 | 回 409，显示当前状态和原因，不覆盖 | | |
| 恢复 | 带「我看到的 version」，变了回 409；已经恢复了再点是幂等成功 | | |

**留痕**：设置接口已写操作记录（谁、什么时候、原因）；再加一条「通知」（和排空提醒同一级别 `daily`，只在开始、结束各写一次，不写倒计时，免得飞书卡片被反复改），不进「要你拍的」（R4）。

**「已停」的确认口径**（GPT 挑错收的）：「本地进程已终止」由引擎在 `runs` 里写结局为准；供应商那头额度是否还在增长，我们读不到，页面只写「本地已终止」，不写「额度已停」。

### 4.5 单任务中止与恢复

| 动作 | 引擎里的真实做法 | 恢复 |
|---|---|---|
| 暂停（新） | 新信号 `taskPause`（`shared/task-signals.ts` 加名字和参数，引擎 `task-contract.ts` 注册）。工作流在下一个检查点（`guard()` 同一些位置）停进「已暂停」：库里 `phase='paused'`、`state` 仍是 `running`（`tasks.phase` 是自由文本，**不用迁移**），任务页和主页显示「已暂停，谁、为什么」，不发 `stuck` 提醒。soft = 当前这一段做完；hard = 用单号停该任务那一段的会话（`oneShotSessions` 加按单号停） | 继续（已有信号 `taskContinue`）；重放安全按 `patched()`，只在收到新信号时才走新分支，老历史不受影响 |
| 叫停（现有） | `taskAbandon`，终局，库里 `stopped`，页面写清「不可恢复」 | 无。要再做只能新开一跑（要创始人定的 #3，推荐不做） |

关于「恢复=原分支重跑」（#820 原写法）：暂停那一路已经是原分支原树继续，是真正的恢复；叫停那一路工作树已存档后删，工作流编号也用掉了，诚实的说法是「重开新跑」，不叫恢复。
