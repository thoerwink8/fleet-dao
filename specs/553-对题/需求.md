# 对题（含建单）：把上下文写在单子上，缺栏拒开（#553）

对应计划：v3 三段一条龙
设计依据：

创始人 2026-10-02 原话：「从拿到需求、建立 GitHub issue 的时候，这个环节其实就已经带有上下文了。而这个上下文是建这张单子的 AI 去处理的，所以要维护的话，也应该由创建这张单子的 AI 来负责：1. 介绍清楚这个场景；2. 顺便把涉及的面也描述清楚（因为他当时是有上下文的）。」

AI 理解：三段里的第一段。建单的那个会话把「只有它知道的事」写进单子——场景、创始人的原话、它确实知道的模块。**涉及面不写**（创始人当场同意：那是算出来的、不是知道的）。缺栏拒开。飞书那一段只做整理、保留原话。

## 要干成什么：三段里的第一段——把你和创始人聊出来的需求，变成一张后面两段能直接开工的单子。

## 为什么现在做：创始人 2026-10-02：「从拿到需求、建立 GitHub issue 的时候，这个环节其实就已经带有上下文了……这个上下文是建这张单子的 AI 去处理的。」下游空手开始是这套流水线最容易断的一处。

## 怎么算做完：
1. 单子必有四栏：**场景**、**创始人的原话**（逐字）、**已知的模块**（建单会话确实知道的）；另有「要什么」「怎么算做完」。
2. **涉及面一律不写**——那是算出来的、不是知道的。
3. 缺栏 `pnpm issue:new` **拒开**，跟现在缺类别、缺里程碑一样硬拦。
4. 飞书那一段只做一件事：群聊理成一段意图，**原话原样保留**，AI 归纳另起一行标出来；用便宜快模型；**不建开单界面**。
