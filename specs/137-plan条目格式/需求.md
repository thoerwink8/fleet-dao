# plan 条目格式：每条随机短码编号一行、按阶段拆成 `docs/plan/P<N>.md`、合并前只查 plan 文件本身（编号唯一、格式、链接）（文档整套改法第①步）（#137）

对应计划：plan.md P0「plan 条目格式」
设计依据：design 第七节「plan、design、ops 的整套改法」第 1、2、6、12 条，`docs/decisions/0001-plan-design-ops.md`。

原话：plan 是「做什么」的唯一来源，每条一个随机短码的终身编号，一行编号、标题、链到 specs；按阶段拆成 `docs/plan/P<N>.md`（如 P1），和里程碑一一对应；合并前检查只查 plan 文件本身：编号唯一、格式、链接。（创始人 2026-09-26 拍「plan、design、ops 整套改法」，第①步）
AI 理解：现在 plan.md 是一整份，条目是自由写的句子，和 issue 靠人手对。这一步先把 plan 的形状定死：条目格式、状态、按阶段拆文件，外加一条只看文件的合并前检查；同步到 GitHub 是第②步，这一步不连 GitHub。

## 要做什么

照 `docs/design.md` 第七节「plan、design、ops 的整套改法」第 1、2、6、12 条：

- 条目格式：一行一条——`[T-xxxx]` 编号（随机短码，谁加谁生成）、标题、状态（未开始 / 已完成 / 待纳入，照第 4 条）、链到 `specs/<编号>-短名/`。给一个生成编号的小命令（本机 AI 加条目时用，查重后再给）。格式在方案里定死并写进 design。
- 拆文件：`docs/plan.md` 只留「现在的目标」和阶段目录；每阶段一个 `docs/plan/P<N>.md`（P0–P6），把现在各阶段的内容、验收搬过去；归档文件的位置和格式一起定（第②步往里挪）。
- 迁移：现有 plan 条目和开着的 issue 各配一个编号；已有的 `specs/<单号>-短名/` 目录保留原名，条目照指（不为改名制造断链），新条目用 `specs/<编号>-短名/`。开着的 issue 正文补上 `<!-- plan:T-xxxx -->` 标记（第②步的同步靠它认），这一次性的补标可以手工跑脚本。
- 合并前检查（进 `pnpm check` 和 CI 的 docs job）：编号唯一、格式对、链接指得到；只看文件、不连 GitHub。
- 跟着改（第 12 条，不留断链）：`packages/conventions` 里读 plan 的——文档指针（`doc-pointers.ts`、`plan.ts`）、PR 必填栏的「对应计划」（`pr-fields.ts`）、阶段收口（`milestone-close.ts`）、`issue-new.ts` 写的「对应计划」、引擎开 PR 时读 plan 的地方——都改成认新格式和按阶段的文件；PR 模板「对应计划」一栏改成写条目编号。
- 一起改的旧说法：design 第七节里「plan.md 只放验收标准」、PR 正文「对应计划写 plan.md 的阶段加那一条的原话开头」、15.6「走向」栏读 plan.md 的说法，AGENTS.md 本仓段开头「计划看 `docs/plan.md`」，README「文档各管什么」里 plan 那行。开单方式的说法（`pnpm issue:new`）留到第②步改。
- 每条读不到、认不出的路径（plan 文件缺、格式认不出、编号重复）报明确的 文件:行，各配一条故意造出失败的测试。

## 怎么算做完

- 测试：两个同编号的条目、一个格式不对的条目、一个链到不存在的 specs 目录的条目，合并前检查各报一条 文件:行；阶段文件缺了报错，不当成「没有条目」。
- 仓里：`docs/plan.md` 只剩「现在的目标」和阶段目录，`docs/plan/P<N>.md`（P0–P6）都在，现有条目都有编号；文档指针检查、PR 必填栏检查、`pnpm milestone:close-check` 在新格式上跑通（CI 绿）。
- 一个真 PR 的「对应计划」写条目编号，合并闸的提醒认得它。
