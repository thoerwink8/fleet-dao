# 新内核的多模型壳：放到另一个工作环境、按环节搭配模型（2026-11-03，讨论稿）

- 状态：讨论中
- 起因：需求方 2026-11-03 提了：除法国新内核外，给新 harness 包一层壳放到另一个工作环境用；那边可用的模型很多（Opus 5.5、GLM 5.3 及 flash、Kimi K3.1 PRO、Kimi 2.7 code、DeepSeek、GPT 系、Luna 等，经统一网关），想按环节搭配（指挥、拆分、写码、核验分别用不同模型）；那边偏人工（没有常驻服务器、可能是 Windows 本机、代码托管在非 GitHub 平台），但希望调度起来像正常 harness。问：好不好做、怎么做。
- 范围：查了新内核各包里哪些东西只在法国 Linux 上才有、怎么换；工人壳现状；几家模型官方的 Anthropic 兼容接口；几个同行壳（Codex CLI、opencode、pi-mono）的做法；按环节选模型的路由配置；对外仓的约束。没查：统一网关本身暴露哪些协议（需求方没给，列进第五节）；Luna 的接口类型（没查到公开资料，不猜）；cc-master 本稿没重读，只引 #3770 稿里已写的结论；GitLab 接口没做真连，只列要换的点。
- 怎么查的：读代码（codegraph + 逐文件读）、读官方文档（WebFetch、WebSearch）、读相关单和稿。证据标**实测**、**按代码**（文件:行号）、**推断**。本稿没有任何实测（没在 Windows 机器上起过内核，没拿任何一家模型的接口跑过），凡是「能不能跑」都是按代码或推断，第六节第 1 片专门补实测。
- 代码版本：`48ce3a26d`

## 一、提出的问题

### 1. 新内核哪些东西只在法国 Linux 才有，换成什么

- **现象**：逐项查（都是**按代码**）：

| 绑定的东西 | 在哪 | 换成什么 | 能做成接口按环境装配吗 |
|---|---|---|---|
| Postgres（`fleet2` schema） | 内核进程 `packages/harness-dispatch/src/bin/kernel.ts:14,64`（`postgres` 驱动）；存储层的类型是 drizzle 的 `PgDatabase`（`packages/harness-store/src/store.ts:9-12`），不绑驱动，`harness-store/src/testing.ts:2-16` 已经用 PGlite 跑过真迁移；调度器和 outbox 用 `FOR UPDATE SKIP LOCKED`、`now()`、`make_interval`、jsonb（`scheduler.ts:79-191`、`store.ts:234-257`、`schema.ts:29`） | PGlite（内嵌 Postgres，落文件）。不换 SQLite：schema、调度器、投影都是 pg 方言，换 SQLite 等于重写存储层 | 能：`kernel.ts` 里按 `FLEET2_DATABASE_URL` 的形态选驱动，存储层不用改。PGlite 现在只是 devDependency（`harness-store/package.json`），要升成正式依赖。PGlite 单连接，对一个人用的单机够，多进程同时开同一份文件不行（推断，第七节） |
| systemd 单元 | `deploy/france/fleet2-kernel.service` 等；代码里内核是普通 node 进程、配置全从环境变量来（`bin/kernel.ts:1-3`），收 SIGTERM 优雅退出（`kernel.ts` 末段） | 人在终端里前台起 `node …/kernel.ts`，Ctrl+C 退；要常驻时是人的事（计划任务、`pm2` 都行） | 能：代码本来就不依赖 systemd，单元只是包了一层，不用改代码 |
| cgroup 隔离、会话用户、sudo 帮手 | 接口 `harness-workers/src/sandbox.ts:18-28`；真实现 `harness-dispatch/src/scope-sandbox.ts`（`sudo -n fleet-agent-scope`）；`slot.ts` 里 sandbox 是可选的，「不给就是同一个用户（本机、CI）」 | Windows 上退一档：不给 sandbox，靠第四条的几层软隔离 | 已经是接口：不用改，只是那边不给。要补的是「隔离档位」读回（见第 4 条） |
| 进程收尸靠 `/proc` | `harness-runner/src/procs.ts:3,10`（`HAS_PROC`）、`process.ts:58`：没有 `/proc` 时 `leftovers` 是 undefined、照实记「没查成」；`process.ts:165,182` 用进程组（`detached`、`process.kill(-pid)`）只在 posix | Windows：进程树收尸（`taskkill /T` 或 Job Object） | 要补：现在 Windows 上收不干净会记「没查成」，不会假装收好，但也没真收。这是实写的活 |
| 出网关（SNI 透明代理 + nftables） | `packages/harness-egress`（`proxy.ts:1-4`）、`deploy/france/fleet2-shadow.nft`、`fleet2-egress.allow` | 不装。那边唯一需要的出口是统一网关一个地址，没有「别的网站要拦」的问题；拦不住的话靠第 2 条的密钥不进工人 | 能：出网关本来是影子模式（对比旧系统、防工人搜到已合并答案）才要的，真干活不需要（`slot.ts` 的 `shadow` 为空就不过自检，`shadow.ts`） |
| GitHub App（读） | `harness-dispatch/src/github-app.ts:15-35`（只读权限、按仓换短期令牌）、`github-read.ts:17`（`https://api.github.com`，`taskFor`、`readMerged`） | 任务来源接口：GitHub 实现留着，GitLab 实现（REST v4 的 issue、merge request 读）另写；没有网络或不想接，就从本地文件或命令行给任务 | 要新建接口：现在内核直接吃 `gh.taskFor`（`bin/kernel.ts:67,88`），没有抽象层 |
| GitHub 写（推分支、开 PR、评论、合并） | 契约里 outbox 种类是 `git.push`、`github.pr.open`、`github.comment`、`github.merge`（`harness-contract/src/index.ts:80-82`）；但**新内核至今一个真实处理器都没装**，内核头注释就写了「对外零写」（`harness-dispatch/src/kernel.ts:2,118`） | 种类名改成平台无关（`change.open`、`change.comment`、`change.merge`），GitHub、GitLab 各一个处理器；第一版 GitLab 一个都不装，补丁和本地分支交给人 | 能，而且这是改契约的最好时机：现在还没有真实处理器依赖这些名字。契约有 `schemaVersion`（认不出的版本拒），改名走版本号 |
| 镜像从 GitHub 匿名建 | `shadow-workspace.ts:3,80`（`https://github.com/${repo}.git`，只认公开仓） | 工作目录从那边人给的本地克隆建（`git clone --local`），不联网 | 能：`mirrorRemote` 本来就是可传的参数（`shadow-workspace.ts:80`） |
| reclaude（Claude 的拼车代理） | 执行体前缀 `FLEET2_WORKER_COMMAND`（`bin/kernel.ts:40`）；`deploy/france/fleet2-worker.sh` 里写死 reclaude 路径 | 直接用 `claude`，经统一网关的 Anthropic 兼容地址 | 能：命令前缀本来就是配置，槽位只管拼参数（`claude-code.ts:39-66`） |

- **根因**：新内核分层时就把存储、沙箱、任务来源放在接口后面（存储用 drizzle 的泛型库、`WorkerSandbox`、`mirrorRemote`、`taskFor`），但**装配只写了法国这一种**（`bin/kernel.ts` 一个文件里直接 new 了 postgres、scopeSandbox、GitHub 读取器）。要的不是重写，是把装配拆成「按环境选」。
- **需求方的思路**：包一层壳放到另一个环境用。
- **判断**：成立，难度中等偏易，没有哪一项是不可替换的。有一件事要先说清：**法国这边的新内核自己还在影子模式、还没有真实写 GitHub 的能力**（按代码，上面第 6 行），壳要的「真实派活、写码、交出结果」有一半是这条主线本来就要做的（#3770 的后续片），壳不能抢在它前面。第六节的顺序按这个排。
- **做法**：见第五、六节。
- **不做什么**：不把法国的部署搬过去；不在那边装 Postgres 服务、systemd、nftables；不把 GitHub App 的凭据放到那边。

### 2. 工人壳：哪些模型走哪种壳

- **现象**（**按代码**）：`harness-workers` 现在有两个壳，Claude Code（`src/claude-code.ts`）和 Grok 命令行（`src/grok.ts`，#3842 已合并），槽位按 `shell` 选（`slot.ts:87-96`）。但选壳和选模型是**整个内核一份**：`FLEET2_SHELL`、`FLEET2_MODEL`（`bin/kernel.ts:51-57,77`），不是按环节、按任务。`buildClaudeArgs` 的模型名校验允许 `.`、`-`、`:`、`[`、`]`（`claude-code.ts:37`），所以 `glm-5.3[1m]` 这类写法能过。
- **查官方文档**（WebFetch，2026-11-03 当天）：
  - **DeepSeek**：官方有 Anthropic 兼容接口 `https://api.deepseek.com/anthropic`，环境变量 `ANTHROPIC_BASE_URL`、`ANTHROPIC_API_KEY`；自定义工具支持（`type: "custom"` 会 422）；`mcp_servers` 参数被忽略（这是服务端的服务器型 MCP，Claude Code 的 MCP 是客户端自己连，推断不受影响，要实测）；`deepseek-v4-pro` 不处理图片，换成文字「[Unsupported Image]」。
  - **GLM**：Z.ai 官方 `https://api.z.ai/api/anthropic`，密钥放 `ANTHROPIC_AUTH_TOKEN`，要同时设 `ANTHROPIC_DEFAULT_OPUS_MODEL`、`_SONNET_MODEL`、`_HAIKU_MODEL`（页面给的是 `glm-5.3[1m]`、`glm-5.3-flash[1m]`）。**三个都要设**：Claude Code 内部有按档位的后台调用（推断），不设会发出对面不认识的模型名。页面还要求 `API_TIMEOUT_MS`、`CLAUDE_CODE_AUTO_COMPACT_WINDOW`。
  - **Kimi**：官方模型页写 Messages 接口「Anthropic Messages API compatible, for integrating with the Anthropic SDK, Claude Code」，推荐 `kimi-k3.1-pro`（另有 `-highspeed`）；但我取到的那页**没写 Anthropic 兼容的具体地址**，只给了 OpenAI 兼容的 `https://api.moonshot.ai/v1`。搜到的第三方页写的是 `https://api.moonshot.ai/anthropic`、`ANTHROPIC_AUTH_TOKEN`，标**推断**，要实测。「Kimi 2.7 code」官方页提到名字但没给接口 id，**没查成**。
  - 以上三家都是**官方直连**的地址；需求方说那边模型经统一网关，网关给不给 Anthropic 格式的入口，是网关的事，**没查**，列进第五节。
- **只有 OpenAI 兼容接口的模型走哪种壳**（GPT 系；Luna 没查到资料）：

| 壳 | 自定义 OpenAI 兼容服务 | 无头 | MCP | 判断 |
|---|---|---|---|---|
| Codex CLI | 配置里 `[model_providers.<id>]`，`base_url`、`env_key`（官方页）；`wire_api` 页面只出现 `responses`，Chat Completions 型提供方页面提到但取值没列，**没核实**；无头 `codex exec` | 有 | 有（`mcp_servers`，页面指向单独文档） | 只认 GPT 系家族时合适；对只有 chat/completions 的网关可能要先实测 |
| opencode | `npm: @ai-sdk/openai-compatible`（`/v1/chat/completions`）、`@ai-sdk/openai`（`/v1/responses`），`options.baseURL`；多家任意模型，`--model provider/model` | `opencode run --format json`，也有 `opencode serve` 常驻后 `--attach` | 有（页面提到「避免每次 MCP 冷启动」，说明支持） | 最通用：一个壳覆盖所有 OpenAI 兼容模型，也能接 Anthropic 兼容的；输出是 JSON 事件，要自己写一个 transcript 解析器（和 Grok 壳同样的活） |
| pi-mono（`pi`） | 多家 provider（`pi-ai`）；自定义 OpenAI 兼容页面**没写** | print、JSON、RPC | 页面**没提** | 工人交结果靠我们的 MCP（`mcp-config.ts`），没有 MCP 就要换交结果的办法，现在没有证据它能做，不选 |

  - **做法**：第一阶段只用 Claude Code 壳 + 改 base URL，覆盖所有有 Anthropic 兼容入口的模型；OpenAI 兼容的 GPT 系、Luna 等放第二阶段，加 opencode 壳（一个壳通吃）。如果统一网关本身就吐 Anthropic 格式（很多网关能做协议转换，**推断**，要问），则第二阶段可以不做。
- **壳要满足的最低线**（来自 Grok 壳的经验，#3842）：能无头、能续会话或一轮一会话、能挂我们的 HTTP MCP（或有替代的交结果办法、事件照样落库）、输出能拆成同一套 `transcript.*` 事件。
- **不做什么**：不为每个模型写一个壳；不碰 Cursor、pi 壳（决定 0124 表里提过，这次不排）；不自己写协议转换层。

### 3. 按环节选模型的路由配置

- **现象**（**按代码**）：现在只有「工人」一个环节真调模型；任务说明由代码拼、核验是机械的（`specs/3842-fleet2-session-split/讨论稿.md` 第一节第 1 条）。指挥官、拆分、模型核验在新内核里还没接模型。`worker.spawned` 事件已经记了 `model`、`shell`（`slot.ts:126-131`），但没有「环节」「渠道」。
- **同行做法**：oh-my-openagent 的配置：每个 category 可设 `model`、`temperature`、`prompt_append`，也能自定义 category；解析顺序是用户覆盖 → category 默认 → 用户的 `fallback_models` → 内置的按服务商回退链（WebSearch 取自它的 v3.13、v3.14 文档，各版本编号略有不同，**没读源码**）。orca 一题多派择优见 #3791（单正文：同需求派给几家，机器核对择优）；cc-master 本稿没重读。
- **做法**（设计，不写代码）：配置分两张表，放在**内核自己的用户目录**（不进目标仓），每次起内核读一遍并校验：
  1. **渠道表**：`id`、协议（`anthropic` / `openai` / `grok-cli`）、`baseUrl`、**密钥只写环境变量名**（不写值）、可用模型清单、超时。例：`gateway-a` 协议 anthropic，`gateway-b` 协议 openai。
  2. **路由表**：键是「环节」（`commander`、`split`、`code`、`verify`）加可选的「任务类型」（界面活、小改动等，沿用 #3842 稿第三节的任务类型）；值是 `{channel, model, shell, 兜底列表, 预算档}`。解析顺序仿 oh-my-openagent：任务类型专属 → 环节默认 → 兜底列表。
  3. **启动校验**（配置错了不起，不是运行时才发现）：引用的渠道、模型存在；shell 和渠道协议对得上（Claude Code 壳只配 `anthropic` 渠道）；密钥环境变量有值；`verify` 的模型族不得等于同一件活 `code` 的族（沿用决定 0006 的「核验换家」，用一份「模型 → 族」小表做判断）；同一环节兜底不得全部同族同渠道。
  4. **每次派工把用到的路由记进 `worker.spawned`**（环节、渠道、shell、模型、命中的是哪一条规则），这样 #3842 稿第三节的「模型 × 任务类型」统计表直接能分，不用另外打标。
  5. **一题多派择优**（#3791）：路由表值允许写多个并列条目（`fanout`），内核对每条各起一个工人、各一棵工作目录，交回后按机器可核的几条择优；这是第二阶段的事，路由表第一版就留这个位置，不然以后改格式。
- **不做什么**：不做运行时自动「看哪家便宜就换」；不按模型自评打分；不做界面编辑路由（先改文件，驾驶舱只读展示）。
- **按模型和任务类型统计效果**：#3842 已在做（稿第三节、`fleet2.shadow_compare`），本稿只要求路由信息进事件，统计表本身不重做。

### 4. 密钥和隔离：模型密钥怎么给、Windows 上怎么隔离

- **现象 1（**按代码**，这是个坑）**：工人环境构造（`harness-workers/src/env.ts:28-35,53-62`）会拒掉名字里含 `TOKEN`、`SECRET`、`API_KEY` 的变量，抛 `ForbiddenEnvError`。而 Claude Code 走第三方地址要用 `ANTHROPIC_AUTH_TOKEN` 或 `ANTHROPIC_API_KEY`——**直接按第 2 条配会被自己的规矩拒掉**。法国上没遇到，是因为 reclaude 自己管上游，工人环境里不带密钥。
- **根因**：设计前提是「工人拿不到任何密钥」（`env.ts:2`）。换成直连模型服务后，这个前提需要另一种办法保住。
- **备选**：
  - (a) 白名单放行：渠道表里指定的那一个变量名放过禁表。代价：真密钥进了工人的进程环境，模型能读到、能写进输出；Windows 本机没有用户隔离，工人和人同一个用户，等于模型拿得到那边的统一网关密钥。
  - (b) 内核起一个**本机回环代理**（只听 127.0.0.1，随机端口），真密钥只在内核进程里；工人拿到的是 `ANTHROPIC_BASE_URL=http://127.0.0.1:<端口>` 加一个**每轮随机的假令牌**（只有这次运行有效，过了就废）；代理核对假令牌后换成真密钥转发到渠道，并按渠道、按轮记用量。代价：多一个小组件（转发流式响应，要测）；好处：密钥不进工人、用量统一在内核里记（顺带给统计用）。假令牌名字仍含 `TOKEN`，要给 `env.ts` 开一个**精确的**例外（只放这一个名字、只放这个形态的值）。
- **判断**：推荐 (b)。法国的出网关是同一思路（工人没权限绕过网络做事），这是它在没有 nftables 的环境里的对应物；且代理必须是**内核**起的，那边的人不用额外配置。
- **现象 2**（隔离，**按代码**加**推断**）：Windows 没有 cgroup、没有会话用户、没有 sudo 帮手。能叠的软隔离，每一层都已经在代码里：
  1. 工作目录是内核建的临时克隆，不是人自己的工作目录（`shadow-workspace.ts:1-8`，要把「从 GitHub 匿名建」换成「从本地克隆建」）；
  2. 工人环境只抄白名单变量，且白名单里本来就有 Windows 必需的几项（`env.ts:4-25`）；
  3. 调工具前的钩子 `agents/hooks/pretool.mjs` 经命令行 `--settings` 传给 Claude Code（`claude-code.ts:24-34,54`），不是写进目标仓；
  4. 权限档不用 `bypassPermissions`，用 `acceptEdits` 或 `dontAsk`（`CLAUDE_PERMISSION_MODES`，`claude-code.ts:5`）；`env.ts` 注释写明放开权限的前提是工人用户读不到凭据，所以 Windows 档**必须**降权限档；
  5. 没有 `/proc`，进程收不干净（见第 1 条表第 4 行），要补进程树收尸。
  这些加起来不是隔离，是「降低出事概率」。要硬隔离的办法：整个内核放 WSL2 里跑（有 `/proc`、能用进程组；cgroup 和 nftables 能不能用取决于 WSL 配置，**推断**）或放一台 Linux 机器，列进第五节。
- **内核启动时读回当前隔离档位**（`强`：会话用户 + cgroup + 出网关；`中`：WSL 或 Linux 无 sudo 帮手；`弱`：同用户软隔离），记进事件、驾驶舱显示。和影子自检同一思路（`shadow.ts`）：不靠自称。
- **不做什么**：不在 Windows 上实现 cgroup 的等价物（Job Object 只用来收进程树，不当隔离宣传）。

### 5. 对外仓：那边的代码仓里不能留下我们的东西

- **现象**：那边的代码仓是对外仓（仓不在需求方自己的 GitHub 下，通用规矩「对外仓和对外内容怎么写」，`agents/shared-rules.md:24-29`）：对外仓必须自己就完整，fleet-dao 只做加法、不往里加骨架、检查、标记文件；提交、MR、文档里不加 AI 署名、不写 AI 工具的事；以仓自己的 AGENTS.md 和规范为准。
- **按代码，现有设计本来就大致兼容**：MCP 配置写在内核的临时目录（`slot.ts:84` 的 `mkdtemp`），令牌不进命令行；调工具的钩子经 `--settings` 命令行传入；`--setting-sources project` 只读仓自己 `.claude` 里的项目级设置（`claude-code.ts:50-55`）——也就是工人读的是**他们仓自己的**设置，我们不往里写。
- **要守的几条**（写成壳的约束，推荐第一版就做成自检）：
  1. 内核、路由表、数据库、临时工作目录全部在内核自己的用户目录下，**目标仓的工作目录里一个我们的文件都没有**；提交前检查「工作树里有没有不属于仓的新文件」交给任务说明和机械核验（`verify.ts` 已有「改到允许范围外的路径」的判法）。
  2. 提示词只写「按这个仓自己的 AGENTS.md 和规范做」，不往提示词里塞 fleet-dao 的规矩；任务说明模板（`harness-dispatch/src/prompt.ts` 的 `buildWorkerPrompt`（`dispatcher.ts:399` 调用））给这个壳准备一份不含 fleet-dao 专有说法的版本。
  3. 提交信息不带 `Fleet-Run:`、`Fleet-Model:` 尾注（#3842 稿里那两行尾注**只给自用仓**，稿里已写明），也不带任何 AI 署名；MR 描述同理。效果统计只进内核自己的库。
  4. 壳不装 git 钩子、不改仓的 `.git/config`、不改 `.gitignore`（用克隆而不是 `git worktree add` 到仓里，后者会往仓的 `.git` 写管理目录）。
  5. 内核的发行方式：那边的人把 fleet-dao 克隆到自己的目录运行（公开仓，不含他们的任何信息）；他们的仓只被它当工作对象。
- **不做什么**：不做「在目标仓里装个插件」；不在他们的仓里放配置文件。

### 6. 先做哪些、做到哪一档

- **现象**：「像正常 harness 一样调度」包含：任务进来、拆分、派工、写码、核验、交回、对外送结果。法国新内核现在这条链走到哪：派工、写码、机械核验、交回都有（`harness-dispatch`），拆分和模型核验没有（没有 `harness-orchestrator` 包，按目录列表），对外送结果（outbox 处理器）没有。那边「比较人工」的说法，正好和「第一版结果交给人送出去」一致。
- **按难度分**：
  - **易**：Claude Code 壳 + 渠道表 + 路由表，覆盖所有有 Anthropic 兼容入口的模型。主要工作是配置、校验、事件里记路由、实测每个模型能不能稳定调工具。
  - **中**：存储换 PGlite、内核按环境装配、任务来源接口加 GitLab 读、Windows 的进程树收尸和降档隔离、回环代理。每项都是一个明确的小片。
  - **难**：OpenAI 兼容模型的第二个壳（要解析它的输出、保证 MCP 交结果）；GitLab 的自动写（推分支、开 MR、合并）；Windows 上要硬隔离。这三项不进第一阶段。
- **注意**：模型能不能稳定当工人（连续调工具、遵守长提示、MCP 交结果），**从文档读不出来**，每家都要真跑。这是整件事最大的未知（第七节）。

### 7. 横向：同一个根因在别处

「装配只写了一种」的同一根因，在驾驶舱、部署脚本也有：驾驶舱（`harness-api/src/bin/cockpit.ts:30`）同样直连 Postgres；`deploy/france/*` 是整套 Linux 部署。这次不动驾驶舱：那边要看进度，第一版用命令行查事件（`harness-api` 已有按事件号续传的接口，本机访问就行）；要界面就是同一套 `harness-web` 连本机的内核，同样需要第 1 行的存储换法，列进后续片。

## 五、要拍板的

1. **做到哪一档**
   - A. 全自动：含向 GitLab 推分支、开 MR、合并。
   - B. 半自动：自动拆分、写码、核验，结果落成本地分支和补丁，**由人推送、开 MR**。
   - C. 最小：只有路由表和 Claude Code 壳，派工由人手工起（不要内核常驻调度）。
   - **推荐 B**，并按 C → B 分步交付（C 是 B 的第一阶段，不是另一条路）。理由：对外仓的写操作风险最大、需求方说那边本来偏人工；GitLab 写可以等第一版稳了再加。A 要新内核先有真实写 GitHub 的处理器，现在还没有。
2. **本机数据库**
   - A. PGlite（内嵌 Postgres，存文件）；B. 改 SQLite（重写存储层）；C. 让那边装 Postgres 服务。
   - **推荐 A**：代码已经按 PGlite 跑过全部真迁移和调度器测试（`harness-store/src/testing.ts`）；B 的代价是重写 schema、调度器、投影；C 违背「没有常驻环境」。风险：单连接、Windows 文件落盘没真测过（第七节）。
3. **OpenAI 兼容才有的模型（GPT 系、Luna）怎么接**——先要问清「统一网关有没有 Anthropic 格式的入口」。
   - A. 有 → 全部走 Claude Code 壳，不加壳；B. 没有 → 第二阶段加 opencode 壳；C. 没有也不加，GPT 系只当「指挥」用，由人手工贴。
   - **推荐**：先问网关，再按 A 或 B；不选 C。第一阶段先只用 Anthropic 兼容的那几家，不等这一项。
4. **模型密钥怎么给工人**
   - A. 白名单放行真密钥；B. 内核起回环代理，工人只拿假令牌。
   - **推荐 B**（见第一节 4）。A 在 Windows 无隔离时等于把网关密钥交给模型。
5. **Windows 上隔离做到哪**
   - A. 同用户软隔离 + 降权限档（起步）；B. 整个内核放 WSL2；C. 要求用 Linux 机器。
   - **推荐 A 起步，第一版就把「隔离档位读回」做进去**，需求方愿意时再升到 B。不推荐 C（违背需求方「可能是 Windows 本机」）。
6. **核验换不换家**
   - A. 沿用决定 0006，路由表校验强制 `verify` 与 `code` 不同族；B. 不强制。
   - **推荐 A**：那边模型多，换家成本几乎为零，独立核验的价值（#3842 稿第二节）更大。
7. **这个壳放在哪个仓、怎么发给那边**
   - A. 就在 fleet-dao 里，加启动「档案」（profile）：`france`、`local`；那边克隆公开仓运行；B. 拆成单独的仓。
   - **推荐 A**：公开仓里本来就没有那边的信息；拆仓增加两仓同步的负担。目标仓里不放任何东西（第一节 5）。
