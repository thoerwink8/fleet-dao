# 方案：全流程巡检（#223）

需求见 [需求.md](需求.md)。规矩写在 design 第六节「断链怎么被发现」第 3 层；运维（要配什么、手动跑一轮、看结论、演练、停）在 docs/ops.md 第五节「全流程巡检」，健康页那一项在第九节。

## 拆成几块、各改哪里

1. **库**（迁移 `0016_canary_runs`，只建表、约束、索引）
   - `canary_runs` 一轮一行：挂在哪次 `schedule_runs` 上、巡检仓、开的单号、任务、开始和结束时刻、结论（pass / broken / not_run）、停在哪一步、为什么、走过的每一步和时刻、留下的单收掉的时刻。
   - 约束：有结论才有结束时刻、反过来也一样；断了、没跑成必须写为什么（不许「没通过，也不知道为什么」）；步骤是数组；单号是正数。
   - `packages/db/src/queries/canary.ts`：记开始、写进度、记结论（有了结论不再改）、健康页读最近一轮有结论的和正在跑的、列前几轮留下没收的单、补记没收尾的几轮、记收掉了；`canaryDbFacts` 读巡检每一回要的事实（仓和接活开关、任务行、会话几个起来了几个结束了几个有用量、每步耗时几笔、块和 PR、这张单工作流报的开着的提醒、最近一次投递怎么处理的）。判断不在库里。
2. **GitHub**（「引擎」机器人，`packages/github`）
   - 开单用 #259 加的 `openIssue`（按键幂等，不贴标签、不挂里程碑）；新加 `setIssueMilestone`（挂完按回执核对编号）、`readOpenMilestones`（找巡检仓的当前版本）、`readIssueState`（看单子关成什么样）；关单照旧 `closeIssue`。
3. **一轮怎么跑**（`packages/engine/src/jobs/canary.ts`，判断是纯函数 `canaryNext`）
   - 开单：记开始 → 补记没收尾的几轮（过了一轮工作流的时限还没结论的，记没跑成）→ 收前几轮留下的单（叫停工作流、关成不做了）→ 找巡检仓的当前版本 → 开单（不挂里程碑）→ 需求文档经 PR 进主线 → 挂当前版本。接活只派挂在当前版本上的单，先挂上的话工作流可能在需求文档进主线之前起来，所以最后才挂。哪一步没成都算没跑成，开出来的单关掉作废。
   - 之后每 2 分钟看一回：读库、问 Temporal（工作流在不在、Fusion 的 status 查询走到哪一步、挂没挂起），任务做完了再读 GitHub 上的单子和驾驶舱读到的样子。一回里能往前走几步走几步。
   - 十一步和期限（分钟，从上一步走完算起；等并发空位、等额度清零的时间不算，那是忙不是断）：开单 10、收单 20、派活 30、规划 45、执行 60、验证 45、开 PR 过 CI 45、合并 30、关单 15、记账 10、驾驶舱显示 10；一轮最长 5 小时。
   - 当场算断、不用等期限的：巡检仓不受管了；派活这一步接活开关关着（或开关是开单之后才打开的）；任务失败、被叫停；这张单的工作流报了要人看的提醒、挂起等人；工作流不见了、没跑完就关了；单子被关成不是做完。
   - 结论三种，分开记：通过（撤掉断了的那条报警）；断在哪一步（推一条卡住报警 `canary:broken`，正文写断在哪、为什么、走到哪了、单子在哪；同一个键，下一轮再断原地更新）；没跑成（没配巡检仓、仓读不到、没有当前版本、开不了单、需求文档没进主线、连着 10 回查不成、工作流没收尾就没了）。`schedule_runs` 里通过、断了记 ok（发现 0 / 1 个），没跑成记 failed——看门狗（#203）照登记表报没跑成，断了由巡检自己报。
4. **定时**：Temporal Schedule `canary`（每 6 小时、偏 26 分，北京时间 2、8、14、20 点 26 分；SKIP 重叠；错过的一小时内补；一轮工作流最长 5.5 小时），工作流 `canaryWorkflow` 调两个活动 `canaryOpen`、`canaryCheck`（job 档）；看一回的活动连着失败到上限工作流就失败，库里那一轮停在没结论，下一轮开始时补记没跑成。登记进 `scheduled_jobs`（期望间隔 13 小时：漏一轮不报，连着两轮没跑成才算过期）。引擎启动时和别的定时任务一起建或更新。
5. **真装配**（`packages/engine/src/real/canary.ts`）：巡检仓读引擎配置 `FLEET_CANARY_REPO`（owner/name，写在法国的 `/etc/fleet-dao/engine.env`，公开仓里不写真值；没配、认不出这一轮记没跑成、写明缺什么）；叫停前几轮留下的单和驾驶舱叫停同一个信号；「驾驶舱显示」读的是驾驶舱后端的 Store（看板、任务详情读的同一份）。
6. **健康页**：`/healthz` 加 `canary` 项（健康页写「全流程巡检」，`packages/api/src/canary-health.ts`）。通过、12 小时内通过过：绿，写几点通过、用了多久；断了（写断在哪一步）、巡检自己没跑成、一轮过了 5.5 小时还没结论、12 小时没通过一轮、一轮都还没跑完：红。对外只说哪一步、几点，原因原文只进日志。不在法国的正式机器上报「未接」。它跟着巡检的结论自己变红，发版脚本只标待处理、不退回（`deploy/release.sh` 的 `DRIFTING_HEALTH_ITEMS`）。

## 需求文档怎么进主线（等 #295）

巡检单和人开的单一样，需求文档要在派下去之前进主线：收单认「文档：」那一行，开 PR 前验证照主线上那份的「怎么算做完」逐条核（不读分支上的，干活的改不了验收条）。引擎不直写主线（0003），所以不能像旧的需求工作流那样经 Contents API 直接写；要走 PR、CI 绿、合进去。这和引擎对账开的后续单缺的是同一样（#295，另一个工人在定做法），不另做一份：巡检留一个口子 `specDoc`（`land` 经 PR 把需求文档合进主线，按这张单幂等），#295 接上后在 `real/canary.ts` 传进去就通。接上之前真装配给的是 `unavailable`：每一轮在开单之前记没跑成、写明等 #295，一张单都不开（开了也注定停住，白占会话）。

## 巡检仓要配的

巡检仓 `fleet-dao-canary`（和 fleet-dao 同一个 GitHub 账号下）：受管（在 `repos` 表里）、「让 AI 接活」开着；一个一直开着的 `v1 巡检` 里程碑（接活只派当前版本上的单）；`.fleet/flow.json` 写测试命令 `node --test`。一样不齐，这一轮照写的原因记没跑成或断在派活。

## 故意造出的失败

- 巡检仓的路由全关：Fusion 起来了、一个会话都起不来、挂起等人，这一轮断在「派活」、推报警、记进库；巡检本身跑成了（登记表上 ok）。真库上也跑一遍（`packages/engine/test/canary.test.ts`）。
- 巡检自己起不来：一次都没跑过登记表上是 never；没配巡检仓、仓读不到都记没跑成，登记表上 failing。
- 接活开关关着：当场断在「派活」。连着查不成到上限、工作流没收尾就没了、需求文档进不了主线（#295 接上之前）、需求文档的 PR 没合进去：记没跑成，不当成没问题。
- 健康页：断了、没跑成、太旧、没收尾、一轮都还没跑完都红；每一种对外的说法拿演示版打包扫描的名单扫，不带仓名、单号。
- 这些测试拿改动前的判法跑是红的（把挂起、报警的判断去掉，路由全关那条就过不了；把没跑成记成 ok，起不来那条就过不了）。
