# 方案：fleet-api 的 socket activation 接到发布脚本上（#405）

## 前提核对（需求「怎么算做完」第 1 条）

「引擎排空发布」那次已经合进主线（#396，c86671b）：`deploy/release.sh` 和 `deploy/france/fleet-api.service` 之后没人在改，不会撞车。
参考稿里的地址和现在的 `api.env.example`（`FLEET_COCKPIT_LISTEN=10.99.0.2:8787`、`FLEET_AGENT_LISTEN=127.0.0.1:8788`）、`release.sh` 的 `COCKPIT`/`AGENT_API` 常量一致。

## 和参考稿不一样的两处

1. **`fleet-api.service` 用 `Wants=fleet-api.socket`，不用 `Requires=`。** 需求第 3 条要求「机器上没有这个 socket 单元时服务照样起得来」，参考稿写的 `Requires=` 做不到：依赖一个不存在的单元，systemd 直接拒启。`Wants=` 加 `After=fleet-api.socket` 两头都顾到：有 socket 单元就先起它，systemd 按默认的 `Sockets=`（同名的 `.socket`）把 fd 传给服务；没有它，服务照旧自己 bind。另外 `Requires=` 还会让「停 socket」连带停掉服务，回退那一步的顺序更难控制。
2. **启动日志写明走的是哪一条路。** 需求第 6 条要在日志里看到「从 systemd 接手 fd」，可现在的 `listen.ts` 和 `main.ts` 两条路都不打日志，查不出来。改法：`main.ts` 在调 `startListeners` 之前记下有没有 `LISTEN_FDS`（`startListeners` 里会把它删掉），然后在「驾驶舱后端已起」那条日志里加一个 `listen` 字段：`systemd`（接手 fd）或 `bind`（自己绑）。顺手把 `main.ts`、`listen.ts` 注释里「deploy 侧还没接、留了后续单」的旧说法改掉。除此以外不碰进程这一侧。

## 改哪些文件

- **新增 `deploy/france/fleet-api.socket`**：照参考稿抄，两个 `ListenStream`、`FreeBind=yes`、`Service=fleet-api.service`、`WantedBy=sockets.target`。注释写明：地址要和 api.env 以及 release.sh 的两个常量一起改；改地址只能人工操作，发布脚本不会自动去动已经装上的 socket。
- **`deploy/france/fleet-api.service`**：`[Unit]` 段加 `Wants=fleet-api.socket`，`After=` 最前面加上 `fleet-api.socket`，旁边一行注释说明为什么用 Wants。
- **`deploy/release.sh`**：
  - `build_release()`：提交里有 `deploy/france/$u.socket` 的，存进 `.units/$u.socket`。可选文件，没有不算错。
  - 新增 `sync_socket_unit 单元 目录`，照参考稿写三种情况：①这一版带、机器上没有：停服务、装 socket、`daemon-reload`、`enable --now`，再强制重启；②带、机器上已有：不动；③这一版不带、机器上有：`disable --now`、删文件、`daemon-reload`，再强制重启。返回的「要强制重启」不用全局变量传，改成让调用方在 `fresh[$u]` 上置 1。哪一步失败都要报红、返回 1。
  - `activate()`：启用的服务在装 `.service` 之前调 `sync_socket_unit`；没启用、要撤掉的服务，**先**撤它的 `.socket`（`disable --now`、删文件）、再停服务。顺序反过来的话，一有新连接 socket 就会把刚停掉的服务又拉起来。
  - `settle_services()`：机器上装了 `$u.socket` 的，还要确认它是 `active`，不是就报红、判不稳。
  - `do_check()`：「服务」这一步里，装了 socket 的列一行「`$s.socket` 在攥着端口」，没在跑就报红。
- **`deploy/test/release-flow.test.sh`**：在最后那段「真起一个服务」（要 root，CI 上用 sudo 跑）后面加一段真 socket 单元的来回。临时单元名用 `fleet-release-test-$$`，端口挑一个本机空闲的高端口：
  1. 这一版带 socket、机器上没有：装上以后 socket 是 active，服务也起来了；
  2. 再跑同一版：socket 的 `ActiveEnterTimestampMonotonic` 没变（没被碰过）；
  3. 切到不带 socket 的一版：socket 文件没了，服务照样在跑；
  4. 故意造失败：先占住那个端口再装 socket，`activate` 返回 1，而且报了红，不假装装好了；
  5. 没启用、要撤掉的服务：撤完 socket 和服务都没了，也没被重新拉起来。
  
  `cleanup_unit` 同时清掉 `.socket`。
- **`docs/ops.md`**：文件表（第 84 行）加 `fleet-api.socket`；第九节发布步骤里补一句 socket 单元的三种情况和「改监听地址要人工一起改」；整套撤掉的命令（第 418 行附近）先撤 `fleet-api.socket` 再撤服务；应用表（第 531 行）注明两个端口由 `fleet-api.socket` 攥着。

## 怎么验证

- 本机：`bash -n`、shellcheck（`deploy/test/run.sh` 里本来就有），`pnpm test:changed`（包括 api 包的类型检查和测试）。
- CI：`sudo bash deploy/test/run.sh` 会跑上面那段真 systemd 的来回，第 4 条是故意造的失败。
- 法国（合并后由自动发布发出去，第 6 条）：`systemctl is-active fleet-api.socket` 是 `active`；`journalctl -u fleet-api` 里「驾驶舱后端已起」那条的 `listen=systemd`；一边用轮询脚本每 50ms 打一次 `127.0.0.1:8788` 和驾驶舱接口的 `/healthz`，一边 `systemctl restart fleet-api`，确认一次 `ECONNREFUSED` 都没有。读数写进 `结果.md`。第一次装会停一下服务（情况①），这次短暂拒连是预期内的，只发生这一次。

## 不做的

- 不改 `listen.ts` 的接手逻辑（上一张单已经测过）。
- 不让发布脚本自动改已经装上的 socket 的监听地址（需求明确说这是人工操作）。
- 不碰 `fleet-engine.service`、防火墙、sudoers。
