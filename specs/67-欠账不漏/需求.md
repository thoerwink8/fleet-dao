# 欠账不漏：开着的需求单都有需求文档和验收；文档里「以后再做」必须带单号；阶段收口前清点（#67）

对应计划：plan.md P1「工作流」
设计依据：design 第三节第 35 条、第七节「欠账不漏」「阶段收口」。

原话：
- 本项目之前约定过，需求要 GitHub 和 docs 目录都要存一遍完整需求，我看没实现？（创始人 2026-09-25；对过 design 第七节后拍：照 design 第七节——完整需求只在仓里 specs/ 存一份，issue 放原话、AI 理解、进度和链接）
- 渐进式实现可以，渐进式记忆绝对不可以：可以现在只实现一部分规则，但剩下的必须在系统里留下机器可追踪的「未完成承诺」，每条带验收标准；任何「以后要做」的事，没有结构化记录和明确验收标准，就不算计划。不要让人保证，让系统保证。（同日）

AI 理解：「欠账表」就是 GitHub 的 issue 加里程碑，不在仓里另抄一份（design 第七节「一件事只存一处」）。要补的是让它漏不掉的检查。

## 要什么

1. 开着的需求单在主线上没有 `specs/<号>-<短名>/需求.md` 就报红；补齐现在缺的；#59 #61 #64 的 issue 正文改短。`pnpm issue:new --specs` 开单时正文写进需求.md，issue 上只留原话、AI 理解和链接。
2. 需求.md 的「怎么算做完」不许空着，写成能检查的样子（测试名、脚本、真机上看到什么）。
3. 文档（docs/、specs/、AGENTS.md）里写「以后再做 / 先不 / 观察后再定 / 后面阶段」这类话，同一句里必须带一个开着的单号，否则报红；认不出、单号查不到都判红。
4. 阶段收口：一个里程碑要关之前，列出里面还开着的单，每张要么做完、要么挪到后面的里程碑并写明原因；有没处置的就不许关（脚本 + 驾驶舱里看得到）。
5. design 第三节「已定」加一条原则：「以后要做」的事必须是一张带「怎么算做完」和里程碑的 issue，否则不算计划。

## 怎么算做完

- `pnpm check` 里跑欠账检查（`node packages/conventions/src/bin/debt-check.ts`），真仓上退出码 0；`packages/conventions/test/debt.test.ts` 里故意造的每一种都被拦下：推后的话没带单号、单号关了、是 PR、查不到、GitHub 读不到（没查成）、一份文档都没读到、需求.md 没有或空着「怎么算做完」、开着的 issue 超过一天没有需求文档。
- `.github/workflows/debt.yml` 在主线上跑 `debt-check.ts --open-issues`，所有开着的 issue 都有需求文档时是绿的。
- `pnpm milestone:close-check P1` 列出 P1 里开着的 issue 和 PR、退出码 1；里面没有开着的时退出码 0；里程碑找不到、GitHub 读不到时退出码 2（`packages/conventions/test/milestone-close.test.ts`）。
- `pnpm issue:new` 正文里没有写了字的「## 怎么算做完」就不开；带 `--specs` 时 issue 正文只有原话、AI 理解和需求文档路径（`packages/conventions/test/issue-new.test.ts`）。
- design 第三节有第 35 条；真仓里认出来的每一句推后的话都带着开着的单号，没单的开了单或改了说法。
- 驾驶舱那半边另开单（#80，P2）。
