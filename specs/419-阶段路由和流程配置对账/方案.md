# #419 方案：阶段路由和流程配置对账

## 两本账怎么对上

- 流程配置（全组织默认 `packages/core/flow.default.json`，加上各项目仓 `.fleet/flow.json` 同步进库的副本 `repos.flow_config`）每个 profile 的 `steps` 按步骤列模型名。模型名就是库里 `routes.model_id`（引擎选路 `real/store-ports.ts` 的 `onlyModels` 就拿它和路由的 `modelId` 比）。
- 库 `stage_policy_routes` 按阶段挂路由（带 `enabled`）。
- 步骤落到哪些阶段，照引擎实际派的（`engine/src/workflows/fusion.ts`）：
  - `lead` → `plan`、`execute`、`ui`（规划走 plan；Lead 自己接手写码时按是不是界面单走 execute / ui）
  - `sidekick` → `execute`、`ui`
  - `review` → `review`
  - `verify` → `verify`
  - `discuss` → 不对（本机 discuss 技能用，引擎不派，库里没有对应阶段）
- 一个 (模型, 阶段) 要是被硬禁令挡着（`@fleet-dao/shared` 的 `hardBanFor`，例如 GPT 不进 `ui`），就不要求挂，不算缺。判禁令要模型的族和显示名：从库 `models` 表读；配置列了、库里 `models` 表都没有这个模型的，照样算缺（写明「库里没有这个模型」）。

**缺**＝这个阶段里没有「挂着、`enabled = true`、`model_id` 是它」的路由。挂着但关着的写「挂着但关着」，一条都没挂的写「没挂」。路由在不在线（探针）不管，那是探针的事。

## 放在哪跑

放进引擎的**每小时对账**（`hourly-reconcile`，每小时 41 分），照「GitHub 机器人权限自检」（`jobs/github-app-check.ts`）的样子加一项，结局并进这一轮的 `schedule_runs`。不放自动发布读回：阶段路由是驾驶舱随时改的，每小时对一次就够，也不用碰部署脚本。

1. **纯判断**（core，新文件 `packages/core/src/flow-stage-drift.ts`，从 `index.ts` 导出）：
   - `FLOW_STEP_STAGES` 常量（上面那张表），注释写明对应 fusion.ts 的哪几处，改派法时必须一起改。
   - `flowStageGaps(input)`：输入是若干份「配置来源（全组织默认 / 某个仓）+ 已解析的 FlowConfig」、阶段路由列表（stage, routeId, enabled, modelId）、模型表（id, family, displayName）；输出按阶段分组的缺口：每条写明哪个模型、从哪一步来（哪份配置、哪个 profile）、没挂还是关着。同一个 (阶段, 模型) 多份配置都列了的并成一条、来源都写上。
2. **库查询**（db，`packages/db/src/queries/flow.ts` 里加 `listStageRouteModels(db)`）：`stage_policy_routes` join `routes` join `models`，给出上面要的字段，外加所有模型的 id/族/显示名。读不出原样抛。
3. **对账一项**（engine，新文件 `packages/engine/src/jobs/flow-stage-check.ts`，导出 `checkFlowStageRoutes(deps): Promise<SweepPart>`）：
   - 流程配置这一边：全组织默认用 `readOrgDefault()`（`real/github-reconcile.ts` 已有）经 `resolveFlowConfig(org, missing)` 解析；各仓副本用 `listFlowReplicas`，只拿 `source = 'project'` 的（`org_default` 的和全组织默认一样），副本整份照 core 现有的判法解析：把 `packages/core/src/fusion.ts` 里的 `decideStoredConfig` 导出来用（和派活同一份判法，不另写一份；太久没同步成的也按它算没查成）。
   - 读不到、认不出的**不当成一致**：全组织默认读不到/认不出 → 这一项 `failed`（写明原因）、不动任何提醒；某个仓的副本认不出、没同步成 → 这个仓记进 `unchecked`，别的照判；阶段路由读不出 → `failed`、不动提醒。
   - 提醒：每个有缺口的阶段一条「要人看」（`level: 'alert'`），键 `flow-stage-routes:<阶段>`（前缀常量 `FLOW_STAGE_ALERT_PREFIX`），标题写阶段、缺几个模型，正文逐条写「哪一步（哪份配置）列了 X，这个阶段没挂 / 挂着但关着」，外加怎么修：去驾驶舱调度台这个阶段挂上/打开，或改流程配置把它拿掉。原地更新，不重复报。
   - 撤：这一轮两边都读全了（`unchecked` 为空）且这个阶段没缺口，开着的那条撤掉（`by: RECONCILE_ACTOR`，写明「对上了」）。有没查成的仓时不撤（那个仓可能正是缺口来源），只报新的。
   - `scanned` = 对的 (阶段, 模型) 对数，`found` = 报的 + 撤的条数。
4. **接上**：`jobs/hourly-reconcile.ts` 的 `round` 里在权限自检之前加这一项，`HourlyReconcileJobDeps` 加 `flowStages` 端口（`orgDefault`、`replicas`、`stageRoutes`），任务名里加上「阶段路由和流程配置」；`real/hourly-reconcile.ts` 接真实现；`jobs/alert-sweep.ts` 开头「谁来撤」清单加 `flow-stage-routes:<阶段>`（每小时对账这一项自己撤）。
5. **文档**：`docs/design.md` 第六节「每小时对账」那条把这一项写进去（一轮做几项、判法一句话、键名）。

## 测试（故意造出失败）

`packages/core/test/flow-stage-drift.test.ts`：
- review 列了 gpt，库里 review 没挂 gpt → 报，写明 review 步、gpt；挂着但 enabled=false → 报「关着」；挂着开着 → 不报。
- lead 列的模型在 plan 挂了、execute 没挂 → 只报 execute。
- GPT 列进 sidekick，ui 阶段没挂 → 不报（硬禁令挡着）；execute 没挂 → 报。
- 配置列了库里 models 表没有的模型 → 报。
- 两份配置都列同一个缺的模型 → 一条、两个来源。
- 用真的 `flow.default.json` 跑一遍：字段都认得（防止 steps 加了新步骤却没进映射表——映射表缺步骤要显式报错，不悄悄跳过）。

`packages/engine/test/flow-stage-check.test.ts`（假端口）：
- 库里缺一个配置列了的模型 → `alerts.raise` 键 `flow-stage-routes:review`、正文含模型名。
- 读不到库（`stageRoutes` 抛）→ `failed` 写明没查成，`raise`/`resolve` 都没调。
- 全组织默认 unreadable → `failed`，不动提醒。
- 某仓副本认不出 → `unchecked` 有它、别的缺口照报、不撤任何开着的提醒。
- 对上了、有开着的旧提醒 → 撤掉；没开着 → 不调 resolve。
- `hourly-reconcile.test.ts` 里的假 deps 补上新端口，确认这一项的结局并进了 `combineParts`。

`packages/db` 的查询给一条测试（同 `catalog.test.ts` 的 `createTestDb` 搭法）：挂一条开的、一条关的，读回字段对。

## 不做的、顺带发现的

- **只留一本账**（流程配置管「哪些模型」、库只管顺序和开关）：要改驾驶舱调度台和装载器，归 #323 一并定，这里不做；做完在 结果.md 里写一句建议，写回这张单。
- 发现：review 步的模型在引擎里其实**没用上**——`fusion.ts` 请第二意见调 `runStage(stage: 'review')` 时没传 `models`，选路用的是 review 阶段所有开着的路由，流程配置 review 那一列只在这次对账里有意义。要不要让第二意见也按配置筛，在 结果.md 里点出来，由帅位决定另开单，这里不改派活行为。
