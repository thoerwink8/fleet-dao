# 结果：ssh 标准错误里的 GBK 中文还原成能读的字（#409）

## 做了什么

- `seat.mjs`、`claim.mjs`：调 ssh 时不再按 UTF-8 解标准错误，原字节交给 `seat-lib.mjs`（标准输出照旧按 UTF-8；claim 里 git、gh 不变）。
- `seat-lib.mjs` 新增导出 `readableStderr`：原字节先按 UTF-8 严格解、再按 GB18030（GBK 的超集）严格解；字符串里连续的 `\200`–`\377` 转义段还原成字节后同样解。解不开的原样留着（坏字节写成 `\NNN`，解不开的转义段保留原文），编码器缺失也不抛错。
- `firstLine` 改成先还原、再取第一行、再抹字；空 Buffer 按「没有输出」判，退回看标准输出。
- 退出码、「按不是帅位算」不变。

## 怎么验证的

- agents/test 下的 seat-claim.test.ts（该文件 2026-10-02 随认领账一起删，#446）新增一组用例：GBK 原字节的「不知道这样的主机。」、ssh 转义后的 `\262\273\326\252…` 都还原成那句中文；UTF-8 中文不被误当 GBK（`C2 A5` 解成 `¥`）；【故意造出的失败】坏字节 `FF FE 80` 原样成 `\377\376\200`、单个坏转义 `\377` 原样、`C:\Users\a` 不动、空 Buffer 退回看标准输出。
- 端到端：`seat check`、`claim show` 碰上 ssh 退出码 255、标准错误是 GBK 时，退出码 2，报错里是「ssh 连不上法国：… 不知道这样的主机。」。
- 本机 `pnpm test:changed`：27 个文件 817 条过（2 条跳过）；biome、`tsc -b` 过；PR 的 CI 绿。

## 还欠什么

- 没在 Windows 真机上复现（本机是 Linux），靠按字节构造的用例覆盖；下次在 Windows 上跑 `seat.mjs check` 连不上法国时顺带看一眼。
- 多行、CRLF 结尾的报错，取出的第一行末尾会带 `\r`（原来就有，不影响本单）。
