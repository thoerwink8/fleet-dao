# 引擎接上 Mirasim 执行方式，先只开 DeepSeek Flash 一条路由（#345）

对应计划：v1 Fusion 接活
设计依据：`docs/design.md` 第十四节「安全」（AI 会话一条：Mirasim 路由配好之前保持关闭）、第九节「自由组合的派工模型」（路由 = 渠道+账号池+模型+执行方式，阶段挂路由、按 `enabled` 开关；选路第 1 步先过滤「执行方式能胜任」「路由在线」）；`docs/reference/adapters.md` 第八节「Mirasim」（协议与坑 MS-01…28）。

原话：创始人 2026-09-27 晚，「接下来的 lead 由 grok heavy 的 grok4.7 担任先吧，干活的用 mirasim 的 ds-4.1-flash」；「接插头为什么没有接呢？我很好奇。现在 mirasim 因为额度不太够了，所以我希望就是只用低级的模型，就用 DeepSeek 4.1 flash，但是接肯定还是要接的」。

## 为什么之前没接
`docs/design.md` 第十四节早就写着「经 Mirasim 起的会话，工具是在 Mirasim 服务的进程里执行的。所以要给会话用户单独起一份 Mirasim 服务（登录一次），不借旧系统那份；配好之前，Mirasim 路由保持关闭」——这只是设计里的一句话，没人把它拆成单子。法国上现在没有 Mirasim 服务（只有 miraquota-sync 这个额度同步的，不是会话服务），插头代码（`packages/adapters/src/mirasim/`）早就写好了，但引擎的 `WIRED_HOSTS`（`packages/engine/src/real/hosts.ts`）里一直没有 `mirasim`，四条 `mirasim-relay:*:mirasim` 路由在目录样例里也一直是 `enabled: false`。没人漏做，是没开单。

## 要做的
1. 引擎接上 Mirasim 这一种执行方式：照 grok 驱动的样子写 `mirasim` 驱动（探针、结局判定、失败分流、记账走同一个形状），接进 `WIRED_HOSTS`。读不到、认不出的一律明确报错，每条这样的路径配一条故意造出失败的测试。
2. 只开 DeepSeek Flash 一条路由：`mirasim-relay:opus-5.5:mirasim`、`mirasim-relay:gpt-5.6-luna:mirasim`、`mirasim-relay:kimi-k3:mirasim` 保持 `enabled: false`，只有 `mirasim-relay:deepseek-flash:mirasim` 打开。理由：创始人原话「mirasim 因为额度不太够了」——Mirasim 中转账号是共用的一份额度（`docs/design.md` 第十节），Opus/GPT/Kimi/DeepSeek 都扣它；旧系统（ai-gateway-stack/windsurf-dao）实测过 DeepSeek 走 Mirasim 中转不稳定过（`docs/reference/adapters.md` 第七节：`dsh-mirasim-relay-deepseek-flash` 档过去停用过，`done+incomplete` 收场），但那是旧协议、旧插头，新插头（这个仓的 `packages/adapters/src/mirasim/`）还没实跑过，所以按创始人的话先只开这一条、观察，不是不知道风险。用路由目录已有的 `enabled` 开关做，不是靠代码注释挡；写测试钉住「只有 DS Flash 能派到 Mirasim」（`deploy/examples/catalog.example.json` 里其余三条 Mirasim 路由的 `enabled` 必须是 `false`）。要特别注意：全组织默认的模型顺序（`packages/core/flow.default.json`）和目录（`stages` 里的路由顺序）是两层——即使 `opus-5.5` 这个模型名也对应着一条 Mirasim 路由（`mirasim-relay:opus-5.5:mirasim`），只要它的 `enabled` 还是 `false`，选路第一步的「路由开着」过滤就会把它挡在外面，不会因为接上了 Mirasim 就让 Opus 的活跑去烧 Mirasim 的额度。
3. 法国：查清 Mirasim 服务在 Linux 上怎么装、怎么给会话用户（`fleet-agent-carpool`）单独起一份、怎么登录（文档、旧仓 ai-gateway-stack /（如果找得到）windsurf-dao、`ssh contabo` 只读查看这台机器上 2026-09-25 之前 `mirasim-server.service`（那时候是给 `orca` 这个已经删掉的旧用户跑的）留下的痕迹）。能自动化的（读回检查）写进 `deploy/`；创始人本人要做的登录那一步，写清楚步骤回报，不代劳。
4. 模型顺序（`packages/core/flow.default.json`）这一轮不改：Lead 换 Grok 是另一张单在跑；副手换 DS Flash 等这条路由真的接通、探针过了再动，避免半成品切流量。

## 怎么算做完
- 引擎代码：`mirasim` 进 `WIRED_HOSTS`，驱动、报告整理、探针接上都有测试覆盖，`pnpm test:changed` 绿。
- 目录样例：只有 `mirasim-relay:deepseek-flash:mirasim` 的 `enabled` 是 `true`，其余三条 Mirasim 路由仍是 `false`，有测试钉住。
- 法国：Mirasim 服务在会话用户 `fleet-agent-carpool` 家里装起来、登录过、`deploy/` 的只读检查认得出它在（这一步要创始人本人做，做完之前这条不算达标）。
- 生产目录（`/etc/fleet-dao/catalog.json`，从保险箱仓放上来的那份）里 `mirasim-relay:deepseek-flash:mirasim` 真的被打开、下一轮路由探针探通：这一步是接了 Mirasim 服务之后另开的操作动作（改法国库、刷新保险箱），不在这张单第一个 PR 里做，留在这张单收尾前一起做完。
- 单子什么时候关：等法国那一步做完、探针探通了，把这几件事写进 `结果.md` 再关；中间那个「引擎代码 + 目录样例 + 部署检查脚本」的 PR 可以先合，不代表这张单做完了。
