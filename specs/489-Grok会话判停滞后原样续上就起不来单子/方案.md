# 方案：停滞的 Grok 会话改走接力，后台命令还在跑不算绕圈（#489）

需求见同目录 `需求.md`。修法是给三处已有判断加分支，不新造一层：接力（`decideContinuation`）、工具还在跑（停滞判断的 W3，和插头的 `busy`）、杀进程按证据归类（`explainKill`）。不再放宽续会话等第一帧的时间——`resumeStartupMs` 已经放到 12 分钟，09-28 凌晨 #276 放宽过，这次续上去照样没有第一帧。

自己定的：停滞的 Grok 直接走接力，不先试一次续。理由：需求里的验收就是「停滞后续会话 → 走开新会话带接力」；当晚 6 次续全都是 startup_timeout，先试一次只会再空等一轮。不碰对外发布、花钱、删数据、改标准。

## 断在哪

| 角色 | 现在是谁 |
| --- | --- |
| 写方 | `sessions.ts` 的 `checkStall` 每分钟调 `judgeStall`。绕圈（L1）或工具卡死就停掉，结局 `stalled`，失败码 `SESSION_STALLED`，写进 `session_runs`。 |
| 存放处 | 库里这一轮的 `outcome` / `failureCode`。工作流 `kit.ts` 的 `stageLoop` 只要结局里有会话号就留着，下次 `startSession` 照传。`resumeSame` 只决定钉不钉同一条路由，不清这个号。 |
| 读方 | `decideContinuation`：同池、同用户、同执行方式、同一目录、真号就 `--resume`。Grok 不能 fork，只有换池才接力。 |
| 报警方 | 没有。「续这个号起不来」还按 ST1 再试，会话号又清不掉，所以 6 次 startup_timeout 打在同一个号上。单子停在 execute，看起来像还在重试。 |

`startup_timeout` 的白话是「起来之后迟迟没有第一帧」。执行体打出的 Terminated 是我们等不到第一帧、经 scope 发 SIGTERM 之后它自己印的（`judge.ts` 先记下 `killed`，再收进程）。不是它自己先死掉。

Claude 判了停滞仍续同一个会话（失败分流 SL1「续一句」）。这次只改 Grok。

## 1. 停滞的 Grok 不原样续；续起不来的号不再续

`decideContinuation`（`packages/engine/src/real/sessions.ts`）在「换了用户 / 执行方式 / 目录 / 不是真号」这些续不上的理由之后、决定 resume 或 fork 之前加两条。上一轮的 `outcome`、`failureCode` 不给，就当没失败，现有测试行为不变。

- 上一轮 `failureCode === 'startup_timeout'`：改 `relay`。why 写明这个会话号续起来没有第一帧，不再续它。resume 和 fork 都算续这个号，都走这条。
- 本来要同池 resume、执行方式是 grok、上一轮 `outcome === 'stalled'`（或失败码 `SESSION_STALLED`）：改 `relay`。why 写明上一轮判了停滞，原样续起不来。

接力就是换池那一套：新会话号，提示词用现成的 `relayBlock`（步骤清单、最近进度、已提交、为什么断）。失败分流的梯子不改（SL1 仍是重试到上限再换模型、挂起）。变的是每次重试开新会话，不再空等第一帧。

## 2. 后台命令还在跑，连着查输出不算绕圈

这台没有法国的库，那 8 次停滞的工具原文没对上。代码上两种分得开，都做，不靠猜那晚各有几次：

- **有后台命令还在跑**：Grok 把 `run_terminal_command` 的 `background: true` 交回之后，这条命令还在跑，工具调用本身已经结束。引擎只看见一次次 `get_command_or_subagent_output` 开始又结束，`toolsInFlight` 是空的。满 15 分钟没推进、同一个摘要做满 3 次，就判 L1。这是误判。Claude 的 `busy`（`claude-code/run.ts`：`toolsInFlight > 0`）和停滞判断的 W3 都是「工具还没结束就不算死、也不算绕圈」，前台命令天然一直占着；Grok 的后台命令要自己算进去。
- **没有后台命令**：反复 `read_file` 自己家里的 `~/.grok/sessions…`，或凭空反复查一个没启动过的任务，仍是绕圈，照旧 L1。

做法在 `packages/adapters/src/grok/stream.ts`：`rawInput.background === true` 的执行，完成帧之后不发工具结束、留在 `toolsInFlight`（`busy` 跟着为真，空闲超时也不会把它杀掉）。后面的 `get_command_or_subagent_output` 写明这个任务结束了（退出、完成、失败、被杀掉）再发结束。结果认不出就不算它结束，也不抛错；拖到现有的工具上限（`toolMaxSeconds`，30 分钟）由 D3 收，依据里写明结果认不出。仓里的 grok 样例没有后台命令，测试用造的帧。

`judgeStall` 已经是先看还在跑的工具、再看绕圈，不用改顺序。加一条测试钉住：有工具在跑、同时又有 4 次一样的 `get_command_or_subagent_output`，结论是在等，不是绕圈。

## 3. 20:45:56 那两次 SIGTERM：这次查不清，把证据补进失败记录

发布 `218b25b2112b`（#483，2026-09-28 12:32 UTC）时引擎会被 `systemctl stop`。发布不碰会话（#412，09-27 已进主线）之后，脱开跑的会话不在引擎这个服务的 cgroup 里，`drainStop` 也不收它们。真是排空或第二次停机信号收的，结局是 `engine_stop`，不会是 `signal_unexplained`。

对得上 `signal_unexplained` 的，是进程被外面 SIGTERM、看守没设 `live.stop`。新引擎起来时 `reapOrphanSessions` 对 `keepForReattach` 没通过的 scope 做 `systemctl stop`（systemd 发 SIGTERM），就是这条，而且一轮循环里同一秒能收掉两个。原因只打在日志里；scope 带 `--collect`，停完单元就没了，失败记录对不上。本机没有法国的 journal 和库，这次是不是它，查不清。

补两处，下一次写进失败原因：

- 收孤儿之前，把原因和时间写进这个会话收发目录里预先建好的文件（目录 0711，会话用户建不了新文件，要像 `exit` 那样先建、0622）。
- 外壳接到 TERM / INT 时，把时刻和父进程名追加进另一个预先建好的文件。`explainKill` 读这两样：读到了就写是谁；文件空着写明没有记录；读失败写没读成，不当成「没有人杀」。依据里照旧带上是否脱开跑、scope 名、那一刻的排空（含发布来的，不只停机信号）。

## 怎么验证

三条故意造出的失败：

1. Grok 上一轮 `stalled`，同池再开：新会话，提示词是接力，不是 `-r`。Claude 上一轮停滞仍 resume。
2. 同一个号续起来的那一轮是 `startup_timeout`，再开一次：仍是新会话带接力，不再 `-r` 这个号。
3. 造的帧：`background: true` 的命令完成之后 `toolsInFlight` 仍大于 0；连着查输出、结果还在跑，仍大于 0，停滞判断是在等不是绕圈。没有后台启动、只反复查或反复 `read_file`，仍是 L1。查输出的结果认不出：不把它算结束，也不抛错。

杀进程：收孤儿的原因写进了失败记录；信号文件读不成时原因里是「没读成」，不是「没人杀」。

法国那一轮不在这次写码里（要等这版发布上去）。看一张 Grok 写码单：停滞之后下一轮是另一个会话号、提示词是接力；单子要么做完，要么明确报卡住或挂起，不再停在 execute 里干等。
