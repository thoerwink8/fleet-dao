# 每小时对账补上三处核对：开着的单都有工作流、合了的 PR 都记了账、每个账号池的额度读数不超过 30 分钟（#293）

对应计划：以 #293 挂的里程碑为准
设计依据：`docs/design.md` 第六节「断链怎么被发现」第 4 层「每小时对账」

原话：创始人 2026-09-27：「我希望断链了能及时发现，下午就没做到这一点，怎么办」。帅位查了第六节的五层兜底，第 4 层「每小时对账」举的三处核对一处都没做，让开这张单。

（本单开出来时仓里没有需求文档，2026-09-27 由这张单的 Lead 按单上的原话和 AI 理解补上。）

AI 理解：
- 第 4 层写的是三处互相核对：每个白名单开的开放 issue 都有工作流、每个合并的 PR 都记了账、每个账号池的额度读数不超过 30 分钟；对不上就报警，能安全自动修的自动修。
- 引擎的每小时对账（`hourly-reconcile`）现在只做两项：清工作树残留，提醒按条件撤、没人处理的再推。对账补漏（`github-reconcile`）里「查开放 issue」只保证每张开着的单在库里有任务行，不管它有没有工作流。
- 所以单子收进来了却没起工作流（或工作流断了）、合了的 PR 没记账、额度读数停了，现在都没人知道。

## 怎么算做完

- 每小时对账每一轮多做三项核对，结果并进这一轮的 scanned / found，没查成的照实记 partial / failed、写明哪里没查成，不记 ok。
- 工作流：库里记着在做（没结束、也不在排队）的单，Temporal 上它的需求工作流不在跑，就报一条要人看的提醒（链到那张单）；工作流又在跑了或单结束了，提醒自己撤。排队中、没派的单（不在当前版本、母单子单、开关关着）不报。
- PR 记账：每个受管的仓，最近一天里 GitHub 上合了的 PR，库里的 PR 镜像没记成已合并的自动补上（算发现一个问题）；我们机器人开的 PR 还要有合并队列的合并记录、是「引擎」机器人合的，没有就报警。人开的 PR（例如帅位本机开的）不查合并人和合并记录。
- 额度：每个启用了的渠道下的账号池，额度读数按 `quotaReadOverdue`（从没读成、上次读成超过 30 分钟、上游数据 30 分钟没前进）判，过期的汇成一条提醒列出是哪几个池、上次读成在什么时候；都新了自己撤。
- 每条读不到的路径（列不出单、问不了 Temporal、读不了 GitHub、读不了额度表）都有一条故意造出失败的测试，结局是 partial / failed，不是 ok。
- `docs/design.md` 第六节第 4 层改成写明三处核对已在 `hourly-reconcile` 里、各自怎么判。
