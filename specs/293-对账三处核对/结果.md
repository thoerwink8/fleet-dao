# 结果：每小时对账补上两处核对——开着的单都有着落、合了的 PR 都记了账（#293）

引擎在法国做了 3 个多小时（计划 → 执行 → Lead 验收都过了），卡在开 PR 前的别家验证；帅位叫停后交本机接着做。本机从引擎分支
接手，并进主线（中间主线又进了看门狗、关单对账、机器人权限自检、补起认领），当那一道别家验证逐条核了「怎么算做完」，改了下面几处，
开 PR 合进主线。

## 做了什么

- 每小时对账（`packages/engine/src/jobs/hourly-reconcile.ts`）一轮多两部分，判法在 `packages/engine/src/jobs/reconcile-checks.ts`，
  结局照原来的写法并进这一轮（scanned、found 照实记，没查成的写明哪里，记 partial / failed，不记 ok）：
  - 开着的单都有着落：「让 AI 接活」开着的项目里没结束的单，需求工作流在跑、或（排队的）最近一次接活处理过的投递上记着为什么
    不派，就算有着落；都没有的照对账补漏同一份接活依赖补拉一次，补拉也没成、或在做的单工作流断了，报 `reconcile:workflow:<任务>`，
    写明哪张单、卡在哪；有着落了、单结束了、项目接活关了自己撤。
  - 合了的 PR 都记了账：先审每个受管的仓最近 26 小时合了的 PR（镜像没记成已合并的补上；我们机器人开的还要是「引擎」合的、账上有
    合并记录，不是就报一次 `reconcile:pr:<仓>#<号>`）；再查镜像里对得上一张单的合并 PR：这条分支上的会话都有结局、跑成了的会话
    用量没拿 0 冒充、单记成做完，缺的报 `reconcile:ledger:<仓>#<号>` 写明哪张单缺什么，不自动补，补齐了自己撤。
  - 撤的清单登记进 `packages/engine/src/jobs/alert-sweep.ts` 开头；design 第六节「断链怎么被发现」第 4 条写实两处怎么判、额度那处
    等 #76；ops 第五节每小时对账那段写这三种提醒怎么处理、库里怎么查。
- 接手后核出来、改掉的（引擎那版照原样上线会出的事）：
  - 接活 #299 止血加的「本机做」（`reserved_local`）不在引擎认的不派理由里：贴着「本机做」的单每小时补拉一次、再报卡住（法国现在
    就有 5 张）。改成不派理由的表以 `@fleet-dao/core` 的接活原因为键（`INTAKE_HOLDS`），接活再加一种原因不在这里定就过不了类型检查
    （故意删掉一条试过，tsc 报缺哪个键）。
  - 机器人关掉的单：接活不叫停自己，库里还排着队（法国有 1 张），会被当成没着落每小时补拉、报卡住。改成那一版 issue 关了就不是开着
    的单，不要求有工作流。
  - 门口没收的投递（外人改了单子）排在最新时，会盖住前面接活判过的「不派」、把单报成卡住；门口没收的往后排，一版都没处理过才用它
    （补拉时照实报「门口没收」，下一轮说法不变）。
  - 合了的 PR 分类靠认中文句子（「已补」「没查成」）：github 包那几句话一改，镜像补上的就会被报成合并人不对。改成
    `packages/github/src/reconcile.ts` 的 `auditMergedPrs` 带上 `findings`（种类 + PR 号），对账按种类分。
  - 记账把跑过的会话用量是 0 都算缺：刚起就被限流、没花 token 的会话照实记的 0 会被报、永远补不齐。改成只查跑成了的会话。
  - 记账带上整张单的会话：重开后的新一轮、更早一轮被强行终止没收的会话（#247）会混进这条 PR 的账；改成只带这条 PR 头分支上的会话。
  - 补拉读了两遍投递，库里没投递的判法放进了真装配；改成核对里一次读、一次判，重放只收投递编号。受管的仓和权限自检用同一份。
  - 对账补漏、补起认领（#299）和每小时补拉共用 `packages/engine/src/real/github-reconcile.ts` 的 `intakeDepsFor` 这一份接活依赖。
  - ops 第五节还写着全熔断提醒不会自己撤：#315 之后不对了（#246 结果里留的那句），一起改掉。
- 没收的：引擎分支上顺带改的 `packages/engine/test/support.ts`（设了 CI 时拿 `/usr/local/bin/fleet-temporal` 当测试用的 Temporal
  命令行）。那是连法国生产 Temporal 的包装脚本（地址、命名空间写死成生产的），拿去起测试服务端不安全，撤回主线原样。
- Lead 留的问题（需求.md 第 6 行的节号没写是哪份文档，文档指针测试会红）：主线上帅位重写的 需求.md 里节号前都带着 design，
  文档指针测试是绿的，不用再改。ops.md、schedules.ts 的改动留着：它们写的是每小时对账做哪几项，机制改了不跟着改就和代码对不上。

## 怎么验证的

- 单元（`packages/engine/test/reconcile-checks.test.ts`，33 条）：两部分各自「对上了不报」「对不上报、写明哪张单缺什么」「条件没了撤」
  「读不到（Temporal、库、GitHub）记没查成、不当成对上、旧提醒不撤」；本机做、机器人关的单、没跑成的会话 0 都不报；不派理由的表
  钉住算哪几种。
- 库查询（`packages/db/test/reconcile.test.ts`）：门口没收的往后排、只带这条分支上的会话、点名的能查到回看窗口外。
- 真装配（`packages/engine/test/real/hourly-reconcile.test.ts`，真库 + 真接活那道门）：白名单作者、挂在当前版本的排队单经真接活拉起来；
  贴「本机做」的经真接活记成不派、下一轮不再补拉；作者不在白名单的补拉被门挡下、报卡住且下一轮说法不变；记账缺的报、别的分支上的
  会话不算、补齐撤。
- github 包：`findings` 的种类和 PR 号对得上，`problems` 就是 `findings` 的原文；单张没查成记 `unchecked`。
- 本机 `pnpm test:changed`（engine、db、api、github、jev、文档指针、agents）159 个文件 3155 条全过；tsc、biome 过。
- 上线前在法国只读查了库（只看计数）：接活开着的项目里 82 张单都在排队；最近一次投递记的是 dispatch_off 的 52 张都是开关打开以前开的
  （第一轮补拉会记成「开关打开以前开的」、不报），本机做 5 张、未排期 9 张、子单 4 张、别的版本 2 张、开关打开前开的 9 张、机器人关的
  1 张都算有着落；最近 7 天引擎开的合并 PR 5 条，会话都有结局、用量没有 0、单都做完了。照这个数，第一轮不该报卡住。
