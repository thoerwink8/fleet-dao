# 方案：每小时对账补上两处核对（#293）

需求见同目录 `需求.md`（本单只做两处，额度读数那处随 #76）。两项都做成每小时对账（`packages/engine/src/jobs/hourly-reconcile.ts`）的新部分，和已有的「工作树」「提醒」「机器人权限自检」并列：各返回一个 `SweepPart`，由 `combineParts` 并成这一轮的结局；提醒自己报、自己撤（不进 `alert-sweep.ts` 的判法表，只在它开头「谁来撤」的清单里补上）。判法在 `packages/engine/src/jobs/reconcile-checks.ts`。一轮的顺序：工作树 → 开着的单 → 合了的 PR（镜像、合并人）→ 记账 → 提醒 → 权限自检（核对在提醒之前，新报的这一轮不被再推）。

## 一、开着的单都有着落（`checkWorkflows`）

- 查询 `activeTaskRefs(db)`（`packages/db/src/queries/reconcile.ts`）：没结束的任务，带仓的 owner/name、issue 号、state、`updatedAt`、项目「让 AI 接活」开没开（`repos.auto_dispatch_since` 不空）。
- 项目接活关着的单：不查、不计 scanned；它的旧提醒撤掉。
- 其余的问 Temporal 它的需求工作流：在跑就有着落。问不了：这一张记没查成，旧提醒不撤。
- 不在跑、而且这张单 10 分钟内更新过：这一轮不查（工作流刚收尾、状态还没写的那一下），旧提醒不撤。
- 排队中的单：读这张 issue 最近一次接活处理过的 issues 投递（`latestIssueDelivery`：按 `github_event_versions` 里这张 issue 那一版的时刻取最新；门口没收的 `ignored` 往后排，一版都没处理过才回它；评论事件不算）。
  - 那一版 issue 已经关了（机器人关的单接活不叫停自己，库里还排着）：不是开着的单，算有着落。
  - 投递上记着为什么不派，算有着落：接活记的 `workflow=<原因>` 查 `INTAKE_HOLDS`——键是 `@fleet-dao/core` 的 `DispatchDecision` 和 `AutoDispatchGate` 里所有「没派」的原因，少一个过不了类型检查；算数的是开关打开以前开的、未排期、不是当前版本、母单、子单、本机做（`reserved_local`）；`dispatch_off`（开关现在开着，这条是旧的）、`version_unreadable`、`created_at_unreadable`（没判成）不算，要重判。投递记成等着（`waiting`，对账补漏每轮重放它）也算。
  - 读投递抛错：记没查成，不补拉。一条投递都没有：报卡住。
  - 两样都没有：补拉一次——重放这条投递（带 force），走的是对账补漏同一份接活依赖（`real/github-reconcile.ts` 的 `intakeDepsFor`，对账补漏的重放、补起认领和这里共用）。重放完接活判了不派、或记成等着，算补上；拉起了（再问 Temporal 在跑）算补上；门没收、重放抛错、重放完工作流还是不在跑，报卡住。那条投递正在处理（`in_flight`）这一轮不动。补上的计 found，写日志。
- 在做的单（分诊、等人回答、写方案、在干、在合并、停滞）工作流不在跑：不补拉——接活对在做的单判 `in_progress`，重放拉不起来；也不自动重起（会和残留的会话、分支撞），直接报卡住。
- 卡住报 `reconcile:workflow:<taskId>`（alert 级、带 taskId 和 issue 链接），正文写库里状态、工作流怎么了、补拉的结果。
- 撤：开着的 `reconcile:workflow:*` 里，对应任务这一轮查成了且有着落、单结束了、库里没了、项目接活关了的撤掉，写原因。

## 二、合了的 PR 都记了账

### 镜像、合并人（`checkMergedPrs`，先跑）

- `GitHub.auditMergedPrs(repo, since)`（`packages/github`，原来写了没人调）：每个受管的仓最近 26 小时合了的 PR，镜像没记成已合并的自动补（算发现、写日志；记账那一部分靠镜像认合了的 PR，所以放在它前面）；我们两个机器人开的 PR 还要是「引擎」合的、有合并队列的合并记录，没有就按 PR 报 `reconcile:pr:<仓>#<号>`（`insertOnce`：条件是「发生过」，只报一次、不自动撤）。人开的 PR 不查这两项（帅位本机开、GitHub 自动合并，没有合并队列这一步）。
- 结果按 `findings` 的种类分（`mirror_fixed`、`not_merged_by_engine`、`no_merge_record`、`unchecked`），不去认 `problems` 里的字。列 PR 失败、有的没查成：这个仓写进 unchecked。

### 记账（`checkLedgers`）

- `mergedPrLedgers(db, { since, prs })`：镜像里 `state = merged` 的 PR，按头分支对上同仓一张单的会话（`session_runs.branch = pull_requests.head_ref`）——对得上的就是引擎开的；`since` 以后更新过的，外加 `prs` 点名的（还开着的 `reconcile:ledger:*` 提醒要复查，出了回看窗口也查得到）。每条带上那张单在这条分支上的会话（重开后另起的一轮在新分支上、更早一轮被强行终止的会话归 #247，都不混进来）。
- 回看 26 小时；合并 30 分钟以内的不查（关单那一步还在走）。
- 缺什么（`ledgerGaps`）：会话没有结局（`ended_at` / `outcome` 空）；跑成了（`outcome = ok`）的会话用量记成 0（读不到要留空、关单评论写「没读到」；没跑成的会话可能真一个 token 都没花，0 照实记不算缺）；合并关单那一步没写完（单不是 `done`）。
- 缺的按 PR 报 `reconcile:ledger:<owner>/<name>#<号>`（alert 级，`raise` 原地更新），正文一行一张单写明缺什么；不自动补。都齐了、或镜像里这条 PR 不再对得上，撤掉。
- 读库抛错：这一部分 failed，旧提醒不撤。列提醒抛错：照查照报，记没查成，旧提醒不复查、不撤。

## 装配和文档

- `hourly-reconcile.ts`：deps 加 `activeTasks`、`latestDelivery`、`repull`、`repos`、`auditMergedPrs`、`ledgers`。
- `real/hourly-reconcile.ts`：接上面几个查询；受管的仓和权限自检同一份（`listFlowReplicas`）；`gh` 和对账补漏同一个（`real/index.ts` 传进来），补拉经 `reconcileIntake`；工厂改成拿 `(client, taskQueue)`（`activities.ts` 跟着传，补拉起的工作流和对账补漏起在同一个任务队列）。
- `alert-sweep.ts` 开头「自己会撤的」写 `reconcile:workflow:`、`reconcile:ledger:`；`reconcile:pr:` 在「只靠 24 小时再推」。
- `docs/design.md` 第六节第 4 层写实两处核对怎么判；`docs/ops.md` 每小时对账那段写这三种提醒怎么处理、去库里怎么查。

- 单元（`packages/engine/test/reconcile-checks.test.ts`，假 deps）：每项「对上了不报」「对不上报、写明哪张单缺什么」「条件没了撤」「读不到记没查成 / failed、旧提醒不撤」；接活关着的不查；排队的记着不派理由（含本机做）不报、单子关了的不报、没理由的补拉（起来了、判不派、等着、没起来、没投递、门没收、抛错、正在处理、补拉后问不了 Temporal）；10 分钟内更新过的不查；合并 30 分钟内的不查；没跑成的会话 0 不算缺。
- 库查询（`packages/db/test/reconcile.test.ts`）：`activeTaskRefs` 带接活开关；`latestIssueDelivery` 取最新、不算评论、门口没收的往后排；`mergedPrLedgers` 只列对得上单的合并 PR、只带这条分支上的会话、点名的能查到窗口外。
