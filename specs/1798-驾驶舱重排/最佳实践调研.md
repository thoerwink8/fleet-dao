## 1. 画布为主体的运维看板布局

推荐做法（【经验】为主）：
- 画布占满主区，侧面信息放右侧"检查器"。选中节点才出来，不选就收起，画布始终是主角。
- 桌面宽屏（>=1280px）：右侧栏常驻，宽 320-400px，可拖拽、可折叠。
- 中屏（768-1279px）：右侧栏改浮层，盖在画布上，不挤画布，点空白处关。
- 窄屏（<768px）：改底部抽屉（见第 2 块）。
- 左侧导航：十几个页面时折叠成 48px 图标栏，Ctrl+B 切换，状态存 localStorage。
- 底部抽屉只放一类东西：会话日志、事件流这种"又长又不是每次都要看"的内容。

依据与参数：
- 【官方】shadcn Sidebar：`collapsible` 有三种 `offcanvas` / `icon` / `none`；默认宽 `SIDEBAR_WIDTH = "16rem"`，手机宽 `18rem`；手机用 Sheet，`openMobile/setOpenMobile/isMobile` 控制；快捷键 Ctrl/Cmd+B。该页没写断点（桌面容器用 `hidden md:flex`，断点是 md 只是我推断）。已取 2026-10-10。https://ui.shadcn.com/docs/components/sidebar
- 【二手】n8n 社区帖：n8n 在做"focus panel"，选中节点时参数显示在画布右侧，目的是少点两下、编辑时仍看得见工作流；原来的节点详情弹窗（NDV）保留为备选。n8n 的 canvas-only 模式也保留日志面板。https://community.n8n.io/t/help-us-test-some-canvas-improvements/201703 ；https://docs.n8n.io/deploy/host-n8n/configure-n8n/deploy-n8n-in-canvas-only-mode （取 2026-10-10，只看到搜索摘要，没读全文）
- 【二手】Linear 的"全宽/窄图标栏"两态折叠，只有一份别家产品的内部规格提到，没有 Linear 一手资料。
- 断点数值（md=768、lg=1024、xl=1280）是 Tailwind 默认值，【经验】，本轮没重新拉 Tailwind 文档核对。

反例：
- 侧栏常驻且不能收，窄屏把画布挤成一条缝。
- 用居中大弹窗（Dialog）看节点详情，盖住整张画布，看不到上下游。
- 同时有左栏、右栏、底栏三个常驻面板，画布只剩中间一小块。
- Atlassian 用户抱怨折叠后还露出一截侧栏（【二手】搜索摘要，jira.atlassian.com/browse/JRACLOUD-71357）。折叠要么完全收，要么收成规整的图标栏，别留半截。

## 2. 手机端看板

推荐做法（【经验】为主，数值有一手来源）：
- 导航：底部导航，最多 4-5 项（总览、会话、告警、更多），"更多"里放其余页。十几个页面不要全放汉堡菜单，高频页要一指够得着。
- 卡片压缩：一行摘要（状态点 + 名称 + 关键数字 + 相对时间），点开原地展开细节，或弹 bottom sheet。列表里不放图表。
- bottom sheet 用 vaul：`snapPoints={['148px','355px',1]}` 做"露头/半屏/全屏"三档；`handleOnly` 让内部内容可滚而不误拖；想让背景画布还能操作用 `modal={false}`（此时不渲染遮罩）；`closeThreshold` 默认 0.25；`dismissible={false}` 可锁住不让划掉。
- 触控目标：每个可点元素至少 44x44 CSS px，相邻间距至少 8px。

数值来源：
- 【官方】WCAG 2.2 的 2.5.8 Target Size (Minimum)："The size of the target for pointer inputs is at least 24 by 24 CSS pixels"（AA 级）。https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html （取 2026-10-10）
- 【二手】2.5.5 Enhanced 为 44x44 CSS px（AAA）；Apple HIG 默认 44x44 pt；Material 48x48 dp；间距 8px/8dp。我没读到 Apple 和 Material 的一手页面，只有 OpenReplay 等二手：https://blog.openreplay.com/improving-tap-targets-mobile-ux/ （取 2026-10-10）。建议落地前去 developer.apple.com/design/human-interface-guidelines 和 m3.material.io 核对。
- 【官方，来源为 vaul 仓库自带文档经 context7 取得】vaul 的 props 如上。注意文档里 `disablePreventScroll` 默认值有自相矛盾（代码 true，注释 false），别依赖。https://github.com/emilkowalski/vaul （取 2026-10-10）

反例：
- 手机上塞桌面表格横向滚动。
- 触控按钮只有 16-24px 的图标。
- 抽屉里再套抽屉再套弹窗。
- 内容很长的 sheet 只有一个全屏档，用户没法"瞄一眼"。
- 画布在手机上硬做全功能编辑：手机端只读、可缩放、点节点出 sheet 就够了【经验】。

## 3. 设置页、额度页的信息密度

推荐做法（【经验】，本块没查到可引用的一手来源）：
- 设置页：左侧分组标题 + 右侧控件同一行（标签左、输入右；标签列固定约 160-200px），一组一个小标题，组内行高 36-40px。每组一句说明，写在组标题下，别写在每个字段下。窄屏回落成标签在上。
- 保存方式：改一项即存（开关类）或页底粘性"保存/还原"条（文本类），别每组各一个保存按钮。
- 额度/指标页：对比多个对象（渠道、账号、仓）用表格，一行一对象，列是已用/上限/剩余/重置时间，右对齐数字、等宽数字（`tabular-nums`），超阈值整行染色；只有 1-3 个全局关键数字才用顶部指标卡（stat card）。进度条放在表格单元格里，不另做卡片网格。
- 什么时候用表格：同一批字段、超过 5 行、要排序/比较。什么时候用卡片：每个对象字段不齐、含操作按钮、手机端。

反例：
- 每个渠道一张大卡片，每张 6 个同样的字段，扫一遍要滚三屏。
- 设置页每个字段上下两行（标签行、输入行、说明行），一屏只放 5 个字段。
- 指标页全是饼图，没有精确数字。

## 4. 实时刷新：SSE + 轮询兜底

推荐做法：
- 主通道 SSE，推的是"哪个 query key 失了效"（事件里带 key），收到就 `queryClient.invalidateQueries`，别把整份数据塞进事件【经验】。
- 兜底轮询：用 `refetchInterval` 的函数形式，SSE 连着时返回 `false`，SSE 断了返回 15-30s（【经验】数值）。v5 里回调只收 `query` 一个参数。
- 页面不可见：`refetchIntervalInBackground` 默认不开，保持默认即可，隐藏页不轮询；回到前台时 `refetchOnWindowFocus`（默认开）会补一次。同时在 `visibilitychange` 隐藏时主动 `EventSource.close()`、可见时重连，省连接数。
- 断线降级：`EventSource` 自带重连；收到 `error` 且 `readyState===CLOSED`，或超过 2x 心跳间隔没收到任何字节，就置 `sseConnected=false`，轮询自动接上。恢复后先全量 invalidate 一次补漏。
- 心跳：服务端每 15-25s 发一行注释 `: keepalive\n\n`；服务端可发 `retry: 3000` 控制重连间隔。
- 代理层：响应头加 `X-Accel-Buffering: no`、`Cache-Control: no-cache, no-transform`、`Content-Type: text/event-stream`；nginx 的 `proxy_read_timeout` 要大于心跳间隔（默认 60s）；别对 `text/event-stream` 开压缩。用 HTTP/2，否则每浏览器每域名只有 6 条 SSE（多开标签页会占满）。

来源：
- 【官方】MDN：`retry` 字段是毫秒整数；"A colon as the first character of a line is in essence a comment, and is ignored"，注释行可定期发送"to prevent connections from timing out"；非 HTTP/2 时每浏览器每域名上限 6 条，Chrome/Firefox 标为 Won't fix；HTTP/2 下流数默认 100。https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events （取 2026-10-10）
- 【官方】nginx：缓冲"can also be enabled or disabled by passing "yes" or "no" in the "X-Accel-Buffering" response header field"，可被 `proxy_ignore_headers X-Accel-Buffering` 关掉。https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_buffering （取 2026-10-10）
- 【官方】TanStack Query：`refetchInterval` 可为数字或函数；`refetchIntervalInBackground`："If set to true, the query will continue to refetch while their tab/window is in the background."；窗口重新聚焦时过期数据自动重取；v5 回调只收 query。https://tanstack.com/query/latest/docs/framework/react/reference/useQuery ；https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults （取 2026-10-10）
- 【官方，经 context7】`focusManager.setEventListener` 可改成按 `visibilitychange` 判定是否聚焦。
- 【二手】Cloudflare 空闲约 100s 超时（Free/Pro/Business）会返回 524，有来源写 125s，两者矛盾，我没找到 Cloudflare 官方页，所以数值待核对；建议心跳 <=30s 即可两种都躲开。https://levelup.gitconnected.com/the-125-second-silence-why-your-ai-stream-dies-behind-cloudflare-40f776d9e055 ；https://smartscope.blog/en/Infrastructure/sse-timeout-mitigation-cloudflare-alb/ ；https://stackharbor.com/en/knowledge-base/cffix-websockets-sse-behind-cloudflare/ （取 2026-10-10，只读摘要）

反例：
- SSE 和轮询同时一直开，数据来两遍。
- 事件里推整张表，客户端手动合并，漏一条就永远不一致。
- 不发心跳，被代理 60s/100s 掐断，用户以为"没事"。
- 隐藏标签页仍每 5 秒轮询（把 `refetchIntervalInBackground` 设成 true）。

## 5. 长会话记录 / CI 日志查看器

推荐做法（【经验】；本轮没拿到 GitHub Actions、Claude Code 网页、Cursor、Vercel 的一手实现资料）：
- 从画布点会话 -> 右侧宽抽屉（桌面约 480-640px，可拉宽）或整页路由 `/sessions/:id`（可分享链接）；手机用全屏 sheet。
- 按"轮次"分组：用户消息、助手文字默认展开；工具调用默认折叠成一行（图标 + 工具名 + 参数摘要 + 耗时 + 成败），点开看入参出参；出错的自动展开；超长输出截断 + "显示全部"。
- 虚拟滚动：条目超过约 200 条再上，用 TanStack Virtual（动态高度测量）；折叠展开会改高度，要重新测量。
- 跳到最新：贴底时自动跟随；用户向上滚就停止跟随并显示浮动"跳到最新（N 条新）"按钮。
- 顶部固定：会话状态、模型、耗时、费用；支持按"只看出错/只看工具"过滤和搜索。浏览器原生 Ctrl+F 在虚拟滚动下搜不到，要自带搜索。
- TanStack Virtual 官方页只写了"headless utility for virtualizing long lists"，并指向一个单独的 Chat 指南（用于聊天、AI 流、日志等反向列表），那页我这次取到 HTTP 500，没读到内容。https://tanstack.com/virtual/latest/docs/introduction （取 2026-10-10）；https://tanstack.com/virtual/latest/docs/guide/chat 【没读到】

反例：
- 所有工具调用全展开，一轮对话几千行。
- 无虚拟滚动，一次渲染几万个 DOM 节点。
- 流式追加时每来一条就强制滚到底，用户没法往上看。
- 纯文本 `<pre>` 倾倒，没有轮次结构。

## 6. LLM 渠道健康探针

推荐做法：
- 连通探测：发最小请求，让模型回一个词（如 "pong"），`max_tokens` 设 5-16，超时 10-20s；只判 HTTP 状态、延迟、返回非空。探测要走和真实工作相同的 base URL、密钥、模型 id。我没查到 Anthropic 官方推荐的探测请求或单次成本，【没查到】。
- 识别被降级/换模型：
  - 公开做法是行为指纹：Cai 等 "Auditing Model Substitution in LLM APIs"（输出统计检验、基准测试、对数概率）；Bruckner "One Token Is Enough"（arXiv:2607.10252，用约 100-400 次便宜的单词补全对比参考分布，其引言引用"31 个商用端点里 11 个的输出分布与官方权重统计上不相容"）。【二手】经搜索摘要取得，没读全文。
  - 用知识截止期问近期事实来判断：我没找到任何公开来源证明这个做法可靠，【没查到】。我的判断是只能当弱信号：模型本来就常答错或拒答，不同渠道的系统提示还会改答案，单次回答不能下结论。若用，要重复采样、只在"连续多次异常"时告警、不自动熔断。
  - 对 Anthropic 渠道，更便宜且更可靠的是核对响应里的 `model` 字段和请求 id；但中转站可以伪造该字段，所以只算一致性检查，不算证明【经验】。
- 探测频率（【经验】）：近 1 小时有真实流量的渠道不主动探（真实请求已是探针）；闲置但在用的 5 分钟一次；久未用的 30-60 分钟一次。
- 派活前按新鲜度探：最近一次成功探测/成功真实请求在 15 分钟内就直接派；超过再探一次，通过才派。
- 真干活报错触发探测：遇到 5xx、超时、连接重置，立刻对该渠道发一次探测；401/403/余额不足这类确定性错误直接标记为需人处理，不当瞬时故障重试。
- 熔断器：
  - 通用定义【官方】Microsoft Azure 架构中心：Closed 里按时间窗计失败，超阈值进 Open 并启动超时计时；计时到进 Half-Open，放有限几个请求，连续成功达标回 Closed，任一失败立刻回 Open 并重启计时；可用定时探测代替计时器；建议提供手动重置；可对 429/503 带的"稍后重试"时间做加速熔断；超时可递增（先几秒，后几分钟）；一个渠道一个熔断器，别把不同供应方混用一个。https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker （取 2026-10-10，页面更新 2026-09-26）
  - Fowler：半开是"ready to make a real call as trial"。https://martinfowler.com/bliki/CircuitBreaker.html （取 2026-10-10）
  - 具体参数参考【官方】Resilience4j 默认值：failureRateThreshold 50%、slidingWindowSize 100、minimumNumberOfCalls 100、waitDurationInOpenState 60s、permittedNumberOfCallsInHalfOpenState 10。https://resilience4j.readme.io/docs/circuitbreaker （取 2026-10-10）。我们流量远小于此，要缩小：窗口 10 次或 5 分钟，连续 3 次失败开路，开路 60s 起、翻倍至上限 10 分钟，半开放 1 个探针请求，连续 2 次成功关路【经验，非官方】。
  - LiteLLM 的做法【官方】：`health_check_interval` 后台探测并把失败的部署移出路由池；`allowed_fails_policy` 按错误类型（鉴权、限流、超时）设容忍次数；`cooldown_time`；文档不建议关掉冷却。https://docs.litellm.ai/docs/proxy/health_check_routing （取 2026-10-10，只读摘要）

反例：
- 把"能回 pong"当成"是真模型"。
- 一次失败就熔断，渠道抖一下全停。
- 熔断后无半开，只能人手恢复；或半开一次放几十个请求把刚恢复的渠道又压垮。
- 对鉴权失败/欠费也做重试和探测，白烧请求。
- 所有渠道同一个熔断器。

## 马斯克五步法：对"十几个页面的内部运维驾驶舱"的删减建议

全部是【经验】判断，没有外部来源，也没看过本仓具体页面，只给页面类型。

1. 质疑需求：每个页面问"谁、多久看一次、看完做什么决定"。没有人、没有动作的页面，不留。
2. 删除：
   - 只读的历史报表、没人看的统计页（可改成总览上的一个数字，或导出）。
   - 与列表页重复的详情页（改成抽屉）。
   - 纯展示配置的页面（配置在仓里，页面只会过期）。
   - 功能重叠的多个"状态/健康/告警"页。
   - 已被替代功能的旧入口。
3. 简化（合并）：
   - 所有"列表+详情"合成一个列表页 + 右侧抽屉。
   - 设置、额度、渠道、账号合成一个"资源与配额"页，分页签。
   - 日志、事件、告警合成一个时间线，用过滤器区分。
   - 总览直接就是画布，不另做"首页+画布"。
   - 目标：十几个页面收到 4-6 个（总览画布、会话/任务、资源与配额、设置、必要时一个运维日志）。
4. 加速：首屏 <1s、状态靠推送而不是点刷新；常用操作（重试、停止、切开关）放在列表行上，一击即达；加命令面板（Cmd+K）直达任何对象，反而让页面数量不再重要。
5. 自动化：只在前四步做完后才做；能自动恢复的告警不进页面只写日志；探针和熔断自己处理，页面只显示结果和"手动重置"。
