# 结果：接活入口（#43）

怎么做的见 [方案.md](方案.md)。

## 做了什么

- 库：新表 `github_events`（一次投递一行：原文、状态、原因、做了什么、次数；状态多一种「等着」，见下面「接活」），投递编号去重从幂等账挪到这里；每次投递带着的对象版本另记一张 `github_event_versions`（`对象 + 版本 + 开关状态`，一条投递里一个对象一行）。`repos` 加自动派活开关 `auto_dispatch_since`，已有的仓升级后一律关着。迁移 `0005_github_intake`。
- 门口（`packages/api/src/github.ts`）：验签照旧按收到的原始字节算；放进来、不收的都落库带原因，出错的留着原文，重投、补收、重放时再来；处理中卡住 5 分钟以上的可以接过来。webhook 收下的对象版本一并记下（评论事件还带上它顶上来的那张 issue），轮询再看到同一版就认成重复、不重做；迟到的旧事件撞上「更新的一版已经处理过、状态还不一样」就按新的算（旧的关单不把重开的单叫停）。缺头、不是 JSON 明确 400 并留日志；形状认不出的记成不收（`payload_unreadable`）并告警。健康检查的 `github_events` 一项真去查库：重放到头还出错、或处理中超过 5 分钟没收尾的，报红，只报条数、不报投递内容。
- 接活（`packages/api/src/issue-intake.ts`）：按方案那张表建任务行、拉起需求工作流、叫停、重开、跟着改原话、评论当回答。补收拼出来的评论只有从没改过（`updated_at` 等于 `created_at`）才算原话，改过的一律不当回答、不记在作者名下；重开撞上还在跑的任务、拉起时报 `already_running`，投递记成等着（`waiting`，webhook 回 503）：每轮对账都重放、不占自动重放的 5 次，上一轮结束后的那一轮落地。
- 对账（`packages/api/src/reconcile.ts` 的 `reconcileGitHub`）：重投、逐仓轮询、查开放 issue、重放出错的投递，结局按 `schedule_runs` 的写法给。GitHub 投递日志里没送成的，库里已经有原文的交给重放、只重投库里没有的（不然同一次投递做两遍）；查库里有没有原文失败，重投这一步报 failed、一条都不重投，别的都查成时整轮算 partial。重放后门挡下的（`ignored`）处理完了，但不算补回；轮询捞到的一版以前的投递带过（门挡掉的也算，比如陌生人评论顺带的 issue 那一版；「仓不受管」时收到的不算），照样过门（关单的 webhook 丢了还靠它叫停），但不算补回。
- 后端进程接上 `@fleet-dao/github` 的事件去处（PR 镜像、CI 汇总），两个机器人的凭据只在启动时读一次，读不到时降级并报红；`@fleet-dao/github` 的轮询改成整条送 issue、评论（原来只留编号和作者，建不了任务）。
- ops 第九节写上后端读机器人凭据、受管的仓与自动派活开关怎么开。

- 读不到、认不出的每一条各造一个：缺头、不是 JSON、形状认不出、处理出错（库连不上、Temporal 连不上、查库里有没有原文失败）、GitHub 读不到（对账报 unscanned 不报 ok）、重放到头还不成、评论的时刻读不出、补收时那个仓已经被删了、补收的评论认不出是哪张 issue（告警）、几个仓里有一个读不到（partial）。

- 重开撞上还在跑的任务、拉起时报 `already_running`：投递记成等着、webhook 回 503；一轮轮等下去（比自动重放上限多两轮）次数不加、健康检查不红，上一轮结束后那一轮拉起；出错过 4 次、第 5 次正好碰上「等上一轮」的，照样每轮重放、不当成到头。都有用例。
- 陌生人在白名单作者的 issue 下评论：下一轮对账不把那张 issue 的这一版算成补回；关单的 webhook 丢了、之后陌生人又评论，关着的那一版照样补收、叫停任务（只是不算补回）。
- Store 契约测试内存版、Postgres 版各加 18 条；真库上再走一遍 webhook → 落库 → 建任务 → 看板实时收到。

## 留下的

- 起工作流到点被取消、其实服务端已经起了：重放时拿到 `already_running`。新开单无所谓（就是起来了）；重开的会被当成「上一轮还没结束」等着，等这一条跑完再起一轮（多跑一轮）。客户端没公开起工作流的 requestId，堵不上。
- ~~对账本身没接上定时~~：已接上，引擎里的 Temporal 定时任务 `github-reconcile` 每 15 分钟一轮，见 [方案-对账调度.md](方案-对账调度.md)「结果」。**GitHub 不会自己重投失败的投递**，靠这一轮对账去调它的重投接口。
- 关着的仓不分诊（design 第九节要的是「只收单、分诊、显示，不派」）：等引擎有「只分诊不派」。
- issue 改了只改任务行，不通知在跑的工作流：等引擎加信号。
- 重放到头（自动 5 次）还没成的投递只报红、没人能手动再推：缺一个「强制重放 / 放弃」的入口。
- 补收按「现在的正文」建任务：正文可能被白名单外、但有写权限的人（或机器人）改过，看不出是谁改的（编辑历史那一套在 `packages/github/src/issues.ts`），补收时不核对。
- 开关关着的仓：issue 关了再重开，任务停在叫停、和 GitHub 上的状态对不上（本来就只收单）。
- 关单的 webhook 丢了、任务还在正常跑的时候又收到重开：这次重开一直等着，等这一轮做完再重新拉起一轮（多跑一轮）。等着的不设期限、不报红：上一轮一直不结束，要从看板上那张卡住的任务看出来。
- 驾驶舱的「交给 fleet」按钮和开关页面、`github_events` 的保留期限。
- 法国上线后的验收：巡检仓在 `repos` 里、开关打开，开一张 issue，几秒内库里有任务行、需求工作流起来了（随 #28 上线）。
