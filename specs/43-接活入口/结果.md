# 结果：接活入口（#43）

怎么做的见 [方案.md](方案.md)。

## 做了什么

- 库：新表 `github_events`（一次投递一行：原文、状态、原因、做了什么、次数），投递编号去重从幂等账挪到这里；`repos` 加自动派活开关 `auto_dispatch_since`，已有的仓升级后一律关着。迁移 `0004_github_intake`。
- 门口（`packages/api/src/github.ts`）：验签照旧按收到的原始字节算；放进来、不收的都落库带原因，出错的留着原文，重投、补收、重放时再来；处理中卡住 5 分钟以上的可以接过来。webhook 收过的同一版，轮询认得出、不再重做。缺头、不是 JSON 明确 400 并留日志；形状认不出的记成不收（`payload_unreadable`）并告警。
- 接活（`packages/api/src/issue-intake.ts`）：按方案那张表建任务行、拉起需求工作流、叫停、重开、跟着改原话、评论当回答。
- 对账（`packages/api/src/reconcile.ts` 的 `reconcileGitHub`）：重投、逐仓轮询、查开放 issue、重放出错的投递，结局按 `schedule_runs` 的写法给。
- 后端进程接上 `@fleet-dao/github` 的事件去处（PR 镜像、CI 汇总），凭据读不到时降级并报红；`@fleet-dao/github` 的轮询改成整条送 issue、评论（原来只留编号和作者，建不了任务）。
- ops 第九节写上后端读机器人凭据、受管的仓与自动派活开关怎么开。

## 怎么验证的

- `pnpm check` 全绿：rebase 到最新主线（带上 #41 的文档指针检查、#21 的卫生检查）后 139 个测试文件、2214 条通过，卫生检查 0 条；CI 的 check、pr-fields 都绿（#56）。
- 需求里点名的三样都有用例：验签过、不过（含「请求体被重新序列化过，空格、键序变了」这一条）；重复投递只建一行任务、只拉起一次；对账补回一条漏的（`reconcile.test.ts` 走 `@fleet-dao/github` 的真轮询代码，对着照 GitHub 接口回话的假服务）。
- 读不到、认不出的每一条各造一个：缺头、不是 JSON、形状认不出、处理出错（库连不上、Temporal 连不上）、GitHub 读不到（对账报 unscanned 不报 ok）、重放到头还不成。
- Store 契约测试内存版、Postgres 版各加 12 条；真库上再走一遍 webhook → 落库 → 建任务 → 看板实时收到。
- 故意改坏三处，对应用例都红：验签改成先解析再序列化、轮询不按版本认、开关不看打开时刻。
