# 方案：接活入口（#43）

需求见 [需求.md](需求.md)。验签、白名单、投递编号去重在 main 上已有（`packages/api/src/github.ts`），PR 镜像和按仓补收也有（`packages/github/src/events.ts`、`packages/github/src/reconcile.ts`）。缺的是：原文落库、issue 变成任务和工作流、跨仓对账，以及把这些接进后端进程。

## 拆成几块、各改哪里

1. **原文落库**（`packages/db` 新表 `github_events`，替掉幂等账里的 `github-delivery:*` 那几行）
   - 一次投递一行：投递编号、事件、动作、来源、仓、原文（jsonb）、状态（处理中 / 收下 / 不收 / 出错 / 等着）、原因、处理结果、次数。「等着」= 现在做不了、要等前一件事做完（重开时上一轮还没结束）。
   - 同一编号再来：处理完了的是重复；上次出错、在等着、或处理中超过 5 分钟没收尾的，重新占住再处理（从等着接回来的不加次数）。记结局凭这次占用的凭据，被接管了就记不上。
   - 每次投递带着的对象版本另记一行到 `github_event_versions`（`对象 + 版本 + 开关状态`；一条投递里一个对象一行）：issue 事件记那张 issue，评论事件记评论再加它顶上来的那张 issue，PR、审查、审查评论记那个 PR。版本号是对象在 GitHub 上的修改时刻。轮询补收的编号是「对象 + 版本」（`pollDeliveryId`）：webhook 收下过的同一版认成重复、不再做；门挡掉的投递带过的那一版照样过门，但不算补回（见第 3 条）。对账报的「补回几条」因此是「这一轮新送进门、以前没有投递带过的几条」，不是「GitHub 上真漏了几条」。
   - 验签不过的不落库（没认证的请求不许往库里写），只回 401、记日志。
   - 健康检查的 `github_events` 一项真去查库：重放到头还出错、或处理中超过 5 分钟没收尾的报红，只报条数、不报内容（公开面上不露投递内容）。
2. **issue 变成任务和工作流**（`packages/api/src/issue-intake.ts`）

   | 事件 | 做什么 |
   |---|---|
   | 开放的 issue（开单，或补收、对账送进来的） | 没有任务行就建一行（原话去掉进度段；提出人记成员编号）；开关允许就拉起需求工作流 |
   | 关了、删了、转走了 | 叫停（`stop`）。工作流不在、任务还在排队（从没派过）：直接把任务记成叫停 |
   | 重开，任务已结束或还在排队 | 开关允许就重新拉起。任务还在正常跑：投递记成等着（回 503 `retry_later`），不硬起第二条；每轮对账都重放、不占自动重放的 5 次，任务收尾后的那一轮落地 |
   | 白名单的人编辑了标题或正文 | 更新任务行的标题和原话；不发信号（引擎还没有这个信号，见「不做的」） |
   | 白名单的人发了评论 | 这张任务正好一条没答的追问、而且是评论之前问的：当作回答（写库 + `answer` 信号）；零条或多条都只记下原因，不猜。补收拼出来的评论只有从没改过（`updated_at` 等于 `created_at`）才算原话：改过的看不出是谁改的，不当回答、不记在作者名下 |
   | 自家机器人引起的 | 只建任务、按开关拉起；不叫停、不改原话、不当回答（防自己叫醒自己） |
   | 迟到的旧事件（重放、投递慢） | 同一张 issue 更新的一版已经处理过、开关状态还不一样：这条旧的不再做（记 `superseded`）——旧的关单不把后来重开的单叫停，旧的重开也不把后来关了的单拉起来 |

   - **自动派活开关**（design 第九节「在哪能做与仓级开关」）：`repos` 加一列 `auto_dispatch_since`，空 = 关。只有开关打开之后开的 issue 才自动拉起；打开以前就开着的要人点「交给 fleet」（驾驶舱按钮不在本单）。关着的仓只收单、显示。
   - 拉起工作流经后端的一个窄接口 `RequirementWorkflows.start`，输入和引擎 `contract.ts` 的 `RequirementInput` 同形；工作流已经在跑就是 `already_running`，不起第二条。新开单撞上「已经在跑」无所谓（就是已经拉起来了）；重开撞上「任务还在正常跑」则抛 `RetryLaterError`：这条投递记成等着、webhook 回 503，每轮对账重放（不占次数，上一轮跑多久都等得住），任务收尾后再落地，不硬起第二条。叫停、回答照旧走 `WorkflowControl.signal`。
   - 每一步都能重放：任务行按（仓, issue 号）唯一，起工作流按工作流编号去重，信号重发引擎会回「已经在叫停」。哪一步出错就整条记成出错，由重投、补收或重放再来。
3. **跨仓对账**（`packages/api/src/reconcile.ts` 的 `reconcileGitHub`）：先看 GitHub 的投递日志，没送成的**由我们调它的重投接口**（GitHub 自己不重投）：库里已经有原文的交给重放，只重投库里没有的；查库里有没有原文读不到，重投这一步就报 failed、一条都不重投（别的都查成时整轮算 partial）。再逐个受管的仓轮询最近改过的 issue、评论、PR，查白名单作者的开放 issue 有没有任务，最后重放库里出错、卡住、等着的投递（出错、卡住的自动最多 5 次，到头的只报出来；等着的每轮都重放，不占次数）。重放后门挡下的（`ignored`）算处理完了，不算补回；轮询捞到的一版要是以前的投递带过（哪怕带它的那条被门挡掉了，比如陌生人评论顺带的 issue 那一版），照样过一遍门，但也不算补回——只有「仓不受管」时收到的不算带过。结局按 `schedule_runs` 的四种写：一个仓都没查成是 unscanned，查了一部分是 partial。重放到头的投递让人手动再推或放弃的入口先不做（见「不做的」）。
4. **接进后端进程**（`packages/api/src/main.ts`）：用 `packages/github` 的事件去处写 PR 镜像、CI 汇总；两个机器人的凭据只在启动时读一次，读不到时后端照样起，issue 照收，PR、CI 事件如实失败，健康检查的 `github_events` 报红——补上凭据要重启后端才会被读到，而对账还没接上定时，所以这段时间要人盯着、重启后端。

## 谁来定时调对账

引擎里起一个 Temporal 定时任务：每 15 分钟一次、往回看 2 小时，活动调 `reconcileGitHub`，登记成定时任务 `github-reconcile`（`expect_every_minutes` 45），每次的结局记进 `schedule_runs`（2026-09-25 #56 复审时拍的）。本单只交函数和测试，接上它随 #28 之后的 PR。

## 先后与依赖

- 依赖 #28 的 PR A：`RequirementWorkflows.start` 的真实现（按 `@fleet-dao/shared` 的 `requirementWorkflowId` 起 `requirementWorkflow`，工作流编号冲突时回 `already_running`）等 PR A 合进来再接；在那之前法国后端拉起工作流如实失败（`WorkflowUnavailableError` 那一类），投递记成出错，等对账接上后重放。测试里这个端口是假的。
- PR A 把 `WorkflowControl.signal` 的第一个参数从任务编号改成工作流编号；本单合并前按 PR A 的写法改（`requirementWorkflowIdForTask`）。
- 迁移号：PR A（#50）也占迁移号、先合；合了之后本单 rebase，按那时的实际号重新生成迁移（测试里写死的迁移名一起改）。

## 不做的

- 关着的仓不分诊：引擎还没有「只分诊不派」，design 第九节要的「关着也分诊」等引擎支持再改。
- issue 改了不通知工作流：`TaskSignal` 加名字会撞上引擎 `contract.test.ts` 的编译期对拍，要引擎先加这个信号。
- 给重放到头的投递一个「强制重放 / 放弃」的入口：现在只报红，接的人还进不来。
- 补收按当前正文建任务时不核对编辑历史：正文可能被白名单外、但有写权限的人改过（`packages/github/src/issues.ts` 有编辑历史那一套），等有了入口再做。
- 驾驶舱的「交给 fleet」按钮、开关页面；原文表的保留期限（P5「数据保留与磁盘告警」）。
