# 方案：接活入口（#43）

需求见 [需求.md](需求.md)。验签、白名单、投递编号去重在 main 上已有（`packages/api/src/github.ts`），PR 镜像和按仓补收也有（`packages/github/src/events.ts`、`packages/github/src/reconcile.ts`）。缺的是：原文落库、issue 变成任务和工作流、跨仓对账，以及把这些接进后端进程。

## 拆成几块、各改哪里

1. **原文落库**（`packages/db` 新表 `github_events`，替掉幂等账里的 `github-delivery:*` 那几行）
   - 一次投递一行：投递编号、事件、动作、来源、仓、原文（jsonb）、状态（处理中 / 收下 / 不收 / 出错）、原因、处理结果、次数。
   - 同一编号再来：处理完了的是重复；上次出错、或处理中超过 5 分钟没收尾的，重新占住再处理。记结局凭这次占用的凭据，被接管了就记不上。
   - 轮询补收的编号是「对象 + 版本」（`pollDeliveryId`）。webhook 收下的 issue、评论、PR 也记下这个版本号，轮询再看到同一版就认成重复：对账报的「补回几条」是真漏的。
   - 验签不过的不落库（没认证的请求不许往库里写），只回 401、记日志。
2. **issue 变成任务和工作流**（`packages/api/src/issue-intake.ts`）

   | 事件 | 做什么 |
   |---|---|
   | 开放的 issue（开单，或补收、对账送进来的） | 没有任务行就建一行（原话去掉进度段；提出人记成员编号）；开关允许就拉起需求工作流 |
   | 关了、删了、转走了 | 叫停（`stop`）。工作流不在、任务还在排队（从没派过）：直接把任务记成叫停 |
   | 重开，任务已结束 | 开关允许就重新拉起 |
   | 白名单的人编辑了标题或正文 | 更新任务行的标题和原话；不发信号（引擎还没有这个信号，见「不做的」） |
   | 白名单的人发了评论 | 这张任务正好一条没答的追问、而且是评论之前问的：当作回答（写库 + `answer` 信号）；零条或多条都只记下原因，不猜 |
   | 自家机器人引起的 | 只建任务、按开关拉起；不叫停、不改原话、不当回答（防自己叫醒自己） |

   - **自动派活开关**（design 第九节「在哪能做与仓级开关」）：`repos` 加一列 `auto_dispatch_since`，空 = 关。只有开关打开之后开的 issue 才自动拉起；打开以前就开着的要人点「交给 fleet」（驾驶舱按钮不在本单）。关着的仓只收单、显示。
   - 拉起工作流经后端的一个窄接口 `RequirementWorkflows.start`，输入和引擎 `contract.ts` 的 `RequirementInput` 同形；工作流已经在跑就是 `already_running`，不起第二条。叫停、回答照旧走 `WorkflowControl.signal`。
   - 每一步都能重放：任务行按（仓, issue 号）唯一，起工作流按工作流编号去重，信号重发引擎会回「已经在叫停」。哪一步出错就整条记成出错，由重投、补收或重放再来。
3. **跨仓对账**（`packages/api/src/reconcile.ts` 的 `reconcileGitHub`）：先让 GitHub 重投没送到的，再逐个受管的仓轮询最近改过的 issue、评论、PR，查白名单作者的开放 issue 有没有任务，最后重放库里出错、卡住的投递（超过 5 次的不再自动重放，报出来）。结局按 `schedule_runs` 的四种写：一个仓都没查成是 unscanned，查了一部分是 partial。
4. **接进后端进程**（`packages/api/src/main.ts`）：用 `packages/github` 的事件去处写 PR 镜像、CI 汇总；两个机器人的凭据读不到时后端照样起，issue 照收，PR、CI 事件如实失败，健康检查的 `github_events` 报红。

## 谁来定时调对账（待拍）

design 第十六节把定时器都换成 Temporal 定时任务，推荐：引擎里起一个 Temporal 定时（Schedule）→ 工作流 → 活动调 `reconcileGitHub`，每 15 分钟一次、往回看 2 小时，登记成定时任务 `github-reconcile`（`expect_every_minutes` 45），每次的结局记进 `schedule_runs`。另一条路是 systemd 定时器（像 `deploy/backup/` 的备份那样）跑一个小命令。本单只交函数和测试，选哪条、多久一次等拍板后随 #28 之后的 PR 接上。

## 先后与依赖

- 依赖 #28 的 PR A：`RequirementWorkflows.start` 的真实现（按 `@fleet-dao/shared` 的 `requirementWorkflowId` 起 `requirementWorkflow`，工作流编号冲突时回 `already_running`）等 PR A 合进来再接；在那之前法国后端拉起工作流如实失败（503 那一类），投递记成出错，接上后对账重放。
- PR A 把 `WorkflowControl.signal` 的第一个参数从任务编号改成工作流编号；本单合并前按 PR A 的写法改（`requirementWorkflowIdForTask`）。
- 迁移号：PR A 占了 0004，本单合并前重新生成成 0005。

## 不做的

- 关着的仓不分诊：引擎还没有「只分诊不派」，design 第九节要的「关着也分诊」等引擎支持再改。
- issue 改了不通知工作流：`TaskSignal` 加名字会撞上引擎 `contract.test.ts` 的编译期对拍，要引擎先加这个信号。
- 驾驶舱的「交给 fleet」按钮、开关页面；原文表的保留期限（P5「数据保留与磁盘告警」）。
