# 接活入口：GitHub issue 进来 → 建任务 → 拉起需求工作流（验签落库、对账补漏）（#43）

对应计划：plan.md P1 的 GitHub 一条（GitHub 事件经香港转到法国，校验签名，漏收的靠对账与轮询补回）。
设计依据：design 第十三节「高响应」（GitHub 事件几秒内到引擎）、第五节（一个任务怎么走完全程）、第十四节「收 GitHub 事件」。

## 要什么

- 后端接 GitHub 事件：香港转发过来的 webhook 先验签（`FLEET_GITHUB_WEBHOOK_SECRET`），按 delivery id 去重落库，原文留着能重放。
- 受管的仓里、白名单作者开的 issue → 建任务行 → 拉起需求工作流（Temporal）。issue 改了、关了、评论了，按设计发信号给对应的工作流。
- 漏收的补回来：定时对账（按仓列最近的 issue 和事件，和库里比），漏的照样建任务，不重复建。
- 读不到、验签不过、认不出的事件：明确失败并记下原因，不当成「没事件」。每条都有故意造出来的测试。

## 怎么算做完

- PR 审过合进 main；需求文档放 `specs/43-接活入口/需求.md`（照本单抄），方案、结果写同一目录。
- 本地：假事件验签过/不过、重复投递只建一次、对账补回一条漏的，都有测试。
- 法国：随 #28 上线后，在巡检仓开一张 issue，几秒内库里有任务行、需求工作流起来了。
