# 开 PR 前别家验证：方案（#213）
> 本文档是历史原话，一字不改。开 PR 前的别家验证（Fusion 第 5 步）已被后来的决定取代：三段一条龙里 Review 在开 PR 之后审一次就合。现行口径见 [#509](https://github.com/thoerwink8/fleet-dao/issues/509) 和 `docs/goals.md`。


对应需求：`specs/213-开PR前验证/需求.md`；设计：design 第五节「第 5 步开 PR 前验证怎么做」、0003 第 5 条第 5 步、`specs/191-Fusion第一步/方案.md` 3.2 第 5 步。

一句话：做成一块给 #214 的 Fusion 工作流调的零件 `packages/engine/src/workflows/verify.ts`（`verifyRound`、`rebutRound`、`verifyLines`），判法全在 core（`packages/core/src/verdict.ts`、`criteria.ts`），引擎只接线。本单不接进旧的需求工作流，旧的第二意见（`subtask.ts` 的 `secondOpinion`）不动。

## 一轮怎么走

1. **读「怎么算做完」**：端口 `readCriteria` 读默认分支上的 `specs/<号>-<短名>/需求.md`，core 的 `criteriaOf` 取文档里标题是「怎么算做完」的那段，逐条原文（顶层列表项或段落；续行、缩进的子项并进上一条；去掉注释，重复的只留一条）。目录由调用方给：单子正文里「文档：`specs/<号>-<短名>/需求.md`」那一行，用 core 的 `specDirOf` 认（`<本单号>` 换成单号；指的是别的单的号就报错）。目录认不出、文档不在主线上（`SPEC_DOC_MISSING`）、没有那一节或是空的（`CRITERIA_MISSING`）都不可重试，失败分流 VF1 挂起报警，不验、也不当成验过了。
2. **作者是哪几族**：端口 `authorFamilies` 按这张单上起过（有开工时刻）的会话，查路由对应模型的族（模型目录的 `models.family`）；验证、审查会话和判断题不算。一个都查不到报 `AUTHORS_UNKNOWN`（VF1 挂起）：空的等于谁都能验。
3. **派别家起验证会话**：`runStage` 跑 `verify` 阶段，选路带 `avoidFamilies`（整族避开，点名的、续会话的路由也一样）和 `uiWork`（改到页面代码：禁令按界面类判，GPT 不派）。渠道自己挑模型的路由（上游串或别名是 auto，比如 Cursor Auto）认不出这次是哪一家在答，也不派。一条都派不出，挂起「没有别家可验：写这张单的是 X 族，验证只派别家」，不拿同族顶。每一轮都是全新会话。
   - 会话端口检出送检的头（完整提交号），主线另取进来钉成 `origin/<主线>`，和第二意见同一套检出；提示词给「怎么算做完」逐条原文和出处、方案摘要、改了哪些文件（最多列 200 个，多的让它看 `git diff`）、怎么答；只读，只写 `.fleet-out/verify.json`（形状是 core 的 `ReportSchema`）。
   - **发出去之前先过卫生检查**：这次真要发的整份提示词（续会话、接力的也算）过 github 包的 `assertPublishable`，名单和推分支、开 PR 同一份（`createGitHub` 按环境变量找的那份）。查出来报 `MATERIAL_BLOCKED`（HY4 挂起报警；报错里只有位置、行号和规则名，没有值）；名单没读到 `HYGIENE_LIST_MISSING`、没扫成 `HYGIENE_UNSCANNED`（HY2 挂起）；会话端口没配检查、检查自己出错都算没扫成。三种都不起会话。
   - 读结论：没写、不是 JSON、过不了 core 的 `checkReport`（认不出、审的不是送检的头、漏答、答了清单外的、同一条答两遍）都判 `wrong_output`，失败分流 DL1 退回同一个会话照原因重写，还不对就换一家别家的模型，再不对挂起。
4. **判**：经 decide（本地活动，结果进历史）调 core 的 `decideVerdict`。作废的（派成了同族、交回的认不出、审错了头……）记一行 `verdict = invalid`、挂起「验证作废：原因」，人点「继续」从第 1 步重验这一轮；作废的不交给调用方。
5. **记**：端口 `recordVerification` 写库里 `verify_rounds` 一行（迁移 `0012_verify_rounds.sql`，只加表、给阶段枚举加值）：送检的头、验证会话和路由、验证模型的族、作者的族、对照的清单、交回的原样、判的（驳回之前）、驳回、驳回之后的结论、挡在哪、备注。库里约束兜底：作废的必须写原因、不许有结论；没作废的必须有结论、交回的不能是空；验证模型说过的，驳回之后照样是过；挡住的必须写挡在哪，过了的不许留着挡的理由；作者的族不能是空的。

## Lead 拿证据驳回

`rebutRound(kit, round, rebuttals)`：给这一轮的全部驳回（`{ target, evidence }`；target 是那条「怎么算做完」的原文，或那条发现的 text），经 decide 再判一次。驳的不是能挡的、没带证据：交回 `{ ok: false, why }` 给 Lead，记录不动；成立：改写同一行（驳回、驳回之后的结论），交回新的一轮。

## #214 怎么调

```ts
import { rebutRound, type VerifyRound, verifyLines, verifyRound } from './verify.ts';

// 第 4 步 Lead 收下、推完分支之后（nextFlow 给的 action 是 'verify'）：
const round = await verifyRound(kit, {
  round: state.verifyRounds + 1,
  repo,
  specDir,        // core 的 specDirOf(issue 正文, 单号) 认出来的
  head,           // 推上去的头：先推后验，推前卫生检查已经过了
  title, request, branch,
  planSummary,    // Lead 写的方案摘要
  changedFiles,   // 相对主线改了哪些文件
  uiWork,         // 改到了流程配置里的页面代码路径
});
let done = round;
if (round.final.verdict === 'block' && rebuttals.length > 0) {   // Lead 拿证据驳回的
  const r = await rebutRound(kit, round, rebuttals);
  if (r.ok) done = r.round;
  else { /* 把 r.why 告诉 Lead：驳回不成立 */ }
}
rounds.push(done);
const next = await judge(kit, 'fusionFlow', { state, event: { kind: 'verified', verdict: done.final.verdict } });
// next.action：open-pr（过了）；dispatch / lead-takeover（挡了，回第 4 步，把 done.final.reasons 交给 Lead 当返工意见）；
// wait-human（2 轮都挡）。开 PR 时：
const { verified, owed } = await verifyLines(kit, rounds);   // 并进 PrBody 的 verified / owed
```

- `verifyRound` 自己会挂起等人的：文档读不到、作者查不到、没有别家可验、材料没过卫生检查、作废。回来的只有过或挡。
- 轮数不在这里管：照 core 的 `nextFlow`（默认 1 轮、最多 2 轮）；单模型模式只对高风险开，也是 `nextFlow` 判的。
- 测试宿主 `packages/engine/test/fixtures/verify/host.ts` 就是照上面这样调的，可以照抄。

## 定下的（帅位日常决定）

1. **「怎么算做完」读默认分支，不读分支上的**：验收条是开单时写定进主线的，写这张单的会话改不了它；需求文档还没进主线就明说读不到。
2. **作者的族按库里现查，不靠工作流传**：工人重启、换模型、副手换了家都算得上；宁可多算（分诊、方案会话的也算）：多算一族只是少一个能验的，少算了就可能同族自己验自己。
3. **会话端口先用 `checkReport` 挡一道，工作流再经 decide 用 `decideVerdict` 判**：两边同一个判法。端口挡是为了让验证模型照原因重写；工作流判是定论，不信端口。
4. **卫生检查放在会话端口起会话之前、提示词拼好之后**：这是发给别家必经的一步，扫的就是真要发出去的那一份。
5. **渠道自己挑模型的路由不派给验证**：Cursor Auto 挑中的可能正是写这张单的那家，「只派别家」就落空了。验证要用钉住型号的路由（cursor-agent 带具体的 `--model`，目录里记成那一家的族）。
6. **验证结论不写成合并闸认的 `second-opinion` 状态**（#191 方案第 8 问归本单定）：合并闸的 `second-opinion` 管先审后合的两种路径（迁移里的删改、碰安全），绑在 PR 当前头上；开 PR 前验证管「怎么算做完」和三种能挡的，验的是开 PR 之前推上去的头，CI 红了再改头就变了。混成一个状态，要么旧头上的验证被当成新头的审查，要么先审后合的路径只经过验收式的核对。两道闸各管各的，验证结论写进 PR 正文。
7. **每一轮全新会话**：不续上一轮的验证，免得带着上一轮的结论看这一轮（和第二意见一样）。
8. **作废的不交给调用方，挂起等人**：作废说明派错了或交回的不能用，照样往下走就等于没验。
