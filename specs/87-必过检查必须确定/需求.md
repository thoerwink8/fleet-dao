# 必过检查必须确定：欠账检查不读单子开关状态；合并后出问题按 4 条走（#87）

对应计划：plan.md P1「工作流」
设计依据：design 第五节「发现问题当场修」、第七节「欠账不漏」。

原话：之前的 PR 有新问题，应该产生 issue 而不是 PR 阻塞流程，并且会误导 PR 的真实意义。（创始人 2026-09-25，讨论后拍「按这 4 条定」）

AI 理解：合并后出问题按 4 条走——
1. 主线坏了（必过检查红、生产坏了）：立刻修，修不简单就先回退；修复 PR 写清是哪次合并弄坏的。
2. 严重问题（数据、泄露、安全）：主线绿也立刻修。
3. 其他合并后才发现的问题：一律开单攒着，不开 PR。
4. 必过检查必须确定：同一份代码什么时候跑结果都一样。依赖外部状态（单子开没开、时间）的检查挪到定时任务，只开单、不挡 PR。

起因：#83 把「推后的话要带开着的单号」接进了必过的 `pnpm check`，#67 一关，主线上一行文档立刻判红，所有 PR 的检查跟着红（#84、#58），靠 #86 解堵。同一份代码前后两次结果不同。

同日创始人另拍一条，一起写进 AGENTS.md 本仓段：谁开的 PR 谁负责到合并——「做完」＝合进去了，或者明确交接给总指挥；推完自己盯 CI，红了修、冲突了并主线、第二意见里必须改的就改，按 PR 算最多 3 轮，超了交接。

## 要什么

- `pnpm check`（PR 必过检查）里的欠账检查只看文件：推后的话带没带单号、需求.md「怎么算做完」空不空；不读 GitHub。
- 「挂的单号是不是开着」「开着的单有没有需求文档」只在 `.github/workflows/debt.yml` 的定时任务里查，查出来留言到对应的单上（同一条只留一次），不让 PR 变红。
- 上面 4 条写进 AGENTS.md 本仓段和 design 第五节，旧说法一起改掉。

## 怎么算做完

- `packages/conventions/test/debt.test.ts`「必过检查必须确定（#87）」：同一份代码，挂的单开着、关了，只看文件的结果一样；GitHub 读不到时只看文件的那一半照常跑完；真起一个把 fetch 换成一碰就炸的进程跑 `debt-check.ts`（不带 `--live`），照常跑完、不出网。
- 同一个测试文件里：定时任务那一半查出挂在关了的单上的话、超过一天没需求文档的单，留言到对应的单上，以前留过的不再留，留言失败不当成留过了。
- CI 的 ci.yml 不再给 `pnpm check` 令牌；debt.yml 跑 `debt-check.ts --live --comment`。
- AGENTS.md 本仓段、design 第五节「发现问题当场修」有这 4 条；第七节「欠账不漏」里的旧说法改掉。
