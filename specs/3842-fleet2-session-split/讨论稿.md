## 一、提出的问题

### 1. 一件活开几个会话

- **现象**：新内核在影子单上只有工人一个环节调模型：任务说明由代码拼（`packages/harness-dispatch/src/dispatcher.ts` 的 `buildWorkerPrompt`），影子模式不核验，交回的核验结论都是 `unverified`（法国库 `fleet2.events` 里 `handback.recorded` 实测 10 条 `completed/unverified`）。每件活每次尝试起一个新工人进程、一个新会话号（`runId = d<事件号>-a<尝试>`，按代码）。
- **根因**：拆不拆会话决定的是「复核的人能不能看到写的人的思路」和「每一轮要重读多少上下文」，和用几家模型是两回事。
- **需求方的思路**：都用同一个模型；问开 3 个会话还是 1 个会话做到底。
- **判断**：不做一个会话到底。理由：
  1. 同一会话里复核会顺着自己写时的理由替自己圆（推断，第六节埋错试验来量）。
  2. 会话越长每轮重读的上下文越多，拆开每段只带自己那一段，总 token 更少（推断，按会话汇总 token 能量出来，`transcript.result` 事件里带用量）。
  3. 出错只重开那一件（按代码：派工器按尝试号重派，`releaseJob` / `retryJob`）。
  同行同样拆开：OmO 桌面端每个任务节点是独立的子代理会话（带 `childSessionId`、`parentTaskId`，各自 `category`/`model`），核验是单独一波节点，指挥官另一个会话（实测，逆向报告 §3–§5）；Claude Code 的子代理在自己的上下文里跑、只把结论交回（按代码）；我们旧引擎写码和冷验收本来就是两个会话（`packages/engine/src/cold-verify-run.ts`，按代码）。
- **做法**：一个指挥官会话（一批或一张母单一个，只派活、看结果）＋ 每件活每次尝试一个新工人会话 ＋ 每次核验一个新核验会话；核验会话只拿改动、验收条和测试输出，不拿工人的过程记录。
- **不做什么**：不做「一个会话从头到尾」；也不做三个常驻长会话。

### 2. 核验用不用同一个模型

- **现象**：决定 0006 规定独立复核要跳过写手那一家，按 GPT → Grok → Claude → DeepSeek → Kimi 选第一家能用的不同家；同族换型号、新开会话不算换家（按决定原文）。旧引擎冷验收照此选（`chooseModelForFamily`、`UNVERIFIABLE_AUTHOR_FAMILIES`，按代码）。
- **根因**：同一个模型新开会话只去掉了「记得自己的理由」，去不掉模型本身的盲点。
- **需求方的思路**：三个环节都用 Grok。
- **判断**：写码 Grok 时，按 0006 核验自动落到 GPT（Cursor 订阅，已有，不新花钱，也不占 Claude 额度）。这已经满足「省 Claude 额度」，又不丢独立那一道。只有坚持核验也用 Grok 才要改 0006。
- **做法**：见第五节。
- **不做什么**：不新开按量计费的接口。

### 3. 每次任务的效果按模型和任务类型记下来，能回溯、能统计

- **现象**：新内核现在只有影子打分（`fleet2.shadow_compare.score` 的 lineJaccard / fileJaccard，实测），分不出「改得对不对」，也没有按模型、按任务类型汇总的地方。旧引擎有 `runs` 表记每次会话的路由和结局（按代码，`packages/db`），但效果判定散在冷验收、合并闸几处，没有一张「模型 × 任务类型」的表。
- **需求方的思路**：每次任务最终的效果，按「哪个模型做了哪类任务」分类判断，可回溯、可统计。
- **判断**：成立，而且是切换模型前必须有的依据：没有它，换 Grok 好不好只能凭感觉。
- **做法**（新内核，事件只追加）：
  1. **每次尝试一条记录**：单（仓、单号）、任务类型、环节（工人 / 核验 / 指挥官）、壳、模型、尝试号、token 进出、用时、会话号（能点进会话详情）。派工那一刻写，`runId` 当主键。
  2. **任务类型**派工时定、存下、不再重算：开单就有的「域」「性质」标签，加「碰不碰界面」（改动路径落在界面包）、「大小档」（旧引擎的规模分档）。
  3. **效果分三层，各自追加一条结论事件**，不改原记录：
     - 机器判：测试、`pnpm check` 过没过，验收条过了几条（核验会话跑）；
     - 独立核验：另一家模型的结论，记核验用的模型；
     - 最终结局：合没合并；合并后 7 天内有没有被撤回、单有没有重开。最可信，但晚到。影子单的最终结局是「和真合并的改动比」加机器判。
  4. **统计表**：「模型 × 任务类型」每格：尝试数、机器判通过率、核验通过率、最终成功率、平均 token、平均用时、每成功一件的 token。结论事件到了才增量更新这一格（只读上次之后的新事件），不在每次打开页面时全表重算；页面读的行数和格子数成正比。每格能点开看是哪几次运行。
  5. **页面**：新驾驶舱一张矩阵表，挂在 `/next/work` 旁边。
  6. **和 GitHub 关联**（需求方 2026-10-31 补充）：
     - **最终结局从 GitHub 读**：PR 合没合并、合并后有没有被撤回（撤回 PR 或提交指向原合并提交）、单有没有重开，都读 GitHub 的事件（PR、单的时间线），不靠模型自报。只读新事件：按上次读到的时刻往后翻。
     - **任务类型从单的标签取**：「域」「性质」标签本来就是开单时贴的（`pnpm issue:new` 强制），派工时读一次存下。
     - **自用仓里留痕**：工人的提交带两行尾注 `Fleet-Run: <runId>`、`Fleet-Model: <模型>`，PR 上挂一条检查结果（Checks API）写机器判和核验的结论、链回会话详情。这样不进驾驶舱，光看 `git log` 和 PR 也能统计、能回溯；驾驶舱的库丢了也能从 git 历史重建大半。
     - **对外仓不留痕**：对外仓（同事、客户读得到的仓）的提交、PR、检查里一个 AI 相关的字都不写（全局规矩「对外仓和对外内容怎么写」），这些仓的记录只进驾驶舱自己的库。
     - **影子期不写 GitHub**：影子模式下新内核对 GitHub 只读（#3776 的验收就是审计日志里没有新内核的写），尾注和检查结果等切换以后才开；GitHub App 现在只有读权限，开检查结果要加 `checks: write`（改 App 权限，不花钱）。
- **不做什么**：不拿模型自己说的「做完了」当效果；不回填旧引擎的历史（另开单再议）；不做实时推送，轮询够用。
