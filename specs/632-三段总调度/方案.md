# 三段总调度：方案（2026-10-02 夜）

> 做法按 `best-practice-first`：先写业务说明和规则，再把现有实现里「怎么做」的部分点名隔开，查业界，从业务重推，摆出「删整层」的选项和代价表。
> 这份方案落在创始人已经拍定的框架里（`specs/509-需求梳理/流程重做方案.md`、`docs/decisions/0010-three-segment-flow.md`：三段、Temporal 留、重试按表办、验收是冷调用），**不改架构**；这里定的是框架下面的做法。拍板点在第七节，凡不碰人闸的我已按推荐定下，创始人要改随时说。

## 一、业务说明

| 谁 | 在什么场合 | 要干成什么 | 干成的标志 |
|---|---|---|---|
| 创始人 | 跟指挥官聊完需求、单子开好、挂在当前版本里程碑上 | 之后什么都不用做，单子自己走到合并、关掉 | 回来打开驾驶舱，这张单在「做完的」那一栏，PR 已合，单已关 |
| 引擎 | 每隔几分钟 | 发现该做的单，一张一条工作流，不重不漏 | 同一张单任何时候最多一条在跑；该做的 5 分钟内被拉起 |
| 动手进程 | 被拉起来写码 | 在隔离环境里按单子写出提交，交给引擎推成 PR | 有真提交；没提交明确失败，不开空 PR |
| 验收冷调用 | PR 的 CI 绿了、合并之前 | 对着单子的「怎么算做完」逐条说做到没有 | 通过才放行；读不到的明确失败，不拿「读不到」当通过 |
| 创始人（人闸） | 碰对外发布、花钱、删数据、改标准，或同一原因挂了两次 | 只在这几处被叫到，一句话看懂卡在哪、选什么 | 工作流停着等他，不占资源；他点一下接着走 |

## 二、业务规则（带出处）

1. 引擎不直写主线：改动都走 PR，CI 绿才合（`docs/goals.md` §五.1；决定 0002 第 7 条）。
2. 四类人闸只在那一步停下等人（goals §五.2）；先审后合的路径要第二意见、改标准要创始人同意，合并闸挡着，工作流不绕（`docs/design.md` 第五节）。
3. 未排期的、别的版本的单机器不碰；母单、子单、贴了「本机做」的不自动派；开关关着不派；开关打开以前开的单不自动派（`packages/core/src/dispatch.ts`；决定 0003 第 2、8 条）。
4. 公开仓陌生人能开单：只有白名单里的人开的单才会被拉起（`packages/api/src/whitelist.ts`；旧接活守着的，新入口必须带上）。
5. 三栏（场景、原话、已知的模块）加「怎么算做完」缺了不派，并写清缺什么（`specs/509…/流程重做方案.md` §三；`packages/conventions/src/issue-new.ts`）。
6. 分档按单子上的「已知的模块」一次定死，不升档、不回退；中途发现错了原地改，不重开上游（方案 §四）。
7. 动手进程一次性：不续会话、默认 60 分钟超时、内存准入放不下不派、不在会话里跑全量测试（`runner/one-shot.ts` 头注释；goals §五.9）。
8. 验收只判「做到了没有」，只有三种能挡：没做到验收条、有证据弄坏原有功能、安全或丢数据；默认 1 轮，最多 2 轮；换一个跟写这张单的会话不同的家族（方案 §五；决定 0006）。
9. 读不到、没跑成、认不出，一律明确失败，不拿空、0 或 ok 冒充（AGENTS 通用段「底线」）。「还没验」和「验了没过」是两种状态，不显示成同一种（方案 §十三.3）。
10. 重试不判、按表办：额度满挂起到清零换路由接着干；进程死、网络断原地重跑；测试红回动手改，最多 3 轮；每类重试有总次数和最长等待两个上限，超了停下报人；同一个原因连续挂 2 次停下报创始人，并把每次的原文写出来（方案 §九 与 GPT 异议 2）。
11. 记账：每段一行 `runs`（单号、段、模型、渠道、起止、token、花费、内存峰值、结果），读不到的字段留空不记 0（`packages/db/src/queries/runs.ts`）。
12. 一次交接 = 控制权从一段转到另一段；读已有的记录（单子、PR、diff）不算交接（方案 §十三.4）。
13. 发布不打断在跑的会话：重启引擎前先排空（goals §五.8；`deploy/release.sh` 排空协议）。
14. GPT 不碰界面类的活（含审界面）；不用 Fable（AGENTS 通用段）。

## 五、从零方案

**业务对象**：Issue（GitHub，需求的唯一来源）→ Task（一条 `taskWorkflow`，编号 `task-<仓>-<单号>`，状态只有 Temporal 一份，库里 `tasks` 行只是给驾驶舱看的镜子）→ Run（一段一行，记账）→ PR。

**拉单（`intakeWorkflow`，Schedule 每 5 分钟一轮）**

1. 活动 `listIntakeCandidates`：对每个 `auto_dispatch_since` 非空的仓，用引擎机器人读开着的单（带标签、里程碑、母单子单关系、作者）。读不到 GitHub → 这一轮记没查成、报警，**不当成没有单**。
2. 判：作者在白名单里；`dispatchDecision`；`autoDispatchGate`（当前版本、母单子单、本机做）；三栏和「怎么算做完」齐。缺的不派，**在单子上留一条评论写清缺什么**（同一缺法只评一次）。
3. 过了的：按内存准入（并发上限）排队，起 `taskWorkflow`。
4. 拉单本身不动单子（不贴「在做」评论、不抢认领）。

**`taskWorkflow`（纯编排，副作用全在活动里）**

```
brief   = readTaskBrief(仓, 单号)            // 单子 + 需求文档 → 交代；缺栏抛 BRIEF_INCOMPLETE（不重试）
tier    = decideTierFromModules(已知的模块)   // 一次定死；反引号里的路径才认：一个文件快档、一个目录或同一 packages/<包>/ 里中档、其余主力档；暂无、有一项认不出 → 主力档（不猜）
route   = pickRoute(tier)
loop 最多 3 轮动手:
    wt     = prepareWorktree
    seg    = runSegment(manual, brief, route, 上一轮的反馈)   // 额度满 → 挂起到清零换路由，不算轮数
    pr     = pushAndOpenPr(wt)                                // 没真提交 → 明确失败
    ci     = waitCi(pr)
    红 → 反馈 = 失败日志 → 下一轮；绿 → 跳出
verify  = runColdVerify(pr)     // 换家族；没过 → 反馈 = 问题表 → 回动手一轮（总共最多 2 轮验收）
merge   = mergeWhenGateGreen(pr)   // 等合并闸 success 再合；闸要人 → 停着等 Signal
close   = closeIssue + 记 runs + 清工作树
```

任何一步的失败分流走 `failure/` 那套表（留）：额度满 → `park`；进程死/网络 → 原地重跑（总次数 + 最长等待）；同因连挂 2 次 → 写出每次原文、报警、停着等 Signal。人闸（对外发布、花钱、删数据、改标准）→ 同样停着等 Signal。

**记账**：每段结束写一行 `runs`（已合，`packages/db/src/queries/runs.ts`）。

**人看到的**：驾驶舱「在跑的」每张单显示卡在哪一环、在等谁；「还没验」不显示成失败。

**不新造的**：不新加表（`tasks` 镜子行沿用）、不新加全局开关（沿用 `auto_dispatch_since`、排空协议）、不新造审官常驻环节。

## 十一、任务工作流怎么落的（S2-4，2026-10-02 夜）

代码：`packages/engine/src/workflows/task.ts`（纯编排）、`task-contract.ts`（输入输出、信号、查询、新活动的入参结果）、`activity-options.ts`（新活动的档位）、`activities.ts`（`EngineTasks`：真端口才有，没装的活动报 `TASK_NOT_CONFIGURED`，不装作做过）。

**一条工作流的路**：读交代（`readTaskBrief`，缺栏就停下等人补）→ 最多 3 轮 \[选路（`pickRoute`，`execute` 阶段）→ 建树（第一轮）→ 动手会话（`runSegment`，只试一次）→ 读交付（`readDelivery`，没有新提交就记意见返工）→ 推分支 → 开 PR（第一轮）→ 等 CI（红了、冲突记意见返工）→ 冷验收（`coldVerify`，最多 2 轮；没过记问题表返工）\] → 查路径（`checkGuarded`）→ 挂自动合并（`armAutoMerge`）→ 等合并（`waitMerged` 长轮询）→ 关单、收树。

**失败怎么办**：不绑路由的步骤和动手会话都走现成的失败分流（`decide('failure')`，规则表在 `failure/rules.ts`）：额度用满等清零原路再来，路由繁忙、模型对不上换路由，上游出错有界重试，同因再犯或重试用完停下。会话只试一次，换谁、等多久由工作流定，不靠 Temporal 自动再起一遍（会话贵又不幂等）。

**停下等人（`waiting.kind = human`，驾驶舱「继续」「放弃」发信号）**：交代不全；没有可用路由；失败分流判挂起；动手 3 轮、验收 2 轮都不过；验收做不出来（读不到 diff、没有别家模型——不算没过，不让写代码的会话白改）；改了「改标准」的路径（人闸第四类）；碰了先审后合的路径（合并闸要第二意见）；自动合并挂不上；PR 被关、头被别人改。「继续」后从头再试这一步；「放弃」存档收树退出，PR 和单子不动。

**硬前提（没做到之前不许给任何仓打开「让 AI 接活」）**：合并闸要认冷验收的结论（#555-2、#625，S2-5）。现状：工作流里挂自动合并一定在验收通过之后；每小时对账的兜底（`jobs/auto-merge-check.ts`）原来会给 CI 绿的机器人 PR 挂自动合并，S2-4b 起它**不碰任务分支**（`fleet/<单号>-t<8 位>`，`task-branch.ts`），所以引擎自己不会绕过验收；但人手挂、或以后别的路径挂，合并闸还是拦不住——结构上的那一层要等 S2-5。
