# plan 与 GitHub 双向同步：合进主线自动建改 issue 和里程碑、关单回写已完成、手改由同步回 plan 的 PR 收进来、阶段收口归档，开单改成写 plan（文档整套改法第②步）（#138）

对应计划：plan.md P0「plan 同步」
设计依据：design 第七节「plan、design、ops 的整套改法」第 2–5 条，`docs/decisions/0001-plan-design-ops.md`。

原话：改动合进主线且动到 `docs/plan/<阶段文件>` 就由 GitHub Actions 以驾驶舱 GitHub App 身份同步：缺的建、不同的改，全量、幂等；标题、阶段、先后听 plan，「关没关」听 GitHub；手动开单、改标题由机器人的「同步回 plan」PR 收进来；阶段收口时归档；每日全量核对只作保险。（创始人 2026-09-26 拍「plan、design、ops 整套改法」，第②步）
AI 理解：在第①步定好的 plan 格式之上，做 plan 和 GitHub 之间的双向同步：正方向把条目变成 issue 和里程碑，反方向把 GitHub 上的关单、手改收回 plan；字段归属写死，防止两边来回改。做完后开单方式从 `pnpm issue:new` 换成「写 plan 条目、合进去自动生成」。

## 要做什么

照 `docs/design.md` 第七节「plan、design、ops 的整套改法」第 2–5 条：

- 正方向：`.github/workflows/` 里加同步工作流，主线上动到 `docs/plan/<阶段文件>` 的推送触发，另加每日一次全量核对（只作保险）；以驾驶舱 GitHub App 身份跑。读全部条目（含归档）和 GitHub 现有的单、里程碑，按正文里的 `<!-- plan:T-xxxx -->` 标记认；缺的建、标题 / 里程碑 / 说明不同的改；阶段文件对应里程碑，标题、说明跟文件走。全量、幂等；翻页读完、限流等待、出错重试；两次同步同时跑不出重复单（用并发组或建之前再查一次）。失败＝主线红叉。
- 反方向：单关了 → plan 那行标「已完成」；有人手动开单、改标题或里程碑 → 机器人维护一个固定的「同步回 plan」PR 往里加，挂自动合并，合并前单显示「待纳入」，这期间正方向同步不改回；机器人自己的改动不触发反方向。plan 不自动关单；归档条目只读，绝不重开。
- 归档：`pnpm milestone:close-check` 通过后，把这个阶段已完成的条目挪进归档文件，编号和链接不变。
- 开单方式换成写 plan：`pnpm issue:new` 退役或改成「生成一条 plan 条目 + specs 目录」，不再直接建单；欠账检查（`debt.yml`）里读 GitHub 的那半按新来源调整。
- 一起改的旧说法（现在先不动，等这一步合进去时同一个 PR 改）：AGENTS.md 本仓段「只有两种事开单……开单一律用 `pnpm issue:new`」那条；design 第七节「构建期也照这套走」「欠账不漏」里的开单脚本、「标签和里程碑不靠人记得贴」里「issue 一律用开单脚本开」、里程碑「描述只有一句」「仓里有的也不往 GitHub 抄」「欠账表就是 issue 加里程碑」「整体走向三样各存一处」；design 15.6「同步回仓」；README「协作」里「开 issue 用上面的 `pnpm issue:new`」。
- 这一步改 `.github/workflows/`，照 `packages/conventions/high-risk-paths.json` 属于先审后合。
- 每条读不到、写不成的路径（GitHub 读失败、令牌拿不到、标记认不出、写单失败）明确报错、工作流红，各配一条故意造出失败的测试（GitHub 接口用假服务端）。

## 怎么算做完

- 测试（假 GitHub）：同一份 plan 同步两次，第二次零写入；两次同步并发跑不出重复单；翻页第二页上的单也认得；限流后重试成功；读失败时退出码非 0、不写任何东西；机器人自己的改动不触发反方向；归档条目对应的单被人重开时不改回 plan、也不重开。
- 真仓：往 `docs/plan/P<N>.md` 加一条合进主线，几分钟内 GitHub 上出现对应的单（正文带标记）和里程碑；再跑一次什么都不变；关掉那张单，plan 那行被标「已完成」；在 GitHub 上手改它的标题，「同步回 plan」PR 里多出这条改动、单显示「待纳入」，PR 合进去后正方向同步不再改它。
- 阶段收口：对一个测试阶段跑收口，已完成条目挪进归档文件，编号和链接不变，同步后对应的单不受影响。
