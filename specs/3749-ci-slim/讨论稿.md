# 从开单到合并为什么慢：CI 不是主因，慢在引擎返工、空等和卡死（讨论稿）

- 状态：在做
- 单：#3749
- 起因：创始人 2026-10-30 觉得「每一次开单、核单的 CI 流程太长了……查的东西太多了」，要结合全盘思路（决定 0122 的开单服务和账本、自建 harness）重新看。
- 数据：GitHub Actions 最近 30 天（09-30～10-30）全部运行 21,100 次的原始记录（`gh api …/actions/runs`），抽 30 次 PR、20 次主线推送的 job 和 step 时间；30 天里 647 次红的 ci 运行逐次归类；法国库 `runs` 表最近 14 天 164 张单（只读）。脚本和查询贴在 #3749 评论里。
- 代码版本：`b7a2b21c2`（origin/main）

## 一、结论先说

1. **GitHub 上的 CI 不慢。** 一次 PR 的 ci 墙钟 p50 4.1 分钟、p90 6.9 分钟；1,757 个合并的 PR，开 PR 到合并 p50 5 分钟、p90 49 分钟。
2. **CI 查的东西都在干活，不该砍内容。** 30 天 647 次红，597 次是后来改了代码才转绿（真拦住），只有 47 次没下文；每一类检查都拦住过东西：单元测试各台合计四百多次、e2e 133、biome 111、deploy 87、hygiene 11、web 11、docs 7。决定 0101 当初的账（全套只比选测多 1 分钟，选测漏到主线连红过 10 轮）照样成立。
3. **「查太多」是旧账，已经降下来了。** 30 天 21,100 次里大头在 10-02～10-22（每天 1,000～1,600 次）；10-23 起一周只有 718 次。现在一个 PR 大约带出 8 次工作流：ci、合并闸 2～3 次、元数据检查、合并后关单、偶发统计、自动重跑。
4. **真正慢在引擎：** 一张单从第一笔开始到最后一笔结束 p50 84 分钟、p90 13 小时。其中真在跑 p50 39 分钟，**两笔之间空等 p50 43 分钟**（p90 9.5 小时）；一张单动手 p50 3 次、p90 11 次；平均每张单 1.5 笔失败或被杀。
5. **最大的一块浪费是 `claude-sub` 渠道卡死：** 10-18～10-27 这个渠道 505 笔里 101 笔（20%）卡在启动的「Syncing config…」，平均白等 34 分钟被总时长强杀，合计约 57 小时；另有 51 笔接口连接出错。

## 二、现状全貌

### 1. GitHub 这边每一站跑什么

| 站 | 跑什么 | 一次多久 |
|---|---|---|
| 本机推送前 | biome、tsc、改到的测试（`pnpm check`、推前预检） | 几十秒 |
| 开单 | `query-metadata`（查类别、域、性质轴） | 秒级 |
| PR 每次推 | `ci.yml` 全套：changes → lint（biome、tsc、文档指针等）、test 8 台、web 打包、e2e 2～4 台、deploy 3 台、heavy（不挡）→ check 汇总；外加 `merge-gate`、`query-metadata` | 墙钟 p50 244s、p90 413s；机器分钟 p50 17 |
| 合并闸 | `merge-gate.yml`：任何检查状态一变（`status` 事件）就跑一次 | 秒级，但次数多 |
| 合并后 | `close-on-merge`；主线推送 `ci.yml`（同一棵树复用 PR 结果，test/e2e/deploy 多数 0 秒） | 主线 p50 202s，机器分钟 p50 5 |
| 主线红 | `ci-rerun` 自动重跑一次失败的 job；`e2e-flaky` 统计偶发 | — |
| 发版前 | `release-train-lib.mjs` 的 `preflightCi` 只读主线头那一轮结论 | 不另跑 |

一次 PR ci 里最贵的几步：heavy 148s（不挡合并）、e2e 103s、单元测试 85s、deploy 第 3 台 82s、lint 66s、e2e 装 Chromium 45s。关键路径的末尾 30 次里 test 14 次、e2e 9 次。

### 2. 引擎这边一张单怎么走（法国库，14 天）

| 指标 | p50 | p90 |
|---|---|---|
| 第一笔开始到最后一笔结束 | 84 分钟 | 787 分钟 |
| 其中在跑 | 39 分钟 | 290 分钟 |
| 其中空等 | 43 分钟 | 573 分钟 |
| 每单笔数 | 5 | 19 |
| 每单动手笔数 | 3 | 11 |
| 动手一笔 | 12 分钟 | 59 分钟 |
| 返工回合 | 2 | 7 |

续会话的原因：重试 65、验收打回 61、自查修 42、CI 红返工 25、审查返工 17、冲突返工 14。笔的结局：完成 1,259、被杀 131、失败 91、准入挡下 25。

失败原因前几：总时长到顶强杀 105（39 笔卡在「Syncing config…」）、接口连接出错 52、退出码 143 没有终帧 31、引擎叫停 11。按渠道：`claude-sub` 505 笔里卡死 101、接口错 51、到顶 39；`cursor` 631 笔到顶 20；`xai` 130 笔到顶 47。

## 三、根因

| 根因 | 证据 | 管到什么 |
|---|---|---|
| 引擎一单一个工人、反复返工，没有拆单和并行 | 每单动手 p50 3 次；`subtasks` 里拆成两个以上的单只有 1 张 | 跨度长、空等多 |
| 返工靠下游打回，问题发现得晚 | 验收打回 61、CI 红返工 25、自查修 42；biome 红 111 次（格式问题本可在提交前自动修） | 每打回一次多一轮排队 |
| 渠道卡死没有快速判死 | 卡在「Syncing config…」的笔平均 34 分钟才被总时长杀掉 | 57 小时白等、单子被拖住 |
| 两笔之间的空等没人管 | 空等和在跑一样长；p90 9.5 小时 | 跨度翻倍 |
| GitHub 侧的附带工作流按事件触发、不看必要性 | 合并闸被 `status` 事件触发 4,553 次（30 天） | 噪音、Actions 排队 |

## 四、总设计

**尺子**（拍板后照这个验）：一张单从派出到合并 p50 ≤ 45 分钟、p90 ≤ 4 小时；每单动手 p50 ≤ 2 次；主线每周变红 ≤ 3 轮；一次 PR 的 ci 墙钟维持 p90 ≤ 7 分钟。

**CI 内容不砍，维持 0101 全套。** 数据说明每一类检查都在拦东西，砍掉省下的一两分钟抵不上漏到主线的代价。

**要改的是这几处：**

1. **卡死快速判死**（引擎，马上能做）：工人起来后 N 秒内没有第一帧真实输出（只有「Syncing config…」这类启动行），就判卡死、换渠道重派，不等总时长。先查清卡在 reclaude 客户端还是 Claude Code（另开单）。
2. **格式问题提交前自动修**（引擎工人收尾一步）：工人提交前跑 `biome check --write`，把 111 次 biome 红挡在提交之前。本机推前预检已经在查，只是工人那一步没自动修。
3. **前移自查，减少下游打回**：工人交付前先跑改到的测试和验收清单里能机器核对的条目（`pnpm check` 同一套），过了再交；这正是 harness 内核编排层的「交回先核验」。
4. **空等要有人管**：两笔之间的空等进账本（0122），超过阈值进决策卡；内核编排层按波次派，减少串行排队。
5. **GitHub 附带工作流减噪**：合并闸不再按每个 `status` 事件触发，改成 ci 的汇总 job 结束时触发一次；PR 上 `changes` 一步因 GitHub 侧没起来被 5 分钟超时掐掉（10-30 #3745、#3747 各一次，一步没跑）时自动重跑一次，现在只有主线有自动重跑。

## 五、要拍板的

1. **CI 内容砍不砍**
   - 推荐：不砍，维持 0101 全套。
   - 备选：PR 上只跑 lint 和改到的测试，e2e、deploy 挪到合并后。省约 2 分钟，0101 记过选测漏到主线连红 10 轮。
   - 理由：每类检查都拦住过真问题；CI 本身只占一张单时间的零头。
2. **卡死怎么判**
   - 推荐：首帧超时（比如 3 分钟没有真实输出）判卡死、换渠道重派，同时查根因。
   - 备选：只查根因、不加判死。根因没查清前每次照样白等 30 多分钟。
3. **先后**
   - 推荐：卡死判死和工人提交前自动格式化先做（小、马上见效）；自查前移、空等进账本、按波次派并进 harness 内核编排层；合并闸减噪最后。
   - 理由：前两样是现成的真实浪费（57 小时、111 轮），后面的要等内核。

## 六、分批

| 批 | 内容 | 怎么算做完 |
|---|---|---|
| 1 | 首帧超时判卡死、换渠道重派；查清「Syncing config…」卡在哪 | 引擎单测：只有启动行、N 秒无真实输出的假工人被判卡死并重派；上线一周 `failure_reason like '%Syncing config%'` 且跑满总时长的笔为 0 |
| 2 | 工人提交前 `biome check --write` | 引擎单测断言收尾步骤含格式化；上线一周 ci 里 lint:biome 红的次数降到个位 |
| 3 | 合并闸只在 ci 汇总结束时触发；PR 上 job 一步没跑就被超时掐的自动重跑一次 | `ci-plan.test.ts` 钉住触发条件；一周合并闸运行次数约等于 ci 运行次数 |
| 4 | 自查前移、空等进账本、按波次派 | 并进 harness 内核编排层的分批，按第四节的尺子验 |
