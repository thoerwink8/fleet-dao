# agents-sync 把 Playwright MCP 的输出目录设成 _tmp/playwright（每台机器）（#380）

对应计划：v1 Fusion 接活
设计依据：`docs/design.md` 第十五节 15.7「项目与标准」——「机器：通用规矩（AGENTS.md 通用段）、skill、钩子、MCP、命令行工具——由现在的 agents-sync 扩出来」，MCP 是已经写进设计里、但还没做的那一项

原话（创始人 2026-09-27 夜，经帅位转达；「临时文件放 _tmp/」这件事拆成三层：通用段写规矩、同步工具设好截图目录和 git 全局忽略、会话收尾钩子兜底提醒——创始人已经点头，git 全局忽略和规矩、钩子那两层已经在别的 PR 里落地，这张单管剩下的最后一小块：Playwright MCP 输出目录）：
「你现在截了很多图，但是不应该截到这种地方上。你应该放到临时文件夹，临时文件夹就是存放这些脏活、脏文件的，你能理解我的意思吗？_tmp」

AI 理解：截图、导出数据、日志这类临时文件不该落在仓根或源码目录，统一放 `_tmp/`（各仓 .gitignore 已忽略这个目录）。本机已经手动在 `~/.claude.json` 里给 playwright 这个 MCP 加了 `--output-dir _tmp/playwright`，但这只管这一台机器、只管 Claude Code 这一家；这张单要让 `packages/agents-sync` 把这件事接过去，`--apply` 时每台机器自己把它设对。

## 现状
- `packages/agents-sync` 现在管三样：AGENTS.md 通用段（写进各家的全局说明文件）、`agents/skills/`（拷进各家 skill 目录）、`agents/hooks/`（拷进 `~/.fleet-dao/hooks/`、登记进 `~/.claude/settings.json` 的 hooks）。三样的落点都写在 `packages/agents-sync/src/targets.ts` 里，每条落点都注明是查了哪家的源码或官方文档定下来的。
- `packages/agents-sync` **不管** MCP 服务器配置：仓里搜不到任何 `mcpServers` 相关代码。
- 一台机器的 MCP 配置在哪、长什么样，各家不一样。Claude Code 是 `~/.claude.json` 的 `mcpServers.<name>.args`，本机这条长这样（路径按本机装的地方改写成了占位符，形状是真的）：
  ```json
  "playwright": {
    "type": "stdio",
    "command": "cmd",
    "args": ["/c", "<本机装 playwright-mcp 的地方>/playwright-mcp.cmd", "--output-dir", "_tmp/playwright"]
  }
  ```
  同一份 `~/.claude.json` 里还配了 codegraph、context7、chrome-devtools、fetch、jev-ultrafast 好几个别的 MCP，格式各不一样。其余各家（Codex、Grok、Gemini……）的 MCP 配置文件在哪、长什么样、是不是都支持 `--output-dir` 这个参数，都还没查过。

## 为什么不当场做（要先定架构，不是当场能扩的功能）
targets.ts 现有的三类「目标」（RULES_TARGETS、SKILL_TARGETS、HOOK_TARGETS）都是「一份文件、整份或按标记块由本脚本说了算」的形状；MCP 配置不是这个形状：
1. 那份 JSON 是用户自己攒的、各家机器上装的 MCP 都不一样，删改哪一条、怎么改都得非常小心，不能像 hooks.ts 那样整段接管，也不能像 AGENTS.md 通用段那样整份文件由脚本说了算。
2. 只能**改**已经配好的 playwright 条目，不能新增——这台没配 Playwright MCP 就不该凭空装一个，这和 RULES_TARGETS/HOOK_TARGETS「没装那家就跳过」不是一回事，得单独设计判断（判断「配没配」本身就要先解析这份因家而异的 JSON）。
3. 每家往 MCP 服务器传参数的方式都不一样（Claude Code 在 Windows 上是 `cmd /c playwright-mcp.cmd --output-dir ...` 这样包一层，Linux、别家未必这样包；已经有别的 `--output-dir` 时改还是不改也没想清楚，要不要去重）。
4. targets.ts 里现有的每一条落点都写明了查过的依据（源码路径、官方文档链接、版本号）——见文件顶部那几段注释。这条要做到同一个可信度，工作量和「把每家的 MCP 配置格式挨个查一遍」差不多，不是改一行代码能带过去的事。

这几条要先想清楚该怎么设计（要不要单独一类 target？只接 Claude Code 一家先上、其余先开一份类似 `HOOK_GAPS` 的「没接、为什么」清单？）才好动手，是「改架构」，照通用段的规矩开单，不当场做。

## 怎么算做完
- `packages/agents-sync --apply` 在这台机器上，把（至少）Claude Code 的 `~/.claude.json` 里 `mcpServers.playwright` 已经配了的那条 `args`，加上 `--output-dir _tmp/playwright`（相对路径，跟着每次话所在的项目走）；已经有这个参数但值不对的改成这个值；这台没配 Playwright MCP 的跳过、不新增。
- `--check` 能查出这台的 Playwright 输出目录对不对，和别的检查一样落一行结论（一致 / 漂移 / 缺失 / 没装跳过 / 没查成）。
- 有测试：真配置文件（临时目录里的假 `~/.claude.json`）覆盖「没配 playwright」「配了但没这个参数」「配了但值不对」「已经对了」几种情况；`~/.claude.json` 本身读不出（不是 JSON、权限问题……）要报没查成，不能猜成「没配」就直接去写，会把用户自己的 MCP 配置搞坏。
- 决定「除了 Claude Code 还管不管别家」：先只做 Claude Code 一家也算做完，前提是单子和 PR 里写清楚别家没接、为什么（类似 targets.ts 里 `HOOK_GAPS` 那种「装了但没接」的说明），别家没接不算没做完，是这单里明确排除在外、留给以后的单。
- 结果记进 `specs/<本单号>-<短名>/结果.md`，`pnpm issue:close` 关。
