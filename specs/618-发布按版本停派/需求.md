## 场景

创始人合一张「发布 vN」PR，等 GitHub Actions 收完尾，法国就换成这一版；平时合进主线的 PR 不再直接上线。

## 怎么算做完

- 主线合并不再触发法国发布；法国只发「发布 vN」PR 合并后的那一版（或指挥官带理由的急修，事后记下来）。
- 发布那一刻先停派活、等引擎在跑的会话都收完尾（有上限，超时照实报、不硬切），部署，再恢复派活；每一步在 Actions 日志和驾驶舱里看得到。
- 引擎关着时（现在的状态）这几步照实写「引擎关着，跳过」，不假装做了。
- 每条读不到、没跑成的路径都明确失败，各配一条故意造出的失败测试。
- docs/ops.md 第九节、docs/design.md 跟着改。

## 现状

2026-10-02 夜：代码、测试和文档已在 PR 里（见 `docs/PROGRESS.md` 当天的表）：法国自动发布只发**版本标记**（版本号最大的 `v<N>` tag，指向的提交得是 `origin/main` 的祖先、得比在用的新、CI 全绿）；标记缺失 / 读不到 / 不是主线上的提交 / 不比在用的新，一律明确失败并报警，绝不退回发主线头、绝不降级；落后读数（`/healthz` 的 `deploy_lag`、后端报警）改成拿版本标记当头数；引擎关着时「停派活 → 等收尾 → 部署 → 恢复派活」四步照实写「跳过」，开着时交给 `release.sh` 的排空协议。
接手时发现并补上的两处（上一个会话留下的改动里是错的）：① 标记比在用的旧、而主线上还有更新提交时，原写法会拿标记去**降级**；② `deploy_lag` 仍按主线头数落后，按版本发之后每次合并都会红一条。两处各有故意造出失败的测试。

**还没做（要创始人点头才能做）**：把新的自动发布装到法国（`bash /srv/fleet-dao/deploy/france.sh`，碰生产，算上线）并真机验一轮——手改一项让它读不到标记看报警、打一个测试标记看它发不发。在那之前法国跑的还是旧的「跟主线头」自动发布，这张单不关。
