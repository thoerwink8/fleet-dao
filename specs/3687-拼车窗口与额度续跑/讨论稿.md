# 拼车 5 小时窗口怎么接满、额度用完怎么到点续跑（2026-10-24，讨论稿）

- 状态：讨论中
- 起因：需求方 2026-10-24 提了：拼车 5 小时 80 美元，本机桌面端常开，想让桌面端定时发探针把窗口点着，日常时段（约 08:30–24:00）每个窗口都用得上；额度用完、任务中断后，到清零时刻自动接着干。主要给本机桌面端自己用，不只是引擎。
- 范围：查了本机 reclaude（守护进程日志、配置结构）、法国库里拼车 5 小时窗的读数历史、本机 Claude Code 2.1.310 的 `/goal` 和 `StopFailure`、桌面端定时任务和会话消息的能力、仓里引擎现有的拼车切号和额度续跑。没查：reclaude 网关拒绝时回给客户端的原文（近 4 天没用满过，抓不到）、桌面端会话是否支持 `/goal` 的「等清零自动续」。
- 怎么查的：本机只读看日志和配置结构（密钥不读值）；法国库只读连接查 `quota_window_samples`；本机二进制里搜文案和判定代码；读仓里代码和文档。证据标实测 / 按代码 / 推断。
- 代码版本：`cf84ba39b`

## 一、提出的问题

### 1. 定时探针能不能让日常时段每个窗口都用得上

- **现象**（实测，法国库 `quota_window_samples`，`label = carpool_5h_usd`，10-20 到 10-24 共 20 个窗口）：
  - 清零时刻一个接一个：10-23 01:51 → 06:50 → 11:51 → 16:52 → 21:50 → 10-24 02:52 → 07:49 → 12:52，每次比上一次晚 0–3 分钟。窗口是**第一次用的时候才开始算 5 小时**（`docs/reference/quota.md` Q27 同一个结论），不是固定钟点。
  - 只断过一次：10-24 12:52 清零后到 13:49 没人用（读数 used=0、没有清零时刻），13:49 才开了下一个窗（18:49 清零）。
  - **20 个窗口一个都没用满**：平均每窗 25.8 美元、中位 24.1、最高 67.3；接近 0 的有 4 个（0.05、0.59、0.72、5.06）。大约 2/3 的额度在清零时作废。
- **根因**：
  - 拼车额度是 reclaude 账号级共用的（Q6；reclaude 网页「设备」里同一账号挂着 5 台设备：本机、另外两台电脑、Mac、法国）。法国引擎的路由探针每 15 分钟一轮、拼车盯读每 1–5 分钟一轮（`docs/ops.md`），它一直在用，所以窗口几乎首尾相连。**窗口能不能接上，取决于整个账号有没有人在用，不取决于本机。**
  - 5 小时不能整除 24 小时，每天固定几个钟点发探针，没法和一个会漂移的窗口一直对齐：探针落在窗口中间时什么也不改变，只有窗口空着时才会开一个新窗。
- **需求方的思路**：在固定时间点发探针。
- **判断**：
  - 拿来兜底是成立的：法国停了、切到独享、或者像今天 12:52–13:49 那样没人用时，本机探针能把空档压到一个探针间隔以内。
  - 拿来"对齐上班时间"不成立：想让窗口在 08:30 刚好清零，就得在前一个窗口故意空着不用；可法国一直在用同一份额度，硬对齐反而少用。窗口连着接上时一天最多 4.8 个窗口，这已经是上限，探针加不出额度。
  - 想"多用上"，真正的缺口在用量：每窗平均只用掉三分之一。需求方的重活应该放心往拼车上压，不用省。
- **做法**：桌面端开一个定时任务，固定间隔发一次最小探针（建议每 30 分钟；间隔见第五节第 1 条）。桌面端由 reclaude 打过补丁（`~/.reclaude/claude-app`），走的就是拼车，所以定时任务每跑一次就是一次探针，不用另写探针程序（按代码：定时任务每次起一个新会话、发真实的模型请求）。
- **不做什么**：不追"窗口对齐某个钟点"；不在法国引擎里另加一套本机探针；不为了对齐去停法国的用量。

### 2. 额度用完、任务中断后，怎么到清零时刻自动接着干

- **现象**：
  - 引擎这边已经做好了（按代码 `packages/engine/src/failure/rules.ts` QT1）：认出额度用满就挂起到清零时刻、续同一个会话；拼车用满还会切到独享接着干（#157、#194、#303）。
  - 本机桌面端没有：会话撞上额度会报错、这一回合就停了，要人回来再发一条消息。
  - 本机 Claude Code 2.1.310 自带两个可以用的点（按代码，二进制里的文案和判定）：
    - `/goal`（目标模式）：限流、回合失败会自己隔几分钟重试；撞上额度时有两种结局——宿主支持"等清零"就显示 `usage limit reached · continues automatically when it resets`、到点自己续；不支持就显示 `send a message after it resets to continue`、停下来等人。桌面端算哪一种没实测。
    - `StopFailure` 钩子：回合因为接口报错（含限流、额度）结束时触发，能把"哪个会话、什么报错"记下来。
  - 桌面端自己能给别的会话发消息（`send_message`，消息作为一条用户消息进那个会话），定时任务的会话也能用。
- **根因**：桌面端会话撞了额度以后，没有一个"到点再发一条继续"的人或程序。
- **判断**：不用自己造调度，把桌面端已有的三样拼起来就够了：`StopFailure` 记账 → 第 1 条那个定时任务顺带巡一遍 → 已过清零时刻的会话发一条「继续」。如果 `/goal` 在桌面端本身就会等清零自动续，长活直接开 `/goal`，自建的这一半只管没开 `/goal` 的会话。
- **做法**：
  1. 用户级设置加一个 `StopFailure` 钩子：报错是额度或限流时，往本机一个待续清单（`~/.fleet-dao/state/` 下一个文件）追加一行：会话号、报错原文、读到的清零时刻（原文里有就照原文，没有就用拼车接口的 `resets_at_ms`，再读不到按报错时刻 + 5 小时估，并标明是估的）。
  2. 第 1 条的定时任务每次跑：读待续清单，已过清零时刻、额度读数显示有余量的，对那个会话发「额度已清零，接着刚才的活继续」，然后划掉；发失败的留着下一轮再发，连续三轮失败就在定时任务的结果里报出来。
  3. 长的、能自己判断做没做完的活，用 `/goal` 起。
- **不做什么**：不自动开新会话去重做（续原会话，上下文不丢）；不在额度没清零时反复重试（白撞，还会被记成异常流量）；不碰法国引擎的那套。

## 五、要拍板的

1. **探针多久一次**：建议全天每 30 分钟一次（空档最多半小时出头；每次是一次很小的请求，一天 48 次，比每窗作废的几十美元小得多）；备选每小时一次（空档最多一小时出头，花得更少）；或只在 06:00–24:00 跑（夜里靠法国）。不定的话：先按每 30 分钟上。
2. **要不要追"窗口对齐上班时间"**：建议不追，理由见一的「判断」；备选：只在法国停用的日子里，07:00 发一次，让第一个窗口 12:00 清零。不定的话：不追。
3. **续跑走哪条路**：建议先上 `StopFailure` 记账 + 定时任务发「继续」，同时实测 `/goal` 在桌面端会不会自己等清零；会的话，长活改用 `/goal`，自建这一半只管没开 `/goal` 的会话。备选：只用 `/goal`、不自建（便宜，但普通会话照旧断）。
4. **用满的样本怎么拿**：拼车网关拒绝时回给客户端的原文还没抓到（近 4 天没用满过），钩子按什么认、`/goal` 认不认得出它，都取决于这句原文。建议：钩子先上线、只记不续，等下次自然用满，按抓到的原文补判法再打开自动续。备选：挑一个窗口故意压重活压到满（反正每窗作废三分之二，不算浪费），当天就能拿到。

## 七、没核实的

- reclaude 拼车网关拒绝时回给 Claude Code 的原文和状态码：等下一次用满（或第五节第 4 条的备选）；影响二的判法和批次 3。
- 桌面端会话里 `/goal` 撞额度是"自动续"还是"等人发消息"：一次实测；影响第五节第 3 条。
- 定时任务的会话能不能对别的会话 `send_message`、能不能读到 `StopFailure` 写的清单：批次 1 上线后试一次；影响批次 3。
