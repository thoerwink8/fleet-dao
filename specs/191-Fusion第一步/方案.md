## 一、目标和怎么算做完（照需求.md，不改标准）

一句话：把旧 P1 验收第 2 步（fleet-dao 自己一张真单由引擎从收单做到合并）换成 Fusion 做法做通——法国一张单一个 Lead 会话，界定清楚的活派给副手，开 PR 前别家验证模型核一遍。

怎么算做完（原文）：

- fleet-dao 一张真小需求由法国引擎按 Fusion 做法（Lead 会话、副手、开 PR 前别家验证模型）从收单做到合并、关单，全程没人插手。
- 在有副作用的步骤之间（推分支后、开 PR 后、合并前）各杀一次 Lead，新会话从存档接着做完：不重复推、不重复开 PR、不重复合并和关单，读回核对只有一个 PR、一次合并。
- 引擎只把活派给探针判在线的路由；登录失效演练里探针能发现并恢复（#129 剩的两条）。
- 会话内存上限、测试进程数是实测定的，交活核对只跑改动影响到的测试（#164）。
- 驾驶舱看得到这张单每一步的耗时和各模型花的额度。
- 这一步新写的判断在 core 包里，有测试。

### 2.2 现有代码做不到、要推翻重写的

1. **需求工作流整条链**（`requirement.ts` 的 `requirementWorkflow`）：分诊会话 → 需求文档会话 → 方案会话 → 每个子任务一条子工作流、各带一个写码会话和一个 PR → 结果文档。Fusion 是一张单一个 Lead、块不开成单、开 PR 前验证。建议新写一条工作流，旧的不打补丁：改旧工作流的调度顺序要按 `patched()` 照顾在途历史（`kit.ts` 头注释），`packages/engine/test/replay/fixtures` 下有 requirement、subtask 的回放夹具。
2. **直写主线**：`writeSpecDoc` 三处调用和 `github/src/contents.ts` 那条写法，0002 第 7 条要去掉。
3. **第二意见的判法**：`subtask.ts` 的 `secondOpinion` 加 `decideAfterVerify` 里审查那一支——合并前、和 CI 并行、按 risk 触发、blocking / minor 两档；验证模型要在开 PR 前、对照「怎么算做完」逐条答、只三种能挡，得重写（CI、冲突、墙钟预算那几支能留）。
4. **会话端口写死 Claude Code**：`sessions.ts` 的 `startSession` 抛 `HOST_NOT_WIRED`，结局判定用 `judgeClaudeRun`；要按执行方式拆开（插头层的 cursor、grok 已有 run，只是包没导出、引擎没接）。#212 拆开了：按执行方式分派给驱动（`real/hosts.ts`），接上了 cursor-agent。
5. **分诊会话**（triage 阶段 + `decisions/triage.ts`）：Fusion 里并进 Lead 规划。
6. **界面禁令按阶段判**：`shared/src/bans.ts` 的 `gpt-no-ui` 看 stage 是不是 `ui`，stage 来自方案 plan.json 里会话自己写的值；Fusion 要按改到的文件路径判（插题：碰到页面代码就不给 GPT），现法做不到。
7. **派活配置以库为准**：`stage_policy_routes` 由驾驶舱直接改、`catalog.ts` 只补缺；Fusion 要仓里 JSON 为准、库里只是副本，存储方向反过来。
8. **停会话只有立刻停**：中途切换要先把没提交的改动提交成临时提交（第 3 题），要新做。

## 三、最短路径

### 3.1 必须做 / 可以后放

必须做（缺了「怎么算做完」过不了）：

- Lead 会话 + 一个副手 + 引擎推分支、开 PR、合并、关单，不直写主线（新工作流）。
- 开 PR 前别家验证模型。
- 接上第一个别家渠道：验证模型必须是别家，副手也该是别家便宜模型（0002 第 1、4、5 条），法国引擎现在只接了 Claude Code（#212 接上了 cursor-agent：会话端口、探针都认它，真流量等法国登录）。
- 存档点和换 Lead 接手，外加杀 Lead 演练。
- 流程配置最小版：Lead、副手、验证三个角色各一串路由（形态等 #169 定稿）。
- 新判断进 core 包、有测试。
- 每一步耗时和各模型额度进驾驶舱。
- #164、#129 剩的两条。

可以后放（这张小单用不上，或做完标准没要求）：

- 方案评审（小单跳过，第 2 题）、讨论记录简报与全文、讨论接着聊 → #193 的 #118、#69，#197。
- 帅位租约、盘面、钩子注入 → #199 和 #169 第四轮。

### 3.2 这张小单在代码里怎么走（建议，待 #169 定稿核对）

1. 收单：`issue-intake.ts` 照旧；后端按模式起 Fusion 工作流（默认 Fusion），工作流编号仍是 `req:<仓>#<号>`，驾驶舱和 fleet 命令的信号照旧发得到。
2. 规划：Lead 会话（拼车池的 Opus 路由）读单、读已有的需求.md（从 issue 正文里的「文档：`specs/…`」认目录，不再按标题拼）、读代码，交方案和任务简报；core 校验；说不清走现成的 `askAndWait`。写存档点。
3. 方案评审：小单跳过（core 按大小判）。
4. 执行：`createWorktree` 建树；按简报起副手会话（别家路由，交活照现成的 fleet done + 交付核对）；续 Lead 会话验收：收下 / 打回（最多 2 次）/ Lead 接手（同一棵树、副手不在跑）。写存档点。
5. 推分支（现成 `pushBranch`，推前卫生检查）→ 验证模型会话（别家路由，检出推上去的头、只读，走现成 review 那套检出）→ Lead 看结论：没做到就回第 4 步（最多 2 轮），有证据可驳回。先推后验的理由：发给别家的改动先过了推前扫描，验证模型也能直接用现成的「检出某个头」。写存档点。
6. 开 PR（`openPr`，正文加方案摘要和验证结论）→ `waitCi`；红了 Lead 写修复简报、副手改，最多 3 轮；绿了 Lead 做最终审查。写存档点。
7. 合并队列合并 → 关单评论写结果（改了什么、用时、各模型额度），正文在工作流里定一次再发。

杀 Lead 演练：在第 5、6、7 步里 Lead 会话在跑的时候（推分支后、开 PR 后、合并前）各杀一次（停掉它的 scope），新 Lead 按存档点接着做；读回 GitHub：这个分支只有一个 PR、一次合并、一条关单评论。副作用做没做以工作流状态为准，不以 Lead 记得为准。

## 四、风险和待定

### 4.1 风险

- **别家渠道是最长的杆**：验证模型必须别家、副手也该别家，而引擎只接了 Claude Code（`sessions.ts` 的 `HOST_NOT_WIRED`，探针只探 claude-code；#212 接上了 cursor-agent）；接第一家还要创始人在法国会话用户下登录一次（plan.md 第五节「需要你们动手的事」P3 验收前那行）。
- **结构性重写**：需求工作流一步一会话、一子任务一 PR、文档直写主线，和 Fusion 不同构；新写工作流工作量大（需求.md 估十几个 PR），而 #169 没定稿，先开工的部分可能返工。
- **「无人插手」的外部条件**：拼车 5 小时窗容易用满、切独享没做（design 第十节，#194），用满只能等清零；CI 偶发超时（#88）；改到先审后合路径的 PR 引擎写不了 `second-opinion` 状态、合并闸会一直等（`subtask.ts` 注释）；打开 fleet-dao 的「让 AI 接活」后新开的单都会自动派（design 第九节），只派一张的办法 #160 没做成（#160 已叫停关单）。
- **杀 Lead 演练的两个坑**：被外面杀掉的会话失败分流只重起一次、再来就挂起（`failure/rules.ts` 的 KL2），三次杀得落在不同的步骤调用上；关单评论的幂等键带正文（`github/src/issues.ts` 的 close_comment），结果评论要是由重开的 Lead 重写一遍就会发第二条。
- **内存**：Lead + 副手 + 测试同时在法国跑，#164 实测 1 个测试进程峰值约 1.6G，现在 2G 硬上限连 1 个测试进程加 Claude Code 都放不下。
- **往外发**：验证模型、副手看得到改动；「发给别家模型的内容要过敏感信息检查」（#169 第 4 题前半）目前只有推前、写文档前两处扫描。
