# CI 耗时实测（母单 #901，只管 CI 与测试耗时）

创始人 2026-10-05 原话：「项目臃肿+ci流程慢，需要优化重构各个模块和流程」。

接着 `docs/ci-speedup-plan.md` 前三轮往下量：那里的验收（小 PR ≤ 60 秒、deploy PR ≤ 90 秒、重推命中缓存 ≤ 40 秒）都已达到，这份只回答「现在最慢的几块是什么、有没有证据支持的、安全的提速」。**不降低必过检查的覆盖面、不改合并闸判红口径、不动第二意见流程。**

## 怎么量

`gh run list --workflow ci.yml` 取最近 60 次，取其中成功的 40 次（2026-10-04 夜到 10-05 凌晨，PR 24 次、主线推送 16 次），每次 `gh api repos/{r}/actions/runs/{id}/jobs?filter=latest` 取每个 job 和每一步的起止时间；跳过的 job 不算。「墙钟」= 第一个 job 开始到最后一个 job 结束；「关键路径」= 最后一个（不含 check）收工的 job。再下 5 次全量 PR 轮的完整日志，读 vitest 每台的 `Duration` 行和每个测试文件的耗时。

| 主线推送 | 16 | 51 / 62 | 3 | 59 |

### 测试台是否匀（PR 全量）

- 普通台之间差得多：同一轮里最快 52–63、最慢 82–102 秒（`37219209031`：54 到 102；`37219911540`：61 到 87）；vitest 自己报的 Duration，`37219911540` 的普通 6 台是 38.6 / 43.0 / 45.7 / 49.8 / 58.7 / 66.3 秒，pg 两台 25.8 / 19.2 秒。
- 原因：装箱用的耗时表 `packages/conventions/test-timings.json` 是 2026-10-03 量的、359 个文件；仓里现在 455 个测试文件，**96 个新文件表里没有、按中位数 98 毫秒估，实际合计 99.6 秒**；几个旧文件现在的耗时也和表里差得远（`db/test/migrations.test.ts` 表里 20.4 秒、现在 11.2 秒；`engine/test/watchdog.test.ts` 5.3 秒对 11.7 秒；`db/test/catalog.test.ts` 9.6 秒对 3.3 秒）。
- 留出一轮检验（用另外 4 轮的中位数装箱、拿 `37219911540` 的真实耗时当真值算每台合计耗时）：旧表装箱，普通台最大 116 秒、最小 84；新表装箱，最大 93、最小 80；pg 台从两台（53 + 48）变成一台（101，vitest 里约 45 秒，不是长杆）。

### 依赖安装 / 缓存 / 重复构建

- `pnpm install --frozen-lockfile` 每台 2–4 秒（pnpm store 缓存已在 setup-node 里开了，命中）。
- 没有两个 job 做同一件事：`tsc` 在 lint 里只跑一遍；web 的 `build:demo` 只在 web 受影响时一台。
- 按改动路径跳过：`changes` 已按包依赖图选 test、web、deploy；纯文档 PR 只起 changes、lint（docs 一步 10 秒）、check，整轮 35–39 秒；主线同树复用已省掉主线的大部分测试。

## 切片结果（2026-10-05 凌晨实测）

### 1. 耗时表刷新 + `ci:timings` 取几轮中位数（#905，已合）——有效

做的：用最近 5 个全量 PR 轮（`37219911540`、`37219602410`、`37219226913`、`37219209031`、`37218431482`）的日志，每个文件取中位数重写 `test-timings.json`（359 → 455 个文件）；`pnpm ci:timings` 可重复给 `--run`/`--log-file` 取中位数，不给时改取「最近 40 次绿运行里头 5 次真跑了 4 台以上测试台的」（原来默认取主线最近一次，而主线大多数轮次复用 PR 的检查、没有测试日志，会拿到空日志退出 2）。装箱均衡的测试原来写「每台 ≤ 目标的 2 倍」，表一刷新总量涨就红，改成「≤ 平均的 1.3 倍」（pg 台只有 db 的文件、不能和别的台互补，最容易偏高）。

前后对比（全量 8 台的 PR 轮，每台 job 总耗时，秒；前 5 轮、后 5 轮，各取同类）：

| | 前（旧表） | 后（新表） |
|---|---|---|
| 一轮里最慢一台，中位数 | 87（87 / 87 / 81 / 102 / 84） | 75（81 / 71 / 75 / 78 / 69） |
| 普通台里最快到最慢的差，平均 | 30 秒 | 23 秒 |
| pg 台 | 2 台（每台 36–49 秒） | 1 台（56–68 秒） |

最慢台的中位数 −12 秒（−14%）。**噪声大**：同一份代码在不同机器上差 ±20%，每组只有 5 轮；留出检验（上面「测试台是否匀」）预测普通台最大合计耗时 −20%，实测最慢台的 vitest 一步：前 66.3 秒（`37219911540`），后 61.1 / 53.4 秒（实验轮 `37223040564`、`37223539140` 里正式的那一遍；后者七台是 36.1 / 41.9 / 47.7 / 49.1 / 52.0 / 52.2 / 53.4，pg 台 45.6）。剩下的不匀不是表的问题：同一轮里每台表上的合计都是 95，而台内文件实际耗时合计是 66–110 秒（每台 vitest 墙钟 ≈ 实际合计的 0.48 倍，贴得很准），也就是每个文件的耗时随同台跑什么变（单文件跨轮的波动：各文件标准差之和 / 均值之和 = 0.16；同一文件最大/最小常有 1.3–1.9 倍；`task-route-wake.test.ts` 同一份代码 6.1 到 39.9 秒，一次离群）。要再匀，得在新装法下再采几轮重刷、再装，逐轮收敛，每轮收益在噪声之内，没再往下做。

表会随新测试变旧（一天加了 96 个文件）。自动保鲜没做（要定时任务、写权限、开 PR，且 GITHUB_TOKEN 开的 PR 不触发检查），开了单跟踪（见文末）。

### 2. vitest 并行进程数——量了，不接

同一台机器、同一批文件，正式一遍之后用 `--maxWorkers=` 3（默认）、4、6、8 各再跑一遍（实验 PR #906，已关；runner 是 4 核 / 16G）：4 个进程八台全比默认快，但只快 0–3.7 秒（0–8%，中位约 4%）；6 个进程有快 4 秒的也有慢 2 秒的（−10% 到 +7%）。这几遍是接在默认那一遍后面依次跑的（4 个进程排第四、6 个排第五），越往后文件缓存越热，这点差距不比热身的偏差大。**没有可接的收益**；`threads` 池没量成（实验步骤的写法有错，后来没补，不影响结论：台内瓶颈不是进程数）。

### 3. 台内按耗时从重到轻排——量了，不接

vitest 在没有缓存（CI 每次新检出）时按文件名顺序排，不是从重到轻。写了一个按耗时表排序的 sequencer，同一台同一批文件对比：`seqB`（第三遍，已热）与 `base2`（默认顺序）相差 −0.3 到 +1.7 秒，`seqA`（排在第一，仍有冷缓存）除一台 +9.7 秒（冷缓存）外也在 ±0.5 秒以内。**台内尾巴不是问题**。

### 4. Temporal 测试服务端每台下载——不是瓶颈

怀疑过：`TestWorkflowEnvironment.createTimeSkipping()` 默认「下载最新版测试服务端、缓存在临时目录」，每台新机器都要下。实测（实验 PR 里每台各量两遍）：81M，**1 秒**，版本跟着 SDK 钉在 1.24.0，不是「最新」。不用缓存。

### 5. 主线推送的 lint（43 秒，主线复用命中时的关键路径）——没做

主线 16 轮里 16 轮 lint 是最后一个收工的，43 秒（tsc 29、docs 22、biome 12 并行，4 核抢）。同树复用已经让这些轮次只剩 3 个 job。要让 lint 也复用得动 `ci.yml`、`ci-plan.ts` 的 `ciVerdict`（lint 现在「每次都得跑且绿」）和 lint 自己先查复用（lint 现在不等 changes，等的话每个 PR 的 lint 晚 8 秒起），都是先审后合路径。收益只在主线那一轮（没有人在等它，自动发布才等）。**不做**，按第二轮定的停的标准（每轮省不到 5 秒或要冒假绿的口子）。

### 6. 多个会话同时开 PR 时，慢的是排队，不是 job——有证据，要创始人定

两批数据对比（每个运行的 job 的 `started_at − created_at` 取最大值）：

| | 运行数 | 最大排队中位 | 排队超过 10 秒的运行 |
|---|---|---|---|
| 平时（上面那 40 次，2026-10-04 晚到 10-05 凌晨） | 40 | 3 秒 | 3 次（31、12、71 秒） |
| 并发开 PR 的这一阵（10-05 凌晨，同一个小时里 8 个别家的 PR + 我自己的 3 个实验轮） | 12 | 53 秒 | 10 次（最长 131 秒） |

后一批里四个全量 PR 轮的整轮墙钟 184–243 秒（平时 100 秒上下），多出来的差不多全是排队：全量 PR 占 15 个 job（8 台测试 + changes + lint + check + web + deploy 3 台），免费档全账号同时只有 20 个，第二个 PR 的 job 就排着等。**其中有我自己实验轮的一部分（3 个 15 个 job 的运行），所以这批数字偏大**，但 8 个别家 PR 在 5 分钟内先后推上来就足够挤满。

另一层：主线复用被打掉。后一批里 3 个主线推送都**没有复用**（`37224213934`：「PR #907 没有同树同基准的成功运行……（合并前主线又动过）」），各自又跑了 15 个 job；平时的 16 个主线推送一个都没跑测试。原因是复用要求「PR 检查测的那棵树 == 这次主线的树」，几个 PR 连着合时，后合的那个检查测的是旧主线，树对不上。所以并发越多，每个合并还要在主线再占一轮 15 个 job，排队更长。

能压的办法（都要创始人定，不是我这轮能做的）：
- 开 GitHub 合并队列（merge queue）：PR 在队里已经和最新主线合起来测过，主线推送那一轮可以不再重测。是改合并流程和主线规则集的事（公开仓免费），要创始人拍。
- 升 GitHub 套餐（并发 20→40）：要花钱，花钱闸。
- 再压每个 PR 的 job 数（web 并进 lint 省 1 个、deploy 3 台并成 2 台省 1 个）：每个只省 1 个槽、deploy 并台墙钟 +10 秒，值不值要看创始人更在意排队还是单个 PR 的耗时；第三轮「机器越少越好」的方向一致。

### 7. 加测试台数（`MAX_BOXES` 8→10）——不做

台数换墙钟：全量轮最慢台约 −10 秒、多占 2 个并发槽，和上一条的排队正好反着来，不做。

### 总的结论

CI 本身已经在很紧的地方：纯文档 PR 35–39 秒、小代码 PR 50–60 秒、全量 PR 100 秒上下（台内是耗时表、台数、每台 12 秒固定开销，再压每一项都在噪声里）。再往下的真收益不在单个 job，在排队和合并后主线那一轮（上面第 6 条），那要改合并流程或花钱，不是这一路能定的。

### 还欠的

- 耗时表自动保鲜：#921（挂 #901，v3）。做完的标准：定时拉最近几轮全量 PR 的日志重写表、PR 自己带检查地合进去；表里缺的文件超过 10% 时 changes 打 `::warning::`。
- 第 6 条（排队、主线复用被并发打掉）：等创始人在合并队列、升套餐、再压 job 数里挑，没挑之前不动。
