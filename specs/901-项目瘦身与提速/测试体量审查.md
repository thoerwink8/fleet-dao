# 测试层的臃肿与慢（母单 #901，第一阶段只读 + 第二阶段不降覆盖的几刀）

创始人 2026-10-05 原话：「仔细审查整个项目，项目臃肿+ci流程慢」。这份只管测试层，CI 整体耗时见同目录 `CI耗时实测.md`（没重复量）。

## 一、先说结论

1. **测试体量**：ts / tsx / mjs 里「放在 `test/` 目录或叫 `.test.*` 的」共 141,673 行，产品代码 146,984 行；每个包的对比见第二节。测试比产品代码多的包：engine（41.0k 对 33.4k）、api（16.6k 对 11.4k）、conventions（15.0k 对 12.6k）、db、hygiene。注意「测试行」里含夹具、辅助文件，不全是用例。
2. **慢不在「复制粘贴」，在每个文件、每条用例的固定开销**：
   - 78 个测试文件用到 PGlite（内存里的 Postgres），占 CI 测试文件耗时 49%（375.6 秒 / 769.5 秒）；每个文件是一个新进程，**原来每个都从头建库、跑全部迁移**（本机新进程 3.2–3.7 秒，其中真干活的只有「载入一份跑完迁移的库」约 1.5 秒）。已改成跨文件共用一份快照（PR #965，已合）。
   - 真 git：`engine/test/real/` 下的会话、并主线、对账那一批每条用例要起二三十个 git 进程。Linux 的 CI 上一个 git 几毫秒；**这台 Windows 机器上一个 git 100–300 毫秒**，同一个文件本机比 CI 慢 5–12 倍（`user-git` CI 11 秒、本机 134 秒；`sessions-grok` CI 14.8 秒、本机单跑 34.5 秒）。所以「本机跑测试慢」主要是 Windows 起进程贵，不是测试写得差。
   - Temporal：每条用例起一个测试服务端 + 一个引擎 worker + 关掉，`task-workflow.test.ts` 31 条用例中位数 0.68 秒、合计 27.7 秒；12 个文件各自打一份工作流包（webpack，每文件约 1–3 秒）。
   - 真 sleep 很少：全仓 ≥100 毫秒的真等待只有 17 处，最大头是 `feishu/test/outbox.test.ts` 的 5 条各等 1.5 秒（共 7.5 秒）和 `test-slots` 的跨进程用例（原 13.6 秒，已改，PR #969）。
3. **同一件事被多层各测一遍**：能确认的有意分层（存储合同在内存版和 Postgres 版各跑一遍、api/db 的 PG 契约）；**复制粘贴式的重复几乎没有**——按「字面量抹掉后函数体相同」扫，全仓只有 6 个文件有 2 条以上相同的用例，没有一个在用例数最多的前 10 个里（第五节）。参数化收表能省的行数很少。
4. **最大的一笔账（要方案、我没动）**：引擎里 Fusion 时代的整条「会话端口」（`real/sessions.ts` 装配的 `startSession` / `awaitSession`，包括 `session-launch`、`session-watch`、`session-prepare`、`session-reattach`、`session-output` 等）**已经没有生产调用方**——`EnginePorts`（`engine/src/ports.ts`）里没有这两个端口了，`real/index.ts` 只从 `createSessionPorts` 取走 `reapOrphanSessions`、`orgSwitch`、`drainStop`、`releaseDetached` 四样。测它们的 7 个测试文件在 CI 里合计 116.9 秒，占全部测试文件耗时的 15%（第六节）。能不能删、删多少，要先弄清那四样对三段新流程是不是还有用，要指挥官出方案、让别家挑错。
5. **「Windows 上红」是 PATH 问题，不是平台缺陷**：从 PowerShell 跑，`user-git`、`github-ports`、`hosts`、`ci-plan`、`agents/test/pre-push`、`sessions*` 整片红，原因都是 PATH 里没有 Git 带的 `sh`（`bash` 找到的是 WSL 的启动器）；从 Git Bash 跑，同一批全绿（第七节）。已改成 vitest 配置里在 Windows 上把 Git 的 `usr\bin` 排到 PATH 最前面（PR #968，已合），**没有加任何平台跳过**，覆盖一条没少。
6. **偶发超时四张单**：根因分两类，修法都不是「把 5 秒调大」；其中 #706（Temporal 放弃那条）我有一个能解释「偶发、只在 CI」的候选根因，本机 8 遍没复现，需要在 CI 上验（第七节）。

## 五、重复和过度

**5.1 参数化（只改一个参数的用例）**：`_tmp/dups.mjs` 把每条用例的体里字符串、数字抹掉后分组。全仓只有 6 个文件有 ≥2 条相同的用例，最多的 `web/src/test/lint-arbitrary.test.ts`（5 条里 3+2）、`agents/test/discuss.test.ts`（4 条，两组各 2 条）、`worker.test.ts`、`issue-groom.test.ts`、`hosts.test.ts`（各 4 条，两组各 2 条）、`engine/test/runner/verdict.test.ts`（4 条完全相同，「结论行带 pass → ok」）。用例数最多的 10 个文件（hosts 94、ci-plan 85、france 71、feishu-routes 65、filter 65、worker 65、discuss 59、session-start 56、issue-new 55、store-ports 54）里，没有一个有 ≥3 条相同的。`issue-new.test.ts` 已经用了 7 处 `.each`。**结论：收成表驱动能省的行数不到 100，不做。**

**5.2 有意的分层（不动）**：存储合同（`store/test/store-contract*.ts` 1,623 行）在内存版、Postgres 版各跑一遍，是为了两份实现不分叉；`db/test` 对 Postgres 查询、`api`/`engine` 里按真库的测试各验各的层。错误码（`HYGIENE_BLOCKED`、`MERGE_CONFLICT`、`WORKTREE_DIVERGED` 等）在 github 包、引擎端口、失败分流各有测试（共 77 处、20 个文件），是每层各自的映射，不是同一条断言抄了几遍。

**5.3 被删代码留下的测试**：和 `代码臃肿审查.md` 第三节对照，**已经删的（S1 #911、S2 #913、S3 #916）不重复**。我另做了两个扫描：
- 文件级（`_tmp/orphans.mjs`：产品文件没有任何非测试文件引用、但有测试引用）：只剩 4 个，都不是死代码——`cold-verify-post.ts`（87 行，v3 流程没接上，代码臃肿审查已列）、三个 `bin/` 入口（被 pnpm 脚本和钩子调用，扫描看不到）。
- 导出级（`_tmp/exports.mjs`：导出的名字只在测试里出现）：58 个名字、41 个文件。新增的（上一份没列）值得看的：`feishu/src/cards.ts` 的 `draftCard`、`draftWaitCard`、`answerCard`、`progressCard`、`pickTaskCard`（全仓只有 `cards.test.ts` 引用，`gateway.ts` 等没调；合计约 250 行产品代码 + 约 120 行测试），`web/src/lib/status.ts` 的 `describeTask` 等 4 个、`web/src/lib/ask.ts` 3 个（上一份说先留的）、`db/queries/subtasks.ts` 的 `insertSubtasks`/`getSubtasks`（只被 db 测试引用，属数据库查询层，先不动）。**这些我没删**：飞书卡片那几张要先确认「意图卡」（`intent-cards`）是不是已经完整接替了它们，涉及旧飞书网关的去留，要指挥官定。

**5.4 最大的一笔：Fusion 会话端口（第一节第 4 条）**。证据：
- `grep` `startSession|awaitSession`（非测试文件）命中 13 个文件，全在 `engine/src/real/` 内部和 `ports.ts` 的注释里；没有任何活动、工作流调用；`EnginePorts` 接口里不再有这两项（`real/index.ts:187-200` 的 `ports` 对象只有 `pickRoute`、`raiseAlert`、`recordTiming`、`saveTaskState`、`authorFamilies`、`createWorktree`、`removeWorktree`、`pushBranch`、`openPr`、`waitCi`、`syncMainline`、`closeIssue`）。
- `sessions-failures.test.ts` 里 `describe('Fusion 的 Lead：…')` 测的是已经删掉的 Fusion 工作流的 Lead 会话，源码注释也写着「Fusion 链路」（`session-launch.ts:1`）。
- 7 个测试文件（`sessions.test.ts`、`sessions-failures.test.ts`、`sessions-cursor.test.ts`、`sessions-grok.test.ts`、`session-detach.test.ts`、`org-switch-sessions.test.ts`、`drain-sessions.test.ts`）+ 夹具 `sessions-rig.ts`，CI 里 26.2 + 28.4 + 22.1 + 14.8 + 13.1 + 6.5 + 5.8 = **116.9 秒（占全部 15%）**，行数约 3,900；对应的产品代码 `real/session-*.ts` 十几个文件约 3,000 行。
- **没删的原因**：`reapOrphanSessions`、`orgSwitch`、`drainStop`、`releaseDetached` 四样还接在引擎里（`real/index.ts:199-205`），它们操作的 `registry`、脱开的收发目录，只有 `startSession` 会往里写——那四样对三段新流程（`segment-spawner.ts`、`task-segment.ts`）是不是已经是空转，我没查清；删之前要先出方案，决定「四样是跟着删、还是改成只认三段流程自己登记的会话」。这是这份报告里最值钱的一刀，也是最大的风险点。

| #706 task-workflow「放弃」超过 60 秒 | CI 上偶发，重跑就绿；日志里 `Cannot close connection while Workers hold a reference to it` | **症状里那句是「果」不是「因」**：它是 afterEach 里 `env.teardown()` 在 worker 还没停时抛的，说明用例已经超时了。**候选根因（我只验到一半）**：这条用例靠「心跳响应把取消送进正在跑的活动」。引擎 worker 没设心跳节流（`createEngineWorker` 没传 `maxHeartbeatThrottleInterval`/`defaultHeartbeatThrottleInterval`），SDK 默认第一次心跳立刻发，之后的心跳最长攒 60 秒才发（`@temporalio/worker` 1.24.0 的 `worker-options.d.ts`：`maxHeartbeatThrottleInterval` 默认 60 秒），而活动的 `heartbeatTimeout` 是 120 秒（`limits.ts:147`）。测试里点「放弃」的信号和活动开始只隔几十毫秒：信号赶在第一次心跳**之前**到，取消随第一次心跳回来（快，常态 1.7 秒）；机器一慢，第一次心跳先发出去、信号后到，取消得等下一次心跳——最长 60 秒，正好等于用例限时。**本机连跑 8 遍都是 1.5–1.9 秒，没复现**，所以这条是推断，没证实 | 试验办法（我没做）：在 `withWorker`（`engine/test/support.ts`）给 worker 传 `maxHeartbeatThrottleInterval: '200ms'`（`createEngineWorker` 要加一个透传的选项），再在测试里让活动先心跳一次、等 500 毫秒再点放弃，改前应能稳定超时、改后稳定 1 秒多。这是改 `engine/src/worker.ts` 的一行 + 测试辅助，要用 CI 连开几轮验 |
| #353 Temporal 用例 60 秒 | 主线、#332、#318 各撞一次，有的卡在 beforeEach 起服务端、有的卡在用例里 | 同 #706 的另一面：`env.teardown()` 先于 worker 停；`useEnv` 每条用例新起一个测试服务端，「上一条留下的工作流会把跳时间锁住」（`engine/test/helpers.ts` 注释）。**没有单点根因的证据** | #706 的验证办法顺带；要有「真卡住时说清卡在哪一步」，可在 `withWorker` 的 `fn` 外包一层自己的限时（比 vitest 的 60 秒短，比如 45 秒）：到点就打 `handle.describe()`、`status` 查询和 worker 状态再抛，失败信息能直接看到卡在哪（#706「怎么算做完」第 3 条要的就是这个） |

**统一办法的结论**：没有一个「全局放宽超时」能同时治这四张单，而且 #718 的补充说明明确说不要全局放。能统一的是两件事：（a）同步子进程一律 `runChild` + `timeout: 0`（子进程自己有上限、卡死会杀）；（b）Temporal 用例在 `withWorker` 层统一加「卡住时的现场」。（a）我已按包推进，（b）要 CI 验证，没做。

### 6.2 「本机 Windows 红、CI 的 Linux 绿」那批

我从 **PowerShell** 和 **Git Bash** 各跑了一遍（同一份代码，2026-10-05）：

| 文件 | PowerShell | Git Bash | 原因 |
|---|---|---|---|
| engine/test/real/user-git.test.ts | 34 红 / 5 过 | 40 全过（134.6 秒） | PATH 里没有 `sh`：`spawn sh ENOENT` |
| engine/test/real/github-ports.test.ts | 21 红 / 9 过 | 30 全过（107.3 秒） | 同上 |
| engine/test/real/hosts.test.ts | 17 红 / 75 过 | — | `sh -c` 起不来 |
| engine/test/real/sessions*.test.ts（4 个文件） | 89 条红（全部 `spawn sh ENOENT`） | 98 条全过 | 同上 |
| conventions/test/ci-plan.test.ts | 15 红 / 70 过 | — | `bash` 解析到 `C:\windows\system32\bash.exe`（WSL 启动器），脚本跑不对 |
| agents/test/pre-push.test.ts | 3 红 / 1 过 | — | 起 `sh` 跑钩子 |
| conventions/test/main-reuse.test.ts | 过 | — | 不需要 sh |

**判断**：全部是「PowerShell 的 PATH 里没有 Git 的 `usr\bin`」，不是 Windows 平台上的真缺陷，也不该加 `skipIf(win32)`——加了这几百条用例在本机就永远不跑，Linux CI 的保险反而成了唯一的保险。修法：`vitest.config.ts` 启动时在 win32 上把同一个 Git 的 `usr\bin`（从 PATH 里的 `git.exe`/`git.cmd` 往上找）排到 PATH 最前面，已经在 Git Bash 里就不动（PR #968，已合；新增 `packages/conventions/src/test-posix-path.ts` 和 6 条测试，含「找不到 sh」「PATH 读不到」两条故意造出的失败）。改后同一批文件从 PowerShell 跑：`ci-plan` 85 过、`github-ports` 30 过、`hosts` 92 过 11 跳（跳的是原有的 win32 跳过）、`pre-push` 4 过。

**原本就有的 `skipIf(process.platform === 'win32')`（共 14 处）逐个看过，都有写明的原因（符号链接、命名管道、被信号杀、root 权限位等），而且各有 Linux 上必须跑的同组用例，不是永远不跑**，不改。

**仍可能在 Windows 上红的**（我没单独验）：被 `onPosix` 变量包住的几个文件（`shell.test.ts`、`scope.test.ts`、`detached.test.ts`、`claude-run.test.ts`、`mirasim-bridge.test.ts`、`session-detach.test.ts`、`session-io.test.ts`、`hosts.test.ts` 的一半）用例内部自己判平台，不是整文件跳过，用例名里能看到。
