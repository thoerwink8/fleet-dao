# 代码层臃肿审查（母单 #901，第一阶段只读）

> 2026-10-05，Sonnet 5.5 子代理，基于 `origin/main` `f07ddb03`。创始人 2026-10-05 原话：「仔细审查整个项目，项目臃肿…需要优化重构各个模块和流程」。
> 方法：`git ls-files` 全量、`pnpm dlx knip`（只用来对照，不装进仓）、手写的 import 图 / 导出引用扫描（`_tmp/*.mjs`，没进仓）、逐项 grep 核对。
> 「没人用」的判法：非测试代码里没有任何 import / 同名引用；「只被测试引用」单列，不算确凿死代码（有的是还没接上的新流程）。

## 一、结论（先说要紧的）

1. **这个仓的臃肿主要是「体量」不是「死代码」**：Fusion、认领账、帅位座位、飞书旧网关的主体在 #531、#556 等几轮里已经删得很干净（引擎里没有 `workflows/fusion.ts`，库里没有 `issue_claims`、`seat_leases`）。能确凿删掉的死代码只有几百行；真正的大头（单文件过千行、两份 Store 实现、测试比源码还多）要靠拆分和「需要方案」的重构，不是删几个文件。
2. **顺带发现一处疑似断链（不是臃肿，但比臃肿要紧）**：驾驶舱后端发信号还在用旧的需求工作流编号 `req:<仓>#<号>`，而引擎现在跑的是 `task:<仓>#<号>`、信号名也换成了 `taskContinue / taskAbandon / taskRouteWake`。证据见第九节。建议指挥官单开一张「按 chain-first 查」的单，这不在本单范围内，我没动。
3. 依赖层面能确凿去掉的很少：`packages/web` 的 `elkjs`、`@xyflow/react` 在源码里一处 import 都没有，但创始人刚说要把首页流程图（react-flow）恢复、别家正在做，所以我**没删**，等他们定。

## 九、顺带发现：驾驶舱后端的信号还指向已经没有的 `req:` 工作流

- `packages/api/src/temporal.ts:40-53`：`requirementWorkflowIdForTask` 把任务拼成 `requirementWorkflowId(repo, issueNumber)`，即 `req:<owner>/<name>#<号>`（`packages/shared/src/workflow-ids.ts:40`）。
- `packages/api/src/cockpit.ts:98-101`（`signalAndAudit`）、`answer-ask.ts:18`、`agent.ts:185-201`（`fleet` 命令的 `ask/done/blocked` 叫醒）都用这个编号发信号。
- 引擎里跑的工作流是 `task:<owner>/<name>#<号>`（`packages/shared/src/workflow-ids.ts:30-32`，`TASK_WORKFLOW_TYPE`），监听的信号是 `taskContinue`、`taskAbandon`、`taskRouteWake`（`packages/engine/src/task-contract.ts:98-100`，`workflows/task-runtime.ts:79-85`）。引擎里没有 `workflows/requirement.ts`、`fusion.ts`。
- 后果（按代码推断、**我没有在真环境里验**）：驾驶舱上的「继续 / 停止 / 回答」和 `fleet ask` 叫醒，发的是一个已经不存在的工作流编号，后端会回 409 `workflow_gone`（`cockpit.ts:113`）。`packages/store/src/pg-store.ts:721` 和 `memory-store.ts:673` 已经改用 `taskWorkflowId`，说明读的一侧改过、发信号这一侧漏了。
- 建议：开一张「驾驶舱发信号改发 `task:`、信号名对上」的单，先用 `chain-first` 在一个假 Temporal 上造出这个失败再修。
