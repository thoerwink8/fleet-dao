## 一、提出的问题

### 1. 全貌：这个仓的单和 PR 现在是什么样

- **现象**（实测，`report.txt` 段 a–i）：
  - 5 周里开了 1503 张单、2231 个 PR；PR 合并 2107 个，不合并就关 108 个。每周开单 148 / 167 / 386 / 720 / 77，第 4 周的高峰主要是自动开的单（见问题 2）。
  - 单越来越小、关得越来越快：开到关的中位数从第一期的 55 小时降到最近一期的 0.5 小时；PR 开到合并全期中位 0.08 小时。
  - 单的结局：完成 1120、不做 334、重复 8、还开着 41（开着的年龄中位 10.8 天，最久 35 天，例：#34、#3140）。
  - 开单人：创始人账号 1211 张（其中带「本机做」602），`github-actions` 261，引擎机器人 31。**创始人本人和本机 AI 会话共用同一个账号**，单从账号上分不出是人开的还是 AI 开的。
  - 流程大改过六次：合并闸和 P0–P6 里程碑起步 → 09-28 起认领和提醒 → 10-03 起砍规矩 → 10-07 起版本制和「交给引擎」 → 10-15 起「一个队列两种执行者」 → 10-23 起时机表。
- **根因**：流程是在快速增长中一次次打补丁长出来的，每次只解决眼前的事，没有一份「哪类信息记在哪」的总设计。
- **判断**：方向上是好的（单变小、合得快）；问题集中在噪音、重复、多条路做同一件事、身份不分，见下面几条。

### 2. 噪音单和重复单

- **现象**（实测）：
  - 10-16 一天开了 385 张单，其中 `github-actions` 开的「e2e 偶发:」单 250 张，全部按不做关掉，中位存活 12 分钟（例：#3433、#3069、#3064）。机器人开的单一共 292 张，259 张不做就关。
  - 标题高度相似（相似度 ≥ 0.7）的有 58 组，涉及 180 张，占 12%。例：「机器人开的 PR 没经合并队列合」重复 9 次（#428、#440、#1418）；「GitHub 对账没过」5 次（#2695、#3030、#3237）；「本机退回的单，引擎接不了」4 张（#3566、#3567、#3573）。真正标成重复关掉的只有 8 张。
- **根因**：开单有好几个入口（本机命令、工作流、引擎、对账），没有一个统一的地方在开单前查重；自动检测把「一次观测」直接变成了「一张要人处理的单」。
- **做法**：所有开单走同一个开单服务，开之前查同题开着的单，命中就在那张下面加一条记录、不新开；自动检测的观测只进事件账本，同一个检测连续命中才升级成一张单。
- **不做什么**：不做语义去重的模型训练，先用标题相似度加关键字。

### 3. 进度单变成流水账

- **现象**（实测）：#1055「进度与创始人引导」累计 1789 条评论，约每天 70 条；第二多的单只有 34 条。「创始人引导」单 15 张，大多 0 到 1 条评论，实际在用的是 `directive/` 分支的 PR（60 个）。
- **根因**：用一张单的评论去承载「进度流水」，GitHub 单不是为这个设计的，人和 AI 都翻不动。
- **做法**：进度从事件账本生成，在驾驶舱里看；#1055 关掉，只保留链接指向驾驶舱；创始人引导照现在的规矩落文件或决定，不再挂进度单。
- **不做什么**：不迁移 #1055 的历史评论，它就留在那里当档案。

### 4. 同一件事有好几条路，关单、开 PR、派单都不唯一

- **现象**（按代码）：
  - 关单 5 条路：PR 的 `Closes` 关键字、`close-on-merge.yml`、`pnpm issue:close`、`pnpm work done`、引擎 `taskCloseClosedIssue`。
  - 开 PR 3 条路：`pnpm pr:open`、引擎 `openPr` 活动、`work run` 工人。
  - 派单 3 条路：引擎每 5 分钟拉单（`packages/engine/src/jobs/intake.ts:160`）、`fleet-api dispatch-issue` 点名、本机 `work claim/run`（`packages/conventions/src/work.ts:206`）。
  - 结果（实测）：只有 39% 的单是被合并 PR 的 `Closes` 关掉的；创始人账号手关了 1129 张，引擎手关了 319 张；20% 的 PR 没提任何单号（447 个，例：#3722、#3721、#3717）。
- **根因**：每加一种执行方式（本机、法国、无头工人）就加一条自己的路，没有收成一条。
- **做法**：派单只经事件账本一条路（谁干、在哪干都是账本里的字段）；开 PR 只经工人适配器的一个接口；关单只有一条路：PR 合并按 `Closes` 自动关，没有 PR 的活用一个命令关、必须带证据。
- **不做什么**：不追溯修正历史上手关的单。

### 5. 三个入口怎么联动（需求方的核心问题）

- **现象**（按代码）：
  - 本机开单走 `pnpm issue:new` 直连 GitHub；开给法国的单开完再经 ssh 戳法国 `fleet-api dispatch-issue` 立刻派，戳不成只提示一句，靠 5 分钟后的拉单兜底（`packages/conventions/src/issue-poke.ts:1-5`）。
  - GitHub 到法国：webhook 叫醒（`packages/api/src/github.ts:90-118`）加三层轮询对账（5 分钟、15 分钟、每小时）。
  - 法国到人：通知写库，飞书每 30 秒推一轮，只推团队群，不推创始人个人（`packages/api/src/feishu-push.ts:1-20`）。
  - 本机认领写法国 `tasks` 表，租约 2 小时（`packages/db/src/queries/local-claims.ts:190`）；法国续的租约本机看不到，本机靠工作树和 PR 猜（`packages/conventions/src/work-queue.ts` 头注释）。
  - 本机和法国有两套 ssh 名字：fleet-dao 用 `fleet-fr-wg`，Mirasim 的 `remote-hosts.json` 用 `fleet-fr-session`。
  - 新的 harness 还不存在，指挥官主动开单和聊天开单目前没有对应机制。
- **根因**：GitHub 是唯一的汇合点，三地都各自直连 GitHub，再靠轮询互相发现，中间没有一个「谁在干什么」的共享账本。
- **需求方的思路**：指挥官能在 harness 上主动开单；在 harness 里聊天就能联动开单；本机 Mirasim 发的指令也能联动到 GitHub 和法国 harness。
- **判断**：成立。关键是在三地中间加一个法国上的「工作账本 + 开单服务」，三个入口都调它，由它去写 GitHub；GitHub 只记要交付、要验收的东西。设计见第五节第 4 条和下面的总设计。
- **做法**（总设计，推断，待第六节第 1 批验证）：

  **每类信息的唯一记录**

  | 信息 | 唯一记录 | 别处怎么看 |
  |---|---|---|
  | 要做什么、怎么算做完 | GitHub 单（一单一个可验收目标） | 账本、驾驶舱只引用单号 |
  | 正在怎么做：拆成哪些节点、哪个工人、哪个会话、到哪了、花了多少额度 | 法国的事件账本 | 驾驶舱波次图；不给节点开单 |
  | 一块能合并的改动 | PR，必须挂单 | 账本记 PR 号 |
  | 要创始人拍的事 | 驾驶舱的决策卡 | 拍完写回单的评论存档 |
  | 创始人的原话 | 驾驶舱库（私有） | 单和 PR 里只写结论 |
  | 进度 | 由账本生成 | 不再写进度单 |

  **一个开单服务，三个入口都调它**

  法国上提供一组工具，同时以 MCP 和 HTTP 接口暴露：开单（带查重、补标签、写来源）、领活、交给法国做、记一条观测、提决策卡。

  - **入口一：法国 harness 上的指挥官主动开单。** 指挥官会话里注入这组工具。规矩：只有「要合 PR」「要跨会话」「要创始人验收」的事才开单；拆出来的节点只进账本。开出的单正文末尾带来源标记（指挥官会话号）。
  - **入口二：创始人在 harness 里聊天。** 指挥官照现有的分拣规矩判断（照做、讨论稿、记成规矩）；判成照做就调开单工具，回执第一行带单号；聊天原话存驾驶舱库，单里写结论和来源（聊天消息号）。
  - **入口三：创始人在本机 Mirasim 下指令。** 本机会话装同一组工具（远程连法国的 MCP 服务，走现有的 WG 通道加令牌），所以本机说「开单」「交给法国做」和在法国说是同一个动作：开单服务写 GitHub、写账本，「交给法国做」直接让法国 harness 起指挥官会话，不再 ssh 戳、不再等 5 分钟。本机自己做的活也在账本里领，取代本机租约文件，法国和本机看到的是同一份。
  - **回到人**：完成、卡住、要拍板，都推到创始人个人（驾驶舱网页推送或飞书个人消息），不再只进团队群。

- **不做什么**：不让 Mirasim 直接改 GitHub 以外的法国状态；不做第二套开单命令（`pnpm issue:new` 改成调开单服务，参数保持兼容）。

## 二、另外查出来的

### 身份不分
- **现象**（实测）：创始人本人和本机 AI 会话都用 `thoerwink8`；1742 个 PR 是这个账号开的，只能靠「本机做」标签和 `local/` 分支近似区分。
- **做法**：AI 一律用 GitHub App 身份开单、开 PR、评论；创始人账号只留给人。来源标记写进正文末尾。

### 引擎机器人 PR 成功率低
- **现象**（实测）：机器人开的 467 个 PR 里 74 个没合就关（16%），例：#3640、#3586、#3520；创始人账号只有 31 个。机器人 PR 开到合并的 P90 是 4.72 小时，本机分支是 0.35 小时。
- **做法**：不在本稿解决；归到 harness 的工人核查和完成闸设计里。

### 返工和撤回
- **现象**（实测）：46 个 PR 标题就是在修刚合并的 PR（例：#103 修 #85，#436 修 #433 合并后的主线红）；14 个 PR 撤回，大多在撤刚定的规矩（例：#542、#2804、#3645）。
- **做法**：规矩类改动先走讨论稿（已是现行规矩），本稿不加新护栏。

### 标签大半闲置
- **现象**（实测）：「冻结」「卡住了」「等你拍」「过时」从没用过；「交给引擎」只用了 3 次、「人闸」5 次；1425 个 PR 没有标签，553 张单没有里程碑。
- **做法**：「本机做」「交给引擎」这类执行状态挪进账本字段；标签只留查询用的类别、域、性质。

### 文档和代码对不上（按代码）
- PR 模板：`README.md:136` 说四栏，`.github/pull_request_template.md:1` 说两栏，实际两栏。
- `debt.yml`：`README.md:62` 说主线推送也跑，`.github/workflows/debt.yml:10-13` 只有定时和手动。
- `pnpm progress`：`README.md:54` 列了 claim、done，`packages/conventions/src/bin/progress.ts` 里没有（#2727 已删）。
- `pnpm check`：`README.md:57` 说四样，`packages/conventions/src/bin/check.ts:61-63` 是五样。
- `pnpm work` 的 return、feedback、ack、resolve、deliver：`README.md:71` 列了，`packages/conventions/src/work.ts:72-74` 的用法文案没列。
- 「人闸」标签：文档说改标准的 PR 会自动贴，`packages/conventions/src/labels.ts` 没有这个标签。
- **做法**：这些随新流程一起改掉，不单独修（新流程会删掉其中大部分命令）。

## 五、要拍板的

1. **单的粒度**：建议一单一个可验收的目标，拆出来的节点只进账本；备选是每个节点也开一张子单（GitHub 上看得全，但会回到今天的单量和噪音）；不定的话指挥官会按习惯每步开单。
2. **进度单 #1055**：建议关掉，进度改在驾驶舱看；备选是保留但只贴每天一条摘要；不定的话它会继续每天涨 70 条。
3. **AI 的 GitHub 身份**：建议 AI 一律用 GitHub App 身份，创始人账号只给人；备选是继续共用账号、靠正文标记区分；不定的话统计和审计继续靠猜。
4. **本机 Mirasim 怎么连到法国**：建议本机会话装法国的同一组 MCP 工具，走现有 WG 通道加令牌；备选 A 是本机只用 pnpm 命令调法国的 HTTP 接口（不进会话工具），备选 B 是用 Mirasim 的远程主机功能直接在法国开会话；不定的话本机继续直连 GitHub 加 ssh 戳。
5. **自动检测的观测**：建议只进账本，同一个检测连续命中 3 次才开单；备选是每周聚合成一张单；不定的话每天还会有几十张开了就关的单。
6. **通知到人**：建议完成、卡住、要拍板推到创始人个人（驾驶舱网页推送为主，飞书个人消息为辅）；备选是继续只推团队群。
7. **先后**：建议先做开单服务加事件账本，再接指挥官和驾驶舱；备选是三块一起做。

## 七、没核实的

- **Mirasim 能不能连法国的 MCP 服务**：要在本机实测一次远程 MCP 连接；影响第五节第 4 条。
- **webhook 线上配没配**：`FLEET_GITHUB_WEBHOOK_SECRET` 是否已在法国配好没读到，要上法国只读查一次；影响「交给法国做」能不能不靠轮询。
- **GitHub App 的权限**：现有 App 能不能开单、开 PR、评论、关单，要在测试仓验；影响第五节第 3 条。
- **噪音单的阈值**：「连续命中 3 次」是拍脑袋的数，要用 e2e 偶发的历史数据算一下；影响第五节第 5 条。
- **别家挑错没讨论成**：2026-10-31 用 discuss 问了 GPT、Kimi、GLM 共 3 次，全部在 30 秒上限内没答完（这台机器上 Cursor 命令行回一个字就要约 20 秒），见 #3737。拍板前要么修好 #3737 再问，要么创始人决定不等挑错直接拍。
- **统计口径**：挂单率只认正文和标题里的 `#号`，没读提交信息和 PR 评论；返工只按标题算；时间线是 120 张抽样。
