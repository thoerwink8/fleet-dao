# PR 正文

法国库里已有的 verify 顺序会被用上。

发布脚本 deploy/release.sh 的 load_routing 只调 applyRoutingDefault，按用途只补缺。routing_purpose_models 里已经有 purpose='verify' 的行时，这个用途进 purposesKept，不插入、不改顺序。本版起验收按 shared 的 SEGMENT_STAGE.verify 选路，这个值等于页面上叫「验收」的那一格，就是 verify。所以库里原有的 verify 顺序从这一版起被验收用上。一行都没有时，第一次发布按 packages/db/routing.default.json 的 purposes.verify 补上，第一名是 gpt-5.6-luna，后面是 grok-4.7、sonnet-5.5、opus-5.5、kimi-k3、deepseek-flash、cursor-auto、glm-5.3-flash。review 的行不覆盖，验收不再读它。

怎么核：在法国以操作系统用户 fleet 连库 fleet，执行

select model_id, position from routing_purpose_models where purpose = 'verify' order by position;

发布日志里 formatRoutingApplyReport 的原文：已有则是「路由两层已齐，这次一行没改」；缺了才是「补了用途 → 模型 … verify」。

这次没有读到行，不能报库里的模型顺序。当前进程是 uid 993、用户 fleet-agent-carpool：peer 认证报角色 fleet-agent-carpool 不存在；psql -U fleet 被 peer 拒绝；sudo -n 因 no new privileges 不能换用户；TCP 127.0.0.1:5432 拒绝连接；10.99.0.2:8787 连不上；https://hangdao.dpdns.org/api/routing/layers 返回 401。
