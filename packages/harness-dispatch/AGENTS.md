# packages/harness-dispatch：新内核的派工层

决定 0124 的新内核（母单 #3770，第 3 片 #3775）里把指挥官的 `spawn_worker` 变成跑着的工人、再机械核验交回的那一层。收请求读 `harness-api` 写的事件，排活和领活用 `harness-store` 的调度器，起工人用 `harness-workers`，所有子进程只经 `harness-runner` 的 `runProcess`（`src/command.ts` 的 `runCommand` 是它上面的薄壳）。不依赖旧包。

## 不变量

- 收请求（`intake.ts`）从 `fleet2.projection_checkpoints` 的检查点往后分页读 `worker.spawn.requested`，读页、排活、推检查点在同一个事务里；活的键 `spawn:<事件号>`，同一会话同一 `taskId` 再来也只算一次（命令回执），检查点丢了重读、并发收两遍都不会出第二个工人。队列 `worker` 必须先 `init()` 登记限速，默认同时 1 个。
- 活的截止时刻含排队时间（默认 12 小时）；工人的绝对截止时刻 = 活的截止时刻减核验留的时间，预算比剩下的长就按 `BudgetTooLongError` 终局，不默默截短（A4）。
- 工人令牌每个工人现发（角色 `worker`，会话号 `worker-<runId>`，不写指挥官的流），工人一退出就撤销，核验时已经是撤销的。令牌只进工人的 MCP 配置文件，不进命令行。
- 租约靠 `heartbeat` 续：回 `cancelled` 叫停工人（原因种类 `user-stop`，写进 `killed.detail`）；回 `lost` 也叫停，且不写交回（活已经是别人的）；库连不上超过一个租约时长按 `lost` 算。指挥官的 `worker.stop.requested` 经 `intakeStopRequests` 取消对应的活。
- 交回先机械核验再记账，不让模型判（`verify.ts`）：`git diff --numstat` 对基线（含未跟踪文件）、越界路径（`allowedPaths` / `forbiddenPaths`，不许做里 `路径：xxx` 行也算禁止）、检查命令退出码。四态 `unverified | passed | failed | unknown`：工人没干净交活或越界或检查失败是 `failed`；有探测没跑成是 `unknown`，永远不当 `passed`；没改动、或既没范围又没检查命令是 `unverified`。核验在工人的工作目录里跑，那里的 git 配置和检查命令都是工人写的，所以走无凭据的工人环境、关掉 `core.fsmonitor`、diff 不跑外部程序。
- 每次尝试结束记一条 `handback.recorded` 进指挥官的流 `session:<号>`（`runId`、`attempt`、`final`、`outcome`、`verdict`、`reasons`、证据：工人退出码/叫停原因/停在哪一步、diff 统计、越界路径、检查退出码和输出末尾、工人自己交的话），整条递归过脱敏器（H1），再 `completeJob`。工人自己交的话只当参考，不参与判定。
- 只有确定没副作用的失败才退避重试（`retryJob`）：进程没起来、起步无进展、影子自检没过、工作环境没建成；记一条 `final: false` 的交回。别的（超时、被叫停、退出码非 0）记终局交回就停。
- 发版停机不是终局（#3776）：`stop()` 对在跑的工人发 `StopReason('release-pause')`，被它叫停的活经 `releaseJob` 退回队列（马上可领，`max_attempts` 跟着加一，等于不消耗尝试次数；attempts 不回退，下一次领取是新的 `runId`），记一条 `final: false, willRetry: true, outcome: released` 的交回，不核验、不 `collect`（不写 `shadow_runs`），影子目录照常 cleanup。选“叫停＋退回”不选“排空等工人跑完”：工人一跑十几分钟，超过 systemd 的 `TimeoutStopSec`，发版等不起。user-stop、看门狗、超时、租约丢失的判法不变。
- 调度器直接收成 `dead` 的活（排队时过了截止、领到 `max_attempts` 的毒活）不经 `processJob`：领活时经 `claimJobs` 的 `onDead` 在同一个事务里记终局交回（`outcome: dead`、`verdict: unknown`、原因取 `lastError`），收件箱不少一件；记不进去整次领取回滚。
- 崩溃后重领不盲重派：重领时若已有终局交回，只补 `completeJob`；若上一次的 `worker:<runId>` 流有 `worker.spawned` 却没有对应交回，说明派工器在中途死了、工人做到哪不知道，记 `unknown` 的终局交回就停。
- 影子自检的真实探测（`shadow-probes.ts`，接 `harness-workers` 的 `ShadowProbes`）：影子工人和会话用户同一个用户，家目录里的推送凭据（`.git-credentials`、`gh` 的 `hosts.yml`、`.netrc`、`.ssh/id_*`）和全局 git 凭据助手工人都拿得到，有一样就没过。这一项是一段 sh 脚本，退出码 0 干净、10 有凭据、别的没查成，不打印文件内容；有 sandbox（法国，内核用户 `fleet` 进不去会话用户 750 的家，#3776）经 `WorkerSandbox.runAsWorker` 以会话用户在 `fleet2-shadow` slice 里跑（`fleet-agent-scope run fleet2-probe-<随机> --slice fleet2-shadow --user … --cwd /tmp`），没 sandbox（本机、测试）同一段脚本直接跑。不看会话用户家的命令（`systemctl is-active`）cwd 是 `/`，不用工人的家。出网规则看 `fleet2-shadow-firewall.service` 在跑且出网关的口连得上；outbox 装了任何真实处理器就没过。查不了一律 `unknown`。
- 影子派工（#3808）：`shadow-driver.ts` 给冻结批次里没派过的单往 `shadow-<批次>` 会话流写派工请求，带 `shadow`（批次、仓、单号、基线）；回执和请求在同一个事务里写，同一张单只出一条。指挥官的 `spawn_worker` 入参只有六项，带不进 `shadow`。`shadow-workspace.ts` 从本机裸镜像 `<镜像根>/<仓>.git` 在空仓里 `fetch` 基线提交（`--upload-pack` 带 `uploadpack.allowAnySHA1InWant=true`）再 `checkout --detach FETCH_HEAD` 建到基线（自带完整 .git：工人以会话用户跑时写不了镜像，#3814；不用 `--shared`、没有 alternates、没有 origin，工作目录里只有基线及以前的历史、看不到基线之后的提交，#3776 法国现场工人 `git log HEAD..origin/main -S` 找到答案搬走），没带 `shadow` 的请求不建；镜像不在就从 GitHub 匿名 https 建（先建到临时名再改名）、缺基线提交就拉各分支，不带令牌所以只认公开仓（#3811）；给了 sandbox 就把建好的目录交给会话用户，cleanup 按回执删。终局交回记完后经 `Workspace.collect` 抓补丁写 `shadow_runs`：索引拷一份到内核自己的临时目录（`GIT_INDEX_FILE`），对象库也换成那里的（`GIT_OBJECT_DIRECTORY`；`add -N` 也写空 blob），工人自己的对象库只当备用库读，不往工人的 .git 里写任何东西。补丁只存库里，不建分支、不推。内核以 fleet 读会话用户的目录，核验和抓补丁的 git 都带 `safe.directory=*`。
- 新内核进程（#3811，`kernel.ts`，入口 `src/bin/kernel.ts`）：一个进程里起接口层（只听回环、影子模式）和派工器，按节拍对还没收完的批次跑影子驱动、领活、`sweepCompare` 评分、`shadowSilence` 静默报警（打 `{"alert":"shadow-silent",…}`）；每一步出错只记错，不挡别的步、不退出。outbox 一个真实处理器都不装（纯影子；开了真执行只装 `git.push`、`github.pr.open`，见下条）。读 GitHub 只经 `github-read.ts`：只发 GET 和 GraphQL 查询；令牌由 `github-app.ts` 用旧引擎同一个 GitHub App 的凭据文件（env `FLEET2_GITHUB_APP_FILE`，json 里的 `id`、`pem`）按仓现换：签 RS256 JWT → 查仓的安装 → 换只带 issues/pull_requests/contents/metadata 只读权限、只含本仓的短期令牌，按仓缓存、到期前 5 分钟换新；换失败直接抛错。没有长期令牌这条路。令牌只在内核进程里。配置全从环境变量来，见入口文件开头；法国上 `FLEET2_SANDBOX=scope`（`scope-sandbox.ts`：经 `sudo -n fleet-agent-scope` 的 adopt / remove / stop，协议照抄旧 `adapters/src/tree-cleanup.ts`，每次先问能力、删时带 adopt 回执的身份）、执行体前缀 `deploy/france/fleet2-worker.sh`（经 `fleet-agent-scope run fleet2-<编号> --slice fleet2-shadow` 以会话用户起 reclaude）。
- 真执行（#3783，第 7 片，`FLEET2_PUBLISH=1`）：影子之后的一步，对**人用 `bin/real.ts freeze` 冻结的真执行批次**（`fleet2.real_batch_items`，和影子批次分开存，影子驱动、波次图不认它）真推分支、真开 PR，**不合并**。一条线：`real-driver.ts` 的 `enqueueRealBatch` 先在旧库认领这张单（`task-claim.ts` 的 `acquireTask`：没有行就插、只有 `queued` 且归引擎的行才改成 `owner = harness`，旧系统手上有的回 `held`、这一轮不派也不记回执，下一轮再看），拿到当时的 `tasks.fencing`，请求写进 `real-<批次>` 会话流，带 `real`（批次、仓、单号、基线、令牌、PR 标题，指挥官的 `spawn_worker` 带不进）；工人的建法、隔离、核验和影子完全一样（`shadow-workspace.ts` 同一套，带 `real` 且内核给了 `publish` 才认，否则 `NotShadowRequestError`）；终局交回后抓补丁交给 `publish.ts` 的 `recordPublish`：补丁、令牌、模型、核验存 `fleet2.publish_runs`，只有「有改动、结局 completed、核验 passed 或 unverified」才同一事务里排 `git.push`，别的记 `held`/`empty` 不推；`processOutbox` 领到期的动作，**执行前先核旧库令牌**（`checkFencing`，对不上进 dead；读不到按没做成退避，不当成对得上）。每个动作先看外面已有什么再动手：`git.push` 在内核自己建的临时目录里从本机镜像取基线、`git apply`、定死作者和时刻提交（同样的基线加补丁永远得到同一个提交号），GitHub 上分支已在且内容一样就补记不再推，内容不一样（别人占了名字）进 dead 不覆盖，推完查证再排 `github.pr.open`；`github.pr.open` 先找以这个分支为头的 PR（开着或已合的认下、被人关了的进 dead 不开第二个），再找这张单有没有别的开着的 PR（有就进 dead），开完读回来核头提交。响应丢了（超时、5xx、限流）记 `unknown`，下一次领到仍是先查再动，到 `maxAttempts` 进 dead。推送的认证头只放那一条 git 命令的环境变量（`GIT_CONFIG_*`，`command.ts` 的 `trustedEnv`），不进命令行、输出过脱敏器，别的 git 命令没有；家目录指到临时目录，读不到宿主的全局配置。写令牌是另一枚（`PUBLISH_PERMISSIONS`：contents 和 pull_requests 的写、metadata 读，只含本仓），只给发布那一步；`github-write.ts` 只有查分支、查 PR、开 PR、改名分支、关 PR，**没有合并**（`test/github-write.test.ts` 扫源码守着）。自检的「真实处理器」一项改成「只许装 `git.push`、`github.pr.open`」（`allowedHandlers`），合并、评论装了就没过；工人的隔离（无凭据、出网受限）不变，出网关名单不放 GitHub。
- 按状态切回（`switch-back.ts`，`bin/real.ts release`）：`specs/3770-harness-rewrite/讨论稿.md` 里的切回表每一行一个分支，先从库里的事实判单走到哪一行（`taskStage`：旧库令牌、派工请求和活、工人流、产物、外部动作、GitHub 上分支和 PR），再动：没开始撤活放回；开始了没外部动作先叫停、等工人流收尾再放；有本地提交没推撤掉还没做的推送（补丁本来就在 `publish_runs`）；推了没开 PR 分支改名 `fleet2-abandoned/…` 留着；开了 PR 要人选 `handoff`（PR 留着、单放回成 stopped 交旧引擎接管）或 `close`（关掉重派），不开第二个；检查在跑（`commitStatus` 是 pending）、外部动作结果未知、工人还没收尾都回 `wait`；已合并回 `none`（走 revert PR）；补偿失败回 `alarm`、所有权不放。所有权最后才放（`releaseTask`，令牌对得上才改），每步幂等，重复调从头判。每次结果记一条 `task.released` 进 `issue:` 流。
- 冻结影子批次（#3776，`shadow-freeze.ts`，入口 `bin/shadow.ts freeze <批次号> [--allow-closed] <owner/仓#单号>…`）：读齐再写，每张单只读 GitHub 确认在、不是 PR、开着（`--allow-closed` 放行已合并旧单的对照批），基线取主线现在的提交，整批经 `freezeBatch` 一次写进 `fleet2.shadow_batch_items`；任何一张不合格整批不冻，冻结后不改。只写 fleet2 影子库，旧生产表和 GitHub 只读；取代手插表。
- 场景脚本（#3775，`scenarios.ts`、入口 `src/bin/scenarios.ts`）：法国真机上把成功、超时、被杀、退回、重复提交、限流各跑一次、按会话号查整条事件链打成表。影子模式下 MCP 不注册 `spawn_worker`，所以脚本以指挥官身份直接写和它一样的 `worker.spawn.requested`（加影子目标，工作目录只会从它建）；每个场景一个只含一张假单的批次，并预先写好影子驱动的回执让驱动不替它读 GitHub 再派，跑完 `cleanupScenario` 删批次、影子产物、回执、已收尾的活，事件留作证据。短截止靠请求和活同一事务里排好（请求里没有截止字段）。限流在专用队列上自己领，不碰 `worker` 队列。重启接回只排一件 sleep 300 的活，重启 `fleet2-kernel` 由人手动做一次，脚本不碰系统服务；断网造不出（见 `MANUAL_SCENARIOS`）。
- 提示词（`prompt.ts`）：指示类字段在块外，`context` 只出现在带随机标记的资料块里，块尾标记伪造不了（SEC1）。

## 没做的

- 重启后上一代遗留的工人进程由 `harness-runner` 的孤儿清扫处理，这里不管。
- 工作环境怎么建（克隆、worktree、基线）由部署传进来的 `prepareWorkspace` 决定；`.gitignore` 掉的文件和仓外写入看不到，范围外写要靠影子用户的文件权限兜。
