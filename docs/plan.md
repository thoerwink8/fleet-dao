## 一、总思路

1. **先把一条真任务从头到尾跑通，再往宽里铺。** 第一个里程碑不是「模块齐了」，而是「一张 issue 进来，Opus 5.5 在法国 VPS 上无头干完，PR 合并，issue 关掉，驾驶舱看得到每一步耗时」。
2. **边造边用自己**：引擎能干活之后（P1 结束），剩下的活都开成 fleet-dao 自己的需求，让它自己造自己；我当总指挥和终审。
3. **每个阶段有一条端到端验收**，自动化、能反复跑，过了才进下一阶段。验收脚本本身就是以后的巡检任务。
4. **构建期全程 Opus 5.5**（创始人拍板；判断阶段例外，见 design 第三节第 8 条）；各家渠道的插头照做，最后各跑一条小任务验收。

## 二、技术选型（我来定，理由写明）

| 块 | 选型 | 理由 |
|---|---|---|
| 语言 | TypeScript，Node 22（VPS 已有 22.23） | 旧代码是 JS，类型能挡住一大类错；各家模型写 TS 最稳 |
| 仓结构 | pnpm 多包仓 | 引擎、驾驶舱、命令行、飞书网关共用类型和数据结构 |
| 工作流 | Temporal 服务端（Postgres 做持久化）+ TypeScript SDK | 断电续跑、重试、信号、定时都现成；旧系统用的单文件开发版已自动重启过 15 次，不再用 |
| 数据库 | PostgreSQL 17 + Drizzle（表结构即代码、迁移自动生成） | 见设计文档「为什么用 Postgres」 |
| 驾驶舱后端 | Hono + zod + SSE（实时推送走 Postgres 的 LISTEN/NOTIFY） | 轻、快、类型全；实时不需要另装中间件 |
| 驾驶舱前端 | Vite + React 19 + React Router v8（纯前端单页模式）+ Tailwind + shadcn/ui + React Flow + ELK + cmdk（⌘K） | React Router v8（2026-06-17 发布）每年一个大版本、升级几乎无破坏，路由类型安全，各家 AI 最熟；画布、思维导图排版、命令面板都有成熟零件；主题色用 CSS 变量，多套可切 |
| 飞书网关 | 官方 Node SDK，长连接收事件和卡片回调 | 不用对外暴露回调地址；香港到飞书 0.17 秒 |

| 测试 | vitest（单元）+ 端到端脚本（真跑一条任务） | 单元测试秒级；端到端就是巡检任务 |
| 备份 | 每晚法国 → 香港（加密），保留 7 天 + 4 周 | 不需要再开一个要绑卡的云存储；香港磁盘还空 26G |
| 看门狗 | Cloudflare 定时 Worker（免费，不用绑卡） | 两台都挂了也能报警 |

## 三、分阶段

### P0 地基（约 6 小时）

- 仓骨架：pnpm 多包、TS、格式与检查、vitest、GitHub Actions（类型检查 + 单元测试，2 分钟内）、一页 AGENTS.md。
- 法国：装 Postgres 16（Temporal 官方测过的最高大版本）、Temporal 服务端（和旧系统的 Temporal 错开端口，互不影响）、systemd 单元、给 AI 会话的资源池（cgroup）、WireGuard。
- 香港：nginx + HTTPS 证书（DigitalPlat 域名）、WireGuard。
- `deploy/france.sh`、`deploy/hk.sh`：一条命令装好，跑第二遍什么都不变。
- 文档整套改法（创始人 2026-09-26 拍，design 第七节「plan、design、ops 的整套改法」；排在 #131 之后，见「现在的目标」）：
  - plan 条目格式（#137，第①步）：每条一个随机短码编号（如 `[T-k7p2]`）、一行（编号、标题、链到 `specs/<编号>-短名/`）；`docs/plan.md` 只留「现在的目标」和阶段目录，每阶段一个 `docs/plan/P<N>.md`；合并前检查只查 plan 文件本身（编号唯一、格式、链接），文档指针、PR 必填栏、阶段收口跟着改。
  - plan 同步（#138，第②步）：动到 `docs/plan/<阶段文件>` 的改动合进主线后，Actions 以驾驶舱 GitHub App 身份全量、幂等地把条目同步成 issue 和里程碑；单关了回写 plan 标已完成，手动开单、改标题或里程碑由机器人的「同步回 plan」PR 收进来；阶段收口时已完成条目归档；每日全量核对只作保险。开单方式从 `pnpm issue:new` 换成写 plan。
  - design 拆分（#139，第③步）：第三节决定表拆成 `docs/decisions/` 一决定一文件；计划性内容搬进 plan 或 issue；按模块拆 `docs/design/<模块>.md`，和 `packages/<包>` 用一张对照清单对上，PR 动了某包 `src/` 没动对应设计文件就留言提醒、不挡合并；`docs/design.md` 只留一句话、架构图、目录。
  - ops 生成（#140，第④步）：端口、用户、目录这些表由 `deploy/` 下的配置和样例生成，放「自动生成、别手改」区块，密钥只出名字；CI 核对生成内容和配置一致（进合并前检查）；ops 只留怎么做、按主题拆文件，`docs/ops.md` 留目录，线上现状链到驾驶舱健康页。

**验收**：两个装机脚本各跑两遍，第二遍零改动；从香港域名打开健康检查页，看到法国的数据库、Temporal、引擎都在线；一个「你好」工作流跑完，耗时记进 Postgres。文档整套改法：plan 条目格式（#137）——故意写两个同编号条目、一个格式不对的条目、一个链到不存在的 specs 目录的条目，合并前检查各报一条 文件:行；plan 同步（#138）——往 `docs/plan/P<N>.md` 加一条合进主线，几分钟内 GitHub 上出现对应的单（正文带 `<!-- plan:T-xxxx -->`）和里程碑，同一次同步再跑一遍什么都不变；关掉那张单，plan 那行被标已完成；在 GitHub 上手改它的标题，「同步回 plan」PR 里多出这一改动；design 拆分（#139）——`docs/decisions/` 下每条决定一个文件、design 第三节只剩目录，改一个包的 `src/` 不改对应设计文件的 PR 上出现提醒留言；ops 生成（#140）——改 `deploy/` 里一个端口不重新生成，合并前检查红，重新生成后绿。

### P1 核心闭环（约 12 小时）

- 数据表 v1：任务、子任务、会话、事件、进度、路由、账号池、额度、通知、操作记录。
- 工作流：需求（分诊 → 写需求文档 → 写方案 → 拆子任务 → 写结果 → 关单）、子任务（建工作树 → 执行 → 验证 → 进合并队列）、每个仓一条合并队列（同步主线、重测、合并）。

- `fleet` 命令：task / plan / say / ask / done / blocked / history，带只对本任务有效的通行证。
- GitHub：两个新机器人（「干活的」只能推分支和开 PR，「引擎」才能合并）+ 主线规则集；白名单作者过滤；issue 进度段原地更新；开 PR、合并、互动限制自动续期；GitHub 事件经香港转到法国，校验签名，漏收的靠对账与轮询补回；防重复写的记录在 Postgres。
- 巡检仓：另建一个小仓 `fleet-dao-canary`，巡检任务只在里面动，不往 fleet-dao 的历史里塞噪音。

**验收：机器接管**（创始人 2026-09-25 重定）：P1 做完的标准是 fleet-dao 能自己把一张真实的 GitHub issue 从收单做到合并，总指挥不一步步插手——不是「代码写完、测试全过」。两步，都在法国真机上：

1. 巡检仓开一张 issue「给 README 加一行当前时间」，全程无人干预：收单 → 分诊 → 需求文档 → 方案 → 派给 AI → 独立工作树 → 写码 → 测试 → PR →（高风险才第二意见一次）→ 合并 → 结果文档 → 关单；每一步耗时进库；中途杀一次引擎进程，任务从断点接着跑完。
2. 吃自己的狗粮：fleet-dao 自己的仓里开一张真实的小需求，由引擎从收单做到合并、关单。

验收过了就把 fleet-dao 这个项目交给引擎接活（打开它的「让 AI 接活」开关，之后新开的单自动派，design 第九节「在哪能做与接活开关」）。

**P1 期间不做的**：不影响上面验收的改动一律不进主路径，开成带「怎么算做完」的 issue、挂到它所属阶段的里程碑——驾驶舱（P2）、额度与调度、多模型（P3）、飞书（P4）、备份与故障演练（P5）、旧系统迁移（P6）。「顺便把 X 也做好」的一律不做。先后以本文件「现在的目标」为准（创始人 2026-09-26 定：先路由探针 #129 和 P1 验收，让 VPS 能接活）。流程也不再加关卡，除非它挡了 P1。

- 插头：cursor-agent、Grok 命令行、Mirasim 运行时接口（中转的 Opus、GPT、Kimi、DeepSeek）、codex（先确认它的登录方式会不会按量扣钱）、接口外壳（命令行够不到的模型）。
- 讨论直连渠道（#118，`specs/118-讨论直连渠道/`）：调度台「讨论」阶段加一种渠道，直接调 OpenRouter 这类接口一问一答，一轮 10 秒内；按字数计费有花费上限，开付费钥匙前先问创始人。
- 每个渠道的额度读法（官方接口 → 网页接口 → 估算），订阅到期日；读失败就报警。
- 调度：过滤、排序、快清零优先、战绩微调、10% 试探（构建期关着，全用 Opus 5.5；判断阶段、第二意见例外，见 design 第三节第 8 条）；每个账号池的并发；模型下架时对应路由自动离线。
- 浏览器端口（`specs/37-浏览器端口/`）：网页操作交给 Jev 选点，一次调用跑完一段；上线时退役本机垫片。
- 第二意见（`specs/64-第二意见/`）：只有两种先审后合、其余合并后审（design 第五节「流程只为快，不当绊脚石」）；接上 Mirasim 后默认走 gpt-6-luna、界面类走 Gemini；上线时退役本机垫片。

**验收**：Kimi（经 Mirasim）和 Cursor 各跑通一条小任务；额度表列出每一个账号池，标明实读或估算；在调度台下架一个渠道，它手上的活跑完后不再接新活；本机一段飞书开发者后台操作一次调用跑完，结果由代码核对，花费进 Jev 记账。另一条（原在 P1，创始人 2026-09-25 挪到这里）：拼车号真用满一次时，会话用户整个切到独享组织、手上的活 fork 续上跑完，到拼车窗口恢复的时刻再自动切回（#59）。

### P4 飞书 v2（约 6 小时）

- 香港网关：2 秒内回「收到」、确认卡、只推三类消息 + 关注、置顶盘面卡原地刷新、机器人菜单、回复即追问（用库里的数据回答）、卡片直达驾驶舱。
- 需求拍板期与需求讨论群（design 第五节「需求拍板期」、15.4 第 5 件）：引擎里加拍板期（倒计时、延长、暂停、跳过，到点读讨论群归纳方案，重大等人拍），飞书按需建讨论群、群里 @ 机器人对话、需求关了归档；调度台加「飞书对话」阶段。排在 P1 验收之后。

**验收**：在测试群里用授权的测试身份真发消息，自动断言每一步回应和耗时（「收到」不超过 2 秒）；按钮和菜单用真实回调数据测网关，再自动操作飞书网页版点几条关键路径（这一项最脆，失败先人工复核）。

### P5 可靠性（约 8 小时）

- 错误按「下一步动作」分流（带旧系统攒下的真实报错样本）、路由熔断、按进展判停滞、AI 帅位（诊断卡单、日报、调调度台并可一键撤回）、每小时对账、每 6 小时巡检、看门狗、每晚备份、数据保留与磁盘告警、引擎升级时在途任务不变僵尸、定期巡审（#69）。
- 讨论（#69，design 第五节「讨论」、15.5）：需求工作流里的讨论环节（重大方案自动触发，人可在飞书 @机器人「讨论一下」或按按钮叫）、结果卡进讨论群或项目群、拍板写回需求文档；调度台「讨论」阶段的渠道配置（每家硬超时 30 秒、同时最多 3 家、连不上换下一家）；驾驶舱「讨论」页和每条渠道的成功率、中位耗时。
- 对账表读文字（#134，design 15.7 分步④）：对账表里要读人写的文字的几条——PR 档位理由写得对不对、「怎么算做完」能不能验证、自下而上的提案是不是真通用——交给 Jev 判，只拦不放，先只记不拦，攒够样本、准确率过线才拦（design 第十一节「怎么管住它」）。
- 发布构建和密钥隔开（#79）：构建换成读不到 `/etc/fleet-dao` 的专用用户，构建期间的第三方代码拿不到密钥。

**验收**：故障演练全过——干活中途杀引擎、让一条路由连续报错、停掉额度读取、删掉一条投影数据、关掉后端，各自在规定时间内被发现并自愈或报警；另加两条接续演练：干活中途让会话撞上额度上限，恢复后续上同一个会话、已提交的步骤不重做；中途强制换池，新会话拿到接力任务书、已提交的不重做。讨论一条：巡检仓一张判为重大的需求自动发起讨论，3 家以上答上，结果卡发进它的讨论群（没群就项目群），点推荐项后需求文档里写进结论和方案版本、讨论变「已拍板」；关掉飞书再来一次，这条讨论出现在驾驶舱「要人拍」里、停着等人，别的需求照常往下走。对账表读文字（#134）：故意开一个「怎么算做完」写成「做好就行」的测试 PR，Jev 的判断记进判断记录（只记不拦，不挡合并），驾驶舱 Jev 判断记录页看得到这一条和准确率。

### P6 迁移与切换（约 6 小时）

- 旧单：按审计的去向表逐条关单（写明去向）或搬成 fleet-dao 需求。
- ai-gateway-stack：还在用的接线搬进来，然后只读存档。
- 香港清理：旧网关（new-api、Devin 与 CommandCode 的转接、gw-* 维护任务）2026-09-25 已停，orca 2026-08-27 已停，数据留着。防火墙开着（默认拒绝，只放 22、80、443 和 WireGuard 的 UDP 口），剩下的旧服务只有下一条的 miraquota-hub。还要做的：防火墙基线写进 `hk.sh`、读回核对「对公网开着的端口 = 白名单」（#48）。

- 旧系统：停并禁用定时任务和服务；数据留着，删不删到时问你们（#78）。
- 规则：fleet-dao 的一页 AGENTS.md 定稿；你的全局 CLAUDE.md 精简稿给你逐条过。

**验收**：你在飞书里随手写一句需求，没人碰任何东西，它被做完、合并、通知到你；旧系统没有任何活动。接 GitLab（#135，真要接时才验）：连一个 GitLab 账号、勾选导入一个仓，体检、补齐 PR、收事件和 GitHub 的项目一样走通；一个成员同时记着 GitHub 和 GitLab 两个账号，两边的操作都认得是他。

## 四、构建方式

- **由 Claude 按阶段自主决定**（创始人 2026-09-25 授权）：在本机还是云端干、开几个会话、每个会话里起多少子代理，以快为准。
- 起步：本机当总指挥，并行起 Opus 5.5 子代理，各自在 fleet-dao 的独立工作树里做一块、带测试提交，总指挥审过再合；两台 VPS 的装机经 ssh 执行。
- **P1 验收过后**：剩下的活开成 fleet-dao 的需求，由 fleet-dao 自己在法国 VPS 上派 Opus 5.5 干，总指挥只做终审和兜底。从这时起活都在云端跑。
- **质量**：每块活「写码的会话」和「审查的会话」分开；每个阶段的验收脚本过了才进下一阶段；踩过的坑（审计里整理出来的）写成测试用例。
- **并发**：同时 5–6 个 Opus 会话，看 VPS 和额度实测再调。
