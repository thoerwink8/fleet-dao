## 一、一句话

创业团队的 AI 全流程：你们写任务，AI 从拆解、写码、测试、审查到合并全包；手上的多家 AI 订阅自由组合、互不闲置；驾驶舱里看得见、管得住。

## 二、为什么从零写

前身是 windsurf-dao（派工与规矩）和 ai-gateway-stack（渠道接线）两个仓。2026-09-24 的盘点结论：

| 现象 | 根因 |
|---|---|
| 没人盯就停 | 新任务要人亲手贴标签才开工；卡住的任务进收件箱，没有自动处理 |
| 订阅额度用不掉 | 派工从不走 Claude 订阅那条线；排序只会「用完就停」，没有「快清零的先用」 |
| 总断链 | 30 本账，一个月断 10 次：闸挂在没人跑的地方、写方漏分支而读方当没事、拿假样本验收 |
| 会话开太多 | 一单拆 4 个角色，审查不过就整轮重来，审查意见互相打转（windsurf-dao#1289、windsurf-dao#1338） |
| 并行撞车、落后主线 | 任务切得太碎、各开各的分支，做到最后才发现主线早就变了 |
| issue、PR 没人读 | 模板为流程和检查而写，又长又全，人不读，AI 也用不着那些套话；没有需求文档，历史无处可查 |
| 看不见进度 | 有的命令行会列任务清单，有的不会；做到哪一步只能猜 |
| 越修越重 | 代码 11.4 万行、测试 11.5 万行、99 项检查；近 30 天关掉的单约 90% 在修机制自己，开放单一半是机器给自己派的「这里该加检查」 |

所以不修补，从零写一个小而硬的核心。旧仓只当参考：好的做法搬过来，踩过的坑写成测试带过来。

- **引擎工人（法国）**：执行 Temporal 派下来的每一步：起会话、跑测试、开 PR、合并、记账。不存状态，以后加机器就是加工人。
- **Temporal（法国）**：每个任务一条工作流。记下每一步的开始、排队、耗时、重试；接收驾驶舱的信号（暂停、叫停、换模型、批准）；接收驾驶舱的信号之外，旧系统约 30 个 systemd 定时器（额度探测、模型扫描、巡检、备份、续期互动限制）里留下的引擎定时任务不在 Temporal 里：是引擎进程里的普通定时器（#1072，`packages/engine/src/jobs/timers.ts`），只有任务工作流留在 Temporal（巡检那条长工作流随决定 0093 删了）。
- **Postgres（法国）**：驾驶舱要的一切都在这：路由配置（带版本）、用量与额度、战绩、进度、GitHub 镜像、通知、操作记录。有变化实时推到驾驶舱。
- **驾驶舱后端（法国）**：驾驶舱的所有读写都经过它——查数据、改调度台、叫停任务（给 Temporal 发信号）、开任务（经机器人写 GitHub）、实时推送、权限与操作记录，以及手机通知：把该推的提醒用飞书应用机器人推进团队群、记送达（`packages/api/src/feishu-push.ts`，运维说明在 docs/ops.md 每小时对账那一节后面；推不通由看门狗进「要你拍」）。推送分级：只有要你拍的（四类人闸和 AI 判定要创始人的）和每日简报马上推；卡住报警开满 120 分钟、主线红开满 60 分钟没自愈才推；其余不推，进引擎每天 08:30 的每日简报（推飞书、同时在置顶进度单 #1055 发评论，到没到只由看门狗判，决定 0096）。读数据只从 Postgres 读，不直接查 GitHub——快，也不撞 GitHub 的调用限额。唯一的例外是 /france 页的发版卡（`packages/api/src/release-card.ts`）：主线头、它的 CI 和最近合并的 PR 以 GitHub 为准、库里没有副本，所以只在打开那一页时现读一次，读不到照实说。
- **香港门面**：只当门卫和信使，不放业务逻辑——驾驶舱页面与飞书登录、收 GitHub 事件（飞书只剩登录和手机单向通知，通知由法国的驾驶舱后端用飞书应用机器人直接推，不再有香港上的飞书网关，决定 `docs/decisions/0090-intake-in-cockpit.md`）。和法国之间走加密通道。
- **为什么分两台**：实测调飞书接口香港 0.17 秒、法国 1.1 秒；Anthropic 对香港封区，Claude 等 AI 活只能在法国跑；`workers.dev` 在国内被 DNS 污染，不能当入口。
- **Cloudflare**：不再用。曾经设想过一个外部看门狗（定时 Worker，#292），一直没部署，#2369 删了：法国失联由香港探活（每分钟探法国 `/healthz`，ops 的「香港探法国」）看，香港由本机巡检看。备份去向见 ops 第十一节「备份与恢复」。

### 执行模式与容量

- **无头**：每个子任务在后台起一个命令行写码助手进程（Claude Code、codex、cursor-agent、Grok 命令行或自研外壳），不开窗口、没有界面会话；Mirasim 中转的路由也走它的程序接口。驾驶舱提供「直播」：实时滚动显示助手每一步在干什么。
- **Temporal 指挥，AI 干活**：派活、等待、重试都是确定性的工作流；AI 只在分诊、写方案、写码、审查和定时的 AI 指挥官出场。每个助手在自己的工作副本里干活，需要时在会话内部再起子代理。
- **插手**：「换模型」「暂停」让当前进程停在干净的点（做完的已提交），再按新设置接着干；临时追加的要求排进下一轮。暂停（含发版前的暂停）后点「继续」，动手那一段按会话号续上原会话（决定 0088，`packages/engine/src/workflows/task-session.ts`、`real/segment-resume.ts`）：同一棵工作树、同一个执行方式、同一个账号池、同一个会话用户，`runs` 里记着那一段的会话号，就用执行体的续会话起，提示词只补一句被打断的原因；续不上（没记下会话号、换了执行方式、池、会话用户或工作树、没查成）原分支原树开新会话，带上「树里有上一次留下的东西」，任务进度里写明为什么没续上。续起来没跑成的，下一次开新会话。发版重启引擎时，命令行那几家（claude-code、cursor-agent、grok）上的动手会话不暂停：会话脱开引擎接着跑，这一段交回 detached，工作流隔 20 秒带上 attach 再调同一段，新引擎从收发目录接回、等它收场（#2238，`real/session-handoff.ts`，ops 第九节「发布不碰会话」）；Mirasim 上的动手会话也一样（#2815）：服务端的会话不靠引擎的 ws 连接活着，放手只断开连接、不发 stop，新引擎按交接单里的会话号重新订阅；一家验的冷验收会话也一样（#2848）：coldVerify 交回 detached，工作流隔 20 秒带上 attach 再调同一次验收（`patched('cold-verify-attach')`），新引擎接回、结论照常贴照常认，结局记回原来那一行；两家都验的两个会话不脱开，发版叫停了、又没接回的不算验收没过，回 retry 重验一次（不算一轮，全程模式「冷验收被拒 2 次」也不数它）；整理这类短会话照旧暂停、续上。
- **会话断了接着干，不重来**：会话被额度、限流、进程被杀、引擎重启打断时，同一个账号池就按会话编号续上原会话，上下文都在；额度用满就挂起，到清零时间续同一个会话，不开新的（Claude 订阅池不干等到清零：引擎切号，切过去接着干，见本条末尾）。非换池不可时，引擎从库里拼一份接力任务书开新会话：原任务、步骤清单做到哪、最近的进度、工作副本里已提交的改动、还没处理的审查意见；已提交的不重做。法国只有一个会话用户，平时挂拼车组织；拼车用满时整个用户切到独享组织，手上的活先停下、切完接着干（三段的一次性会话在原分支上重跑那一段；见第九节）：同一台设备上切号，会让上面所有在跑的会话一起断（2026-09-25 构建期实咬：本机一次切号，总指挥和十几个子代理全断；把记录接回新会话后，各自从断点接着干完）。两种不再续这个号、改开新会话带接力任务书（#489）：这个号上一轮续起来没有第一帧（startup_timeout）；Grok 的号上一轮判了停滞、本来要同池 `-r` 的。
- **容量（6 核 12G）**：

| | 旧系统（实测） | 新系统（起步值，实测后调） |
|---|---|---|
| 同时在写码、验证 | 3 个任务（2026-09-22 负载 15 后封顶，windsurf-dao#1748） | 6 个会话（约 5 个子任务 + 1 个审查），压力低往 8–10 加 |
| 同时跑测试 | 全机 2 份 | 2–3 份（新测试秒级） |
| 一个任务占几个会话 | 2–4 个 × 返工轮 | 1 个主会话 + 需要时 1 个审查 |

- 旧系统那次负载 15，主要是机器在忙自己：5 个任务同时执行、一个工作副本里 13 个测试进程、一份 109 秒的全量检查、Mirasim 轮询 30 个工作副本、用量采集器每轮扫 1526 个文件。新系统这些都没有。
- **放行看三样**：内存与机器压力（不看整机 CPU 百分比）、账号池并发空位、额度够不够。真正的上限多半在订阅，不在机器。排队的任务在驾驶舱写明在等什么：等空位、等额度、等前一个子任务。
- 每个会话连同它跑的测试的内存上限，2026-09-26 按法国实测定（#164，原先按 1.2–1.6G 估，#160 在软 1.5G、硬 2G 里跑测试卡死），2026-09-28 按新一次断链改过推导（法国实测：单会话被自己那道窄墙——旧的三等分值——卡死，整机却还有 6.8G 空闲）：安全垫从「单会话」挪到父节点 fleet-agents.slice，总量上限 =（能分给会话的 11G − 平台常驻服务约 0.6G）≈ 10.4G，软上限低 512M；单会话硬上限放宽到「一次放得下 tsc -b 全仓 + 测试 2–3 个进程 + 代理本身」这种最坏组合，约 6G（约总量的一半），仍明显小于父节点总上限，多个会话同时冲高由父节点兜住；测试开几个进程按所在 cgroup 的上限算。算法在 `packages/engine/src/limits.ts`、`packages/conventions/src/test-run.ts`，单元文件在 `deploy/france/fleet-agents.slice`，运维见 ops 第五节。以后加机器就是加工人。

### 为什么用 Postgres

| | SQLite | MySQL | Postgres |
|---|---|---|---|
| 是什么 | 一个文件，嵌在程序里 | 数据库服务 | 数据库服务 |
| 多个程序同时写 | 容易「库被锁」（旧系统专门写了重试代码，windsurf-dao#1814） | 可以 | 可以 |
| 跨机器用 | 不行 | 可以 | 可以 |
| 数据一变就通知 | 没有 | 没有，要另加中间件 | 自带，驾驶舱实时刷新就靠它 |
| 存结构不固定的数据 | 弱 | 有 JSON 类型 | JSONB，能建索引，查得快 |
| Temporal 同库 | 只能单机开发模式 | 支持 | 官方支持 |
| 扩展 | 少 | 少 | 多：库内定时、向量搜索（以后按意思搜历史任务）等 |

引擎工人、驾驶舱后端、定时任务会同时写库，以后还要跨机器，所以 SQLite 不合适；MySQL 和 Postgres 都成熟免费，Postgres 多了实时通知、JSONB 和扩展这几样我们正好要用的。

## 五、一个任务怎么走完全程

> 本节写引擎里一张单怎么走完全程。现行流程有两种并存（决定 0105）：三段（对题 → 动手 → 验收，决定 0010，默认）和全程（动手会话一路带到合并，试点中）；需求从驾驶舱「提需求」进，飞书只发手机通知（决定 0090、`specs/2047-提需求/方案.md`）。下面凡标「已删」的是已被替代的旧做法，只作历史对照。

```mermaid
flowchart TD
  D[对题 · 建单<br/>指挥官和创始人对话 · 单子写全场景、原话、已知的模块、怎么算做完] --> W[动手<br/>工人按改动面分档 · 开 PR · 过 CI]
  W --> V[验收<br/>合并前一次冷调用 · 换一家 · 只判做到了没有<br/>默认 1 轮 最多 2 轮]
  V -- 没做到 --> W
  V --> G{要人拍吗<br/>发布 花钱 删数据 改标准}
  G -- 要 --> HN[驾驶舱待点头] --> M
  G -- 不要 --> M[合并 · 关单]
```

- **两种流程并存**（决定 0105；记账 `task_flow_assignments`、`tasks.flow_mode`、`task_rounds.flow_mode`，开关设置 `engine.flowMode`，名单和读法在 `packages/shared/src/flow-mode.ts`）：
  - **三段**是上图的样子，默认流程，也是对照组：动手、验收各是一个会话，CI 红或验收拒绝时由引擎另起一轮返工。
  - **全程**：同一个写码会话从动手带到合并。先出几行方案、自己跑改到的测试、提交；CI 红、和主线冲突、冷验收拒绝，引擎把失败的 job 名、日志尾巴或拒绝原因交回**同一个会话**接着修，不算新的一轮，整张单有推送次数和 token 的上限；等 CI 时会话不挂着，本轮先结束、有结果再续。上图里引擎做的那些事（推分支、开 PR、等 CI、合并）一样不少，只是失败后续的是原会话。
  - 两种的合并闸、冷验收、改标准人闸完全一样，写码用同一个模型。全程现在只在 fleet-dao、只走 Claude Sonnet 5.5 这一条路由；碰迁移、合并闸、凭据、权限、任务工作流、发布脚本、改标准路径的单、跨仓的单一律走三段。
  - 怎么分组（单上贴「全程」「三段」标签，没贴的按单号哈希并按档位分层对半分，分组一次定下不改）、成功怎么算、非劣效边界、样本量、三类止损各怎么算和谁来判，都在决定 0105；每日简报「流程健康」按模式分两栏对照（`flowModeHealth`），两组都不满 30 单只写「还不够判」。
  - 「低风险单免冷验收」不在这套里，另做独立试验。
- **合并前的验证（冷验收）怎么做**（#555；原来开 PR 前的验证零件 `workflows/verify.ts` 已随 Fusion 删除，见本节「合并闸」）：

## 六、任务颗粒度与合并（已定）

> 层级是版本 → 母单或单独的小单 → 子单 → 块（决定 0010 替掉了 0003 的 Lead 按块循环）。

旧系统的毛病：一张 issue 一个工人、各开各的分支；颗粒太碎就并行撞车，分支活得久，做完才发现主线早变了。

做法：

1. **层级**：GitHub 上是版本（里程碑）→ 母单或单独的小单 → 子单（GitHub 子议题，别人开的具体问题）。Lead 规划时拆出的块不开成单，只存在引擎里、驾驶舱看得到，免得单子爆炸；母单页面自动显示子单进度，GitHub 上也看得出脉络。
2. **拆的时候就标出会动哪些地方**：Lead 规划时每块写明要改的文件或模块，以及依赖哪块先做完（写在方案和任务简报里，见第七节）。
3. **不撞车的调度**：会动同一块地方的不同时跑——两张母单要改同一批文件的不同时跑，排队，或交给同一个 Lead 连着做；一张单里拆得开才同时派副手（最多 3 个），先定接口和谁改哪些文件，各在自己的工作副本里改，Lead 逐个合进来、每合一个跑一遍测试。
4. **永远从最新主线起步**：开工时从最新主线建工作树；交审前先同步最新主线，有冲突当场解决；主线一变，在途分支自动同步。分支活不过一天。
5. **合并靠 GitHub 自动合并、CI 全套兜底**：验收通过后挂自动合并（squash），必过检查 `check` 绿了 GitHub 自己合；引擎直接合时核头、核不落后主线、核 CI 绿，落后主线就把 PR 同步到最新主线、对新头重跑 CI 和验收（`packages/engine/src/real/task-activities.ts`）。不排自己的合并队列，也不用 GitHub 的（要组织账号，本仓归个人账号）：PR 和主线的 CI 一律全套（决定 0101），「两个 PR 各自绿、合起来红」近 7 天一次都没有，主线红的根子是 PR 上只跑了一部分。
6. **颗粒度有目标**：一个 PR 是一个能单独验证、单独回滚的变化——够小，很快验得完；够完整，能单独合进去（创始人 2026-09-25）。大约一个会话一小时内做完；同一块地方的零碎小单合并成一个子任务一起做；不为了小把一件事拆成一串没法单独验证的碎 PR；太大的继续拆。

### 断链怎么被发现

旧系统断了没人知道，是因为没有东西盯着整条链。创始人 2026-09-27 问「我希望断链了能及时发现，下午就没做到这一点，怎么办」，同日定下原则：「我认为你补上的机制应该是fleet引擎的核心链路，是要保存在仓库的，换台机器一样好，才行」。所以兜底的几层都做在引擎里、进仓、跑在法国，换哪台机器干活都一样（从外面看法国的是香港每分钟的探活，脚本同样进仓）；指挥官会话里的临时检查只算垫片，不算哪一层，对应的那层上线就删。五层兜底：

1. **能断的地方少**：一件事只存一处，只认 GitHub、Postgres、Temporal 三处（外加仓里的需求文档）。

## 七、需求文档与 issue、PR 的组织（已定）

> 引擎不直写主线，需求、方案、结果随 PR 进仓；每张单另有一份讨论记录（简报加全文），写进公开的单、法国库存一份。下面的需求文件夹照旧。

旧模板是为流程和检查写的：人不读，AI 也用不着那些套话。业界现在的做法（GitHub Spec Kit、AWS Kiro）是每个需求在仓里建一个文件夹，放需求、方案、任务几份短文档，AI 每次干活都读进去。

```
需求（一张 issue：场景、原话、已知的模块、怎么算做完——正文就是需求的唯一的家，#654）
 ├─ specs/12-登录验证码/方案.md   （复杂的活才写）怎么做、拆成哪几块、各改哪里、先后依赖
 ├─ 子任务 A ── PR #31   正文四栏：做了什么、怎么验证的、还欠什么、需求（Closes #12）
 └─ 子任务 B ── PR #32
```

- **一个事实一个家**（#654，创始人 2026-10-03「我们的流程不应该冗余，一切要为了提速而服务」）：需求只在 issue 正文里（场景、原话、已知的模块、怎么算做完），不再另存一份 `specs/<号>-<短名>/需求.md`——两份各改各的，对账、检查的活全是它引出来的；做成了什么只在 PR 里（正文四栏，合并时 `Closes #号` 关单），不再另写 结果.md；怎么做（方案）复杂的活才写 `specs/<号>-<短名>/方案.md`，单上放链接。`specs/` 和 `docs/decisions/` 下已有的文档是历史记录：不再改、CI 不再查。
- **创始人只说一句话**：需求单由 AI 按原话写（`pnpm issue:new`），同时推一张「我理解为……」卡片。
- **长度上限**：需求一页以内（GitHub 一张单的正文最多 65536 字，`pnpm issue:new` 超了拒开；长的方案放 方案.md、单上留链接）；PR 正文 14 行以内（#654 起只有四栏）；issue 顶部 5 行是给人看的摘要。
- **方案里写明会改哪些地方**（有方案.md 的活）：这正是第六节「不撞车的调度」要用的输入。
- **查历史**：开新需求前，AI 先翻以前改过同一块地方的单子和 PR（先按改动位置和关键词找，以后加按意思搜），再动手。
- **构建期也照这套走**（创始人 2026-09-25 拍；此前构建期的活是用对话里的任务书直接派的，仓里没留需求）：创始人提的需求和「以后再做」先开 issue（正文就是需求），任务书只给单号；AI 自己发现自己修的不开单，直接开 PR（第五节「发现问题当场修」）。方案要写才写，放进 `specs/<号>-<短名>/方案.md`、跟 PR 一起合。审查返工这类不另开。PR 正文只有四栏、不再写对应 plan 和 specs（#654，替掉创始人 2026-09-26 拍的「缺了只提醒」）；CI 查 design、ops、README 里的文件和章节指针都指得到（章节后面引的话照抄原文，写大意的查不出真断），写法本身的毛病（「第 X 节」没说哪份）和读不到的（目录列不出来，报「没查成」、不当成没有）照报；specs/ 下的文档是历史记录，不查（`packages/conventions/src/doc-pointers.ts`）。
- **关单要有证据**（#241，2026-09-27：做完的单一直开着，开着 79 张；#654 起证据不再是 结果.md）：「做完」＝合进去了、单也关了。最后一个 PR 在「需求」栏下面另起一行写 `Closes #<号>`，合并时 GitHub 自己关，PR 就是交付记录。
  - 没有 PR 的收尾（母单、做完了没人关的、配置类的手工事）用 `pnpm issue:close <号>`（`packages/conventions/src/issue-close.ts`）：关成「完成」要有证据——同仓里合并了的 PR 提到它（时间线上的交叉引用，评论里贴链接），或它下面的子单都关了，或 `--note "做成了什么"` 写一句（贴进评论、不去读时间线）；三样都没有、下面还有开着的子单、是 PR 都拒关；读不到 GitHub、时间线读不全（1000 条以上）报错不关；关完回读是「关了、完成」才算关上。`--superseded-by <号>`、`--reason not_planned|duplicate` 关成「被取代」「不做了」「重复」，不要证据。不直接 `gh issue close`。

### 标签与里程碑（2026-09-25 定）

GitHub 上只用标签和里程碑两样容器。issue 照第七节建（创始人 2026-09-25 改：当初「先不建」是怕法国自动派活，现在由第九节的「让 AI 接活」开关和「在哪能做」管住）。每个标签的颜色和一句说明以 GitHub 上为准，这里只写有哪些、谁贴、为什么。

| 组 | 标签 | 意思 | 谁贴 |
|---|---|---|---|
| 类别 | `需求` `缺陷` `杂项` | 要新东西 / 现有的不对 / 文档、整理这类不改行为的 | AI 分诊时贴，人可以改；只是分类，不影响派工和合并 |
| 结构 | `母单` | 一组能一起验收的子单；子单用 GitHub 自带的子议题挂在它下面，母单页面看得到做完几张 | 开母单时贴（`pnpm issue:new --mother`）；有子单的必须带，带了的必须写清怎么算做完（2026-09-26 晚加，#169）。子单用 `pnpm issue:new --parent <母单号>` 开：母单没贴这个标签它拒开，先挂到母单下面再挂版本（第九节「母单、子单不自动派」） |

> 2026-09-26 晚：下面「一、plan」被 #169 第 5 件替代——计划以 GitHub 加驾驶舱为准，plan.md 改成每个版本生成的快照（#654 起快照也删了）；①#137 关单，②#138 缩成版本快照写回仓。design、ops 两部分照旧。

## 八、进度看得见（已定）

进度一份两用：给人看（放心），给机器看（按进展判死活，第六节）。

- **先被动**：各家命令行在无头模式下都会输出结构化的过程记录。转接层直接从里面读步骤清单（Claude Code、Codex 自带的）和动作（改了哪些文件、跑了哪些测试）。不用 AI 配合，进度和「活还在不在干」就有了。（各家记录的具体格式开发时逐个实测。）
- **再主动，做成 `fleet` 命令**：只有 AI 自己知道的事才让它主动说。照 Codex 的做法维护一张步骤清单，每步「未开始 / 进行中 / 完成」，同一时间只有一步在进行，用白话写（「正在写验证码过期的测试」）。
  - 为什么是命令不是 MCP：所有写码助手都会跑命令，一条命令各家通用（包括我们自己的写码外壳），不用给每家配插件；人和测试能直接敲同一条命令；命令只在用时才进 AI 的视野，不像 MCP 的工具说明每轮都占上下文。
  - 命令初稿：`fleet task`（看自己的需求、方案、要改哪里、怎么算做完）、`fleet plan`（列步骤、改状态）、`fleet say`（一句话进度）、`fleet history`（翻历史需求）、`fleet discuss`（发起一条讨论、看它的结论，挂在自己的需求上；总指挥会话还能挂「规矩」，第五节「讨论」）、`fleet done` / `fleet blocked`（交活或报卡住；引擎会核实，不是说了就算）。
  - 安全：开工时引擎给会话一张只对本任务有效的通行证；命令只能动自己的任务，不能合并、不能改调度台。每条命令写进 Postgres 并通知工作流。
- **两级进度**：需求 → 子任务（来自方案）→ 步骤（来自会话）。按过去同类活的耗时估「预计还要多久」。
- **沉默就催**：一段时间没更新进度，先提醒这个会话；再没动静，标「停滞」交指挥官诊断。
- **在哪看**：
  - 驾驶舱：实时，卡片上有进度条和当前这一步。
  - **三段的耗时和用量只计引擎起的会话，对题不计**（#761，2026-10-05）：动手、验收每一笔会话写进 `runs`，任务页和主页按段汇总；对题是创始人和指挥官在对话里做的，那个会话在创始人自己的机器上，开单脚本读不到它的起止、模型和 token，法国库本机也写不进，凑一笔空行进去只会让合计看上去三段齐了。所以任务页「三段」里对题那一行写「在对话里做的，不计」和原因，主页对题泳道头写「在对话里做的，不计耗时」，不再出现永远的「没记」「没有记录」；这句话和只有对题不计的名单在 `packages/web/src/lib/segments.ts` 的 `SEGMENT_UNMETERED`，动手、验收没有行照旧点名读不到。以后引擎自己起了对题那一类会话（如 #553 的需求归纳，段记 `scope`），那几笔照常显示，段名下写明「只含引擎起的会话」。
  - GitHub issue：进度那段原地更新，不刷评论。
  - 飞书：见 15.4。
  - PR：做了什么、怎么验证的、还欠什么写在 PR 正文（#654 起不再另写 结果.md）。

     **能力下限**（#2725，创始人 2026-10-16「不能为了用额度把难单派给弱模型」）：排序之前按用途和派工档定最低强弱档，够不上的硬挡（`packages/engine/src/routing/floor.ts` 的 `STRENGTH_FLOOR`，判据只在这一张表）——动手、界面：主力档要强档、中档要标准档以上、快档不设；验收：主力档和中档要强档、快档不设；别的用途、没给档的单不设。额度剩多少、池子落后多少都不放宽。只有够格的全被挡、2 小时内好不了（硬挡，或等额度清零在 2 小时以后、清零时刻不知道；等空位、熔断快到点不算）才降一档（强档降到标准档），永远不降到轻档，理由写「下限是强档，……这一次降一档到标准档；轻档仍不派」；够不上的那条写「够不上能力下限：主力档的动手要强档，deepseek-flash 是轻档（额度剩多少都不放宽）」。冷验收照样按族一家家问（0006 的族顺序），每一问都过这道下限；判「够格的是不是全被挡」时不算「只派别家」的换族挡因（别家够格的问到它那一族时照样能派，不提前降档）。验收的派工档工作流不带，选路端口按这张单最近一次动手记下的档（`runs.tier`）从库里读。人的指令不驳：任务点名的路由、整段钉住、钉住的行、人在驾驶舱给这张单指定了模型都不按下限挡。没标强弱档的模型认不出强弱，在有下限的档（主力档、中档）上按不够格挡，理由写「没标强弱档，够不上能力下限：去 deploy/catalog.json 标档」，降档也不放行；快档、没有下限的用途照旧不管。
     **按池压力加权抽签**（决定 0104，#2757，创始人 2026-10-16「模型排了优先级，怎么雨露均沾，都你自己设计」）：过了上面的过滤和能力下限，在剩下能派的候选里按权重抽一条，不再取第一条能派的。权重 = q × min(ρ, 4)²：ρ 是池压力（剩余比例 ÷ 剩余时间比例，取这条路由扣的、5 小时窗以外最紧的窗口，和驾驶舱额度页的池压力同一个算法），ρ > 1 照时间均匀用也用不完、多喂，ρ < 1 快用完、少喂；读不到（额度未知、读数过期、只有 5 小时窗）按中性 1，不排到最后。q 是动手这一档的收缩质量下界（下面第 3 条那个公式），没打分的按候选里打了分的平均，都没打分为 1，不低于 0.05；非动手用途 q 一律 1。中档单不进 ρ < 1 的强档池（权重记 0，留给只有强档能做的主力档）。抽签的数是 `seedDraw(单号:段:第几次选)`，在 `pickRoute` 活动里算、结果进活动历史，同一单同一段重算不变。权重平手（比如读数全读不到）不抽，照下面第 2、3 条的排法取第一；权重全 0 也照它。人钉住的、任务点名的路由照人排，不抽。理由写「按池压力加权抽签（抽到 0.xxx）」和「候选权重 = q × min(ρ, 4)²：」逐条列出每个候选的权重。代码在 `packages/engine/src/routing/allocate.ts`，参数在 `routing/policy.ts` 的 `allocate`（`rhoCap`、`neutralRho`、`minQuality`）；`allocate.mode` 置 `'legacy'` 就回到下面第 2–4 条那套（快清零、按进度、战绩重排、强弱档、试探）。weighted 下那套只在权重平手时排先后，约 10% 试探不做；稳定一个版本后另开单删掉（删除条件见 #2757）。
  2. 按顺序取第一条（`allocate.mode = 'legacy'` 时；weighted 下只在权重平手时用，见上面「按池压力加权抽签」）：先按这个用途的模型顺序，再按模型下的路由顺序（两层摊平成一串，`packages/db/src/queries/engine-route-facts.ts` 的 `routeFactsForPurpose`）。被过滤掉的（不在线、开关关着、犯禁令……）跳过并写明；一条都派不出、又等不来，明说派不出、逐条写原因，用途没有模型（这个用途没有模型，派不了）、模型下一条路由都没有这类配置缺口也写进去，不拿空的、默认的顶。
  3. 微调：按消耗进度排（#2363，参考广告预算「按进度花」，创始人 2026-10-16「各个渠道额度有的用到90%了，但是有的没怎么用上」）：每个窗口算落后量 = 窗口已过比例 − 已用比例（`packages/shared/src/quota.ts` 的 `quotaPace`，窗口长度按种类取，种类是 other 的按标签开头的时长〔Mirasim 的 30d〕，都推不出〔Cursor 的桶〕按 30 天并标「估算」）；落后 10% 以上的往前提（剩的反正要作废，越早清零越前；其余适用窗口〔含 5 小时窗〕都要读成、还剩两成以上，快满的池不顶到最前），超前 10% 以上的往后放（一个窗口超前就算超前，照这个速度清零前会用完），其余照人排；5 小时窗只用来挡、不参与排序；读数过期、上游这次没报的窗口不参与。派工理由写明「按时间该用 X%、实际用了 Y%」；驾驶舱额度页每个窗口也多一行「按时间该用 X%，实际 Y%」，和选路同一份算法。总开关是 `routing/policy.ts` 的 `pace.enabled`，关掉就回到原来的「快清零还没用完的往前提」（只看周窗、月窗）。战绩明显差的往后放；样本少时不动。额度没读成（或读数过期）的账号池不挡，但排在读到了的后面，派工原因里写明「额度未知」；读失败本身按第十节报警。**微调只在同一个模型的几个渠道之间生效（标了同一强弱档、挨着的几个模型合成一组时在组内生效，见下面「强弱档」），模型之间严格按用途里排的先后**（#1089，创始人 2026-10-05「如果第一个模型不能用，就选第二个；但也不是说选第二个模型，而是选第二个渠道」）（动手两个用途已被决定 0095、0098 改动：创始人 2026-10-14 授权后按真实战绩重排，2026-10-16 起按这一单的派工档排，见下面的例外；一键关掉是 `routing/policy.ts` 的 `trackScore.byTier` 置 false，或 `trackScore.stages` 置空）：（动手除外，见下）排第一的模型额度未知、战绩差，照样先派它，下面多个渠道时额度读成了的渠道排在未知的前面；只有它下面的渠道都被过滤掉（死了、关着、犯禁令）才轮到第二个模型，后面模型的渠道不会因为微调插到前面模型前面（`routing/rank.ts`）。例外只有动手（写码、界面两个用途，PLAN 3f，决定 0093、0095、0098）：引擎每次选路现算各模型近 14 天、按这一单派工档（快档 / 中档 / 主力档，取 `rt.status.tier`）的第一段动手战绩（`packages/db/src/queries/model-track.ts` 的 `modelTierTracks`：一单只记第一段动手的模型和它的分钟，后面接手返工的段不记在第一个模型名下，也不记到接手的模型头上；只数算路由账的段、到了终态 done / failed / stopped 的单）。质量分是收缩后的下界：m =（一段过 + 4 × 本档平均一段过率）/（单数 + 4），分 = m − √(m(1−m)/(单数+4))；本档平均是这一档全部模型一段过之和除以第一段之和。打了分的模型在它们自己占的位置之间按这个分重排，要比前一个高 0.08 才往前挪；分打平手才比每段分钟，低的往前。不再把一轮做成率低于 15% 的模型挪到最后。这一档没有行的模型留在人排的位置；有钉住的行整段不动；战绩读不成就照人排的先后，理由里写「动手战绩没读成」。`trackScore.byTier` 置 false 就回到决定 0095 第 2–4 条（期望成本低三成才前挪、少于 5 单不动、一轮做成率低于 15% 不进动手，别的都派不了时兜底），取数窗口仍是 14 天；`stages` 置空则模型之间严格按人排。阈值都在 `routing/policy.ts` 的 `trackScore`，理由写在旁边；派工理由里带派到的模型这一档的质量下界，各模型的分变了时引擎记一行日志「动手战绩（选路按它排模型）」。
     **强弱档**（决定 0099，#2614）：模型目录给每个模型标强弱档（`models.strength`：strong / standard / light，目录 `deploy/catalog.json` 独占、装载器每次对齐；没标的照以前）。强弱档说模型多强，派工档说单多难，是两回事。三条，阈值都在 `routing/policy.ts` 的 `strength`：
     - 重活先给强档：动手、派工档是主力档（`strongFirstTiers`）时，强档的模型整体提到别的档前面，档内仍按上面的质量下界和人排的先后。强档某个模型没被硬挡、额度读成了的渠道每一条都超前时间进度 30% 以上（`yieldAhead`，同一个 `quotaPace`，5 小时窗不算；人关掉的、避开的这类硬挡的渠道不算，它们「持平」拦不住让位）时它让位，只在强档之间换：排到不超前的强档后面、仍在别的档前面，理由写「强档池超前 X%（…），让给强档 Y」；强档都超前时照派强档（超前少的在前），理由写「强档都超前，照派」，不让给标准档（#2724）。被挡的照旧被挡：强档全被挡（没额度、熔断、关着）就往下派。中档、快档不受这条影响。
     - 探索：动手、给了派工档时，按单的编号算出 [0, 1) 里的数（`rank.ts` 的 `seedDraw`，同一单重算不变），小于这一档的比例（主力档 20%、中档 10%、快档 5%，`explore`）就把样本少于 5 单的强档模型提到第一，理由写「探索：opus-5.5 重活样本 4 单，少于 5」。让位的不探，战绩没读成不探。小样本的强模型靠它攒战绩（收缩分把三四单的样本拉向平均，靠排序自己挪不上来）。
     - 同档分流：任何用途里强弱档相同、在模型先后里挨着的几个模型合成一组，组内所有渠道按同一模型几个渠道之间那套微调一起排（落后的先用、超前的往后、额度未知的排后），进度打平手按模型先后；不同档之间、没标档的照旧。理由写「与 X 同档，X 的池超前 Y%，先用这条」。开关 `pool`。
     `strongFirstTiers` 置空、`explore` 各档置 0、`pool` 置 false 就回到决定 0098。

## 十、额度与账单

**每个渠道、每个账号池的剩余额度都要读到**——驾驶舱才能管，调度才能规划用什么模型。读法按顺序选：① 官方接口；② 读不到就找它自家网页显示用量的那个接口（MiraQuota 读 Mirasim 就是这样）；③ 再不行按我们自己的用量估，撞到限额就记下上限。驾驶舱上每个数都标明「实读」还是「估算」。订阅到期日也记进来。

两本账，都在 Postgres，一个写入口：

1. **还剩多少**：每个账号池、每个时间窗（5 小时 / 周 / 按月美元 / 点数）用了多少、几点清零、订阅哪天到期。定时读（引擎进程里的定时任务），读失败要报警，不许只写进某个文件就算了（旧系统的额度探针就这样静默失败过）。调度直接看它；驾驶舱「额度表」看它。
2. **花了多少、值不值**：每个会话记模型、路由、token、耗时、所属任务。订阅月费（在驾驶舱设置里填，不进 git）按月摊到任务，算出每完成一个任务的成本、每个订阅浪费了多少额度。驾驶舱「账单」看它。

账号池的实际划分（额度读取 PR #6 在真机上查实）：
- **Claude 订阅**：一个组织一个账号池（`pools.org_kind` 标拼车还是独享）。reclaude 的组织是按设备（家目录）定的，不能按会话选；一个账户最多挂 4 台设备，法国只占 1 台（创始人 2026-09-26），所以两个池共用法国唯一的会话用户，同一时刻只有它挂着的那个池能派。挂着哪个由引擎现读（以会话用户跑 `reclaude org list`，认带 `*` 的那行的类型，第九节「一个会话用户」那条），不假定；会话派到挂着的那个池，额度（会话流里的读数、被拒原文）就记在那个池上，认不出时两个池都不派，不会记错池。拼车用满时按第九节整个用户切到独享，按拼车窗口恢复的时刻切回（#157 已做，由引擎切）；切的那一刻手上的会话先停下、切完接着干（三段在原分支上重跑这一段）。
- **Mirasim 中转**：一份账号额度就是一个池，另有「只扣某一族模型」的窗口。经它走的 Opus、GPT、Kimi、DeepSeek 都扣这个池；codex 也只走这条路，不单独建池，不用任何按量计费的第三方网关。
- **Cursor**：一个池，Auto 和 API 两个桶是只扣对应模型组的窗口。走订阅、没开按量计费、没额外充钱（创始人 2026-09-27 确认）：两个用量池（Composer、Grok 这类 Cursor 自家模型一个，其他模型一个）都在订阅里，用完请求被拒、不多扣钱，失败分流按额度用满（QT1）整池等清零；和创始人自己在编辑器里用的是同一份额度（`specs/212-接第一个别家渠道/方案.md`「花费」）。
- **拼车号的真实上限 /usage 看不见**（2026-09-25 实测）：reclaude 的系统拼车组织对每个成员另有 5 小时上限。/usage 显示本窗只用了 16%，同一时刻真实请求已被拒「拼车 5 小时额度已用完，约 20 分钟后重置」。所以 Claude 池的额度以真实流量为准：会话流里的 rate_limit_event 和被拒原文都记成一条读数（被拒 = 用满，清零时刻取原文），/usage 只作参考。
- **拼车成员上限改读 reclaude 开放接口**（2026-09-25 起）：reclaude 网页「设置 → API Key」生成一把账号级的 Key，`GET /api/v1/carpool/quota` 直接给出这个上限的已用美元、上限、清零时刻，`GET /api/v1/orgs` 给各组织的到期日。拼车池的读法就用它（`reclaude-carpool`）：不起 Claude Code、不看这台机器挂哪个组织，本机、法国都读得到。独享号的用量这套接口不给，仍跑 /usage；/usage 只读得到这个家目录此刻挂的组织，会话用户挂拼车时独享池照实记「没读成」（读取器不为读数切号）。Key 放法国 `/etc/fleet-dao/reclaude-api.key`（进保险箱）、创始人电脑 `~/.fleet-dao/reclaude-api.key`。
- **一个 5 小时窗能干多少活**（同日按会话记录实数，当量按输入 1、缓存写 1.25、缓存读 0.1、输出 5 折算）：拼车号约 3400 万输入当量（14 个会话约 20 分钟用满）；独享号至少 2.8 亿（约 12 个会话撑了 3 小时 20 分），差 8 倍。

**经 Mirasim 起的会话用量从哪读**（#1933 查实、#1935 接上，Mirasim 服务端 0.0.466）：真账是 Mirasim 的用量账本（中转计量），会话结束时的快照只是近似。

- **上线前没有会话号的老记录只补一次**（#1948）：#1946 之前结束的 run 没记 `session_id`，上面那个定时任务对不上账本。一次性命令 `fleet-api usage-backfill-once`（`packages/engine/src/jobs/usage-backfill-once.ts`，默认只读列出要改的行，`--apply` 才写）按分支名最后一段（工作树目录名）加这一笔的起止，对上用量账本里 `workspace` 目录名相同、调用时刻落在起止之间的会话。对上唯一一个会话，才把还空着的输入、输出、缓存读、缓存写、花费补上；已经有的数、已经有的 `usage_note` 一律不动，也不写会话号（写了会被定时任务整套覆盖，快照里的输出就没了）。对不上、同一段时间对上不止一个会话、同一个会话对上不止一笔、还在等回填或行认不出的，只在 `usage_note` 写原因，不猜。同一分支（`workspace` 目录名相同）里有一行时间认不出的，不能把它丢掉再当成只对上剩下的会话：判不了这行落不落在这一笔的起止之间，也就不能排除它是另一个会话，这一笔不补，原因写明时间认不出。补不齐的就是这几类。不是经 Mirasim 起的、已经有会话号的（交给每 5 分钟的用量补记）、四样 token 已经齐的、结局不是 done 的，这次不碰。再跑一次，已经写过的行不会改。法国库上由 fleet 用户跑这一次（`fleet-api` 换成 fleet 身份、本机 socket peer 认证）：先只读，能补几笔、对不上几笔写进 #1948，再 `--apply`，抽 10 笔和账本核对后把结果再写进 #1948。对不上而只写了原因的，就是上面那几类。
- 流量账本 `~/.mirasim/traffic/<会话>/index-*.ndjson` 每行没有 token 字段，只用来核走了哪条上游（MS-27）。

## 十二、卡住与自愈

- 采用 windsurf-dao 2026-09-24 的盲设计结论（windsurf-dao 仓 `docs/decisions/2026-09-24-agent-isolation-and-error-routing.md`）：
  - 错误先认结构化信号（状态码、退出码、原因码），再认已知文本；认出是哪一种打断原因，按那一种的处置办（#1072 瘦身，依据 509 §九「重试不判、按表办」、0010 第 7 条）：

    | 打断原因 | 怎么办 | 总次数上限 | 最长等待 |
    |---|---|---|---|
    | 我们自己停的（切号、发布暂停和排空） | 马上接着干，不记账 | 不设（停几次续几次） | 0 |
    | 额度用满 | 歇到额度清零时刻再来：读到上游给的清零时刻就用读数，没读到（或读到的已经过了）按估计 15 分钟起翻倍，原因里写明是估计；Claude 订阅池回去选路等（切号会换池） | 重试次数（默认 2） | 6 小时，超了停下报人 |
    | 限流、繁忙 | 按上游给的时间（Retry-After、原文里的「N 分钟后」）再来；没给按 1 分钟起翻倍 | 重试次数（默认 2） | 6 小时，超了停下报人 |
    | 临时的（网络、上游出错、进程被杀、起不来） | 原路重试：AI 会话 1 分钟起翻倍，不绑路由的（建树、推分支、开 PR）15 秒起翻倍 | 重试次数（默认 2） | 10 分钟一次 |
    | 返工（测试红、合并冲突、没交付） | 退回会话去改：续上一轮的会话、只补返工意见（下面「返工少花 token」） | 返工轮数（默认 2） | — |
    | 只有人能修（没权限、配置不对、缺材料） | 停下报警，写清原因和修法 | — | — |

    超任一个上限，或原文和上一次一字不差（重试不会变），就停下报人；停下的原因里写「已重试 N 次」。要停下之前，下面「停下之前先自动处理一次」列的几种先自动换一条路由再来一次（轮数用完、连着两轮没提交才整族避开；超时、起不来、中转欠费按失败原因避开，不整族避开）；其余没有「换路由、换模型」这一级。#1118 的运行中换渠道在 2026-10-06 拿掉（创始人「都按照你推荐」），重试用完就停下，熔断照旧。一条路由病了由路由熔断（`packages/engine/src/failure/breaker.ts`）让选路绕开，要人修的整池问题整池暂停。登录失效、封号、设备被撤销停的是池不是这张单：池暂停并报警，单马上回去选路避开这个池；只凭一次 HTTP 401 先换路由，同一个池短时间里第二次才停池（时刻所有任务共用，不单记在这一张单里）；避开之后没有能派的路由才挂起（原因「能派的池都停了」）。老历史没有 `patched('auth-reroute')`，仍把这张单挂起；
  - 认不出的按「临时的」办一两次再停下报人，缺原因的单独标出来数。
  - 分档冷却（决定 0093，借 magpie（github.com/yetone/magpie 的 gateway-routing 文档「不同失败分开歇」、gateway/routing.go 的 failureOf、Rest））：额度、限流繁忙、其他三档分开定歇多久，不并成一档（上表三行）；分流结论带 `cooldown`（哪一档、按读数还是估计），原因里照写。
  - **有界耐心**（决定 0093，借 magpie 的 Patience：全忙时有预算地再试，代替直接报错）：动手会话撞上上游临时故障（规则表上标了 blip 的：限流、繁忙、容量满、503……）、重试次数用完要停下时，先不停：歇 15 秒起翻倍（封顶 30 秒）、不粘原路由重新选一次再起，从第一次该停下起最多 60 秒（`ROUTE_PATIENCE_SECONDS`，上限 240 秒），歇掉的从这一段的会话时限（60 分钟）里扣；用完照旧停下，原因里写「耐心等待用完（已等 N 秒）」。任务进度每歇一次写一行。
  - **同一张单不并发两段**（决定 0093）：动手会话原路重试、自动重派、耐心再起之前，先问 `segmentSettled`（`real/segment-resume.ts`：这张单从这一段起跑以来最近的动手那一行收场了没有，没收场最多等 20 秒）；没收场就停下等人，写明「上一段会话还没收场，不起第二段」，不起第二个会话。问不成（库一时不通）只记日志，照今天的做法接着走。老历史（没有 `patched('route-patience')`）不问、不耐心等，照旧。
- **停下之前先自动处理一次**（决定 0093；法国库 14 天卡住 114 次、205 小时，大头是人只机械点「继续」的）：下面几种不先停下等人，自动处理一次，任务进度（库里的 doing）写一行做了什么；再撞上才停下：
  - 动手 3 轮或验收 2 轮用完：这张单头一回用尽，不停下，轮数清零、重读单子，下一轮动手避开最近动手的那个模型和它那一族（作者族按 `authorFamilyOf` 认，目录记成 unclassified 的按模型 id 开头再认一次，认不出的只避开模型；同族换个模型多半重蹈覆辙），记进这张单的避让，和没提交的避让同一处；别的族一条都派不出就退回只避开模型（同族换一个），还没有别的候选就照旧派原来那条，带着返工意见或验收意见接着做；动手轮数用完的直接再动手，不先重走 CI 和验收。这一次算进「继续」的累计上限（`MAX_ROUND_RESETS`，3 次）：之后再用完照旧停下等人，点「继续」再清零，累计超过 3 次交指挥官。交指挥官之后「继续」不再清零：命令行 `task continue` 和驾驶舱「继续」都拒绝，写明「继续次数已用满（N 次），继续无效；要重开用 redo」（`continueExhausted`）。`task redo` 遇到上一代还停在 parked（或已经在收尾放弃）会先叫停、等到工作流终止再另起，真在跑仍拒绝。新一代开 PR 时，上一代自己留下的开着的 PR 关掉并评论「被第 N 代重做取代」，别人开的 PR 仍挡住（`ISSUE_CLAIMED`）。
  - 动手一轮跑完没有提交（#1408）：下一轮避开这条路由；连着第二轮还没提交，再避开这个模型和它那一族（同上，别的族派不出退回只避开模型），返工意见写明避开了什么。动手阶段整族避开派不出时，选路的话写「换一族没有能派的路由」，不说冷验收那句「只派别家」。带着整族避让去选路，回的是等额度或等空位：先放掉整族避让再选一次，别族在线的路由照常派，还派不出才等（#2261，`patched('avoid-scope-by-cause')`）。
  - 动手会话被引擎在时限上叫停（`aborted`，跑满 60 分钟）、总时长到顶、起不来（`spawn_failed` 这类）、中转这一路额度用完或欠费（`relay_quota_exhausted`，失败分流 QT3：中转把欠费通知当回答回来，Mirasim 插头认整段回答，#2249）：失败分流判停下时，这一段先换一条路由重派一次（`workflows/task-session.ts`）。超时、起不来只避开这条路由，同一模型第二次再避开模型；中转欠费避开那个池。都不整族避开（#2261，`patched('avoid-scope-by-cause')`）——这些跟模型能力无关，整族避开会把别族在线的路由也挡在外面。老历史没有这个标记，仍避开这个模型和它那一族。总时长到顶第一次仍原路续同一个会话（这一次记下了执行编号就问 planSegmentResume，下一轮带 resumeSessionId 起；没有编号，或老历史没有 patched('wall-clock-resume-session')，就只钉原路由）；同一张单、同一条路由上第二次不再原路续，换路由时提示词带上树上的进度（接着做，别从头重来）。这条路由在这张单上只是慢，再续只烧额度。换路由那一步选路若只剩等额度或等空位，不进最长约 4 小时的长睡（那一睡不写任务行，工作流仍 Running、没有开着的会话，拉单把它算进在干活）：当场停下等人，写明选路在等什么；点「继续」再选一次，选得出就起会话。已经睡在这一步里的老历史，`fleet-api task continue` 和驾驶舱「继续」同时发 taskRouteWake 把它叫醒，醒了同样要么起会话要么停下。看门狗每 5 分钟查 running、executor=engine、没有 ended_at 为空的 runs、任务行超过 20 分钟没动的，报一条，条件没了自己撤。
  - 推分支报空交付（起会话前的头之后没有新提交）：这张单里先自动再派一轮动手（返工意见写明要 git commit），再撞上停下。
  - CI 的结果没查成（不是 PR 被关了、不是强制 CI 的仓根本没配检查——那要人去配）：隔 2 分钟自己重查，最多 2 次，再停下（`workflows/task-ci.ts`）。
  - 推分支被卫生检查拦下（`hygiene_blocked`，`patched('hygiene-blocked-handoff')`）：不在推这一步里原地重推。命中处（文件:行 规则，不带命中的原文）退回下一轮动手会话；同一处连续被拦、会话改过仍一字不差，才停下等人。老历史没有这个标记，照旧在这一步里重推，第二次一字不差就停下。没有 workflows 权限、token 预算超了、改标准、交代不全这些要人看的照旧当场停下。
- **首轮少熟悉仓库**（决定 0093；首轮会话第一次改文件前要花 50–57% 的时间读仓库）：新开的动手会话（不是续的）起之前，引擎以会话用户从工作树读出单子「已知的模块」里写成具体文件的路径（目录、通配不展开，最多 20 个），原文放进提示词「已给你的文件（别再读）」一节，合计上限 6 万字，按单子里写的先后放，截了哪些、没放哪些、哪个不在逐个写明（`runner/preload.ts`）。会话用户家里不装通用 skill（`agents-sync --no-skills`，见 ops 第五节）：grok、cursor 起的会话一启动就去读家里的 SKILL.md，和单子无关；提示词里也写明别去读。
- **返工少花 token**（决定 0093；返工轮花掉动手 token 的 47%，一轮约 463 万缓存读，`packages/engine/src/workflows/task.ts`）：
  - 返工续会话：CI 红、验收没过、合并冲突、没交付这些返工，下一轮动手续上一轮跑成的那个会话（同一棵树、同一个执行方式、同一个账号池、同一个会话用户，和暂停后继续同一个判法 `real/segment-resume.ts`），提示词只补返工意见（CI 失败摘要、验收理由），不重述整张单；续不上照旧开新会话，进度里写明为什么。连着两轮续着改还没过，下一轮开新会话，返工意见精炼过、第一行写明为什么清空重来。轮数用尽点「继续」重读单子后也开新会话。
  - 交活没提交续一次（#2722）：会话收场时没有新提交、或树里留着没提交的改动（常见是把测试丢到后台就结束了回答，一次性会话收不到后台回调），读完交付先续同一个会话一次，让它在前台跑完、提交；不算一轮，一轮只续一次。续不上（同上判法）不在这一轮另开会话；续了还没交干净，照旧按「没提交」返工进下一轮。提示词也写明不许把命令放到后台再结束回答。
  - 每轮收场记进库（#2762，`patched('round-outcome')`）：每一轮返工、合并、停在一轮里被放弃叫停时，任务工作流写一行 `task_rounds`（怎么结束的：做成、冷验收拒、CI 红、交活有剩、没提交、推分支冲突、等合并冲突、超时、叫停、别的；档位、首派模型、最近一次推上去的头相对主线的新增行数），记不成只写日志不挡原流程。每日简报新加的流程健康这部分按它算近 7 天的总轮数和各类占比、按档一轮做成率（这一档收场的轮里做成的占比）和合并的平均轮数、重活 PR 新增行 p90、冷验收拒绝占比，和再往前 7 天比涨跌；读不到写「没查成」（`packages/db/src/queries/pipeline-health.ts`）。另有一行「发版叫停的动手会话」（#2797，`releaseKilledSessions`）：近 7 天动手段里被发版停下的段数（按北京时间每天的数、一共跑了几小时，和再往前 7 天比）。认三种：排空到了宽限截止按切号那一套停下（`org_switch`、原因以「发布排空：」开头）、引擎按 `StopReason('release-pause')` 叫停（「引擎叫停（发版暂停…」）、引擎停机时 Temporal 取消了还在跑的活动（「引擎叫停（其他：CANCELLED）」，Mirasim 上不脱开的会话就是这样没的；法国 10-10～10-16 这一种 47 段，结束时刻全落在某次发版前 20 分钟到后 5 分钟里）；这一行读不到写「没查成」、这一轮记 partial，别的行照写。
  - 重活先出方案、有体量预算（#2755：近 7 天重活一轮做成 18%、PR 新增行 p90 7117）：heavyweight 的第一轮先跑一段只读会话（`patched('plan-first-heavy')`），规矩照给，最后一条回复只回方案 JSON（改哪些文件、预计新增行数、对应哪几条验收）；格式不对续进同一个会话重出一次，还不对照常动手、不停下；认下了方案带进意见，动手那一段续这个会话。推之前看交的头相对主线新增几行（`Limits.prLineBudget`，默认 3000，0 = 关，开工时解析一次进历史；`patched('pr-line-budget')`）：超了第一次打回让会话收窄（意见带上方案估的和方案外改的文件），收窄过还超就停下等人并附按改动面分组的拆单建议，人点「继续」照这一版推、这张单后面不再按预算打回。没量到新增行（老历史、没数成）不判。
  - 冲突引擎先自己并：上一轮因和主线冲突返工、树里没留冲突标记时，动手前并最新主线（git 自动合并）并干净了就直接推上去重跑 CI（不强制 CI 的仓就再合一次），不派模型、不算一轮（最多 3 次）；并不干净才交给会话解。锁文件这类机械解法还没做。
  - 引擎自测：会话交活、交付核对过了，推之前引擎以会话用户的身份在会话的树里跑仓的测试命令（`repos.test_command`，fleet-dao 是 `pnpm test:changed`，只跑改到的）和 tsc（`tsc -b`，树里有 tsconfig 和装好的 tsc 才跑）（`real/self-check.ts`）。红了把精炼输出（失败的行加末尾一段，4000 字以内）续进同一个会话再改一次，再测一次就推，不论红绿交给 CI；测试 30 分钟、tsc 5 分钟为限；普通那次超时、没装依赖记「没跑」，不算红。`test:changed` 判要全跑（退出码 3）时不跑全量，改在整机同一时刻只跑一个的锁下跑受影响的包（`pnpm test:changed --affected`，排队和这一跑合用这 30 分钟），超时记「自测超时」、算没过。没跑成不挡原流程。最近一次的输出交给冷验收当材料（只给和要验的头对得上的那份）。只要求测试、检查、构建或类型检查通过的验收条不靠这份输出核对，归合并闸的 CI；输出里明确写了失败才写成问题。
  - 单任务 token 预算：每次起动手会话之前查这张单当前这一代的动手、验收会话合计花掉的 token（输入、输出、缓存读、缓存写四样相加；重做另起的一代从它自己的开工时刻算起，不背上一代，点「继续」多给的份数也按这一代），超了预算就停下等人，写明花了多少、预算多少；点「继续」再给到够用。四样还空着的行（被叫停、超时杀掉、中转用量还没补）按这张单记到用量的行的每分钟速率估一个下限一起算进判断，写给人的话里分清多少是量到的、多少是估的——不然一张单反复被叫停可以一直换会话、账面一次都不超。默认 700 万（`packages/engine/src/limits.ts` 的 `DEFAULT_TASK_TOKEN_BUDGET`，可在上限里改，0 = 不设）：**按输入当量判（#2859）**，权重是 shared 的 `INPUT_EQUIVALENT_WEIGHTS`（输入 1、缓存写 1.25、缓存读 0.1、输出 5），驾驶舱单子页「输入当量」那一格同一个数。法国库 2026-10-16 查近 14 天 346 张单，每张单所有会话的输入当量相加，p95 是 6,715,274，取整到 700 万（p50 161 万、p99 1127 万）。原先四样 1:1 相加让续会话越多越早撞线（缓存读占 94%），#2830 改成缓存读乘 0.1 的「折算 token」后上限 3700 万没跟着改、永远碰不到，#2859 并回输入当量。当量只在 `taskSpend` 活动里算（`packages/engine/src/task-spend.ts`），结果带原始四样和 `inputEquivalent`；工作流判超没超用 `inputEquivalent`，#2830 记下的老历史里是 `weighted` 就读 `weighted`，更老的只有 `tokens` 就读 `tokens`，重放判法不变（没动步序，不用新标记）。某一样读不到折不成当量时不给 `inputEquivalent`、不拿 0 顶。停下等人的话写输入当量用了多少、上限多少，原始四样另列；驾驶舱把预算用量写在「输入当量」那格的小字里；每日简报「每合并单」按输入当量给，原始四样相加另列。开工早于这一版的任务不查。
- **合并后等发版那一段记进 `step_timings`**（决定 0093）：合并到上线是整个流程里最长的一段（中位 91 分钟），但它不是工作流里的等待（没有哪个活动在等部署），工作流里量不到，原先只有发布那一侧的日志。现在由后端补记（`packages/store/src/release-waits.ts`，随后端起、只在生产起，每 5 分钟一轮）：读发布历史（`/srv/fleet-dao-releases/.history`）和自动发布状态里的主线提交表，对近 7 天合进主线、还没记过的合并提交，取「第一版带上它的那一版切上去的时刻」（按提交在主线上的前后位置判，回滚也算切上去的一版；判不出来不记，不拿时间先后猜），写一行 `kind='wait'`、`wait_for='release'`、`temporal_run_id`=合并提交、`started_at`=合并时刻、`ended_at`=上线时刻的 `step_timings`（`detail` 写清哪个 PR）。记过的按合并提交去重，同一笔不写第二遍；合并时刻比上线时刻还晚（钟差）记 0，不记负的。
- **定时指挥官会话**：定时起一个 Opus 5.5 会话，每次只干一件事：诊断卡住的任务、写日报、调整调度台。停下等人只剩人闸一种情况。它和创始人对话的指挥官（技能 `agents/skills/commander`）是两回事：指挥官就是创始人正在对话的那个会话，不设座位、不在库里认领（决定 0074）。

- **定时指挥官会话的权限**：能自己调路由先后、下架连续出错的渠道；每次改动写明理由、推飞书、驾驶舱一键撤回；创始人手动钉住的顺序它不动。

## 十三、高可用与高响应

- **高响应**：GitHub 事件经 Cloudflare 几秒内到引擎（旧系统 10 分钟轮询一次）；驾驶舱实时推送，不用刷新；驾驶舱上的操作是发给工作流的信号，立即生效。驾驶舱的接口经香港转到法国，一趟往返约 0.2 秒，所以香港到法国的连接留着复用（ops 第八节），首屏的读取和确认登录一起发、一轮发完，不排成「登录 → 仓列表 → 看板」一个等一个（`packages/web/src/test/first-screen.test.tsx` 按轮数核对）；连上推送时的全量重拉不打断正在读的。
- **高可用**：服务挂了自动重启（干净退出也重启）；Temporal 保证任务断电重启后接着跑；法国失联由香港探活（每分钟探法国 `/healthz`，连续 3 次不通推飞书，ops「香港探法国」）看，香港由本机巡检看（#2369 删了一直没部署的外部看门狗 Worker，同一件事不留两个判的人）；每晚备份（去向见 ops 第十一节「备份与恢复」）；两台各自一条命令重建，最坏半小时恢复。
- **资源**：每个 AI 会话一个资源上限（沿用 windsurf-dao 2026-09-24 决定的 cgroup 做法）；准入看内存和压力，不看整机 CPU。

## 十四、安全

- 公开仓 + 互动限制「只限协作者」（每次最长 6 个月，引擎自动续）；引擎只认白名单作者的任务和评论，防止陌生人往任务里藏指令。
- 密钥、账号、组织编号、代理地址放机器本地配置，不进 git；加密副本在私有仓 fleet-dao-vault（决定 0069）。仓根 `.gitignore` 另挡密钥文件名，多一层保险。

## 十五、驾驶舱

> 驾驶舱按三段一条龙和「在跑的＝卡在哪一环＋在等谁」显示（`specs/509-需求梳理/流程重做方案.md` §十一）；提需求页见决定 0090 和 `specs/2047-提需求/方案.md`。

两块：**看板**（极客、易懂、强大）+ **后台管理**（常规）。两块都要做到尽善尽美。

- **法国没应**（2026-10-15）：香港 nginx 对 `/api`、`/auth`（含 `/api/events`）自己造的 502/503/504 回固定 JSON「驾驶舱后端暂时没应，它所在的机器可能在重启或关机」，不回网页。登录页和外壳遇到这类（含浏览器根本连不上）多一个指向 `/health/` 的链接。后端自己回的、带 code 的 503 原样显示；别的页面上的其他错不改。

### 15.1 看板

补充提议（画布 `/board` 上的设想，不排期：主页以上面三块为准，要做下面哪条就开单）：

- **按项目切换（已定，创始人 2026-09-26 从「按仓」改成「按项目」，15.7）**：看板一次看一个项目，顶上切换，每个项目的全局任务树就是首屏；另有一页总览看全部项目（隐藏的项目不进，有等你拍板的除外）。首屏另有「走向」一栏（15.6）。

### 15.3 提醒

驾驶舱提醒中心 + 飞书，分三级：要人拍 / 卡住报警 / 日报。点提醒直达对应页面。等你拍的讨论也在「要人拍」里，点开直达那条讨论（15.5）。改标准的 PR 也进「要人拍」，1 天、3 天没点再提醒（第五节「人闸第四类：改标准」）；隐藏的项目不进提醒，等本人拍板的除外（15.7）。

**「要人拍」必须带选项加自己输入**（#1915，创始人 2026-10-12：「让用户拍的时候，你要给用户选项，让用户点击一个选项或者自定义输入内容……而不是说只是单单的一个确认」）：

- 产生 decision 级提醒的地方都给选项：至少两项，每项一个按钮上的字、一句选它会怎样，恰好一项标推荐并写理由（`packages/shared` 的 `DecisionOptionSchema`、`decisionOptionsProblem`；落库前 `upsertAlert` / `insertAlertOnce` 再核一遍，decision 级没带选项、带了认不出的动作都照抛）。外加一个自己输入的框。现有几处：人闸待批（`approvalOptions`）、整池暂停（`poolHoldOptions`）、机器人没装到仓（`githubAppMissingOptions`）、飞书推送不通（`pushWatchOptions`），都标「只有人能做」。
- **库层强制**（#2729，决定 0097：只为掏新钱、删找不回的东西问创始人）：`notifications` 上两条 CHECK（迁移 0084）——decision 级必须带至少两个选项、带原因 `decision_reason`（`new-money` 掏新钱、`irreversible-delete` 删了找不回、`human-only` 只有人能做，`packages/shared` 的 `DECISION_REASONS`）；原因只给 decision 级。统一写入口 `upsertAlert` / `insertAlertOnce` 落库前先核原因（`decisionFieldsFor`），没写原因照抛「AI 自己能做的写成卡住报警或直接做掉」。AI 自己能做的不进要你拍：工作流挂起、返工用完记卡住报警（引擎 `store-ports` 的 `raiseAlert` 一律 alert）；残留工作树里剩着没推的东西照决定 0097 直接删（每小时对账，见第十四节）。法国上的发版脚本写提醒走 `fleet-api notify raise`（经 `upsertAlert`，只收 alert、daily），不直写表。迁移先把旧的没有两个选项的 decision 行降成 alert，再加约束。
- 补不出选项的，页面写明「没有选项，请直接回复」（`NO_OPTIONS_TEXT`）并给输入框，不静默退回单纯确认。老通知没有选项，照旧显示。
- **选完系统照着做，结果写回卡上**（#2353，创始人 2026-10-16：「只让用户填写或者选择，而不是点击 已处理了，这解决不了问题」）：每个选项带一个动作（`DecisionActionSchema`：删工作树、留着、整池暂停/放开、重查 GitHub App 或飞书推送、把仓移出受管、只留言；老数据没写的按只留言读）。点选项或输入后（`POST /notifications/:id/answer`），先把答案（选项的字或原文、时刻、谁）和操作记录存下，再由 `packages/api/src/decision-actions.ts` 按动作做，结果（成没成、一句话、时刻）写进答案（`answer.execution`），做成了、选的又不是要留着的项才转已处理；没做成卡留着、写原因、可以再选。删工作树要 sudo 调 `fleet-agent-scope`，后端提不了权，所以只记「交给引擎」（`execution.queued`），由下一轮每小时对账的工作树那一段删、再把结果写回（`settleQueuedDecision`）；#2729 起残留工作树直接删、不再报要你拍，迁移 0084 把开着的旧卡降成了卡住报警，这条路只剩兼容。通知中心的「要你拍」卡上直接摆选项和「自己写一句」，没有「处理了」。再报（原地重开）清掉上一次的答案。
- 自己写的、只留言的交给指挥官（创始人 2026-10-12 01:57：「用户拍完之后，就应该交给指挥官去处理了」）：往进度单 #1055 记一条待处理的创始人引导「创始人已选：<选项或原文>（通知 <id>）」（无主，开会话钩子和 `pnpm progress read` 读得到；指挥官接手时 `pnpm progress directive --from-inbox <评论号>` 把它搬进仓、挂一张单，之后办没办完看那张单）；通知挂了任务的，给那张单也留一句。卡上写「已转给指挥官」。法国上走引擎机器人的 `commentIssue`，没接上、没写成的照实回在 `handoff` 里，卡上写没做成和原因，不冒充交出去了。
- **不许有假选项**（#1931）：每个选项的说明写的就是选了之后真发生的事——系统自己做的（转已处理、池子放开、这棵树不再提醒）照实写，系统做不了的写明「记下交给指挥官去办」。开着本身就起作用的提醒（整池暂停 `pool-hold:<池>` 开着池子就停着）：「先停着」把这个池写进整池暂停开关（`engine.poolHolds`，探针探通也撤不掉）再转已处理，「修好了，放开」拿掉开关再转已处理；还没想好的那类（「这个池不要了」「先看看里面」）带 `keepsOpen`：交给指挥官，提醒照旧开着（`answerResolves`）。这条有要留着的选项时，自己输入的也留着。每个选项的效果有测试（store 契约、`store-ports.test`、`hourly-reconcile.test`）。

提醒不是推一次就完（09-26 查断链：法国上两条提醒条件早没了，挂了十几个小时没人撤），由每小时对账（`hourly-reconcile`，第六节「断链怎么被发现」第 4 条）补两处：

- **条件没了就撤**：能现判条件的——挂起（工作流不在跑了、不挂着了、那一次挂起早过去了）、事件数到线（工作流结束了）、需求没做完（需求不再是没做完）、要人批（批了、拒了、在等它的子任务或 Fusion 工作流不在等了）、工作树没收掉（子任务的、Fusion 的都算：树删了、不在了、改成要人拍了）、全熔断（`routing:all-open`：阶段里有路由不熔断了）——每小时现算一遍，条件没了就撤：正文开头写「已撤：为什么」，处理人记 `engine:hourly-reconcile`，操作记录里也有一条。条件还在的原样留着。「某阶段没有能用的路由」挂着时路由恢复了：任务还挂着等人点「继续」，这条留着，正文开头写一句「路由已经恢复…点继续就接着干」。本来就会自己撤的（整池暂停、会话用户切号那几种 `session-org:*`、流程配置、发布落后、自动发布、备份）不在这里判。**过期兜底**（2026-10-06，母单 #1121）：以上都不管的提醒（没有判法、别处也不撤，比如已删机制留下的老键、`<工作流>:failure:…` 这类「发生过」的通报），最近一次被再报（`updated_at`）过了 3 天，就标「已撤：过期」（写处理时刻、原因，记录不删；条件还在的话报警者再报一次会重新打开）；要人拍的（decision）、别处自己会撤的（`SELF_RESOLVING_PREFIXES`）不碰。各种提醒谁来撤，清单在 `packages/engine/src/jobs/alert-sweep.ts` 开头。
- **没人处理的再推**：卡住报警超过 24 小时没人处理，每天最多再推一次——另写一条「还没处理：<原标题>」，驾驶舱弹一条、飞书发一张新卡（原来那张只会原地改，早沉在群里了）；原来那条处理掉，它跟着撤；在它上面点「处理」也算处理了原来那条。要人拍的不在这里再推。键以 reconcile:pr:、reconcile:ledger: 开头、对应 PR 已合并超过 7 天的，不再每天重推（沿用静默：驾驶舱留原来那一条，不发飞书卡）。日报还没做（定时指挥官会话写日报，第十二节），在它之前没人处理的卡住报警只靠再推和立案。同一条再立案（#1406）：还开着、超过 24 小时、没人处理、没静默、不是自己会撤的，开一张未排期的缺陷单（每次对账最多 2 张、每个仓每天最多 4 张），单号写回提醒正文开头；同一键只一张，那张关了而提醒还在，隔 7 天才再开。reconcile:* 条件没了由核对撤掉，还开着的立案；看门狗、备份这些自己会撤的不立案。例外（#1420）：键以 reconcile:pr:、reconcile:ledger: 开头且对应 PR 已合并超过 7 天的不立案——说的是已经发生、改不了的历史事实（当时没经合并队列合，或记账当时缺了），开单没有能做的事。合并未满 7 天的仍立案；合并时刻读不到的不跳过，记没查成。立案前再自检：单的「怎么算做完」只有「提醒的条件不再成立」一条、且类别不在自己会撤的清单（SELF_RESOLVING_PREFIXES）里，不开单，提醒正文写「没有可做的事，已跳过立案」。
- 判不了条件的只靠再推：换池接着干这类通报（条件就是「发生过」，要人知道）。全熔断（`routing:all-open`）由每小时对账判，阶段里有路由不熔断了就撤。
- **谁在处理（只给驾驶舱看；「提醒派单」那一层已经删掉，#445）**：创始人 2026-09-27 夜拍过要标上谁在处理（`specs/169-Fusion形态/需求.md`「帅位改回只一个」第 5 条，原话「提醒标上谁在处理……更类似于一个派单状态的东西」），照 PagerDuty、Opsgenie、Alertmanager、k8s、Sentry/GitHub 的做法做过一版「提醒派单」：定时任务每 5 分钟一轮，没人认领 20 分钟推一条「没人认领」、没挂单的同一轮自动开一张跟进单，有人认领了停一步 60 分钟再推一条「停着没动」。跑起来发现这套本身比它要挡的噪音还吵（自动开的跟进单没人看，比如 #428；`reconcile:pr:<仓>#<号>` 这类没人处理的提醒堆着），2026-09-28 创始人拍「过度的部分全删掉，改到最干净」（`specs/169-Fusion形态/需求.md`「删减清单全按帅位的做」第 3 条），把这一层整个删掉：不再自动开跟进单、不再要求认领、没人认领和认领了停着都不再按分钟再推——提醒只进驾驶舱和日报；主线红、生产挂这类头一次报还是照样推一次飞书（那是提醒第一次建卡时的推送，跟这里删掉的按分钟再推是两回事，design 15.4）。
  - **跟进单**：要修的提醒历史上可能挂在一张单上——提醒挂着任务的就是那张单，或者是当初「提醒派单」自动开的、指挥官当初 `alert claim --issue` 挂的（这两条路都删了，`alert_work` 表里只剩历史数据，不再有新的）。
  - **谁在处理 = 跟进单上的认领**（历史；座位和认领账已删，决定 0074），不另记一套「谁在看」。引擎自己的认领不算：提醒是引擎自己搞不定才报的，单列「引擎拿着、它自己卡住了」；本机接手要创始人说改派。
  - **修到哪从真实记录现算**（`packages/core/src/alert-work.ts` 的 `alertHandling`，只喂给驾驶舱看板）：已静默 → 修复的 PR（正文「修提醒」栏写了提醒的键，或挂了跟进单：需求栏、关单词；外加认领登记过的）开着 → 合进主线 → 法国已发布（合并提交在法国在用那版的主线第一父链上，读自动发布的状态文件；判不了写明没查成）→ 本机认领了 → 等创始人拍（要人拍的）→ 引擎卡住 → 没人在修。每一步带进入的时刻，「多久了」从它算。PR 镜像在 PR 事件和对账补收时记下正文的链接、开的时刻、合并提交（`packages/github/src/events.ts`）。

### 15.7 项目与标准（创始人 2026-09-26 拍，选项 1）

驾驶舱最顶层从「GitHub 仓」改成「项目」；fleet-dao 放一份「标准」，每个项目、每台机器都照它对齐。分五步做，单号见本节末「分步」，先后以当前版本里程碑说明里那段为准（pnpm plan 看）。

**一、项目**

1. **一个项目就是一个代码仓**：一对一，创始人明确不会拆仓。项目名默认用仓名，可以加备注。仓标明来自哪个平台（现在是 GitHub，以后有 GitLab）；认仓认平台内部的编号，不认名字——仓改了名、转了主人照样认得；同一个仓不许导入两次。
2. **导入**：新项目在本机一条命令 `pnpm project add <owner/仓>` 做到底（#2749，`packages/conventions/src/project.ts`）：登记进驾驶舱、把两个 App 装到这个仓、对齐流程标签、写仓档案、开补齐 PR、检查全绿才打开「让 AI 接活」、开一张冒烟单。驾驶舱不再走浏览器 OAuth 装仓、不再存用户令牌（`github_tokens` 已删：那条从上线起没成过，App 用户令牌会过期且不存续期令牌）。设置页的导入列表用两个机器人的安装令牌读 `GET /installation/repositories`，只列出已经装上的仓，用来看装没装全、在不在驾驶舱；还没装上的仓不在这张表里。GitLab 仍是以后再做（分步⑤）。
3. **谁能看、谁能动**：导入的人是项目主人。可见范围两档：只有我 / 团队都能看，新导入的默认「只有我」。能看就能操作，所有操作进操作记录；碰人闸的拍板只推给项目主人。
4. **一张项目列表**（不分成几块）：隐藏是一个开关，团队分享是一个标签，先后靠拖动排序，列表能筛选；增删改查都有。「移除」只是从驾驶舱里拿掉，仓本身不动；历史留 30 天，期间能恢复；到期真删之前先问创始人（删数据是人闸）。
5. **隐藏的项目**不进总览、看板、提醒；但有等本人拍板的事，照样出现在总览里（标「有待你拍板」），也照样推送。
6. **导入不等于开工**：导入后 AI 不动手，「让 AI 接活」开关默认关（第九节「在哪能做与接活开关」）。标准里「缺了就不能开工」那档没补齐时开关点不动（下面第 10 条）；引擎每次真正派活之前再查一遍达标没有，防止抢跑。
7. **总览和看板**：总览一页看全部项目，看板一次看一个项目、顶上切换（15.1）。（原先飞书里「一个仓一个项目群」的说法，随飞书收话一起删了，见 15.4。）成员身上记的平台账号这次不改，接 GitLab 时再做（分步⑤）。

**二、标准**（自上而下推、自下而上提，是同一套机制）

8. **一份带版本号的标准，推两类对象**：
   - 机器：通用规矩（AGENTS.md 通用段）、skill、钩子、命令行工具——由现在的 agents-sync 扩出来。钩子（`agents/hooks/`）2026-09-26 查断链时补上：开发机开会话时，开会话钩子拿一份**只归同步工具的检出**（`~/.fleet-dao/origin-main`，永远停在 `origin/main` 上，本机自己的检出在哪个分支都不影响它）切到主线、跑一遍 agents-sync，规矩、技能、钩子自己跟上（2026-10-01 改成这样；原来是拿本机自己的检出快进 main，主检出停在功能分支上就同步不了）；`agents-sync --check` 报这台同步到哪个提交、落后主线几个，同步不成时会话里明说（怎么装、装给哪几家见 ops 第五节）。往后改成只认主线发布、签过名的标准版本：按版本装、报到驾驶舱、一键加电脑、卸载还原、坏版本自己退回（创始人 2026-09-27 拍，排在 v1 之后；方案见 `specs/195-项目与标准/方案.md`，单 #239）。
   - 两类走同一套：体检（只查不改）→ 补齐（机器上直接装；仓里开 PR，不直接改主线）→ 每天复查，报「落后标准几个版本」；引用断了也算不达标、照样补。个别项可以豁免，但要写理由。
   - 每个项目的体检有状态：发现 → 补齐 PR 待合 → 已合 → 复查通过 / 复查失败 / 已豁免；同一个事件重复来只处理一次。驾驶舱能看体检结果、一键补齐。
9. **仓里的标准项全部必须一致**，按能不能引用分两种做法：
   - 能引用的就引用，不往各仓抄：账号下的 `.github` 仓放 GitHub 自带的默认社区文件（PR 模板、开单表单等）——这个仓必须公开；仓自己有同类文件时以仓自己的为准；标签不跟着走（[GitHub 文档](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/creating-a-default-community-health-file)）。CI 用可复用工作流，引用 fleet-dao 里的那份。新项目从模板仓建。
   - 引用不了的（标签、里程碑）由体检调 GitHub 接口对齐。
   - 仓根 AGENTS.md 只写这个仓特有的内容，但栏目固定。
10. **「缺了就不能开工」那档**没补齐，「让 AI 接活」开关点不动。
11. **本机一条命令**：`pnpm project check` 只查，`pnpm project add` 做到底（#2749，`packages/conventions/src/project.ts`）。驾驶舱没有另一套装仓按钮：OAuth「一键授权」删了，设置页只读安装令牌能看到的仓。
12. **自下而上**：任何仓里的 AI 发现通用做法，直接给 fleet-dao 的标准开 PR，写清至少两个仓或场景用得上；创始人说的原则、偏好默认各仓通用，当场开、不用另证，只此仓有效的要他明说过或在仓里写明为什么（决定 0081）。驾驶舱列出这些提案；超过 2 天没人处理，推给总指挥。合进去后第二天各仓复查，收到补齐 PR。本机 AI 的「记忆」当收件箱：通用的教训走这条线固化进标准，固化后删掉那条记忆。
13. **人闸第四类「改标准」**：怎么判、怎么点头见第五节「人闸第四类：改标准」。
14. **对账表**：每条规矩写明用代码查还是 Jev 查、自动补还是提醒人、在哪个环节查。驾驶舱后端收到 webhook 就查，每天全量扫一遍。结构化的（标签、里程碑、路径、状态）全用代码查；要读人写的文字的（档位理由、「怎么算做完」、提案是否通用）用 Jev，只拦不放，先只记不拦（见 `docs/design/jev.md`「怎么管住它」）。
