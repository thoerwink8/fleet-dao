## 拍了什么

1. **standard-paths.json 加顶层 `security-base` 清单**：`packages/conventions/`、`packages/hygiene/`、
   `.github/workflows/`、`.github/actions/`、`deploy/`、`pnpm-lock.yaml`、`pnpm-workspace.yaml`、
   `package.json`、`.env*`、`.npmrc`、`.yarnrc*`。碰了这些的 PR = 动了安全计算基。
2. **合并闸对安全基前置「要你拍」**：碰安全基的 PR 合并前要在「要你拍」对一个具体 head SHA 拍板；
   闸读当前头上的 `security-base-approved` 提交状态；SHA 换了旧批准作废；正文写「创始人原话」也过不了
   （原话锁不住 SHA，挡不住拍完又加东西）。
3. **「干活的」App git 令牌发 `workflows:write`**（token-scopes.ts）：App 注册表本来就有这权限，
   只是代码以前不发——「不给 workflow 权限」那道闸是假防线（真正判法在 conventions/hygiene 的 TS 里），
   换成安全基前置闸后放开它。
4. **「要你拍」从后置通知升级为前置批准**（待做：驾驶舱后端 `decision-actions.ts` 加
   贴 `security-base-approved` 状态的批准动作，绑定 PR 号 + head SHA）。

## 为什么（discuss 收敛的三条）

- 挡 `.github/workflows/` 是假防线：真正的判法在 `packages/conventions/`、`packages/hygiene/` 的 TS 源码里，
  普通 AI PR 就能改，改完 CI 绿就自动合（近 300 个合并 PR 里 18 个碰过）。
- 「先合再通知」致命：恶意 PR 在通知前就能读 secrets、发请求，回滚追不回已外泄的东西（GPT 第 2 轮判死方案 X）。
- 「点一下才合」才有安全边界：AI 自动化能等自动合，等不了人拍板。创始人不在时安全基 PR 排队（默认拒绝），普通 PR 不受影响。
