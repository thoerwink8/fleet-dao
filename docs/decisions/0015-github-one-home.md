- 状态：已采纳，分片落地（#654：A #655、B #656、C 本提交；计划、CI 分片、分支清理在 #654 的清单里）
- 现状（2026-10-05 回写）：生效。第 4 条列的「没落地」已落地：`pnpm plan` 现读计划、每天一轮 GitHub 对账（`github-audit.yml`）、CI 分片、已合并分支清理；#654 已关。

## 原话

```
我们的流程不应该冗余，一切要为了提速而服务，多考虑这个点，然后大改github相关
```

## 起因（量出来的，不是感觉）

- PR 模板有 12 栏，最近 49 个 PR 里「认领」「修提醒」全填「无」，「按推荐先做了」「specs」「文档」九成上下是「无」或「不适用」；合并闸对它们只提醒、从不挡。
- 一张单有两个家：issue 正文和 `specs/<号>-<短名>/需求.md`（160 份镜像）。两份各改各的，于是有了「开着的 issue 有没有需求文档」「需求.md 写没写怎么算做完」两道检查、开单脚本的 `--specs`、引擎收单时「照正文写需求文档」这一步；做完又要再写一份 结果.md，才有了「关单要有结果」、PR 上的「这个 PR 做完就关单」栏、每天的关单对账。每一道都是上一道兜底带出来的。
- 82 个 PR 挂着里程碑，里程碑页把 PR 也数进完成度，v3 页上的进度是虚报的。
- 每个 PR 的 CI 中位 239 秒，关键路径是 deploy（238 秒）、test rest（173）、test engine（141）。

## 原则

**一个事实一个家；每道关必须有人用，没人用就删。**只在 GitHub 页面上看的东西，不再加一道 PR 页检查去兜；检查只查活文档，历史（`specs/`、`docs/decisions/`）不动、也不查。

## 决定

1. **PR 页上没人读的检查删掉**（#655）：`conflicts`、`pr-labels` 两个工作流（冲突 GitHub 自己就显示，也合不进去）、debt 的 PR 触发。PR 不贴类别标签、不挂里程碑（里程碑页只数单子）。
2. **PR 模板只留四栏**（#656）：做了什么、怎么验证的、还欠什么、需求；要在合并时关单就在「需求」栏下面另起一行写 `Closes #号`。合并闸只留两条真门：改到先审后合的路径要有通过的第二意见、引擎任务流程开的 PR 要有通过的 `cold-verify`；判法不再看草稿、冲突、标签、正文栏；主线推送只在闸认的东西（高风险清单、判法、工作流本身）变了才触发，重算开着的 PR。
3. **需求只在单子正文里**（本提交）：
   - `pnpm issue:new` 没有 `--specs`，整份正文原样进 issue（超过 GitHub 上限拒开）；欠账检查和文档指针检查不再扫 `specs/`、`docs/decisions/`；
   - 关单证据换成「合并了的 PR 提到它 / 下面的子单都关了 / `--note` 写一句」，不再要主线上有 结果.md；做成了什么就在 PR 正文里；
   - 删 结果.md 那一整套：引擎每天的关单对账（conventions、github、engine 三处）、旧提醒由 `retireCloseSweepAlerts` 一次性撤掉。
4. 还在 #654 清单里、没落地的：计划不再存 `docs/plan.md` 快照而是现算、每天一轮 GitHub 对账（日报）、CI 分片提速、远端已合并分支清理、引擎收单改成读单子正文。通用段和技能说明里提到被删机制的文字，是改标准，另开 PR 等创始人点头。

## 没动的

`specs/` 和 `docs/decisions/` 下已有的文档（历史记录，不改）；通用段、技能说明（改标准）；先审后合那两种门和人闸四类。
