## 结论（和方案一一对应）

1. **三段一条龙：对题（含建单）→ 动手 → 验收。** 每段一个用完就退的无头进程，段之间不传副本、现读单子和 PR。不设常驻环节，名字用动词不用名词。
2. **对题（建单）就把上下文写下来。** 单子必须有「场景、原话、已知的模块」三栏，缺了 `pnpm issue:new` 拒开；「涉及面」拒写（那是算出来的、不是知道的）；「要什么」和「怎么算做完」是验收那遍唯一的对照物。
3. **动手按改动面分档，一次定死、不升档、不回退。** 分档判据是 git 数得出来的改动面（一个文件/一个模块内几个文件/跨模块碰接口），不按难度。中途发现错了原地改、留备注。
4. **验收就是合之前那**一次**冷调用**，换一家跟主力不同的家族；只喂 diff、要什么、怎么算做完；只判「做到了没有」（GPT 挑错收的第 1 条），不判「做得好不好」（质量判断另走周期性 review，不挂在单子上）。
5. **只有三种能挡**：没做到验收条、有证据弄坏原有功能、安全或丢数据。默认 1 轮、最多 2 轮。
6. **「交接条」不造**：审官要的三样（diff、要什么、怎么算做完）都在单子和 PR 里，验收那一遍现读，不存副本。单子三栏、PR 正文三栏由 `pnpm issue:new` 和 `.github/pull_request_template.md` 钉死；缺栏只提醒不挡合并，但验收那一步读不到必填栏必须明确失败（通用段底线第三条）。
7. **重试按表办、每类带「总次数 + 最长等待」两个上限**（GPT 挑错收的第 2 条），超任一个停下报人；停下那一刻把「这原因出现过几次、每次的原文」写出来，防自循环。
8. **驾驶舱「在跑的」那块要显示「卡在哪一环 + 在等谁」**（GPT 挑错收的第 3 条），「还没验」不许显示成「失败」，四件事同时发生时显示成它们有先后依赖、不是并列四条。
9. **「交接次数」的口径定死**（GPT 挑错收的第 4 条）：一次交接 = 控制权从一段转到另一段；**读已有记录不算交接**。按这个口径三段正好 2 次交接，卡住目标。
10. **路由配置改成两层**（模型 → 各渠道）：加一条新渠道只加一个子项，不再平铺三行；每层要能一眼看出「这条现在活着吗」。
11. **Temporal 留**（10-02 创始人拍）：负责「额度切号」和「跑一半被打断后从断点续上」；记账不进 Temporal，每次调用回来时记 `runs` 表。
12. **删 / 留对照**（方案 §九）：删 Fusion 编排层（状态机、认领租约、重试策略）、「模式 A/B」、「判难度」这一层；留 GitHub 当计划、引擎层（起进程、喂什么、判档位）、四条人闸、先审后合、`runs` 表。
