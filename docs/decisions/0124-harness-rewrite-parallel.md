## 背景

近五周引擎、适配器、核心包 660 个提交，修卡住、超时、重复、漏记的上百个。根子是一张单的状态散在 Temporal 工作流、`tasks`/`runs` 表、GitHub 标签、通知表几处，靠对账拉齐；认领也散在标签、本机租约、`tasks` 行三处，撞过两次（#3721/#3722、#3737 对 #3744）。

## 决定

1. **新包整套重写，旧包并行期只改认领**：同一个工作区新开 `harness-contract`、`harness-store`、`harness-runner`、`harness-workers`、`harness-orchestrator`、`harness-api`、`cockpit`；不依赖旧包，要用的旧代码复制进来再改。旧引擎唯一的改动是拉单和点名派单改走统一认领表。
2. **存储**：同一个 Postgres 实例的独立 schema `fleet2`，独立库用户和连接池；事件表加投影加命令回执加 outbox；对外副作用只经 outbox，至少一次投递，外部动作走「预留、执行、查证、补偿」，结果未知记 `unknown` 不盲重试。生产上不拿删 schema 当回退。
3. **不用 Temporal**：自建调度器单独成一片，故障矩阵（见讨论稿第五节）全过才进入真实执行；过不了只在调度这一层接回 Temporal。
4. **认领只有一处**：`issue_owner` 表带租约和 fencing，旧引擎、点名派单、本机领单、新内核四个入口都走它；标签只给人看。所有状态写和外部副作用都带 fencing；租约过期不自动转手，先确认原执行方停了。
5. **影子比对零副作用**：影子工人在单独系统用户下跑，拿不到 GitHub 凭据和宿主密钥、出网只放模型服务、MCP 只给读工具；旧的结果永远是权威；同时最多 1 条影子，池紧先停。
6. **切换梯度**：影子 → 真执行不合并 → 金丝雀合并 → 默认交新内核 → 关旧引擎拉单（留着能开）。切回按单所处状态逐行处理，每一级的退回随这一级交付并真机演练。
7. **界面**：照参考工作台的外壳和浅色令牌（取代 0121 第 3 条）；0121 第 1、2 条和对比度闸、`lint-design` 照旧；暗色第一版不做。
8. **每片四样证据**：CI、法国真机调用（执行类覆盖成功、超时、被杀、断网、重启接回、重复提交、限流、退回）、库里记录、碰界面的两种屏宽截图和参考工作台并排；对照旧坑验收用例写明过了哪几条。点验完再往深一层：从原始材料找体验问题，拆竞品实现，好用、适合 VPS、符合最终目标的功能都加，逐个开单。
9. **关旧引擎前**：旧系统行为清单逐项有对应或明确不要、历史回放、含新内核的恢复演练都过，再观察两周。
