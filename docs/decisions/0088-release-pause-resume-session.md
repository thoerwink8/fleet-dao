## 原话

```
我觉得这样也不对，有些任务安排就是想要修复驾驶舱本身的问题，所以不能先施法。

我思考这样怎么样？还是围绕着"先暂停后继续"的方式。暂停后继续，都能恢复到上一次的会话内容嘛。因为我们是用 cli的方式，所以肯定能恢复的，难道不是吗？
```

```
落后的规则就是要删掉的。我们之前定了很多规则，我后面其实连规则册都想大改掉，我们后面再讨论一下吧。你先把这个规则去掉我同意你的拍板
```

（第一段「不能先施法」指指挥官上一版提的「等法国空闲再发」：修驾驶舱自己的单要马上发上去，不能干等。）

## 为什么

- 法国近 7 天：发了 64 次版，平均一天 9 次；被发版截断的会话约 19 个，占全部会话的 2%，每个截断的会话中位约 11 分钟、最多 60 分钟的活白做；每次发版排空要停接新活最多约 10 分钟，一天累计 1 到 1.5 小时。
- 截断的会话白做，是因为引擎每次都开新会话（`segment-spawner.ts` 写死 `session.mode = 'new'`，`one-shot.ts` 见到续会话号直接抛 `RESUME_FORBIDDEN`）。三家命令行（Claude Code `--resume`、cursor-agent `--resume`、grok `-r`）和 Mirasim 都能按会话号续上，`packages/adapters` 里早就写好并有测试；法国只有一个会话用户、工作树停下后留着、会话记录也存着（只有探针不存），续会话要的东西都在。`docs/design.md` 第 151 行原本就写着「暂停后支持续会话的命令行按会话编号续上，不支持的带进度摘要开新会话」。
- 「等空闲再发」会让修驾驶舱的单最多等 2 小时才上线，创始人否了。

## 决定

1. **主线绿了就自动发。** 主线头的 CI 是绿的就发，不等人点。两次自动发版之间至少隔 1 小时，期间合进来的攒成一次发。驾驶舱「发布到法国」按钮留着，想马上发时用，不受 1 小时间隔限制。
2. **发前暂停、发完续上。** 发版不再给在跑的会话 10 分钟收尾：先给所有在跑的任务发 hard 暂停，记下每个被停会话的会话号，等进程收掉后部署，新引擎起来后给这些任务发「继续」。
3. **继续时按会话号续上原会话。** 被暂停（含发版、人手暂停）停下的那一段，继续时用同一条路由、同一个会话用户、同一棵工作树，按记下的会话号续上，提示词只补一句「刚才被打断了（为什么），接着做」。续不上的（会话号没记下、执行体不支持、会话记录没了、换了执行方式或会话用户），退回现在的做法：原分支原树开新会话，带上「树里有上一次留下的东西」的说明，并在任务进度里写明为什么没续上。
4. **删掉「不许续会话」这条规矩**：`one-shot.ts` 第 1 条和 `RESUME_FORBIDDEN`、`segment-spawner.ts` 开头「一次性：会话号一律开新的」这句，连同 `docs/decisions/0021` 里「不续会话」的说法一起改掉，不留两种说法。
5. **自动发版也照 0032 第 4 条恢复引擎开关**：发前开着的发完开回，发前关着的保持关；恢复不成功照旧报警。
6. 发坏了照现在的做法自动回到上一版；结果记在驾驶舱发版卡上，不另推飞书。
