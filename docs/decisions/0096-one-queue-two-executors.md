## 为什么

两条线各记各的，派活规则还把法国饿着：

- 近 7 天合并 PR：本机线 329 个，法国线 171 个（其中 97 个是 10-10 一天）。
- 开着的 29 张单里 14 张贴「本机做」、8 张「要人拍」、5 张母单、2 张「待补」，引擎能接的几乎为 0。
- 法国机器一周 92 小时空闲，另一家订阅的容量白白浪费；本机会话会被登录过期、重启打断，断了不会自己续。
- 法国线单：建到做完中位 28 分、p90 123 分；开单到被引擎接中位 3.3 分；一轮做成率 7 天 46%、近 4 天 24%。

法国线是被饿着，不是被比下去。

## 决定

1. **一个队列、一本账、两种执行者。** 队列就是 GitHub 单。能写成四节、验收在 diff 里看得见、不要本机资源的活，一律开单、不贴「本机做」，默认由法国接。
2. **本机只做四类**：创始人在场来回讨论中的；急修（主线红、生产坏、数据、泄露、安全）；要本机资源的；改标准的（引擎开的 PR 正文没有创始人原话，合并闸会判红）。其余开给法国。拿不准就开给法国，法国一单做不成再摘标签本机接。
3. **他不在、过夜、无人值守**：能写成单的写成单交法国，本机子代理不留过夜的活。
4. **Temporal 冻结，不推翻。** 瓶颈不在编排（没活接、一轮做成率低），碰 Temporal 的约 5.1k 行，去掉要补状态机、租约、围栏、幂等、演练约 2.5–3.5k 行，净省很少、工期 2–3 周；运行代价小（295M 内存、两库 142MB）；0021 写明推翻每步要创始人拍。冻结的意思：新功能不再往工作流里加信号和查询，能放活动或普通函数就放；新流程状态先落 Postgres（`runs`、`tasks`），Temporal 只管一单的步骤推进。外围清理（`workflows/hello.ts`、老 Schedule 退役代码、过期的 `patched` 分支）逐个小 PR。
5. **复议触发条件**，任一满足就重开，把 0021 的方案拿出来问创始人：①要在第二台机器（另一台 VPS 或本机）跑执行者；②一个月内 ≥3 次事故根子在 Temporal（重放、测试服务端、挂着的工作流）；③引擎要按任务并发扩到内存吃紧。迁移形态届时优先「Postgres 任务表 + `FOR UPDATE SKIP LOCKED` 领活 + 租约围栏」，或评估 DBOS 这类建在 Postgres 上的库，不自己从零写。去掉 Temporal 的切换、删 temporal 库仍要创始人逐步拍（删数据）。
6. **不接 webhook，不加 `ready` 标签。** 轮询只占一单约 10% 的时间；webhook 要给法国开公网入口（香港入口刚删）、会丢，轮询还得留着对账，等于多一套；准入已是「四节齐、没贴拦截标签」，再加正向标签是让人多点一下。改成：`pnpm issue:new` 开给法国的单，开完顺手经现有 ssh 调一次 `fleet-api dispatch-issue`，让法国立刻接（中位 3.3 分降到约 0.5 分）。戳不成不影响开单、照实说，5 分钟轮询兜底。
7. **每日简报放法国引擎的进程内定时任务**（`jobs/engine-timers.ts` 一类），北京 08:30 一条：昨天上线了什么、要你拍的、失败要你的；同一份贴到置顶单 #1055 并由法国机器人账号 @ 创始人（本机 gh 是他本人账号，自己 @ 自己不推送）。不放本机（会被打断，简报恰恰要在他不在时到），不放 GitHub Actions 去读法国库（要交库凭据）。第三路看守用 GitHub Actions 定时查 #1055 当天有没有简报评论，只用自带令牌。读 GitHub 失败写「没查成」，不写「0 件」。
8. **两条线按同一把尺**：每周比一次「一轮做成率」和「合并后 7 天内被修/回退率」。

## 别家挑错与处理

第 1 轮（kimi-code）3 条，全收：
- 四节单写作质量是新瓶颈、喂多了做成率先降：加影子模式，攒满 30 件或 5 天先看「能写成四节的比例、写单多花几分钟、推算中位」，比例 <30% 或推算中位 >45 分就只把过夜的活交法国；止损线加「单被退回率 >20%」。
- 量上去后先恶化的是排队：止损线加排队深度（可接未接的单连续 2 小时 >3 张或任一单排队 >30 分）。

第 2 轮四家都没查成，不算数。

第 3 轮（gpt-6-luna）4 条，全收：
- 合并 PR 不等于完整记账：两条线每件活都登记进法国 `tasks`（来源、类型、起止、结果、失败原因、接手）。

- 两路通知不独立：加 GitHub Actions 定时看守当第三路。
