## 为什么（数据取到 2026-10-22，见 `specs/3604-冷验收口径/根因.md`）

- 冷验收拒绝占全部轮次 25%，10-22 当天 44%，是做成率 43% → 21% 下跌里涨得最多的一项；10-17 每天 7 轮，10-18 起每天 21～27 轮。
- 10-18 动手换成 Claude 后，按 0006 顺序它们的活全由 GPT 验：10-19～10-22 GPT 通过 44%（83/188），Claude 88%（95/108）；「其他」类单 GPT 58% 对 Claude 93%。
- 抽样 24 条拒绝：13 条是验收条要 diff 外证据（诊断单），5 条是并发 / 精确性边界一类验收条以外的意见，真没做到 10 条（有交叉）；1 条是模型误判。一半以上不是「验收条没做到」。
- 旧提示词的缺口：「这一条本该在 diff 里看得见却找不到」可以拿来挡；「弄坏原有功能」「安全或丢数据」两类只凭模型的推测也能挡，是边界类意见挡路的口子。

## 决定

1. **能挡合并的只有三类**（#3624 修订：初版收成只有第一类，把真出事的两类也降成了建议，筛子 #3587 的 F1 指出这不对）：
   - 某条验收条在 diff 或测试输出里看得到没做到（问题前缀「没做到验收条」，带「第 N 条」）；
   - diff 或测试输出里看得到弄坏了原有功能（前缀「弄坏了原有功能」，要指出具体文件 / 测试 / 行为）；
   - 安全或丢数据（前缀「安全或丢数据」，要指出具体位置）。
   后两类没指出具体证据的，按推测算，进建议、不挡（`isBlockingProblem` 判）。其余一律不算不过。
2. **推测和验收条以外的意见记成建议**，不挡合并：「可能会」类推测、验收条以外的边界担心（并发、精确性）、风格、没指出具体证据的「弄坏原有功能」「安全或丢数据」。建议随结论带出（`suggestions`），冷验收通过时在单上留一条评论列出（`packages/engine/src/real/task-verify.ts` 的 `suggestionsBody`，每个头一条）。
3. **看不到 diff 外证据而判不了的走转人**（结论里的 `outOfScope`，运行记录里的 `handedOver`），不判不过；沿用 0093 第 5 条和 0113：留言转人，代码照合，单子留着。
4. **模型写 `verdict: fail` 却没有任何能挡的问题时按过算**（只有建议或只有转人的）；一条都没写才算这一家没验成，换下一个候选。
5. **每日简报「流程健康」加一行按验收族分的通过率**（近 7 天，每族「过 / 有结论」，数自 `runs` 验收段结论，族取 `models.family`），以后验收松紧不同家会立刻看得见。
6. **验收族顺序不动**（0006 创始人定的 gpt → grok → claude → deepseek → kimi，同族兜底验也不动），只改「什么算不过」。GPT 继续参与发现问题，但推测只进建议、不挡路。
