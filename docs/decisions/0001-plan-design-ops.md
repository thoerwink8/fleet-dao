# 0001 plan、design、ops 整套改法

- 日期：2026-09-26
- 谁拍的：创始人
- 状态：已采纳（一决定一文件，只增不改；被推翻时在这里标「已被 xx 替代」，不删）
- 细则：`docs/design.md` 第七节「plan、design、ops 的整套改法」
- 单：①plan 条目格式与合并前检查 #137；②plan 与 GitHub 同步、归档 #138；③design 拆决定记录和模块 #139；④ops 生成和拆分 #140

## 起因

plan、design、ops 三份文档各自长成了一大份：plan 里的条目和 GitHub 上的单靠人手对，谁记得谁补；design 把拍板记录、设计、还在讨论的事混在一起，第三节的决定表越改越长，看不出哪条被哪条推翻；ops 里端口、用户、目录这些表是手抄的，和 `deploy/` 里的真配置会走样。

## 决定

**plan**

1. plan 是「做什么」的唯一来源，GitHub 是镜子。每条一个终身编号，用随机短码（如 `[T-k7p2]`，谁加谁生成，免得并行的 AI 撞号）；一条一行：编号、标题、链到 `specs/<编号>-短名/`（验收和细节在 specs）。
2. 按阶段拆：`docs/plan.md` 只留「现在的目标」和阶段目录；每阶段一个文件 `docs/plan/P1.md`，和 GitHub 里程碑一一对应（建文件就是建里程碑，标题、说明跟文件走）。
3. 正方向：改动合进主线且动到 `docs/plan/**`，GitHub Actions 以驾驶舱 GitHub App 的身份跑同步程序：读全部条目（含归档）和 GitHub 现有的单、里程碑（单正文里藏 `<!-- plan:T-xxxx -->` 标记），缺的建、不同的改；每次全量、幂等，漏跑一次下次补齐；处理翻页、限流、重试、两次同步同时跑；失败就是主线红叉，按规矩立刻修；每天全量核对一次只作保险。
4. 字段归属，防死循环：标题、阶段、先后以 plan 为准；「关没关」以 GitHub 为准。单关了，plan 那行标「已完成」；有人手动开单、改标题或里程碑，机器人维护一个固定的「同步回 plan」PR 往里加，挂自动合并，合并前单显示「待纳入」，这期间正方向同步不去改回；机器人自己的改动不触发反方向同步。plan 不自动关单。归档条目只读，绝不重开。
5. 阶段收口（关里程碑前的检查）时，把这个阶段已完成的条目挪进归档文件，编号和链接保留。
6. 合并前检查只查 plan 文件本身：编号唯一、格式、链接（确定性，不连 GitHub）。

**design**

7. 决定表拆成决定记录：`docs/decisions/<编号>-<短名>.md`，一决定一文件，只增不改，被推翻标「已被 xx 替代」；design 只留目录。本文件是第一条。
8. 计划性内容（待讨论、下一步、讨论中等）全部搬进 plan 或 issue，design 不留。
9. 按模块拆 `docs/design/<模块>.md`，和 `packages/<包>` 对应，用一张明确的对照清单；`docs/design.md` 只留一句话、架构图、目录。PR 动了某包 `src/` 却没动对应设计文件，在 PR 上留言提醒，不挡合并。

**ops**

10. 端口、用户、目录等表由部署配置（`deploy/` 下的配置和样例文件）生成，放「自动生成、别手改」区块；密钥只出名字不出值；CI 核对生成内容和配置一致（确定性，进合并前检查），线上现状不在核对范围。
11. ops 只留「怎么做」（发布、回滚、恢复、出事看哪），按主题拆文件，`docs/ops.md` 留目录；线上现状链到驾驶舱健康页。
12. 拆分时文档指针检查跟着改，不留断链。

**顺序**：①条目格式和状态 + 合并前检查 → ②同步程序（正反方向）+ 归档 → ③design 拆决定记录和模块 → ④ops 生成和拆分。

## 替掉了什么

- 总指挥先定的「`pnpm issue:new --plan` 开单回写单号 + 每天定时查 plan 和 issue 对不对得上」那版（没落地）：创始人对「每天定时查」有异议，改成这一版——plan 是来源、合并后自动同步、每日核对只作保险。
- 落地之后作废的旧说法（由第①②步的 PR 一起改）：开单一律用 `pnpm issue:new`、里程碑说明只写一句、「仓里有的也不往 GitHub 抄」，见 design 第七节那一段的「落地前后」。
