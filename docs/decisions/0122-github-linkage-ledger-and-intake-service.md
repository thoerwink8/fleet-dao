## 背景

建仓五周，1503 张单、2231 个 PR。单越来越小、合得越来越快，但问题集中在几处：一天自动开 250 张开了就关的「e2e 偶发」单；12% 的单标题重复；进度单 #1055 累计 1789 条评论；关单有五条路，只有 39% 的单是被合并 PR 的 Closes 关掉的；人和 AI 共用一个 GitHub 账号；本机、GitHub、法国三地只在 GitHub 汇合，靠轮询互相发现。讨论稿第一到三节有逐条实测和代码出处。

## 决定

1. **单的粒度**：一张单一个可验收的目标；任务拆出来的节点只进事件账本，不开单。这是对决定 0015、0040 的细化：「要做什么、怎么算做完」仍以 GitHub 单为准，「正在怎么做」的唯一记录改成账本。
2. **进度单**：关掉 #1055，进度从账本生成、在驾驶舱看；历史评论留在那里当档案，不迁移。
3. **AI 的 GitHub 身份**：AI 一律用 GitHub App 身份开单、开 PR、评论；创始人账号只留给本人。
4. **本机怎么连法国**：法国上做一个开单服务，同时以 HTTP 和 MCP 暴露（开单、领活、交给法国做、记观测、提决策卡）。本机会话（含 Mirasim）装同一组工具，经现有 WG 通道加令牌连过去；法国 harness 的指挥官也用这组工具。三个入口（指挥官主动开单、harness 聊天开单、本机下指令）都经它写 GitHub，不再 ssh 戳单。开单前查同题，命中就并进原单。
5. **自动观测**：只记进账本，同一个检测连续命中 3 次才开单（阈值落地时用历史数据核一次）。
6. **通知**：完成、卡住、要拍板推到创始人个人，驾驶舱网页推送为主、飞书个人消息为辅；这部分取代决定 0044 里「只进团队群」的做法。
7. **先后**：先做开单服务加账本，再做 App 身份和关单收成一条路，再处理噪音和进度单，最后接本机 Mirasim、harness 指挥官和通知。

## 没做的

- 不追溯修正历史上手关的单，不迁移 #1055 的历史评论。
- 不做语义去重的模型，先用标题相似度加关键字。
- 第四批里 harness 指挥官那部分要等 harness 建好再接，本决定不排 harness 本身。
