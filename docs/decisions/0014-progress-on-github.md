## 起因（读会话记录量出来的）

2026-10-03 03:35–06:01，创始人说「全部做完、不要停」之后 86 分钟：一个会话发了 407 次工具调用，只合了 1 个 PR；时间 84% 花在调用之间（模型想和写），工具真正在跑的只占 16%；97% 的回合只发 1 个调用，读文件、看状态占调用的 60%；第 2 片改了 71 个文件才第一次跑测试，44 分钟没推到远端。创始人只看得到每轮最后一条，中间的进度他看不到，于是看起来「没开工」。

## 决定

1. **原则**：减少或优化流程步骤；不要把 80% 以上的时间花在读文件上，想办法处理。
2. **GitHub 是进度的对外面**：里程碑里的单子都要显示对（只有真有子单的才贴「母单」、子单挂在母单下、版本先后清单只排母单和单独的单、做完的关单并带结果文档）；PR 开着就写明做到哪；进度文件随做随更；断了当场修，不攒。
3. **怎么落**（AI 拍的，创始人说「按你认为的最优解」）：
   - 读文件：先定位再读。用类型检查、测试输出、grep 给出的行号直接跳到那几行；独立的读放进同一个回合并行发；要整文件就一次 Read 读完，不用 sed 分段翻。
   - 改文件：用 Edit，或一次脚本批量改；改完在同一个回合里跑检查；改完一个包就跑这个包的测试，不等全改完。
   - 同步：每次合并，同一个 PR 里更新进度表和计划快照（`pnpm plan:snapshot` 会拒绝不合规的先后清单，是现成的断裂检测）；`pnpm debt:check --live` 报的欠账当天清。
4. 通用段：改标准，PR #650。10-03 当时判他没选「通道、发完接着做、每 20 分钟推一次、超时拆小」那版，打算按他这两句原话改成一句话版本；但那版草稿没推上去（正则被工具吞坏，存在本机 `_tmp/rules-visible-uncommitted-draft.patch`），PR 里一直是四句那版。创始人 2026-10-04 约 08:50 对晨报第 9 条（列了 #650、#646、#624）回「9 条改标准的我都通过。」，按四句那版合进通用段「无人值守」那条（为过字数预算压短了措辞，意思没丢）。第 1、2 条的原则没写进通用段，仍只在本决定里。
