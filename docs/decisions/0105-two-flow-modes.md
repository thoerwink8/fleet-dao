## 两种模式各是什么

- **三段**（三步单，现行默认）：对题（指挥官和创始人对话建单）→ 动手（引擎派写码会话）→ 验收（另一家模型冷验收，只看 diff 和单子里的验收条）。动手和验收是两个分开的会话，段间不传副本。
- **全程**（模型全流程自己走完）：同一个写码会话从动手一路带到合并：先出几行方案、自己跑改到的测试、提交；CI 红了、和主线冲突了、冷验收拒了，都带着结构化的失败信息回到**同一个会话**接着修，不另起新一轮。这些续修不算新的一轮，但整张单有上限（最多推 6 次、token 不超预算）。等 CI 时会话不挂着，本轮先结束，有结果再续。

## 第一期的边界（轻量版）

1. 全程只走 Claude 5.5 路由（Sonnet 或 Opus），按档位和模型分层，同一层里两组的模型一样，比的只是流程（历史上三步单大量用 Grok 的成功率不能当基线），只在 fleet-dao 这一个仓。
2. **会话不拿凭据、不开工具口**：推分支、开 PR、等 CI、合并、冲突后并主线，全部仍由引擎在会话外做；会话只管改代码、跑测试、提交、修引擎退回来的失败。不让会话经本地口替引擎 push、开 PR（混淆代理和提示注入风险），也不让它自己 rebase、改 git 配置、钩子、子模块。引擎推之前照旧做卫生检查、只推本单分支、不许强推。CI 日志在提示词里标明是数据、不是指令。
3. **合并闸、冷验收、改标准人闸两组完全一样**。冷验收两组都保留：本机工人的 90% 没有冷验收、又用更强的模型，不能当基线；去掉它会同时改两个变量。
4. 冷验收拒绝要有独立上限（不能无限续同一个会话，免得针对验收器改代码、token 失控），拒绝的原因记账分四类：真实缺陷、验收误拒、需求不全、基础设施（`task_rounds.verify_reject_class`，人工审过才填）。验收器版本或规则中途改了（例如修「实现不在 diff 里」的误拒），前后数据分段看，不混成一个结果。
5. 状态幂等：一张单只认一个有效会话，旧会话一律拒；冷验收拒绝后，旧的 CI 和验收结果作废；分组一次定下写进 `task_flow_assignments`（只写一次，不覆盖），重放不再读配置。

## 试点规则（开跑前定死，跑的过程中不改）

**成功**：一张单同时满足三条才算成功。
1. 预算内合并：全程组 token 不超单预算、推送不超 6 次，三段组按现行轮数上限（最多 2 轮验收），并且最后由引擎合进主线。
2. 无人介入：从分到组到合并，没有人在驾驶舱点过「重试」「换路由」「继续」，没有人往单子或 PR 里补过指令，没有人改过会话的产物。指挥官为拍板人闸（对外发布、改标准）点头不算介入；其余算。
3. 合并后 7 天内没有被修复也没有被回退：7 天内主线上出现 `Revert` 该合并提交的提交，或有另一个 PR 的正文「修提醒」/ 需求栏明说修这张单合进去的东西，都算被修或被回退。合并不满 7 天的单**不进成功率**（单列「还在观察」），不拿它当成功。

**分母**：所有分到组的合格单（source ≠ ineligible），包括失败、超预算、中途被叫停的；任何单分到组后不许因为失败而踢出。观察窗内还没合的单算「未合并」，不算成功也不被排除。

**单位**：按单，不按轮；一张单只算一次。

**非劣效边界**：5 个百分点。判法：全程成功率减三段成功率，差值的 Newcombe 95% 区间（用两边 Wilson 区间拼出，z = 1.96）的**下界高于 −5 个百分点**，才算非劣效成立。

**时长**：起点是分到组的时刻，终点是合并；只看已合并的单，报中位数和 p90（只看中位会漏长尾）；未合并的单单列、不进时长。「快 20% 以上」要看区间，不看样本中位数的点值。

**样本量**
- **安全门槛 90 单**：每组先跑满 90 单。这一档只用来看有没有安全问题和明显的成本、效果事故，**不据此改默认**（90 单一组大约只有常见 80% 把握发现 35% 对 55% 这种大差，还没算中途查看、失效单、分层）。
- **正式样本量**：90 单跑满时，用当时两组观察到的成功率 p₁、p₂ 和差值 d = p₁ − p₂，按 n = (1.96 + 0.84)² × (p₁(1−p₁) + p₂(1−p₂)) ÷ (d + 0.05)² 算每组要多少单（80% 把握、单侧 2.5%），n 不足 90 取 90；算出来就在单 #2807 上留一条评论写死，之后不再改。d + 0.05 ≤ 0（点估计已经比三段差过边界）时不算样本量，直接按效果类止损处理。
- **改默认**：只有跑到正式样本量，并同时满足：非劣效成立；合并时长中位数比三段快 20% 以上（区间下界为准）；严重事故为 0；7 天被修或被回退的比例不高于三段；每合并单 token 没超过三段的 2 倍。五条缺一条都不改。改默认本身是改 0010 第 1 条的默认流程，要另写决定。

**止损三类**（一出现就按下面办，原因写进操作记录）
- **安全类**：任何一次——会话拿到或用到凭据、动了 git 配置或钩子、借引擎推出本单分支以外的东西、绕过合并闸或冷验收、日志里的提示注入让会话做了范围外的事、数据损坏、合并后引发线上事故——**立即**停用全程（`fleet-api flow-mode set three --reason ...`）并**锁住证据**（会话记录、`runs`、`task_rounds`、分组记录、PR 都不许清理）。谁判：发现的人（指挥官、日报、任何会话）当场判并执行，不等创始人；事后报。
- **成本类**：全程组每合并单 token 超过三段组的 **2 倍**。每合并单 token ＝该组所有单（含没合并的）的四样 token 之和 ÷ 该组合并数。两组都至少合并过一张单才算。谁判：每日简报按库里的数现算并写在「流程健康」里，指挥官看到「触发成本类止损」就停用。
- **效果类**：每组满 **30 单**之后，全程比三段更差的把握超过 95%：全程减三段成功率差的 Newcombe **90%** 区间（z = 1.645，即单侧 95%）的**上界低于 0** 就停。谁判：同上，每日简报现算，指挥官停用。

停用只是把开关改回 `three`：已经在跑的全程单照原路径跑完，不中途改流程。止损后要重开，必须另写决定说明改了什么。
