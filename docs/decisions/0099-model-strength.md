## 为什么

法国库 2026-10-16 查的近 14 天动手第一段：主力档 144 单里 127 单给了 grok-4.7，一段过 24 单（19%）、平均 3.3 轮、每单约 1650 万 token；它写的 PR 动辄 +8000 行（#2385、#2401），最后由本机重做。opus-5.5、sonnet-5.5 在主力档上只有 4、3 单，0098 的收缩分把小样本拉向本档平均，永远挪不到 grok 前面——战绩学不到它们。

另一头：模型之间严格按人排，能力相当的模型分不了流。验收排第一的 gpt-6-sol 只有 Mirasim 一条路，30 天积分照现在速度很快见底，同样能做验收的 Cursor 桶只用了 12%、快作废。

两件事是同一个缺口：路由不知道模型「有多强」。

## 决定

1. 模型目录加强弱档 `models.strength`（strong / standard / light，可空，迁移 0079）。目录 `deploy/catalog.json` 独占、装载器每次对齐（没写的清空）：strong = opus-5.5、sonnet-5.5、gpt-5.6-luna、gpt-6-sol；standard = grok-4.7、kimi-k3；light = cursor-auto、deepseek-flash、glm-5.3-flash、haiku-5.5。没标的模型选路照以前。强弱档说模型多强，派工档（fast / medium / heavyweight）说单多难，是两回事。
2. 重活先给强档：动手（`trackScore.stages`）、这一单派工档在 `strength.strongFirstTiers`（默认只有 heavyweight）里时，强档的模型整体提到别的档前面，档内仍按 0098 的收缩分和人排的先后；别的档之间不动。强档某个模型额度读成了的渠道每一条都有窗口超前时间进度 30% 以上（`strength.yieldAhead`，shared 的 `quotaPace`，5 小时窗不算），这个模型让位、回到原来的位置。被挡（没额度、熔断、关着）的照旧被挡，强档全被挡就往下派，打分不把能派的排没。中档、快档不受这条影响。
3. 探索：动手、给了派工档时，按单的编号（tasks.id）算出 [0, 1) 里的数（`routing/rank.ts` 的 `seedDraw`，同一单重算不变），小于这一档的比例（`strength.explore`：主力档 0.2、中档 0.1、快档 0.05）就把样本少于 `trackScore.minTasks`（5）的强档模型提到第一，几个都少时也由这个数挑。让位的不探；战绩没读成（不知道谁样本少）不探。
4. 同档分流：任何用途里，强弱档相同、在模型先后里挨着的几个模型合成一组，组内所有渠道按同一模型几个渠道之间那套微调（#2363 的按消耗进度：落后的先用、超前的往后，额度未知的排后）一起排，进度打平手按模型先后。不同档之间、没标档的照旧。开关 `strength.pool`。
5. 派工理由各写一句：「重活先给强档：opus-5.5」「强档池超前 34%（…），让给标准档」「探索：opus-5.5 重活样本 4 单，少于 5」「与 X 同档（强档），X 的池超前 Y%，先用这条」。

## 一键关掉

`packages/engine/src/routing/policy.ts` 的 `strength`：`strongFirstTiers` 置空关掉先给强档；`explore` 各档置 0 关掉探索；`pool` 置 false 关掉同档分流。三样全关就回到 0098。也可以在目录里把某个模型的 `strength` 删掉，让它不参加。
