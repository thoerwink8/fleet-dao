## 为什么（近 7 天主线 ci.yml）

- 主线红 40 轮、487 分钟；其中 18 轮、234 分钟是 PR 上只跑了预测出来的那部分测试、漏到主线才红。一红就挡住后面所有人和发版：
  - #2399：PR 上 e2e 被推迟到主线（`deferE2eToMain`），主线连红 10 轮、91 分钟。
  - 提需求页 12-intake 的窄屏用例：PR #2079 只跑 1920 宽，合并后那轮又因同树复用跳过 e2e，到下一次全跑才红，连红 7 轮、128 分钟，背锅的是无关提交。
  - #2502 只改了 `agents/…/release-train-lib.mjs`，agents/ 的规则不开 deploy，PR 那轮 deploy 被跳过。
- 每出一次事往清单里补一条路径（#2674 的 `E2E_PR_RISK_PATHS`）是打地鼠：预测永远比真实依赖少一块。
- 「两个 PR 各自绿、合起来红」一次都没有，所以漏的根子是选测，不是并发合并；不上 merge queue（仓归个人账号，merge queue 只给组织）。
- 全套实测墙钟 3.4 分钟（夜跑 run 38821616731，26 个 runner-分钟），PR 选测 p50 2.2 分钟，只省 1 分钟上下；仓是公开仓，Actions 分钟不收钱。高峰约 16 个并发 job，免费档上限 20。
- 主线 push 的并发组按分支分、一组只许一个排队：7 天 49 轮被后来的推送挤掉，那些提交没有结论（发版只认「这个提交自己那次绿」）。

## 决定

1. **CI 一律全套。** PR、主线推送、每夜、手动都跑：lint（biome 整仓、tsc 整棵树、文档指针、技能测试、deps、release_smoke）、全部单元测试（按耗时分台）、web 打包、e2e 全套（playwright 配置里的两种屏宽，切 2 台）、deploy 全套（切 3 台）。e2e 回到 PR 闸，仍是发版闸。
2. **只留两种「输入完全相同才跳过」的省法。** PR 上测试台的结果缓存（`ci-cache.ts`，同一 PR 重推、这一台输入没变、上一轮全绿）；主线提交和某次成功的 PR 检查是同一棵树就整轮复用（test、web、e2e、deploy 都跳过），树对不上就全套。复用只认决定之后的 PR 声明（`已测的树 tree=<树>`），之前选测时代的声明（带 `base=`）一律不认。
3. **删掉选测那一套。** `deferE2eToMain`、`E2E_PR_RISK_PATHS`、PR 只改 deploy/ 时窄跑（`DEPLOY_NARROW_RULE`、`deploy-readers.ts`）、找「上一次主线真绿的头」按区间选测（`main-baseline.ts`、`bin/main-base.ts`、ci.yml 的 mainbase 步）连测试一起删。汇总 job（check）只认两种 plan：全套，或主线同树复用；按改动选出来的 plan 交给它就红。
4. **主线每个提交都有结论。** 并发组 PR 按号分（新推的挤掉旧的），别的事件按提交号分（`github.sha`），主线推送一个都不挤掉、不取消。
5. **本机仍按改动选**（`pnpm test:changed`、推前预检问 `planCi`）：那是推之前的快反馈，CI 全套兜底。

## 不动

- 隔离集（`packages/web/e2e/quarantine.json`）照旧不在 ci 里跑、每天定时跑（`e2e-quarantine.yml`）；偶发统计、开单（`e2e-flaky.yml`）照旧。
- 发版只认主线头 ci.yml 这一轮 conclusion=success；四类人闸；必过检查只认 `check` 一个 job 名。
