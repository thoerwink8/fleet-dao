# 0002 Fusion：主脑指挥帮手，别家模型挑错

- 日期：2026-09-26
- 谁拍的：创始人（原话：「我推荐fusion这套，然后需要支持2种模式；和devin一样，默认选fusion，有时候我额度不够就只开普通正常会话模式」）
- 状态：已采纳。实施计划等创始人同意开工（09-26 下午起本机和法国放下手上的活、专心讨论架构）。
- 替代：引擎「一张单拆成分诊、写需求、写方案、写码、测试、写结果多个独立会话，需求 / 方案 / 结果文件直写主线」的做法，和「CI 绿就合的 PR 合并后再补审一次」。`docs/design.md` 正文（第五节、第九节等）里的旧说法在实施时一并改。

## 起因

- 从第一笔提交（2026-09-24 16:36 UTC）到 09-26 这 40 小时：合并 105 个 PR，全是本机会话做的；其中 44% 在改流程规矩和文档，至少 10 个是返工。引擎只做完 1 张小单（巡检仓 #12），第二张（#160）撞上会话内存上限和交活核对，走不完。
- 一张单拆成 5–6 个会话，每个都重读大段上下文（实测额度 63%–83% 花在重读上），每步各有核对规则；单和单共用的东西太多（引擎直写主线把别人的 PR 弄红、全仓文字检查、一台机器上发布和干活抢）；关键上限（会话内存、测试命令）是估的，没实测。
- 创始人要三样：高级模型指挥低级模型；订阅的多个渠道（reclaude、Mirasim、SuperGrok、Cursor）里的模型都用上；方案要能让别家模型挑错。

## 决定

1. **默认 Fusion 模式**：一张单一个主脑会话（高级模型，现在是 Opus 5.5），只做方案、歧义怎么理解、拆活、验收、最终审查，尽量少亲自动手。帮手是各订阅里的便宜模型，各保留自己的上下文，干界定清楚的活（查代码、写某个模块或测试、修小错、写文档）；帮手连着做不好，升级回主脑。
2. **普通模式**：一张单一个会话、一个模型从头做到尾。额度不够时用：创始人手动选，或引擎按剩余额度自动切（切了记一笔，驾驶舱看得到）。帮手渠道没额度时由 Claude 单干；Claude 没额度时，简单的单由一个便宜模型单干，难的等。
3. **写代码同一时间只一个模型写**：引擎给单子的分支加锁；并行只派只读的、或互不相干的活。
4. **别家挑错两道**：不是小单的，方案开工前一问一答发给 1–2 家别的模型挑错（1 分钟内）；开 PR 前另一家模型当验证员，对照单子的「怎么算做完」核一遍改动（CI 管不到需求理解、安全、界面效果）。去掉合并后补审。
5. **派帮手按「活的难度 × 渠道剩余额度 × 最近战绩」选渠道**；Claude 额度优先留给主脑；照禁令：界面类的活（含审界面）不给 GPT，不用 Fable；每个渠道有花钱上限和限速。
6. **主脑随时存档**：进度、已定的事、子活状态随时写成存档；会话断了，新主脑从存档接着做。
7. **单和单不互相牵扯**：不往主线直接写，需求、方案、结果写进 PR 正文和单的评论；能不能合只看 CI 必过检查，合并前别家复核只留删数据的迁移和碰安全的路径；文字类检查只提醒、不挡。
8. **每个项目一份小清单**：改动影响到的测试怎么跑、会话要多少内存、哪些路径高风险、同时最多几张单。会话内存、测试进程数按实测定。
9. **考核**：每张单从开到合并多久、人插手几次、花多少额度（分渠道）、严重缺陷、合错、上线后回退。第一道门：fleet-dao 连续 10 张真单，至少 8 张没人插手做完、返工不超过 2 张、每张 1 小时内；过了再接更多渠道和项目。

## 容量（法国 VPS，2026-09-26 实测）

- 机器 6 核、约 11.7G 内存。平台常驻四个服务合计约 0.6G、全机 CPU 约 2%：引擎 0.27G（单核 0.5%）、后端 0.09G（单核 1%）、Temporal 0.12G（单核 10%）、库 0.13G（单核 1.5%）。
- fleet-dao 的测试：开 1、2、3 个进程时内存峰值约 1.6、2.5、3.2G，用时约 279、151、99 秒；会话里的 Claude Code 进程约 0.27G。
- 估算（还要实测）：一张 Fusion 单平时约 0.6G（主脑加一个帮手），跑测试时峰值 2.5–3G；法国同时约 3 张。测试轻的项目能多开。真正先到顶的多半是各渠道的额度。
