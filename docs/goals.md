> 2026-09-29 由指挥官（原帅位）整合：146 张单（`gh issue list --state all`，#28–#489）、134 份 `specs/*/需求.md`、决定记录 `docs/decisions/`、`specs/169-Fusion形态/需求.md` 里创始人的逐条拍板，和 09-28 晚到 09-29 凌晨的对话。

## 一、一句话

给创始人一个人用的 AI 开发流水线：他用语音说想法，AI 把需求聊清楚、写码、审查、合并；手上的几家 AI 订阅都用上、互不闲置；在一台 6 核 12G 的服务器上同时推进 10 张左右的单；驾驶舱一眼看到三件事——要他拍什么、在跑什么、做完了什么。驾驶舱也是他的简历作品，能开演示版给别人看。

出处：`docs/design.md` 第一节（原来写「创业团队」「两位创始人一起用」，09-29 改成一个人用）；并行 10 张：`specs/169-Fusion形态/需求.md`「并行提速走方向 A」；作品门面：#54；下面第二节原话。

## 二、这一轮创始人的原话（2026-09-28 晚—09-29）

- 「我感觉我们原来做的很多方式都是错误的……现在有很多单子不是你之前觉得不应该做，并且太严了。而且我觉得，这个驾驶舱主要是给个人用的。」
- 「你把帅位加到驾驶舱里面，UI 特别怪，而且你没有仔细考虑过 UI。」
- 「自建 Fusion 这套流程难度有一点大，因为怎么样都完不成……Fusion 其实设想得挺好，但是真实落地的话断点太多了，因为通讯的环节太多了。」
- 「核心诉求点是：尽可能在有限的服务器资源下（比如 6 核 12G 的情况下），能多开任务去并行。」
- 流程设想：第一阶段需求讨论，有一个「指挥官」；正式环节是指挥官、工人、Review 三段，「一条龙走到底」；旁边有一个「副手」。
- 副手：「要常驻，但是不能耗内存」「我希望它能获取到全盘的信息……它能获取到指挥官的想法，当工人在询问它的时候，它刚好能把指挥官的想法也告诉工人；它能获取到工人做活的思路，并告诉 Reviewer」「只要指挥官想问，副手就能回答；在 review 的环节，其他人也可以向副手提问」。
- 模型：「用 GPT-6 或者 5.6 的 Luna 模型更合适……GPT 在审查代码方面是最合适的。」
- 「不需要做前置检查吧？」（09-28 上午已拍过：全量测试都在 GitHub 上跑，见「并行提速走方向 A」第 3 条）
- 「我觉得要删的东西都要删。」
- 「工人放到 GitHub 免费机器上跑不合适吧？」（指挥官查过：不合适，理由见第四节 B）
- 09-28 晚：「未排期旧单」交给闲置清理照常收（`specs/448-自动打标挂版本/结果.md`）；出事时引擎接走的 7 张「全部叫停」。

## 三、他怎么用（操作剧本）

| 场景 | 他要做的 | 目标 |
|---|---|---|
| 有个想法 | 语音说给指挥官；指挥官复述、追问到清楚，给出「怎么算做完」；他说「行」 | 他只说话和点头：不复制粘贴、不切到别的工具 |
| 做的过程中 | 什么都不做。工人有疑问问副手，副手答不了、又碰到方向岔路的，才推给他 | 只在方向岔路和四类人闸（对外发布、花钱、删数据、改标准）上出手 |
| 回来看一眼 | 打开驾驶舱，或问指挥官 | 一屏三块：要我拍的、在跑的、做完的；每张单在哪一步、谁在做 |
| 出事了 | 收到一条通知（主线红、生产挂） | 指挥官当场修；他不用追问「进展如何」「为什么卡住」 |
| 给别人看 | 打开演示版 | 和正式驾驶舱同一套代码、假数据、刷新复原（#54） |

09-28 晚那一夜，他实际做了：追问进度 4 次、追问「为什么卡住」1 次、批准叫停 2 次、批改标准的 PR 若干。目标是这些都不用他做。

## 五、业务规则：新设计必须守住

1. 引擎不直写主线：改动都走 PR，CI 绿才合（`docs/decisions/0002-fusion.md` 第 7 条、0003 第 5 条）。
2. 四类人闸只在那一步停下等人：对外发布、花钱、删数据、改标准（通用段）。
3. 真密钥的值不进仓、对话、日志（通用段「底线」）。
4. GPT 不做界面类的活（包括审界面）；不用 Fable（通用段）。
5. 未排期的单机器不自己接；只有带证据的急修能自动开单（0003 第 8 条；09-28 晚再确认）。
6. 急的当场修：主线红、生产坏、数据、泄露、安全（通用段）。
7. 几个 AI 同时干活，各用各的工作树（通用段）。
8. 发布不打断在跑的会话（09-28 凌晨拍）。
9. 会话里不跑全量检查，全量交给 CI（09-28 上午拍）。
10. 读不到、没跑成要明说失败，不拿空或 ok 顶（通用段「底线」）。
11. 先改仓库再部署，不在机器上手改（09-27 晚拍，#323）。
12. 创始人的决定当场记，只记他亲口说的（通用段）。

## 六、要删的，和怎么删

**根子（一句话）**：一开始按「多人公司 + 模型不可靠」来设计，每断一次就加一道关卡、一次交接、一个对账任务去兜，每道兜底又带出新的断点。数据：引擎到 09-29 只做完 12 张单、叫停 75 张；09-25 到 09-28 主线约 290 个 PR，引擎开的只合了 3 个，本机的约四成在修引擎和流程、约四成在记规矩；09-28 晚几起事故全是兜底机制自己出的（自动打标误挂 52 张、作废的认领把 PR 标红、帅位租约过期把自己拦下、叫停信号没生效）。

**怎么删**：

1. 已经停了：两个仓的「让 AI 接活」09-29 凌晨关掉，法国上没有在跑的单。
2. 一块一个 PR，删干净：代码、测试、库表、驾驶舱入口、设计和运维文档、`AGENTS.md` 里的说法一起删，不留开关、不留兼容层。新旧不并存：三段一条龙上线的同一个 PR 删掉 Fusion（#250 两套工作流并存的教训）。
3. 先后：从外往里——本机脚本和提醒派单（没人依赖）→ 帅位和认领（本机和法国两头）→ 合并闸和卫生检查收尾 → 引擎流程换成三段一条龙 → 驾驶舱按个人用重做 → 最后删库表。
4. 删库表就是删数据，属于人闸：要删哪几张表、里面有什么，列一次清单请创始人点头。
5. 每删一块，在巡检仓跑一张完整的单，确认没把能用的删坏。

## 七、还没定的（要创始人拍）

1. 工人自己定方案接着干，还是指挥官先写详细方案、工人照做。指挥官推荐前者：业界的教训是写代码这种环环相扣的活，拆给两个会话就会互相不知道对方的决定（Cognition「Don't Build Multi-Agents」，2025-06；Anthropic 多代理研究系统，2025-06）。
2. 副手的具体做法：推荐「每张单一份档案（指挥官的想法、工人边干边记的思路、问答记录），谁问副手就把档案连同问题一起交给 GPT，一问一答」（依据：Anthropic「Effective context engineering for AI agents」的结构化笔记）。要定：档案放在哪（单子的评论、分支里的一个文件、法国库）；GPT 走哪条渠道（Cursor 命令行、Mirasim 云端，还是按量计费的直连接口 #118——按量计费算花钱）。
3. Temporal 留不留：只剩「排队、有空位就放单、盯死活、失败换模型重试」四件事，要不要换成一个更轻的调度。
4. 飞书整块（第四节 F）还要不要。
5. 「项目与标准」（体检、一键补齐，#195）个人用之后要不要做，做多重。
6. 本机和法国一样的环境（#450）：流程简化之后还要不要「本机验过再上法国」。
7. v2「引擎打磨」（#257：环节像乐高一样配、检验制度）和这次的简化方向相反，建议关掉，只留「仓库经验库」另开一张。
